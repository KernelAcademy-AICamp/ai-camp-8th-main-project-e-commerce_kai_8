- 개정: 외부 리뷰 6건 반영 — evidence span 서버 계산, `should` 실행 의미, 보수적 부정 범위, 1차 출하선 명시. 0건 완화 순서는 미결로 기록

- 범위: 컬러웨이별 프린팅 데이터에 대한 자연어 검색 해석, `SearchPlan` 생성, LLM ON/OFF 운영
- 선행 설계: [Phase 3 closed-world 결정화 검색](2026-08-01-provenance-search-phase3.md)

## 1. 목표

사용자가 다음처럼 서로 다른 정밀도의 표현을 사용해도 컬러웨이와 프린팅의 관계를 보존하여 검색한다.

- 정확한 표현: `블랙 바탕에 화이트 백프린팅`
- 동의어 표현: `검정 티에 흰색 등판 나염`
- 생산적인 구어 표현: `시커먼 티에 푸르딩딩한 프린팅`
- 외부 맥락이 포함된 표현: `까무잡잡한 피부에 어울리는 검은 티`

검색의 기본 경로는 항상 결정적으로 동작해야 한다. LLM은 사전만으로 해석하기 어려운 표현을 DB의 통제어휘 후보로 번역하는 선택적 의미 해석기이며, SQL이나 최종 강제 조건을 직접 결정하지 않는다.

핵심 원칙은 다음과 같다.

1. 상품 결과는 계속 한 상품 링크당 한 건이다.
2. 컬러웨이와 프린팅 색의 조건은 동일한 `product_prints` 행에서 검사한다.
3. 정확한 표현은 결정적 파서가 우선 처리한다.
4. LLM은 원문 표현을 허용된 DB 값의 후보로만 변환한다.
5. 서버의 결정적 Resolver와 Compiler가 최종 `SearchPlan`을 만든다.
6. LLM이 꺼지거나 실패해도 기본 검색은 정상 동작한다.

## 2. 전제 데이터 모델

### 2.1 상품과 프린팅의 관계

> 저장 구조 확정(2026-08-07): 물리 저장은 `m_raw_goods.prints` jsonb 배열이다. 아래의 "행"은 배열 원소에 해당하며, 논리 모델과 검색 의미는 동일하다.

- 상품(`m_raw_goods`)은 상품 링크당 한 행이다.
- `base_colors`는 판매 중인 옷 색 전체다.
- `prints` 배열은 컬러웨이별 프린팅 관측을 저장한다. `null`은 미라벨, `[]`는 라벨 완료·무지다.
- 같은 컬러웨이와 같은 면에 프린트 객체가 여러 개면 원소를 병합하지 않는다.
- 재라벨링할 때 해당 상품의 `prints` 값을 통째로 교체한다.

따라서 검색 관점의 실제 자식 단위는 다음처럼 이해한다.

> 컬러웨이 × 프린트 객체. 면은 객체의 검색 속성이며, 같은 면에 여러 객체가 존재할 수 있다.

### 2.2 검색에 직접 사용하는 필드

| 필드 | 의미 |
|---|---|
| `base_color` | 해당 프린팅 행이 속한 옷 컬러웨이 |
| `sides` | 검색에 사용하는 최종 면 배열 |
| `graphic_types` | 도안·무늬의 통제어휘 배열 |
| `colors` | 확인된 프린트 잉크색 배열 |
| `colors_status` | `확인`, `없음`, `판독불가`, `미촬영` |
| `motif` | 로고명, 글자, 동물, 사물 등 열린 어휘 |

`sides`는 다음 의미를 가진다.

- `{}`: 프린팅 검색 대상이 아님
- `{앞}`, `{뒤}`, `{소매}`: 해당 면의 프린팅
- `{앞,뒤,소매}`: 전체 또는 올오버 프린팅

소매 배색이나 스트라이프처럼 무늬만 있는 객체는 `side=소매`로 관측되더라도 DB의 `sides={}`가 될 수 있다. 따라서 `소매 프린팅` 검색을 오염시키지 않는다.

### 2.3 상태별 검색 의미

| 상태 | `colors` | 정확한 프린트색 검색 | 구조 검색 |
|---|---|---:|---:|
| `확인` | 한 개 이상 | 가능 | 가능 |
| `없음` | `[]` | 불가 | 비프린팅 객체로 처리 |
| `판독불가` | `null` | 불가 | 관측된 면·유형 범위에서 가능 |
| `미촬영` | `null` | 불가 | 추론값임을 전제로 제한적으로 가능 |

`미촬영` 행의 면, 그래픽 유형, 모티프는 다른 컬러웨이에서 복사한 추론값이다. 정확한 잉크색 조건에는 절대 사용하지 않고, 구조 조건에 사용할 때도 provenance를 남겨 부분 일치와 정확 일치를 구분한다.

## 3. 전체 검색 구조

원문을 LLM이 먼저 자유롭게 재작성하고 그 결과를 다시 파싱하지 않는다. 원문을 결정적 파서와 LLM 의미 해석기에 함께 제공하고, 두 결과를 결정적 Resolver가 합친다.

```text
사용자 원문
   ├─ 결정적 파서 ───────────────────┐
   │  정확어·가격·브랜드·위치·부정       │
   │                                  ▼
   └─ LLM 의미 해석기 ────────→ 결정적 Resolver
      대상·색 후보·뉘앙스·원문 근거       │
                                      ▼
                                SearchPlan Compiler
                                      │
                                      ▼
                                 DB RPC / SQL
                                      │
                                      ▼
                                상품당 한 건 반환
```

이 구조에서 LLM 결과와 원문을 함께 사용하는 이유는 다음과 같다.

- LLM이 제시한 근거가 실제 원문에 존재하는지 확인할 수 있다.
- `까무잡잡한 피부`의 색을 옷 색으로 잘못 적용하는 것을 막을 수 있다.
- `검정 말고`, `화이트 제외`처럼 부정 범위를 원문 기준으로 판정할 수 있다.
- 정확한 사전 매칭을 LLM 해석보다 우선할 수 있다.
- LLM이 원문에 없는 가격, 브랜드, 색, 배제 조건을 만드는 것을 거부할 수 있다.

## 4. 책임 분리

### 4.1 결정적 파서

결정적 파서는 원문에 직접 근거한 닫힌 조건을 추출한다.

- 브랜드 alias
- 가격 범위
- 성별과 표준 사이즈
- 정확한 캐논 색과 검증된 고정 alias
- 프린팅 위치
- 그래픽 유형
- 명시적 부정과 강제 표현
- 일반 상품 탐색 의도

각 결과에는 원문 span, 적용 규칙 버전, 극성, 출처를 남긴다.

한국어 부정은 다음처럼 보수적으로 처리한다.

- `검정 바탕 말고`, `화이트 프린트 제외`처럼 대상 명사와 속성값이 같은 인접 명사구 안에 있을 때만 해당 대상의 `must_not`으로 만든다.
- 조사, 쉼표, 접속 표현, 다른 대상 명사는 부정 범위의 경계로 취급한다.
- 색 표현만 있고 바탕색과 프린트색 중 어느 대상을 부정하는지 하나로 결정할 수 없으면 하드 부정을 만들지 않고 미해결 표현으로 남긴다.
- LLM은 부정 후보와 evidence를 제안할 수 있지만, 결정적 규칙으로 대상과 범위가 확인되지 않은 부정은 `must_not`으로 승격하지 않는다.

### 4.2 LLM 의미 해석기

LLM은 자연어를 상품 행이나 SQL로 바꾸지 않는다. 전달받은 통제어휘의 의미를 기준으로 원문 표현을 후보값에 배치한다.

LLM에 제공하는 문맥은 다음으로 제한한다.

- 사용할 수 있는 캐논 색 후보와 각 색의 의미
- 검색 위치와 그래픽 유형 enum
- 옷 바탕색, 프린트색, 외부 맥락의 구분 규칙
- 계열색, 명도, 채도, 탁도 등 표현 해석 지침
- 출력 JSON Schema
- 대표적인 긍정·부정 예시

전체 상품 데이터나 실제 DB 행을 프롬프트에 넣지 않는다. 어휘 레지스트리에는 버전이나 해시를 부여하여 같은 입력을 재현하고 캐시할 수 있게 한다.

### 4.3 결정적 Resolver

Resolver는 원문, 결정적 신호, LLM 의미 해석을 함께 검증하고 충돌을 해결한다.

우선순위는 다음과 같다.

1. 원문에 직접 근거한 결정적 결과
2. 검증된 고정 alias와 조합 규칙
3. LLM이 반환한 계열 또는 의미 후보
4. 해결하지 못한 표현

LLM은 후보를 제안하지만 다음 항목은 정하지 않는다.

- `must`, `should`, `must_not`
- SQL 연산자
- 조건 완화 순서
- 결과 정렬 가중치
- 서로 다른 조건을 동일한 자식 행에 묶을지 여부

### 4.4 SearchPlan Compiler

Compiler는 검증이 끝난 중간 표현을 실행 가능한 `SearchPlan`으로 바꾼다. 모든 enum을 다시 런타임 검증하고, `PrintClause` 단위로 동일 행 조건을 생성한다.

## 5. 통제어휘와 표현색

### 5.1 enum은 입력 제한이 아니라 출력 계약이다

사용자는 enum만 사용하지 않는다. `까무잡잡한`, `시커먼`, `푸르딩딩한`처럼 새로운 표현을 계속 만들 수 있다. 따라서 사용자 입력을 평면 alias 사전 하나로 모두 해결하지 않는다.

캐논 enum은 다음 용도로 사용한다.

- LLM 출력의 허용 범위
- Resolver 검증
- SearchPlan 계약
- SQL 컴파일
- UI 해석 칩
- 골든셋 기대값

TypeScript에서는 별도의 `enum`보다 하나의 `as const` 어휘 레지스트리에서 리터럴 타입을 파생하고, 같은 소스로 런타임 검증 스키마를 만든다. 실제 색 목록은 DB 적재와 검색이 함께 참조하는 단일 소스에서 생성하며 문서에 중복 작성하지 않는다.

고정된 그래픽 유형은 다음 12개다.

- 도안: `레터링`, `로고`, `캐릭터`, `그래픽`
- 무늬: `스트라이프`, `도트`, `체크`, `배색`, `카모플라쥬`, `그라데이션`, `타이다이`, `패치워크`

검색 계획의 위치 값은 `앞`, `뒤`, `소매`, `전체`다. `전체`는 계획 전용 값이며 DB에서는 `앞`, `뒤`, `소매`가 모두 포함된 배열 조건으로 컴파일한다.

### 5.2 LLM의 색 표현 출력

색 표현은 바로 `SearchPlan`에 넣지 않고 중간 해석으로 보존한다.

```json
{
  "surface": "푸르딩딩한",
  "target": "print",
  "candidates": ["블루", "네이비"],
  "resolution": "family",
  "source": "llm",
  "evidence": "푸르딩딩한 프린팅"
}
```

필수 개념은 다음과 같다.

| 속성 | 허용 의미 |
|---|---|
| `target` | `garment_base`, `print`, `external_context`, `unknown` |
| `resolution` | `exact`, `family`, `semantic`, `unresolved` |
| `source` | `alias`, `composition_rule`, `llm` |
| `candidates` | 현재 캐논 색 enum에 속하는 값만 |
| `evidence` | 실제 원문에 존재하는 부분문자열 |

LLM에게 문자 오프셋 계산을 맡기지 않는다. 서버가 `evidence` 부분문자열을 원문에서 검색해 `{start, end, text}` span을 계산한다. 같은 문자열이 여러 번 등장해 대상을 하나로 정할 수 없으면 주변의 대상 표현과 결정적 신호로 해소하고, 그래도 모호하면 해당 해석을 미해결로 남긴다.

`tone`은 초기 `QueryInterpretation` 스키마에 넣지 않는다. 명도·채도·탁도 정보가 검색 품질에 실제로 필요하다는 골든셋 근거와 소비 규칙이 생긴 뒤 별도 필드로 도입한다.

### 5.3 표현 해석 예시

사용자 쿼리:

> 까무잡잡한 피부에 어울리는 시커먼 티인데 푸르딩딩한 프린팅

의미 해석은 다음처럼 분리한다.

| 원문 표현 | 대상 | 캐논 후보 | 검색 적용 |
|---|---|---|---|
| `까무잡잡한 피부` | 외부 맥락 | 브라운 계열 가능 | 옷 색 하드필터로 사용하지 않음 |
| `시커먼 티` | 옷 바탕 | 블랙 | 검증 정책에 따라 하드 또는 강한 선호 |
| `푸르딩딩한 프린팅` | 프린트 | 블루, 네이비 | 계열 OR 또는 소프트 선호 |

핵심은 표현이 가리키는 대상을 색 후보보다 먼저 판별하는 것이다.

## 6. 중간 해석과 SearchPlan 계약

### 6.1 LLM 출력과 실행 계획을 분리한다

LLM은 `QueryInterpretation`을 반환한다. 서버만 `SearchPlan`을 만든다.

```text
QueryInterpretation
  - 색 표현과 대상
  - 위치 후보
  - 그래픽 유형 후보
  - 모티프 표현
  - 외부 맥락
  - 미해결 표현

SearchPlan
  - 상품 단위 조건
  - 같은 자식 행에 적용할 PrintClause
  - 강제 수준
  - 정렬
  - provenance와 버전
```

이 분리로 LLM 프롬프트를 변경해도 SQL 계약과 안전 규칙을 유지할 수 있다.

### 6.2 SearchPlan의 닫힌 값

`SearchPlan`에서 enum으로 제한할 항목은 다음과 같다.

- 캐논 색
- 위치: `앞`, `뒤`, `소매`, `전체`
- 그래픽 유형 12개
- 성별
- 정렬 방식
- 강제 수준: `must`, `should`, `must_not`
- 출처: 결정적 규칙, alias, 조합 규칙, LLM
- 검색 종류: `browse`, `filtered`

열린 값으로 유지할 항목은 다음과 같다.

- 브랜드 원문과 캐논 브랜드 ID
- 제목 검색어
- 모티프 검색어
- 가격 범위
- 미해결 표현

### 6.3 PrintClause

서로 관계가 있는 프린팅 조건은 하나의 `PrintClause`에 묶는다.

```json
{
  "baseColor": {
    "values": ["블랙"],
    "enforcement": "must"
  },
  "printColor": {
    "values": ["화이트"],
    "enforcement": "must"
  },
  "placement": {
    "values": ["뒤"],
    "enforcement": "must"
  },
  "graphicType": {
    "values": ["레터링"],
    "enforcement": "must"
  }
}
```

이 절은 다음 의미다.

> 블랙 컬러웨이이면서, 같은 프린팅 행에 화이트 잉크와 뒤 위치와 레터링 유형이 함께 존재해야 한다.

다음처럼 조건별 `EXISTS`를 분리하면 안 된다.

```text
EXISTS(base_color = 블랙)
AND EXISTS(colors contains 화이트)
```

위 방식은 블랙 컬러웨이의 다른 프린트와 화이트 컬러웨이의 화이트 프린트를 교차 결합할 수 있다. 하나의 절은 반드시 하나의 상관 서브쿼리 안에서 컴파일한다.

사용자가 `앞에는 흰 로고, 뒤에는 빨간 캐릭터`처럼 서로 다른 객체를 요구하면 `PrintClause`를 두 개 만든다. 각 절은 독립된 자식 행 존재 조건이 된다.

강제 수준은 절 전체가 아니라 필드별로 보존한다. 예를 들어 `블랙 티에 푸르딩딩한 프린팅`은 바탕색이 `must`, 프린트색 후보가 `should`일 수 있다. 이 경우에도 semantic match를 계산할 때는 `블랙`과 `블루·네이비`가 동일한 자식 행에 있는지 검사한다.

## 7. 강제 수준 결정 정책

강제 수준은 LLM confidence 숫자가 아니라 출처와 원문 근거에 관한 서버 규칙으로 결정한다.

| 해석 | 기본 처리 |
|---|---|
| 정확한 캐논 표현 | `must` 가능 |
| 승인된 고정 alias | `must` 가능 |
| 검증된 색 계열 규칙 | 후보 집합 OR, 축별 승인 후 `must` 가능 |
| LLM의 의미 해석 | 기본 `should` |
| 외부 맥락 | 상품 속성 하드필터에서 제외 |
| 미해결 표현 | 하드필터로 사용하지 않음 |
| 명시적 부정 + 원문 span | `must_not` 가능 |
| LLM만 제안한 부정 | `must_not` 금지 |

`시커먼 → 블랙`처럼 운영 골든셋에서 충분히 안정적인 표현은 LLM 경로에서 결정적 alias나 조합 규칙으로 승격한다. 승격 후에는 LLM을 꺼도 같은 해석이 가능하다.

LLM 해석을 곧바로 하드필터로 승격하려면 표현 해석 precision뿐 아니라 해당 DB 속성의 커버리지와 검색 recall을 함께 검증해야 한다.

### 7.1 `should`의 실행 의미

`should`는 임의의 가중치나 자동 완화 표시가 아니다. 초기 실행 의미는 다음으로 고정한다.

1. `must`와 `must_not`으로 먼저 적격 상품 범위를 결정한다.
2. `should`는 적격 범위 안에서 별도의 deterministic predicate로 평가한다.
3. 하나 이상의 `should`가 있는 검색의 기본 응답에는 `should`를 하나 이상 만족한 의미 일치 그룹만 노출한다.
4. `should`를 만족하지 않지만 `must`를 만족한 상품은 넓은 결과 그룹으로 분리하며, 사용자나 UI가 명시적으로 결과 확장을 요청하기 전에는 기본 결과에 섞지 않는다.
5. `must`가 하나도 없는 의미 검색은 검색 대상 카테고리의 라벨 완료 상품을 적격 범위로 삼되, `should`를 만족한 상품만 기본 응답으로 반환한다.

같은 `PrintClause` 안에 `must`와 `should`가 함께 있으면 두 단계 모두 같은 자식 행 관계를 유지한다. 예를 들어 적격 범위는 `블랙` 행의 존재로 만들고, 의미 일치는 그 블랙 행에 `블루·네이비` 프린트가 함께 있는지로 판정한다.

의미 일치 그룹 안에서는 학습되지 않은 임의 가중치를 두지 않고 다음 순서를 사용한다.

1. 일치한 `should` 절 수
2. 같은 절 안에서 일치한 속성 수
3. 관측값 우선, 추론값 후순위
4. 기존의 결정적 관련도와 상품 품질 순서
5. 안정적인 상품 ID 순서

LLM은 위 순서나 점수를 출력하지 못한다. 서버가 고정한 이 정책을 변경하려면 골든셋과 운영 지표를 근거로 별도 버전을 만든다.

## 8. LLM 운영 모드

LLM은 다음 세 모드로 운영한다.

| 모드 | 결정적 파서 | LLM 호출 | 검색 결과 반영 | 목적 |
|---|---:|---:|---:|---|
| `off` | 사용 | 안 함 | 결정적 결과만 | 기본 경로, 비용·장애 대응 |
| `shadow` | 사용 | 함 | 반영하지 않음 | 품질·지연·비용 비교 |
| `on` | 사용 | 함 | 검증된 의미 결과만 병합 | 실제 의미 검색 |

모드는 서버 환경 설정으로 제어한다.

```text
SEARCH_LLM_MODE=off | shadow | on
```

요청 단위 override가 필요하면 내부 실험이나 관리자 요청에만 허용한다. 일반 사용자가 임의로 운영 정책을 바꾸게 하지 않는다.

### 8.1 OFF

- LLM을 호출하지 않는다.
- 결정적 파서만으로 `SearchPlan`을 만든다.
- 정확한 캐논 표현, 승인된 alias, 가격, 브랜드, 위치, 부정 조건은 정상 동작한다.
- 의미 표현을 해석하지 못하면 해당 표현은 미해결 로그에 남기고 하드필터를 만들지 않는다.

### 8.2 SHADOW

- 결정적 검색 결과는 OFF와 완전히 같아야 한다.
- LLM 해석과 후보 `SearchPlan`을 별도로 생성해 저장한다.
- 실제 SQL에는 결정적 계획만 사용한다.
- 두 계획의 차이, 유효성, 지연, 예상 결과 건수를 비교한다.

### 8.3 ON

- 결정적 결과를 먼저 만든다.
- 검증을 통과한 LLM 의미 해석만 Resolver에 추가한다.
- 결정적 결과와 충돌하면 결정적 결과가 우선한다.
- LLM 결과가 없거나 무효여도 OFF와 같은 기본 검색을 계속 실행한다.

### 8.4 장애 폴백

다음 상황은 모두 요청 실패가 아니라 LLM 해석 없음으로 처리한다.

- 호출 타임아웃
- 모델 또는 API 장애
- JSON 파싱 실패
- 출력 스키마 불일치
- 허용되지 않은 enum
- 실제 원문에 없는 evidence
- 결정적 조건과 해결 불가능한 충돌

즉, 장애 폴백은 별도의 네 번째 운영 모드가 아니라 모든 LLM 사용 모드에 내장된 OFF 경로다.

## 9. 검증 규칙

Resolver와 Compiler는 최소한 다음을 검증한다.

1. LLM의 evidence 부분문자열이 실제 원문에 존재하는지 확인하고 span은 서버가 계산한다.
2. 모든 후보값이 현재 어휘 레지스트리에 존재한다.
3. 같은 표현이 옷 바탕색과 프린트색에 이유 없이 중복 배치되지 않는다.
4. 외부 맥락의 색을 상품 속성 필터로 사용하지 않는다.
5. 결정적 파서와 충돌하면 LLM 조건을 버리거나 소프트로 강등한다.
6. 원문에 없는 가격, 브랜드, 위치, 배제 조건을 추가하지 않는다.
7. `must_not`은 명시적 부정 span이 있을 때만 생성한다.
8. `PrintClause`의 바탕색, 프린트색, 위치, 유형은 같은 자식 행 조건으로 컴파일한다.
9. `colors=null`인 `판독불가`와 `미촬영` 행은 정확한 잉크색 검색에서 제외한다.
10. 잘못된 LLM 결과를 넓은 전체 검색으로 바꾸지 않고 안전하게 무시한다.

## 10. 검색 결과와 UI

검색 결과는 해석 근거와 관측 품질을 서로 다른 축으로 구분한다.

- 해석 근거 `exact`: 결정적 `must` 조건으로 성립
- 해석 근거 `semantic`: LLM 후보나 계열색 `should` 일치로 성립
- 관측 품질 `observed`: 실제 촬영·확인된 값으로 성립
- 관측 품질 `inferred`: `미촬영` 컬러웨이에 복사한 구조 등 추론값에 의존

따라서 의미 일치이면서 동시에 추론값에 의존한 결과도 표현할 수 있다. `판독불가`와 `미촬영`은 정확한 프린트색 일치를 만들 수 없으므로, 색 조건의 `observed` 결과로 승격하지 않는다.

UI에는 서버가 실제 적용한 해석만 칩으로 보여준다. LLM 원출력을 그대로 노출하지 않는다.

예시:

- `시커먼 → 블랙 바탕`
- `푸르딩딩한 → 블루·네이비 프린트`
- `까무잡잡한 피부 → 스타일 맥락`

사용자가 해석을 수정할 수 있게 하면 수정값을 결정적 조건으로 재검색하고, 해당 피드백은 표현 사전 승격 후보로 수집할 수 있다.

## 11. 로그와 재현성

검색 로그에는 원문 전체를 무조건 저장하기보다 개인정보 정책에 맞춘 샘플링 또는 비식별 저장을 사용한다. 최소 운영 메타는 다음과 같다.

- LLM 모드
- 결정적 계획 hash
- LLM 후보 계획 hash
- 최종 실행 계획 hash
- 어휘 버전
- 파서 규칙 버전
- LLM 프롬프트 버전
- 모델 식별자
- LLM 유효성 및 거부 사유
- LLM 지연과 전체 검색 지연
- 폴백 여부
- 해석 근거별 `exact`·`semantic` 결과 수
- 관측 품질별 `observed`·`inferred` 결과 수

동일한 정규화 쿼리, 어휘 버전, 프롬프트 버전, 모델 식별자의 조합은 캐시 키로 사용할 수 있다. 다만 캐시는 정확성 구조를 대신하지 않으며, 캐시가 없어도 OFF 폴백이 동작해야 한다.

## 12. 평가와 단계적 전환

### 12.1 필요한 골든셋

평가 데이터는 두 종류로 분리한다.

1. 상품 라벨 골든셋
   - 컬러웨이, 면, 그래픽 유형, 잉크색, 상태의 정확도
   - 같은 면의 복수 객체를 병합하지 않고 객체 단위로 비교
2. 검색 쿼리 골든셋
   - 원문에서 기대하는 결정적 신호
   - 의미 표현의 대상과 캐논 후보
   - 기대 `PrintClause`
   - 기대 상품과 제외 상품

컬러웨이와 면이 양쪽 라벨에 모두 있을 때는 `(base_color, side)`만으로 단순 병합하지 않는다. 동일 면 복수 객체가 존재할 수 있으므로 객체 간 최적 매칭 또는 명시적인 객체 정답을 사용한다.

### 12.2 비교 지표

OFF, SHADOW 후보, ON을 같은 쿼리 집합에서 비교한다.

- 조건 해석 precision
- 대상 귀속 정확도: 옷, 프린트, 외부 맥락
- 색 후보 recall
- 검색 결과 Recall@K와 Precision@K
- 0건 비율
- 잘못된 하드필터 발생률
- 계획 불일치율
- LLM 유효 출력률
- p50/p95 지연
- 쿼리당 비용
- 실제 운영의 클릭률과 해석 수정률

### 12.3 권장 전환 순서

1. `off`: 결정적 파서와 컬러웨이 검색 기준선 확립
2. `shadow`: 결과에 영향 없이 LLM 해석 수집
3. 제한된 트래픽 `on`: 의미 후보는 낮은 영향도로 시작
4. 골든셋과 운영 지표 통과 후 `on` 비율 확대
5. 반복적으로 정확한 표현은 alias 또는 조합 규칙으로 승격
6. 언제든 환경 설정 하나로 `off` 전환 가능한 상태 유지

## 13. 구현 순서와 완료 기준

출하선은 다음처럼 나눈다.

- **1차 출하선:** §13.1 어휘 계약과 §13.2 결정적 검색 기준선. `SEARCH_LLM_MODE=off`로 출시 가능하며, 컬러웨이 결속 검색 자체의 가치를 먼저 검증한다.
- **2차 출하선:** §13.3 의미 해석 계약의 최소 구현과 검증·로그만 연결한 `shadow`. 실제 검색 결과는 1차 출하선과 동일해야 한다.
- **후속 출하선:** §13.4~§13.6의 Resolver, `on` 운영, 평가 게이트. shadow 데이터가 없는 상태에서 바로 기본 `on`으로 전환하지 않는다.

### 13.1 어휘 계약

- 캐논 색, 위치, 그래픽 유형, 상태값의 단일 소스를 만든다.
- 적재 검증, 결정적 파서, LLM 출력 검증, SearchPlan, SQL 테스트가 같은 값을 참조한다.
- 완료 기준: 존재하지 않는 enum은 어느 진입점에서도 실행 계획에 들어가지 않는다.

### 13.2 결정적 검색 기준선

- 정확 표현을 `PrintClause`로 만들고 컬러웨이와 프린트 조건을 같은 행에서 검색한다.
- 완료 기준: `블랙 바탕 + 화이트 프린팅`이 다른 컬러웨이의 화이트 프린트와 교차 매칭되지 않는다.

### 13.3 의미 해석 계약

- LLM이 `QueryInterpretation`만 반환하게 하고 원문 evidence와 enum을 검증한다.
- 완료 기준: `까무잡잡한 피부`는 외부 맥락, `시커먼 티`는 바탕색, `푸르딩딩한 프린팅`은 프린트색 후보로 분리된다.

### 13.4 Resolver와 Compiler

- 결정적 신호와 의미 후보의 우선순위, 강제 수준, 충돌 규칙을 고정한다.
- 완료 기준: 서로 다른 LLM fixture를 넣어도 결정적 `must`와 `must_not` 조건이 임의로 바뀌지 않는다.

### 13.5 모드 운영

- `off`, `shadow`, `on`과 장애 폴백을 연결한다.
- 완료 기준: `shadow` 결과가 `off` 결과와 동일하고, LLM 타임아웃 시 검색 요청은 결정적 결과를 반환한다.

### 13.6 평가와 전환

- 상품 라벨 골든셋과 검색 쿼리 골든셋으로 모드별 차이를 측정한다.
- 완료 기준: 합의한 정확도·누락률·지연·비용 기준을 통과한 표현과 축만 ON 검색에 반영된다.

## 14. 남은 결정과 권고

### 14.1 프린팅 없음 검색의 관측 범위

`printing_labeled_at`이 있고 검색 대상 `product_prints`가 없다는 사실만으로 상품이 완전히 무지라고 단정하면, 뒷면이 촬영되지 않은 상품을 무지로 오판할 수 있다.

권고는 컬러웨이와 면별 관측 상태를 별도 구조로 보존하는 것이다. 이 구조가 도입되기 전에는 `프린팅 없음`을 강한 검색 조건으로 제공하지 않거나, 촬영 범위가 충분한 상품으로 제한한다.

### 14.2 미촬영 컬러웨이의 구조 추론

다른 컬러웨이에서 복사한 면, 그래픽 유형, 모티프는 관측값이 아니다. 권고는 적재 또는 검색 provenance에 `observed`와 `inferred`를 구분하는 것이다. 최소한 관측 결과와 추론 결과를 나누어 사용자가 추론값에 의존한 결과임을 알 수 있어야 한다.

### 14.3 의미색의 하드필터 승격

`시커먼`, `푸르딩딩한` 같은 표현을 언제 `must`로 승격할지는 구현 상수가 아니라 골든셋 기준으로 결정한다. 초기에는 LLM 의미 결과를 `should`로 두고, 표현별 precision과 검색 누락률을 통과한 항목만 결정적 규칙으로 승격하는 것을 권고한다.

### 14.4 0건 자동 완화 순서 — 미결

프린트색, 위치, 바탕색 중 무엇을 먼저 완화할지는 현재 근거가 없어 확정하지 않는다. 이 순서는 상품 발견의 핵심 의미를 바꿀 수 있으므로 구현 편의로 정하지 않고, 검색 쿼리 골든셋에서 조건별 정답 누락과 오염을 측정한 뒤 별도 결정한다.

결정 전 기본 동작은 다음으로 고정한다.

- `must` 조건을 자동으로 제거하거나 `should`로 강등하지 않는다.
- `should` 후보를 임의로 다른 색 계열이나 위치로 확장하지 않는다.
- 의미 일치 그룹이 0건이면 넓은 전체 상품을 자동으로 섞지 않고 정직한 0건을 반환한다.
- UI는 조건 수정이나 명시적인 결과 확장을 제안할 수 있지만, 실행에는 새로운 `SearchPlan` 요청이 필요하다.

## 15. 최종 결정 요약

이 검색 시스템은 **결정적 검색을 본체로 유지하면서 LLM을 선택 가능한 의미 컴파일 보조 계층으로 사용한다.**

- 원문은 결정적 파서와 LLM이 함께 본다.
- LLM은 DB 통제어휘에 맞는 의미 후보와 원문 근거를 반환한다.
- 서버가 원문과 두 해석 결과를 다시 결정적으로 검증한다.
- 최종 `SearchPlan`과 SQL은 서버만 생성한다.
- 컬러웨이와 프린트 조건은 같은 `product_prints` 행에 묶는다.
- LLM은 `off`, `shadow`, `on`으로 운영하며 실패하면 자동으로 결정적 검색으로 돌아간다.
- 운영에서 검증된 구어 표현은 점차 결정적 alias와 조합 규칙으로 승격한다.

이 구조를 사용하면 LLM이 켜졌을 때는 표현의 폭이 넓어지고, 꺼졌을 때도 정확하고 재현 가능한 기본 검색이 유지된다.
