구현 착수 전에 고정해야 하는 계약을 기록한다. 이 문서의 결정을 바꾸려면 사유를 남기고 관련 문서를 함께 갱신한다.

## D1. 저장 구조 = m_raw_goods.prints jsonb (확정)

프린팅 관측은 별도 자식 테이블(`product_prints`)이 아니라 **상품 원본 테이블 `m_raw_goods`의 jsonb 배열 컬럼 `prints`** 에 저장한다. 팀 확인으로 확정(2026-08-07).

- 배열 원소 = 컬러웨이 × 프린트 객체: `base_colors`(배열), `sides`, `graphic_types`, `colors`, `colors_status`, `motif`
  - **2026-08-10 정정**: 초기 기록은 단수 `base_color`(문자열)였으나, 실제 라벨 산출물은 복수 배열 `base_colors`로 착지했다(여러 컬러웨이가 같은 프린트를 공유하면 한 원소에 함께 라벨 — 배색 표현에 필요). 검색 코드(어댑터 사전필터·기준 판정기)를 배열 기준으로 정합화했다. 이 불일치로 결속 검색이 전량 0건이 되는 버그가 있었다.
- 상품의 옷 색 전체 = 상품 수준 `base_colors` 배열 컬럼(원소 내 `base_colors`와는 다른 위치)
- 라벨 구분: `prints` null = 미라벨 / `[]` = 라벨 완료·무지 / 원소 있음 = 프린팅 관측
- 결속 검색의 실행 의미: "같은 프린트 객체 안에서 조건이 함께 성립" = jsonb 배열 **원소 단위** 포함 검사. 조건을 서로 다른 원소에 흩어 검사하면 교차 매칭 오류 — 금지.
- 미결(데이터 측): 라벨 provenance 3종(라벨 시각·스키마 버전·프롬프트 버전) 재도입 여부. jsonb 전환 때 빠짐. 재라벨링·골든셋 비교에 필요하므로 재도입 권고.

## D2. Phase 3 기반 구조는 부분 재사용

기존 결정화 검색 기반 구조(P3-F: ResolvedIntent·ConstraintMeta·QueryPlan)에 대해:

**재사용하는 것 (개념·패턴)**
- 출처(provenance) 표기와 원문 근거(evidence span) 기록 방식
- 강제 수준·극성·규칙 버전 필드 설계
- 결정성 보장(같은 입력 → 같은 계획) 검사 방식
- "꺼짐 상태 동일성" 테스트 패턴

**신규로 만드는 것**
- 결속 조건 구조(PrintClause 계열)와 동일 객체 결속 의미
- 상품 수준 바탕색 조건(무지 포함 검색 경로)
- 잉크색 관측 상태(확인·없음·판독불가·미촬영)의 검색 의미
- jsonb 실행 어댑터

근거: 기존 ResolvedIntent·CandidateHardPlan은 평면 구조라 "같은 자식 객체 안 결속"을 표현하지 못한다. 평면 구조에 끼워 넣지 않고, 기존 외곽 구조에 프린팅 전용 가지를 합성한다.

## D3. 기능 스위치는 신규로 분리

기존 `SEARCH_DECISIVE_LANE`을 재사용하지 않는다. 다음 두 축은 수명주기가 다르므로 각각의 스위치를 둔다.

1. **컬러웨이 데이터 검색 활성화** — 데이터 적재 커버리지에 따라 켠다. 이번 계획이 만드는 스위치.
2. **LLM 의미 해석 모드(off/shadow/on)** — 2차 출하선 이후. 설계 문서 §8의 `SEARCH_LLM_MODE`.

기본값은 꺼짐. 꺼진 동안 현행 검색과 완전 동일해야 한다.

## D4. 조건 소유권 — 소비한 표현의 중복 적용 금지

컬러웨이 해석기가 원문에서 소비한 표현(예: "백프린팅", "등판", "나염", "블랙 바탕에")은 **결속 조건이 소유**한다.

- 같은 표현이 기존 제목 검색어 추출, 기존 상품 수준 색·패턴 필터에 다시 들어가면 안 된다(이중 적용은 결과를 임의로 좁힘).
- 현행 제목 토큰 추출은 스톱워드 목록 방식이라 span을 모른다. 통합 시 해석기의 소비 span을 제목 추출 입력에서 제외하는 연결이 필요하다.
- 반대로 해석기가 소비하지 않은 표현은 기존 경로가 그대로 처리한다(현행 동작 보존).

## D5. 해석 골든셋은 신규 작성, 구현 전 동결

- 신규 24~30건. 기대값 2층: ①기대 해석(조건·대상 귀속·미해결) ②기대 결속 계획.
- 버킷: 결속 / 바탕색 단독 / 위치 단독 / 복수 객체 / 부정 / 외부 맥락 / 미해결.
- 검색 담당 초안 → 데이터·라벨 담당 의미 검토 → **구현 착수 전 동결**. 구현에 맞춰 기대값을 고치지 않는다(고칠 땐 사유 기록).
- 기존 자산의 역할: 색 표현 골든셋 50건 = 색 별칭 기대값 참조원, 의도 쿼리 골든셋 33건 = 전체 검색 회귀용.

## D6. 실행 형태 — 논리 계약은 지금, 어댑터 포함

- 저장 구조가 확정되고 실데이터(라벨 12건)가 존재하므로 jsonb 실행 어댑터까지 이번 범위에 포함한다.
- 논리 실행 계약(동일 객체 결속, 상품당 1건, 상태별 잉크색 규칙, 빈 sides 제외, '전체'=세 면 순서 무관)은 합성 사례 + 기준 판정기로 먼저 고정하고, 어댑터의 DB 실행 결과가 판정기와 일치함을 검증한다.

## D7. 바탕색 단독 검색은 당분간 기존 colors 필드 사용 (2026-08-07 추가)

결속 묶음(PrintClause)이 없는 계획 — 예: "블랙티" — 은 `base_colors`(라벨, 현재 12건)가 아니라 **기존 `colors` 필드(전 카탈로그 3,658건)** 로 검색한다. 팀 결정: base_colors는 당장 사용하지 않는다.

- 실행 방식: 어댑터를 태우지 않고 기존 색 하드필터(intent)로 이관 — 기존 쿼리·랭킹 파이프라인 재사용.
- 결속 묶음이 있는 계획("블랙티에 화이트 프린팅")은 계속 라벨(prints) 기반 — 여기에 colors 폴백을 쓰면 교차 매칭 오류로 회귀하므로 금지.
- 캐논 색과 기존 facet 표기의 차이는 변환표(toLegacyColorTerms)로 흡수(라이트그레이↔"라이트 그레이" 등).
- 재검토 조건: 라벨 커버리지가 충분해져 base_colors가 전 카탈로그를 대표할 때.

## D8. 원소 base_colors는 컬러웨이 매핑 키 — 색 값의 진실은 colors (2026-08-10 추가)

prints 원소의 `base_colors`(사진 추출 관측)는 검색·표시의 색 "값"으로 직접 쓰지 않고, **그 원소가 어느 컬러웨이의 관측인지를 상품 `colors`(판매자 옵션 = 진실)에 잇는 매핑 키로만** 쓴다. 근거: 라벨 1,892건 실측에서 40%가 colors와 불일치(원인 = 표기·톤 세분화 차이 ~15%p, 다른 컬러웨이 사진 라벨 ~19%p, 추출 오류 ~5%p).

- 매핑 규칙(`color-family.ts`): 정확 일치 우선 → 톤 접두(라이트/다크 등)·계열 별칭(차콜↔그레이, 아이보리↔화이트 등) 접기로 판매자 표기에 연결. 네이비·카키처럼 별개 캐논 색은 접지 않는다.
- 결속 판정(`colorway-evaluate`): 바탕색 조건은 매핑된 판매자 색의 계열 키로 판정. colors에 연결되지 않는 원소(다른 컬러웨이 관측)는 결속에 쓰지 않는다 — "검정 바탕" 검색에 화이트 단품이 나오지 않는다.
- 어댑터: jsonb 사전필터에서 base_colors 포함검사 제거(계열 매핑은 @>로 표현 불가 — superset 유지 위해 재판정으로 미룸).
- 상세 표: 바탕 열은 매핑된 판매자 표기로 보이고, 연결되지 않는 원소 행은 제외.
- 데이터·라벨 파이프라인은 무변경(원본 관측 보존). 매핑 불가 원소 중 추출 오류 의심분은 별도 검수 큐.

## 데이터 측 요청 사항 (병행)
