# 데이터 확보 현실성 조사 (Data Feasibility)

> 유형: foundation · 2026-07-21 · 갱신 2026-07-30(무신사 전환 §6, 캐파 2축·종합 재작성) · 방법: 웹 리서치(집중 조사)
> ⚠️ §1~4의 네이버 전제 서술은 D14(무신사 전환) 이전 히스토리 — 현재 기준은 §6·종합.
> ⚠️ 네이버 개발자 문서(developers.naver.com) 직접 fetch 차단 → 공식 swagger 스펙 + 다수 구현사례로 교차검증. 법령·판례는 1차 출처 대조 완료(§3), **약관 원문만 미대조**.

## 0. 캐파 전제 — "1인"이 아니라 두 개의 예산

현실성 판단의 기준선. 이 문서에서 "무리"라고 쓸 때 **어느 예산이 모자란 건지**를 구분한다(→ README D6).

| 예산                 | 실제                               | 되는 것                                                  | 안 되는 것                                          |
| -------------------- | ---------------------------------- | -------------------------------------------------------- | --------------------------------------------------- |
| **코드**       | 개발 1명(+AI 코딩하는 비개발 인원) | 매니지드 서비스, API 호출, 단일 파이프라인 스크립트      | 자체 모델 학습, 우회형 크롤링 인프라, 대규모 백엔드 |
| **사람(검증)** | 4명 중 3명                         | 수작업 태깅, 기준표 실측, 샘플 검증·오답률 집계, 인터뷰 | 수천 건 전수 수작업                                 |

→ **자동화 정확도가 임계에 못 미쳐도 사람 검증 루프로 신뢰도를 담보할 수 있다**는 게 이 팀 구성의 실제 강점이고, 파이프라인(D6: 자동추출→사람 샘플검증→정확도 측정)이 그 위에 서 있다. 반대로 "사람이 더 붙으면 되는 문제"와 "붙어도 안 되는 문제"(차단·약관·모델 성능)는 섞지 않는다.

## 1. 네이버 쇼핑 검색 오픈API

**결론:** 상품명·가격·판매몰·브랜드·제조사·카테고리·이미지는 안정적으로 주지만 **소재·리뷰·상세설명은 응답에 없음.**

- 응답 필드: `title, link, image, lprice, hprice, mallName, productId, productType, brand, maker, category1~4`
- 한도: 일 25,000회 / `display`≤100 / `start`≤1000 → **키워드 1개당 최대 1,000개까지만 페이징** (2000개 채우려면 키워드 다양화 필수)
- 정렬: `sim`(유사도)/`date`/`asc`/`dsc`(가격)
- 리스크: 상업적 이용·재배포 약관 **원문 미확인**(차단). 상용화 전 확인 필요.
- 근거: [응답필드 velog](https://velog.io/@pjh5365/Naver-검색-API를-이용한-쇼핑몰-검색서비스-만들기) · [swagger 스펙](https://github.com/naver/naver-openapi-guide/blob/master/ko/naver-openapi-swagger.yaml) · [일 25,000회](https://choonghyunryu.github.io/posts/2022-03-01-open-api/)
- 주의: 일부 블로그가 reviewCount·score 필드를 언급하나 이는 **비공식 내부 엔드포인트**이며 공식 오픈API엔 없음.

## 2. 스마트스토어 소재(성분) 정보

**결론:** 소재/혼용률은 **판매자 본인만** 커머스API로 정형 조회 가능. 제3자는 상세페이지 이미지·HTML(고시정보 표)에 파묻힌 걸 **파싱/OCR**해야 하고 포맷이 제각각 → 정확도 편차 큼.

- 커머스API 토큰은 `SELF`/`SELLER`만 → 남의 상품 상세 정형 조회 불가. 근거: [SELF/SELLER 토큰](https://github.com/commerce-api-naver/commerce-api/discussions/780) · [필드 추가 요청](https://github.com/commerce-api-naver/commerce-api/discussions/2127)

## 3. 리뷰

**결론:** **공식 수집 API 없음.** 크롤링은 기술적으로 가능하나 캡챠·JS동적렌더·레이트리밋·로그인 다층 차단 + 약관/법적 리스크(민법 750조). **핵심 의존축으로 두는 것 비권장** — 막는 건 인력이 아니라 차단·법적 리스크라 **사람이 더 붙어도 결론은 같다**(§0). 단 **수십 건을 사람이 직접 읽는 샘플 실험은 검증 3인 캐파로 가능** → D5의 "소규모 샘플 실험"은 유지.

- **1차 자료 — 약관(원문 미확인)**: [네이버 서비스 이용약관](https://policy.naver.com/policy/service.html) · 오픈API 이용약관(developers.naver.com 내). **둘 다 직접 열람 실패**(fetch 차단, 헤더 ⚠️) → "약관상 금지/허용"은 이 문서 근거로 단정하지 않는다.
- **1차 자료 — 법령**: [민법 제750조(불법행위)](https://www.law.go.kr/법령/민법) · [저작권법 제93조(데이터베이스제작자의 권리)](https://www.law.go.kr/법령/저작권법) · [정보통신망법 제48조(침해행위 금지)](https://www.law.go.kr/법령/정보통신망이용촉진및정보보호등에관한법률) — 크롤링 분쟁에서 실제 다퉈지는 조문(민법 750조 단독 아님).
- **1차 자료 — 판례**: 대법원 2022. 5. 12. 선고 **2021도1533**(야놀자–여기어때) — 공개된 정보 크롤링에 대해 정보통신망법·저작권법·업무방해 **모두 무죄 확정**. 리스크는 "크롤링=위법"이 아니라 **접근 방식·수집 규모·약관 위반 여부**에 달림. 해설: [법률신문](https://www.lawtimes.co.kr/news/articleView.html?idxno=182087)
- 근거(⚠️ **2차 자료 = 보조 참고**): [네이버 크롤링 차단 다층방어](https://blog.hashscraper.com/posts/reasons-why-naver-crawling-is-blocked-and-solutions?locale=ko) · [리뷰 크롤링 구현사례](https://velog.io/@kimjk4031/파이썬-네이버-스마트스토어-리뷰-크롤링) · [크롤링 법적 리스크](https://velog.io/@nnijgnus/크롤링-해도-될까)
  - 위 블로그들은 **약관 내용·법적 리스크를 그 자체로 입증하지 않는다.** 법령·판례는 위 1차 링크로 대조했고, **약관 원문만 여전히 미대조**. "법적 리스크가 있다"는 서술은 약관 대조 전까지 **가능성 플래그**로만 읽는다. 단 D5 결론(리뷰 = 소규모 샘플만)은 법적 판단이 아니라 **차단 다층방어라는 기술적 사실**만으로도 성립한다.
- → **결정 D5: 리뷰는 v1에서 소규모 샘플 실험만** (수십 개, LLM 리뷰요약→느낌태그 가능성만 검증).

## 4. 대안 소스

소재+리뷰를 정형 API로 주는 국내 소스 사실상 없음. 쿠팡 파트너스 API는 검색 **시간당 10회·최대 10개** 제한(데이터 수집 부적합). 무신사 공개 API 없음(크롤링만). 29CM API 확인 안 됨.

- 근거: [쿠팡 파트너스 제한](https://yourtime.kr/entry/쿠팡파트너스-deeplink딥링크-API-활용하는-법) · [무신사 크롤링](https://blog.hashscraper.com/musinsa-category-crawling-bot?locale=ko)

## 5. 이미지 속성 추출 스택 (6주 · 코드 예산 1인 현실)

- **색상**: OpenCV + KMeans / `imagedominantcolor` — **단일 대표색 추출의 저비용 베이스라인**(정확도는 미실측). **바탕색/프린팅색 분리는 별도 검증이 필요**하다 — 단일 dominant color로는 "흰 바탕+노란 프린팅"을 못 가르므로 **H1**(색 바탕/프린팅 분리 추출 정확도)에서 샘플 검증으로 판정한다(→ 미해결 질문·`living/solution-design.md`). 근거: [imagedominantcolor](https://github.com/akamhy/imagedominantcolor)
- **프린팅 문구 OCR**: EasyOCR/Tesseract(한글) — 티셔츠 프린팅은 폰트·왜곡 심해 정확도 낮음 → **비전 LLM이 더 강함**. 근거: [한글 멀티모달 OCR](https://velog.io/@cathx618/한글이-포함된-사진에서-Multimodal-model으로-Object-Detection을-잘-하는-방법)
- **스타일/핏/모티프**: 비전 LLM(멀티모달)에 이미지+프롬프트→JSON. 별도 학습 불필요.
- **비용 주의**: 비전 LLM은 상품 수에 비례해 비용 선형↑ → 색상 등 저난도는 OpenCV, 프린팅·스타일 등 고난도만 LLM에 태우는 **하이브리드**. 단 **하이브리드는 Loop1 계약이 아니다** — D12(확정)대로 Loop1은 비전 LLM 단일 호출 단독으로 가고, OpenCV/OCR 보조는 카탈로그 확장·정확도 미달 시 **Loop2/P1 정밀화** 단계에서 붙인다.

## 6. 무신사 전환 후 현실성 (2026-07-30 갱신, D14)

**결론:** 공개 API 없음 → 수집은 크롤링(§4에서 기확인). 대신 상품 메타데이터 품질이 높아 추출·검증 축이 유리해짐.

- **확인된 것(팀 실측)**: **바탕색 기준표용 44색 확정**(팀 실측) — 무신사 컬러칩 54색(반소매 티셔츠 카테고리 `/category/001001` 2026-08-04 관측값 — 사이트 전체 색 체계로 일반화하지 않음) 중 ΔE 비교가 불가한 10색(청 워싱 5·메탈릭 3·클리어·기타색상)을 제외한 값 → 바탕색 기준표(ΔE 비교)로 사용 (태깅 repo 커밋 `cfe4e84`) · 상품 수집·적재는 백엔드 담당, 팀 Supabase에 1,685행 적재됨 — **이 1,685행은 수집된 전체 재고 풀이며 MVP 대상이 아니다.** Loop1의 평가·노출 대상은 이 풀에서 선별한 50~100개(→ [mvp-plan](../living/mvp-plan.md) Loop1)
- **네이버 대비 장점**: 패션 전문 → 반팔티 상품 밀도·이미지 컷 품질 높음, 54색 공식 색 체계 존재 → 태깅 기준표·검증에 직결
- **미확인·리스크(플래그)**: 크롤링 약관·차단 정책 원문 미확인(→ **D16**: 포트폴리오 범위 소량·저빈도로 진행, 상업화 전 원문 확인) / 소재(상품정보 고시) 필드 일관성 미실측 / 리뷰·스냅 수집 난이도 미조사 / 대량 수집 시 레이트리밋
- 근거: 무신사 공개 API 부재·크롤링 사례 — §4와 동일 출처(hashscraper)

## 종합 — 6주 최현실 경로 (2026-07-30 재작성, 무신사 기준)

> 이전 판(네이버 API 뼈대)은 D14로 폐기. 아래가 현재 기준.

**코드 예산(1인)이 감당하는 축**

1. **뼈대 = 무신사 상품 수집**(백엔드, 소량·저빈도 크롤링) → Supabase 적재. 공개 API 없음(§4·§6).
2. **색·프린팅문구·스타일 = 이미지에서 추출**(**Loop1 = 비전 LLM 단일 호출 단독**, 저난도 OpenCV 하이브리드는 **Loop2/P1 정밀화**에서 — D12). 소재는 상세 파싱으로 **추정(플래그)** — 보조.
3. **리뷰 = 핵심축 제외.** 차단·법적 리스크가 이유라 캐파로 못 뚫음(§3).

**사람 예산(3인)이 감당하는 축 — 자동화의 부족분을 메우는 자리**
4. **기준표·태깅**: **바탕색 기준표 44색**을 실측 확정(완료, §6) → 추출 결과를 ΔE로 검증. 라벨 표기 어휘는 카탈로그 색 어휘 53종(용도 구분 → [iterate-log 2026-08-04](../living/iterate-log.md)).
5. **샘플 검증 루프**: 속성별 오답률 집계 → 임계 미달 속성은 검색 노출 제외/플래그(D6). **정확도 주장의 근거는 자동화 성능이 아니라 이 루프다.**
6. **리뷰는 수십 건 사람이 직접 읽는 샘플 실험만**(D5) — 크롤링 의존 없이.

**둘 다 아닌 것 = 미해결로 남긴다**
7. **무신사 크롤링 약관 원문·상업적 이용 판단** = **D16으로 범위를 정해 진행**. 상품정보는 사이트에 공개돼 있으므로 포트폴리오·비상업 범위에서 **소량·저빈도 수집**으로 가되, 약관 원문 미확인이므로 **"상업적으로 문제없다"는 주장은 하지 않는다.** 상업화·서비스화 시점에 원문 대조가 선행 조건.
