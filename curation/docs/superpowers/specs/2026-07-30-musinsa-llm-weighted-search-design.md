# Phase 1.5 — LLM 가중 검색 (검증 쿼리 DSL) · 설계

> 유형: design · 2026-07-30 · 브랜치: feature/musinsa-migration
> 선행: [Phase 1 컷오버](2026-07-30-musinsa-search-cutover-design.md) 완료 · 후행: [Phase 2 UI](2026-07-30-musinsa-ui-phase2-design.md)
> 위치: Phase 1(구조화 필터 컷오버) → **Phase 1.5(검색 코어 재설계)** → Phase 2(UI). 메모리 [[musinsa-migration]].

## 1. 목표 · 문제

Phase 1 검색은 **LLM = 필터 번역기 + 하드 SQL 필터**다. LLM은 쿼리를 `QueryIntent`(색·패턴·소재·핏·사이즈·가격·성별 enum)로 축약만 하고, 실제 매칭은 소수 enum의 정확일치 필터가 한다. 그 결과:

- DB의 풍부한 의미신호(제목 자유텍스트 · **`wear_chars` 착용감**)를 **버린다**.
- 통제어휘가 빈약해(패턴 14 · **핏 단 3종** · 소재 14) "부드러운·시원한·쫀쫀한·머슬핏" 같은 자연어를 못 잡는다.
- 결국 무신사 자체 필터 UI의 열화판 — LLM 비중이 낮다.

**목표**: 벡터 DB 없이, **DB에 실재하는 값**만으로 LLM 비중을 높인다. LLM이 구어/vibe를 실재 옵션값에 연결하고 **검색 쿼리를 직접 생성**하되, 검증·수정으로 안전·정확을 보장한다.

## 2. 핵심 원리 — LLM은 "데이터"가 아니라 "쿼리"를 본다

LLM 비중을 **검색 실행이 아니라 쿼리 전략 생성**에 둔다.

- LLM 입력 = 사용자 쿼리 + 스키마/통제어휘(조건). 출력 = **검증 가능한 쿼리 DSL**.
- 실행 = 인덱스 Postgres. LLM은 상품 행을 읽지 않음 → **카탈로그 크기와 무관하게 토큰 고정** = 확장에 안전.
- 대비: 후보를 LLM에 다 넣는 "리랭크"는 데이터가 커지면 병목 → Phase 1.5에선 안 씀(백로그 레이어).

## 3. 아키텍처

```
쿼리 → LLM(파싱 + DSL 생성; 스키마·통제어휘·wear_chars 어휘·사이즈사전 주입)
     → 검증(화이트리스트·캐논화·구조검사)   ──실패──▶ 1회 피드백 재시도 → 안전 기본쿼리
     → DSL→SQL 컴파일 → search_goods 실행
     → 결과 적음? ──▶ progressive relaxation(약한 절 완화) 재실행
     → 소프트 스코어 랭킹 top-N → 결과(+선택 reason)
```

기존 코드 대비: `parse-query-intent`(파서)와 `build-goods-query`(빌더)를 **DSL 생성 + DSL 컴파일러/검증기**로 재작성. `score-row`/`rank-goods`는 소프트 스코어에 `wear_chars` 가점 추가로 확장.

## 4. 쿼리 DSL (안전 수위 B — 원시 SQL 아님)

LLM은 **화이트리스트 필터트리**만 출력한다. 코드가 이를 검증 후 Supabase 쿼리로 컴파일한다.

```jsonc
{
  "and": [
    { "gender": "여성" },                       // 하드(정확)
    { "price": { "lte": 30000 } },              // 하드(범위)
    { "sizeStd": { "in": [90, 95] } },          // 하드(사이즈)
    { "or": [                                    // 소프트(스타일/vibe)
      { "colors": "블랙" },
      { "title~": "쿨링" }, { "title~": "에어로쿨" }
    ]},
    { "wear_chars.촉감": { "in": ["부드러움", "약간|부드러움"] }, "soft": true }
  ],
  "not": [ { "patterns": "레터링" } ],
  "sort": "relevance"
}
```

**허용 요소(화이트리스트)**:
- 컬럼: `gender·price·sizeStd·colors·patterns·materials·fits·category·brand·title~`(ILIKE) + `wear_chars.{촉감·두께·비침·신축성·계절·핏}`.
- 연산: `eq`(값) · `in`(배열) · `range`(gte/lte) · `title~`(ILIKE 부분) · `and/or/not` 트리 · 노드별 `soft` 플래그.
- 그 외 컬럼·연산·원시 SQL·서브쿼리 = **거부**.
- `LIMIT` 항상 강제(후보 상한).

**하드 vs 소프트 분류**(컴파일러가 강제):
- **하드(정확·완화 최후)**: `gender·price·sizeStd` (객관 제약).
- **소프트(완화·가점 대상)**: `colors·patterns·materials·fits·title~·wear_chars·keywords`.

## 5. `wear_chars` — 부활시키는 축 (이 설계의 핵심)

현재 뷰엔 있으나 `Goods`/`QueryIntent` 매핑에서 **버려진다**. 이를 쿼리·랭킹·UI 축으로 살린다.

**통제어휘(실측 distinct, §10)** — 각 축 서열형:
- 촉감: 부드러움 · 약간|부드러움 · 보통 · 약간|뻣뻣함
- 두께: 얇음 · 약간 얇음 · 보통 · 약간|두꺼움 · 두꺼움
- 비침: 없음 · 거의 없음 · 보통 · 약간 있음 · 있음
- 신축성: 있음 · 약간 있음 · 보통 · 거의 없음 · 없음
- 계절: 봄 · 여름
- 핏: 레귤러 · 오버|사이즈 · 슬림 · 루즈 · 스키니 (메인 `fits` 3종보다 풍부)

**구어→캐논 매핑(LLM, 서열 인식)**:
| 사용자 표현 | DSL |
|---|---|
| "부드부드한/부들부들" | `촉감 ∈ {부드러움, 약간\|부드러움}` |
| "시원한" | `두께 ∈ {얇음, 약간 얇음}` OR `비침 ∈ {없음, 거의 없음}` OR `계절=여름` |
| "도톰한/두꺼운" | `두께 ∈ {두꺼움, 약간\|두꺼움}` |
| "쫀쫀한/신축 좋은" | `신축성 ∈ {있음, 약간 있음}` |
| "비침 없는" | `비침 ∈ {없음, 거의 없음}` |

**커버리지 41% → 반드시 소프트/완화 축**. 하드 배제 시 태그 없는 59%가 통째 빠짐. 따라서 `wear_chars` 절은 기본 `soft:true`(가점) 또는 완화 1순위. "부드러운 반팔"이 표본만 뜨는 사고 방지.

## 6. 검증·수정 루프 ("틀리면 도와준다")

1. **캐논화·어휘검증**: 화이트리스트 밖 컬럼/연산 = 드롭. enum 값은 통제어휘로 강제(퍼지매핑: "검정"→"블랙", 실패 시 드롭). LLM이 "부드부드"를 그대로 뱉어도 촉감 어휘에 스냅.
2. **구조검증**: DSL 파싱·연산 허용목록·범위 정합(min≤max)·`LIMIT` 강제. 깨지면 검증 에러를 LLM에 **1회 되먹여 수정**.
3. **빈결과 progressive relaxation**: 결과 < 임계치면 **가장 약한 소프트 절부터 완화**(순서: `title~` → `wear_chars` → `patterns/materials` → `fits/colors`; 하드 `gender/price/size`는 최후). 완화할 때마다 재실행, 임계 충족 시 정지. 완화 이력 기록.
4. **폴백**: 2회 재시도·완화에도 실패하면 하드 제약만 남긴 안전 기본쿼리. 그래도 0건이면 빈 결과 + 재시도 안내(Phase 2 §4.3).

## 7. 랭킹

- 하드 필터 통과 후보에 **소프트 스코어**: 매칭된 소프트 절 수·가중(색·핏 > wear_chars 가점 > title~ 부분매칭)·리뷰(review_score·count 보정)·완화 페널티.
- `sort`: relevance(기본) · price_asc · review_count.
- 기존 `score-row`/`rank-goods` 확장(회귀 테스트로 방어).

## 8. 확장 로드맵 (DSL은 안 버려짐)

데이터가 커져도 DSL/검증/수정 골격은 유지하고 아래를 **얹기만** 한다:
- **`title~` → Postgres FTS**(tsvector + GIN, `websearch_to_tsquery`) — `%kw%` 풀스캔 해소, 대규모 인덱스 검색.
- **top-N LLM 리랭크** — 품질 한 끗 필요 시 K 고정으로 top-N만(쿼리당 O(1) 유지).
- **오프라인 LLM 태깅** — 제목에 안 드러나는 vibe를 적재시 태그화(검색은 계속 인덱스).
- **pgvector**(Supabase 내장, 별도 DB 아님) — 시맨틱 리콜 필요 시.

## 9. Phase 2 UI 영향 (별도 스펙 갱신)

- **의도칩**: **검증·캐논화된 DSL에서 파생**(실제 실행된 쿼리 = 사용자에게 보이는 "이해한 것"). `wear_chars` 축 칩 추가(예 "촉감:부드러움") — 조건제거 = 해당 DSL 절 제거 후 재검색.
- **상세**: 착용감(촉감·두께·비침·신축성) 요약 표시(사이즈 cm 표와 함께 "우리 기준").
- **(선택) reason**: "부드러운 촉감·시원한 소재로 매칭" 등 LLM 매칭 근거 노출로 LLM 비중을 UX로 가시화.
- 완화 발생 시 "조건을 조금 넓혔어요" 안내(선택).

## 10. 데이터 근거 (2026-07-30 · `search_goods` 2,472건)

- `wear_chars` 41% 채움, 축별 distinct 4~6값(§5 목록). `title` 자유텍스트에 통제어휘 밖 어휘 풍부(머슬핏 156·크롭 124·퀵드라이 75·에어로쿨 54·소로나 99·메쉬 39·기능성 96·폴로 44·링거 40 등).
- 상세 카탈로그·통제어휘·채움률은 [Phase 2 §12](2026-07-30-musinsa-ui-phase2-design.md) 프로파일과 공유.
- 추출 스크립트: 스크래치패드 `profile_goods.py`·`profile_llm_signals.py`. `wear_chars` 어휘는 `gen_musinsa_vocab` 방식으로 상수화(플랜).

## 11. 리스크

- **LLM DSL 오출력**: 검증·1회 수정·폴백으로 방어. 검증기는 **거부 기본(fail-closed)** — 모르는 컬럼/연산은 통과 금지.
- **wear_chars 41% 커버리지**: 소프트/완화로만 사용(하드 배제 금지). 완화가 과하면 정밀도 저하 → 임계치·완화순서 튜닝, 완화 이력 로깅.
- **지연**: DSL 생성 1콜 + (드묾)수정/완화 재쿼리. 리랭크 없어 후보 스캔 LLM콜 없음 → 리랭크안보다 가벼움.
- **완화 불투명성**: 사용자가 왜 이 결과인지 혼란 → UI 완화 안내·칩으로 투명화.
- **회귀**: 파서·빌더 재작성 → 스냅샷/골든쿼리 테스트로 방어.

## 12. 테스트 · 완료 기준

- **단위**: DSL 검증기(화이트리스트·캐논화·거부), DSL→SQL 컴파일러, 완화 로직, wear_chars 매핑, 스코어러 — TDD.
- **골든 세트**: 대표 자연어 쿼리 N개(부드러운·시원한·머슬핏·3만원 이하 여성 등) → 기대 DSL/결과 스냅샷.
- **완료 기준**: 골든 쿼리에서 vibe/구어가 실재 옵션에 연결되고, 검증·완화·폴백 경로가 동작하며, `client/` `npm run check` 그린 + 실데이터 수동 확인(정상·빈결과·완화·degraded).
