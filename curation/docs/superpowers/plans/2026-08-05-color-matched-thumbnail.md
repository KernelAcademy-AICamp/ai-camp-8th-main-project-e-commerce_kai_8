# 계획 — 검색 결과 "색 매칭 썸네일"

- 작성일: 2026-08-05
- 상태: 개정 초안(브레인스토밍 + codex 설계 검토 + codex 계획 검토 반영). 사람 검토(개선) 대기.
- 관련: 검색 결과 화면(`/search`), 카탈로그 데이터(Supabase `search_goods`)

---

## 1. 배경 · 문제

티셔츠가 여러 색으로 나오는 상품(표본상 다색 상품 약 26%)일 때, 검색 결과 카드는 항상 **대표색 사진 1장**만 보여준다. 예를 들어 "흰티"로 검색해 흰색 변형이 있는 상품이 걸려도, 그 상품의 대표색이 검정이면 **검정 사진**이 나온다. 사용자는 **검색한 색에 맞는 사진**을 보고 싶다.

## 2. 데이터 현실 (실측으로 확인)

- 상품 데이터에는 색↔이미지 연결이 없다. 각 상품은 **대표 사진 1장** + **색 라벨 없는 상세 사진 여러 장** + **색 이름 목록**만 갖는다. 검색 응답에는 상세 사진 목록조차 실려 오지 않고 대표 사진만 온다.
- 다만 상세 사진 안에는 **다른 색 변형의 사진이 실제로 섞여 있다**(색 대비가 뚜렷한 상품에서 옐로우·라임·짙은 회색 변형 사진이 각각 존재함을 실측). → 상세 사진을 색으로 분류하면 "검색한 색의 사진"을 골라낼 수 있다.
- 더 신뢰도 높은 원천(무신사 원본 옵션 이미지)은 현재 우리 접근 권한(읽기 전용)으로는 확인 불가. 같은 디자인의 색별 형제 상품도 다색 상품의 약 10%뿐이라 일반 해법이 못 된다.

## 3. 접근 방향 (확정된 결정)

- **오프라인 배치로** 상품별 "색 → 대표 사진" 인덱스를 한 번 만들어 저장하고, 검색 시에는 만들어둔 결과만 사용한다(검색 때마다 이미지 분석하지 않는다).
- 색을 절대적으로 맞히지 않는다. 각 사진을 **그 상품이 이미 가진 색 후보 중 가장 가까운 것**에 배정하거나, 애매하면 **배정을 포기(abstain)** 한다.
- 분류는 **가벼운 색 추출 휴리스틱 + 배경/모델 제거(옷만 남기기)** 로 한다.
- 약속을 **"틀린 색 절대 안 보여줌"이 아니라 "높은 정확도 + 애매하면 교체 안 함"** 으로 둔다. 확신이 없으면 지금처럼 대표 사진을 그대로 보여준다(안전 기본값).
- 원본 옵션 이미지 원천은 **카탈로그 담당에게 병행 문의**하고, 있으면 더 견고한 원천으로 교체 검토한다(휴리스틱은 그 경우 fallback).

## 4. 미정(가정하지 않고, 선택 기준·결정 게이트만 둔다)

- **배경/모델 제거 방법**: 흰 배경 임계 제거 같은 가벼운 것부터 오프라인 세그멘테이션까지. 결정 게이트 = 단계 B의 holdout 정확도. (특정 방법으로 못박지 않는다.)
- **정확도 목표치(교체 허용 게이트 수치)**: holdout 평가 **전에** 목표 수치와 최소 표본 수를 고정한다(단계 B 시작 조건).
- **저장 위치**: DB 파생 데이터 / 서버 전용 파일 인덱스 중 택일. 결정 게이트 = 단계 D 종료 전, 쓰기 권한 확보 여부에 따라 한 경로를 확정(그 전엔 두 경로의 선택 기준만 둔다).
- **원본 옵션 이미지 유무**: 카탈로그 담당 답변(단계 A). 있으면 원천 우선순위에 따라 이미지 원천을 교체한다.

> 주: 아래 단계에서 언급하는 저장 항목·상태값·응답 필드는 **확정이 아니라 요구 정보의 목록**이다. 실제 스키마·이름은 구현 계획에서 정한다.

## 5. 단계

두 국면으로 나눈다. **국면 1(A·B·C) = 타당성 검증**(핵심 위험을 먼저 없앤다), **국면 2(D~I) = 저장·연동·노출.** 국면 1을 통과 못 하면 국면 2로 넘어가지 않는다.

### 국면 1 — 타당성 검증 (핵심 첫 블록)

#### 단계 A — 원천 우선순위 결정 게이트 (짧은 기한)
- 카탈로그 담당에게 "원본 옵션 데이터에 색별 이미지가 있는가"를 정해진 기한 안에 묻는다.
- 원천 우선순위를 **옵션 이미지 매핑 > 같은 디자인(style_key)의 색별 대표 사진 > 갤러리 휴리스틱** 으로 명시하고, 여러 원천이 동시에 존재할 때 무엇을 택하는지 **결정적 충돌 규칙**을 적는다.
- 완료 기준: **담당 답이 오면**, 어떤 원천으로 국면 1을 진행할지와 충돌 규칙이 문서에 확정되어 보인다. (기한 내 무응답이면 휴리스틱으로 진행하되 그 사유를 적는다.)

#### 단계 B — 색 기준표(팔레트) 산출·버전 고정
- 통제 어휘의 **모든** 색을 덮는 기준 색표를 만든다(누락 0). 각 색은 **고정 식별자**와 기준색을 갖고, 색군별 거리 기준과 **팔레트 버전**을 함께 둔다. (현재 UI 스와치 색표는 일부만 덮으므로 분류 기준으로 쓰지 않는다.)
- 완료 기준: **기준표를 열면**, 통제 어휘의 모든 색이 식별자·기준색으로 존재하고 **누락 0**이 확인되며, 버전이 찍혀 있다.

#### 단계 C — 라벨링 정확도 검증 (핵심)
- 다색 상품 표본(먼저 2색·색이 뚜렷이 다름·옷만 찍힌 사진 위주)에서, 각 사진(대표 사진 포함)을 **배경/모델 제거 → 지배색 추출 → 단계 B 기준표로 그 상품 색 후보 중 최근접 배정(또는 abstain)** 한다. (상품에 적힌 대표색 라벨은 노이즈가 있어 그대로 믿지 않는다.)
- **튜닝용 표본과, 보지 않은 holdout을 분리**한다. holdout에서 **교체 precision · coverage · abstain 비율**을 각각 측정한다(측정은 "엉뚱한 색으로 바꾸는 오류 최소화"를 우선).
- 완료 기준: **holdout 표를 열면**, (상품, 색)→배정 사진이 눈으로 확인되고 **세 지표 수치와 오분류 사례 목록**이 보인다. 이 수치로 단계 D의 교체 게이트 목표치를 사람과 확정한다.

### 국면 2 — 저장·연동·노출

#### 단계 D — 교체 규칙·결정성 확정
- 교체 허용 조건을 보정한다: 검색 의도 색에 포함(제외 색 아님) · 상품 색 목록과 겹침 · 대상 색과의 색 차이 상한 이하 · 2순위 색과의 여유 하한 이상 · 옷 영역/사진 품질 하한 이상 · 상태가 "검증됨" 계열. **"검증됨/자동-높음/보류" 상태가 각각 어떤 근거로 생기는지** 정의한다.
- **결정성**: 같은 사진 중복 제거, 같은 색에 후보가 여럿이면 결정적 tie-break, **같은 입력이면 재실행해도 같은 인덱스·같은 표시 사진**이 나오는지 확인한다.
- 완료 기준: **규칙을 holdout에 적용하면** 각 후보가 `교체함/보류/로드실패`로 분류되어 표로 보이고, **교체함 중 오교체 건수가 사전에 고정한 목표 이하**이며, **재실행 결과가 동일**함이 확인된다.

#### 단계 E — 인덱스 저장 경로 확정·저장
- 저장 경로(DB 파생 데이터 / 서버 전용 파일 인덱스)를 이 단계 종료 전에 **택일**한다. 파일 인덱스로 가면 빌드·배포·용량·갱신 절차를 함께 정한다. 어느 쪽이든 **클라이언트 번들에 전체 인덱스를 넣지 않는다.**
- 저장에 필요한 정보: 색(고정 식별자) · 사진 출처 · 상태 · 색 차이/여유/품질 · 방법·팔레트 버전 · 원본 사진 목록 해시(내용 지문) · 생성 시각. 무효화는 가격과 무관, **색 목록·사진 목록·방법/팔레트 버전이 바뀔 때만** 재생성. 원격 사진이 같은 URL로 내용만 바뀌는 경우(캐시 잔존)를 **내용 지문 ↔ 실제 전달 URL/캐시 정책**으로 잇는다.
- 완료 기준: **저장소를 조회하면** `(상품, 색)→검증된 사진 + 메타`가 나오고, **null·깨진·구버전 레코드를 넣어도** 조회 측이 기존 대표 사진으로 정상 동작함이 확인된다.

#### 단계 F — 데이터/뷰/권한 배포 (하위호환·롤백 체크)
- 배포 순서 = **데이터 → 뷰 권한 → 서버 코드.** 뷰를 다시 만들 때 읽기 허용·쓰기 차단을 다시 적용한다.
- 완료 기준: **구버전 서버로도** 응답이 정상이고(추가 필드는 additive), **뷰 권한이 읽기 허용·쓰기 거부**로 확인되며, **조회 실패 시 검색이 기존 대표 사진으로 닫힌다.**

#### 단계 G — 서버 후보 계산 shadow 계측 (노출 없음)
- 서버가 최종 검색 의도·최종 결과로 색 하나를 고르는 계산을 **노출 없이** 돌려, 각 결과가 `교체 가능/교체함/보류/로드실패(배치 다운로드)`와 사유로 로그에 쌓이게 한다. 분모·관찰 기간을 정한다.
- **회귀 기준**: 결과 ID·순서·개수·모드·순위 지표와 기존 계측/라우팅이 배포 전과 **동일**하고, 오직 후보 사진 관련 계산만 추가됨을 기준 응답과 비교해 확인한다.
- 완료 기준: **검색을 돌리면** 화면은 그대로인데 **로그에 교체/보류/사유와 분모가 쌓이고**, 회귀 비교가 통과한다.

#### 단계 H — 접근성·실패 폴백·성능 마감 (노출 전 완료)
- 교체 색은 화면·스크린리더에 라벨로 알린다. 대표 사진 fallback일 땐 검증 안 된 색을 알리지 않는다. 그리드는 지연 로딩 유지·전체 미리 불러오지 않음·고정 비율 틀(레이아웃 밀림 없음)·허용 출처만.
- 완료 기준: **깨진 URL·느린 이미지·비허용 출처를 넣으면** 한 번만 대표 사진으로 되돌아가고 레이아웃이 안 밀리며, **키보드·스크린리더로** 교체 카드 색이 안내된다.

#### 단계 I — 제한 노출 + 활성화 게이트
- 단계 G/H 통과 후 **제한 노출**로 실제 렌더(서버가 표시 사진 한 장만 additive로 응답, 클라는 있으면 그걸·없으면 대표 사진)와 **브라우저 렌더 실패** 계측을 켠다.
- 완료 기준(활성화 게이트): **단계 C/D에서 고정한 precision·coverage·오교체율**과 **검색 실패율·지연 변화**가 정해둔 관찰 기간·표본에서 게이트를 통과하면 노출을 넓히고, 못 하면 스코프(색군·상품 유형)를 좁힌 사유를 남긴다.

## 6. 스코프 (1차 한정)

2색 상품 · 색군이 서로 멀리 떨어진 색 · 옷만 찍힌 고품질 사진 · 기준 색표가 완비된 색 · 단일한 명확한 색 질의만. (여러 색·제외 색·"바탕색×프린트색"이 섞인 질의, 모델 사진, 비슷한 중성색, 프린트 비중 큰 상품은 1차에서 보류(abstain).) 정확도 게이트 통과 후 확장.
