## 확정된 저장 구조 (2026-08-07 기준)

- 프린팅 관측은 별도 자식 테이블이 아니라 **상품 원본 테이블(m_raw_goods)의 jsonb 배열 컬럼 `prints`** 에 저장한다. 각 배열 원소가 "컬러웨이 × 프린트 객체" 하나이며 컬러웨이(base_color), 면 배열(sides), 그래픽 유형, 잉크색, 잉크색 상태, 모티프를 가진다.
- 상품의 옷 색 전체는 `base_colors` 배열 컬럼이다. 라벨 완료 여부는 `prints`가 값(빈 배열 포함)을 가진 것으로 구분한다(무지 = 빈 배열, 미라벨 = 값 없음).
- 현재 실데이터: 라벨 12건, 프린트 객체 4개(전부 앞면·확인 상태·단일 컬러웨이). 다컬러웨이+프린팅, 뒤/소매/전체, 없음/판독불가 케이스는 아직 없다 — 데이터 측에 요청됨.
- 검색 결속의 실행 의미: "같은 프린트 객체 안에서 조건이 함께 성립"은 jsonb 배열 원소 단위의 포함 검사로 표현한다. 조건을 서로 다른 원소에 흩어 검사하는 것은 교차 매칭 오류로 금지.

## 이 계획이 다루는 것

"옷 바탕색(컬러웨이)과 프린팅 잉크색의 관계를 보존한 검색"의 검색 측 전체를 만든다. 구체적으로:

1. 착수 계약 결정 (기존 검색 기반 구조와의 관계, 조건 소유권, 기능 스위치 역할)
2. 해석 골든셋 동결 (구현 전에)
3. 어휘 계약 (검색·적재가 함께 참조할 단일 소스)
4. 정확 표현의 결정적 해석
5. 결속 조건 구조와 컴파일 규칙 + 합성 사례 기반 검증
6. jsonb 실행 연결(어댑터)과 실데이터 검증 — 실데이터가 이미 적재되기 시작했으므로 이 계획에 포함
7. 기존 검색과의 통합 (기본 꺼짐, 켜짐 검증 포함)

이 계획의 완료는 "1차 출하선 완료"가 아니라 **"1차 출하선의 검색 측 선행분 완료"** 다. 라벨링 운영·대량 적재는 데이터 측 몫이며, 데이터가 충분히 쌓이면 기능 스위치를 켜는 것으로 컬러웨이 검색이 사용자에게 열린다.

주의 — "LLM 없음"의 의미: 현행 검색이 이미 사용 중인 LLM 쿼리 파서는 그대로 유지된다. 이 계획에서 만들지 않는 것은 **신규 컬러웨이 의미 해석 LLM**(구어 표현 번역)뿐이다. 그것은 2차 출하선(shadow) 별도 계획이다.

배경을 모르는 독자를 위한 요약: 이 서비스는 무신사 상품 데이터 위에서 "블랙 바탕에 화이트 백프린팅" 같은 자연어로 프린팅 티셔츠를 찾는 검색이다. 같은 상품이라도 컬러웨이(판매 색상)마다 프린팅 잉크색이 다르다는 사실이 확인되어(예: 같은 로고가 화이트 바탕엔 그린, 블랙 바탕엔 화이트로 인쇄됨), 프린팅 관측을 컬러웨이 단위로 저장하고 검색 조건도 같은 관측 객체 안에서 검사해야 한다.

## 이 계획이 다루지 않는 것 (비목표)

- 라벨링 운영(VLM 실행·검수)과 대량 적재 — 데이터 측 담당
- 신규 컬러웨이 의미 해석 LLM(shadow·on) — 2차 출하선 별도 계획
- "프린팅 없음(무지)" 강한 검색 조건 — 설계 문서 §14.1 보류 유지
- 0건 자동 완화 — 설계 문서 §14.4대로 미결, 정직한 0건 반환이 기본

## 확정된 결정 (구 미정 — codex 권고 채택)

1. **기존 Phase 3 기반 구조는 부분 재사용**: 출처(provenance)·원문 근거(evidence span)·강제 수준·규칙 버전 개념과 "꺼짐 동일성 테스트" 패턴은 재사용한다. 결속 조건 구조(PrintClause), 상품 수준 바탕색 조건, 관측 상태 의미, 실행 어댑터는 신규로 만든다. 기존 기반 구조의 평면 표현에 억지로 끼워 넣지 않고, 기존 외곽 구조에 프린팅 전용 가지를 합성한다.
2. **기능 스위치는 신규로 분리**: 기존 결정화 검색 스위치를 재사용하지 않는다. "컬러웨이 데이터 검색 활성화"와 "LLM 의미 해석 off/shadow/on"은 수명주기가 다른 별개 축이므로 각각의 스위치를 둔다. 이 계획에서 만드는 것은 전자다.
3. **해석 골든셋은 신규 작성** (24~30건): 기존 색 표현 골든셋 50건은 색 별칭 기대값의 참조원으로, 기존 의도 쿼리 33건은 전체 검색 회귀용으로 유지하고, 컬러웨이 결속을 표현하는 골든셋은 새로 만든다. 검색 담당이 초안을 쓰고 데이터·라벨 담당이 색과 프린트 의미를 검토한 뒤 **구현 전에 동결**한다.
4. **실행 형태**: 저장 구조가 jsonb로 확정되고 실데이터가 존재하므로, 논리 실행 계약과 jsonb 실행 어댑터까지 이 계획에 포함한다(연기하지 않음).

## 남은 미정 (데이터 측 확인 필요 — 진행 병행 가능)

- **[미정 A] 라벨 provenance 재도입** — jsonb 전환 때 라벨 시각·스키마 버전·프롬프트 버전 3종이 빠졌다. 재라벨링·골든셋 비교에 필요하므로 재도입 여부와 형태를 데이터 측이 결정.
- **[미정 B] 커버리지 공백 배치 시점** — 다컬러웨이+프린팅(교차 매칭 검증용), 뒤/소매/전체 면, 없음/판독불가 상태 케이스가 실데이터에 없다. 이 계획의 7단계 실데이터 검증 폭이 이 배치에 달려 있다(없으면 합성 사례 검증으로 대체하고 실데이터 검증은 후속).

## 단계

### 1단계 — 착수 계약 결정 기록

**무엇을**: 위 "확정된 결정" 4개(부분 재사용 범위, 스위치 분리, 골든셋 신규, jsonb 실행 포함)와 **조건 소유권 규칙** — 컬러웨이 해석기가 소비한 원문 표현(예: "백프린팅", "등판", "나염")은 결속 조건이 소유하며 기존 제목·색·패턴 필터가 같은 표현을 중복 소비하지 않는다 — 을 짧은 결정 기록으로 남긴다. 설계 문서의 저장 구조 서술(자식 테이블 전제)에 jsonb 확정 사실을 반영한다.

**완료 기준**: 결정 기록 문서가 저장소에 보이고, 설계 문서에 jsonb 확정 변경이 반영되어 있다.

### 2단계 — 해석 골든셋 동결 (구현 전)

**무엇을**: 쿼리 원문 → 기대값 형태의 골든셋 24~30건을 만든다. 기대값은 두 층으로 보존한다: ①기대 해석(조건·대상 귀속·미해결 표현) ②기대 결속 계획. 필수 버킷: 결속(바탕+잉크), 바탕색 단독, 위치 단독, 복수 객체("앞엔 A 뒤엔 B"), 부정, 외부 맥락, 미해결. 데이터·라벨 담당의 의미 검토를 받은 뒤 동결한다.

**완료 기준**: 골든셋 파일이 두 층의 기대값과 버킷 표기를 갖추고 저장소에 있으며, 검토 완료 표시가 있다. 이후 단계에서 이 파일을 기준으로 실패가 판정된다(구현에 맞춰 기대값을 고치지 않는다 — 고칠 땐 사유 기록).

### 3단계 — 어휘 계약 (단일 소스, 신규)

**무엇을**: 캐논 색, 검색 위치(앞·뒤·소매·전체), 그래픽 유형 12개, 잉크색 상태 4개의 단일 소스를 만든다. 기존 검색의 facet 어휘를 그대로 재사용하지 않는다(값 체계가 다름). DB 저장값 / 계획 전용 값('전체') / 내부 상태값을 구분된 이름공간으로 관리하고, 어휘에 버전 또는 해시를 부여한다. 데이터 측 적재 검증이 나중에 같은 소스를 참조할 수 있는 위치에 둔다. 확정 스키마에서 삭제된 값(멜란지·피그먼트 등 가공 계열)은 넣지 않는다.

**완료 기준**: 어휘 밖 값으로 검색 조건을 만들려는 시도가 거부되는 것과, 타입 검사·실행 시 검증이 같은 소스에서 파생되는 것이 자동 테스트로 보인다. 어휘 버전이 조회 가능하다.

### 4단계 — 정확 표현의 결정적 해석 (핵심 기능)

**무엇을**: 정확·검증된 별칭 표현을 조건으로 해석한다. 범위: 바탕색과 잉크색의 대상 구분, 위치(백프린팅·등판·올오버 등), 그래픽 유형, 보수적 부정(인접 명사구 안에서만, 모호하면 미해결). 각 해석에 원문 근거(span)를 남기고, 해석하지 못한 표현은 조건 없이 미해결로 남긴다. **해석기가 소비한 표현이 기존 제목 검색어 추출에 다시 들어가지 않게** 소비 span을 후속 처리에 전달한다.

**완료 기준**: 2단계 골든셋의 해석 층(acceptance 부분)이 자동 검증으로 통과한다. 검증 항목에 최소 포함: 표기 정규화, 가장 긴 표현 우선, 중복 별칭의 단일 조건화, 대상 귀속, 부정 범위, 미해결 처리, 소비 표현의 제목 필터 재유입 없음.

### 5단계 — 결속 조건 구조와 컴파일 + 합성 사례 검증

**무엇을**: 해석 결과를 실행 계획으로 바꾸는 규칙을 만든다. 계약: ①한 묶음의 바탕색·잉크색·위치·유형은 같은 프린트 객체 안에서 함께 성립(분리 검사 금지) ②서로 다른 객체 요구는 묶음 복수 개 ③강제 수준은 필드별 보존 ④잉크색 상태가 판독불가·미촬영이면 잉크색 조건 불성립 ⑤'전체'는 세 면이 모두 포함(순서 무관) ⑥면 배열이 빈 객체(무늬 전용)는 위치 조건 불성립 ⑦**바탕색 단독 요청은 상품 수준 옷 색 배열로 검색**(결속 불필요 — 무지 상품 포함) ⑧여러 객체가 일치해도 결과는 상품당 한 건. 구조 검사만으로는 의미가 증명되지 않으므로, 합성 상품·객체 사례와 기준 판정기(참조 구현)로 다음 진리표를 검증한다: 동일 객체 일치 / 교차 매칭 거부 / 묶음 2개 / 판독불가·미촬영 거부 / 빈 면 배열 거부 / 올오버 포함 / 바탕색 단독 / 복수 객체 일치 시 상품 1건.

**완료 기준**: 같은 해석 입력이 항상 같은 계획을 내는 것(결정성)과, 진리표 8케이스가 합성 사례에 대해 전부 기대대로 판정되는 것이 자동 테스트로 보인다.

### 6단계 — jsonb 실행 어댑터와 실데이터 검증

**무엇을**: 컴파일된 계획을 실제 DB(jsonb `prints` 컬럼)에 대해 실행하는 어댑터를 만든다. 어댑터의 실행 결과가 5단계 기준 판정기와 같은 의미인지 — 같은 합성 사례를 DB에 임시 적재해 — 대조한다. 이어 현재 실데이터(라벨 12건)로 스모크 검증한다. [미정 B]의 커버리지 배치가 도착해 있으면 교차 매칭 거부까지 실데이터로 검증한다.

**완료 기준**: "블랙 바탕에 화이트 프린팅"을 실행하면 실데이터의 6660007(블랙 컬러웨이·화이트 잉크)이 나오고, "블랙 바탕에 블랙 프린팅"에는 나오지 않는 것이 보인다. 합성 사례의 DB 실행 결과가 기준 판정기 판정과 전건 일치한다.

### 7단계 — 기존 검색 통합 (기본 꺼짐 + 켜짐 검증)

**무엇을**: 신규 기능 스위치 뒤에서 현행 검색 흐름에 연결한다. 꺼짐이 기본이며, 다음 네 가지를 데이터 유무와 무관하게 검증한다: ①꺼짐이면 신규 실행기가 호출되지 않고 현행 결과와 완전 동일 ②켜짐(검증 환경)이면 컴파일된 계획이 실행기에 전달됨 ③신규 해석이 소비한 표현이 제목·기존 색 필터에 중복 적용되지 않음 ④실행기 실패 시 정의된 안전 동작(현행 검색으로 폴백)이 수행됨.

**완료 기준**: 위 4개 검증이 자동 테스트로 보이고, 기존 테스트 전체가 통과하며, 프리뷰에서 꺼짐 상태의 현행 검색이 그대로 동작한다.

### 8단계 — 전체 회귀와 마무리

**무엇을**: 2단계 골든셋 전체(해석 층 + 계획 층)와 기존 의도 쿼리 33건 회귀를 실행한다. 품질 체크(lint·typecheck·빌드) 통과 후 PR로 develop에 병합한다. 후속 메모를 남긴다: 스위치 켜기 전환 조건(데이터 커버리지 기준), 데이터 측 요청 목록([미정 A]·[미정 B]), 2차 출하선(LLM shadow) 착수 조건.

**완료 기준**: 회귀 결과 표에서 합의 기준(결속·부정 버킷 전건 통과)이 충족되고, develop 병합 후 프리뷰에서 현행 검색이 그대로 동작한다. 후속 메모 문서가 저장소에 보인다.

## 후속 (이 계획 밖)

- **데이터 측**: 라벨링 운영·커버리지 배치([미정 B])·대량 적재·provenance 재도입([미정 A])
- **스위치 켜기**: 데이터 커버리지 기준 충족 시 — 이 계획 완료 후에는 어댑터가 이미 검증돼 있으므로 실제로 "켜기 + 실데이터 확인"만 남는다
- **2차 출하선**: 신규 컬러웨이 의미 해석 LLM 최소 구현 + shadow — 별도 계획
