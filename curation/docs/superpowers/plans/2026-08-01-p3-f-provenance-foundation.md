## 배경 — 이 작업이 무엇이고 왜 하는가

Phase 3a(색 축 결정화 파일럿)는 "값이 어디서 왔는가(출처)"에 따라 하드/소프트를 가르는 구조를 요구한다. 지금 검색 파이프라인은 LLM이 추출한 값과 결정적으로 추출한 값(브랜드 사전·가격 정규식·제목 잔여 토큰)이 **같은 평면 의도 객체에 출처 구분 없이 섞여** 있어, 어떤 값을 하드필터로 믿어도 되는지 코드가 알 수 없다. P3-F는 이 토대를 만든다:

1. **값 단위 출처 메타**(어느 추출기가, 원문 어느 구간에서, 포함/배제로, 하드/소프트로, 완화 가능 여부와 함께) — 설계 §3.5의 ConstraintMeta.
2. **내부 해석 산물**(의도 + 값별 메타)과 **조회 계획**(후보 조회에 실제 적용될 조건 집합)의 분리 — mode 판정·칩 표시·계측·완화 사슬이 **같은 근거**를 쓰게 하는 준비.
3. **결정화 경로 feature flag**(환경변수, 기본 off) — 3a shadow 배포와 3b 원자적 cutover의 전제.
4. **grounded 신호 재정의**(flag-on에서만 발효) — "결정적 추출 값이 하나 이상 있어야 검색 신호"로. flag-off에서는 현행 신호 판정 의미를 그대로 유지한다(설계 v2.1 명문화).

**외부 계약(응답 형태·화면·GA4 파라미터)과 검색 동작은 바뀌지 않는다.** 기존 동작을 새 구조로 재표현하는 리팩터링이며, 완료 증명은 "기존 테스트 전부 통과 + flag-off 동작 동일성"이다.

## 확정 사항 (1단계 질문 답변)

- **임계값 확정됨**: 기준 2 precision ≥0.95, 기준 3 축별 누락률 ≤5% — T0a 판정 문서에 확정 표기(본 브랜치에 포함).
- **결정성 게이트를 P3-F 범위에 포함**: 서로 다른 LLM 의도 fixture를 주입해 **후보 하드 계획**을 비교하는 유닛 게이트. flag-off에서는 "LLM 값이 바뀌면 하드 계획도 바뀌는 현행 상태"를 **기준선으로 기록**하고, flag-on에서는 fixture 무관 **후보 하드 계획 해시 동일**을 단언한다 — LLM 출처가 하드 조건에서 배제되므로 P3-F 시점에 이미 성립하며, 3a·3b에서 결정적 추출기가 늘어도 유지된다.
- **flag는 환경변수**(서버 측, 기본 off) — 코드 배포 없이 전환·롤백. P3-F 기간 프로덕션은 off 고정이며 on은 테스트·shadow 전용.
- **flag-on의 의미(모순 없이 통일)**: flag-on은 두 가지가 함께 바뀐다 — ①신호 판정(grounded 재정의) ②**하드 조건 정책**(LLM 출처 값은 하드 조건이 될 수 없음 — 미결정화 축의 LLM 값은 소프트 강등, 설계 §2 부분 출시 조항의 시맨틱스). 정렬은 후보 집합에 영향이 없으므로 하드 정책 대상이 아니며, LLM 추출 정렬은 flag-on에서도 그대로 적용한다(정렬 결정화는 3b).
- **출처 enum과 규칙 버전 불변식**: 값 출처 enum은 설계 §3.5의 전체 집합(facet 사전·브랜드 사전·가격 정규식·규칙 파서·제목 휴리스틱·LLM)을 P3-F에서 전부 예약해 확정한다(현시점 미사용 값 포함 — 3a·3b가 채운다). 규칙 버전은 **비어 있지 않은 안정적 문자열**이어야 한다는 불변식을 테스트로 고정한다(문자열 체계 자체는 구현 자유).

## 범위에서 제외 (비목표)

- facet 사전·수식어 문법·소비 span 통합 — Phase 3a.
- promote/exclude 재정의, 성별·사이즈·정렬·강제 표현의 결정적 파서 — Phase 3b.
- browse 입구 분기·searchKind — Phase 3c.
- 랭킹 가점·완화 사슬 변경 일체(사슬 단계 추가는 3a·3b).
- LLM 프롬프트/스키마 변경(출력 계약 불변).
- 외부 응답 형태·화면·계측 파라미터 변경.

## 단계

### 1. 값 단위 출처 메타와 내부 해석 산물 도입 (핵심)

- 설계 §3.5의 값 단위 메타(출처·원문 구간 근거·포함/배제·하드/소프트·완화 가능 여부·규칙 버전)를 담는 내부 표현과, "평면 의도 + 값별 메타"를 함께 든 내부 해석 산물을 도입한다.
- 현행 파이프라인의 각 추출 결과에 출처를 부여한다: 브랜드=브랜드 사전, 제목 잔여 토큰=제목 휴리스틱, 나머지(색·핏·소재·패턴·키워드·착용감·성별·사이즈·정렬·배제)=LLM. **가격은 이원**이다 — 현행 결정적 가격 파서는 원문에 명시 가격이 있을 때만 LLM 값을 덮어쓰므로, **명시 가격이 파싱된 경우만 가격 정규식 출처, 그 외 남은 가격 값은 LLM 출처**로 기록한다. 원문 구간 근거는 결정적 추출기가 이미 아는 범위에서만 채운다(모르면 비움 — 지어내지 않는다).
- **완료 기준(가격 이원 포함): 명시 가격 쿼리와 LLM-only 가격 fixture 두 경우 모두, 가격 값의 출처가 각각 정규식/LLM으로 갈리는 것이 테스트로 보인다.**
- 외부로 나가는 평면 의도 객체는 그대로 둔다(클라이언트 계약 불변).
- **완료 기준: 대표 쿼리 fixture로 단위 테스트를 돌리면, 값마다 위 출처가 정확히 기록된 내부 해석 산물이 만들어지는 것이 보인다.**

### 2. 조회 계획 분리 (하드/전체 이원 구조)

- 후보 조회에 실제 적용될 조건을 내부 해석 산물에서 파생하는 "조회 계획"으로 분리한다. 계획은 두 층위로 나눈다(결정성 게이트의 해시 대상이 다르므로):
  - **후보 하드 계획**: 후보 집합을 결정하는 모든 것(브랜드·가격·성별·사이즈·facet 하드·배제 NOT·제목 tier 조건·**고정 후보-fetch 정렬**(현행 DB 백스톱: 리뷰점수→상품번호 — 상한 앞에서 실행돼 후보 집합을 결정하므로 포함)·상한). 비교·해시 가능한 순수 자료 — **사용자(LLM 유래) 정렬과 소프트는 포함하지 않는다**(해시 경계). 고정 fetch 정렬은 의도와 무관한 상수라 fixture 간 해시 동일성을 해치지 않는다.
  - **전체 실행 계획**: 위에 더해 소프트 주석(랭킹 재료)·**사용자 정렬**·적용 순서 — 해시 동일성 대상이 아니라 flag-off 동일성 비교와 관측·기준선 기록용.
- flag-off 동일성 비교는 **전체 실행 계획 수준**으로 한다: 현행 쿼리 빌더가 실제로 거는 조건의 집합에 더해 제목 tier 구분, 배제 NOT, 정렬, 상한, 적용 순서까지 일치해야 한다(동작 변화 없음의 핵심 고리).
- **완료 기준: 같은 의도를 넣었을 때 ①후보 하드 계획이 현행 하드 조건·상한과 일치하고 ②전체 실행 계획이 정렬·순서까지 현행과 일치함을 단언하는 비교 테스트가 통과한다.**

### 3. feature flag 배선 — flag-on의 세 가지 발효(신호·하드 정책·resolved 응답)

- 환경변수 기반 결정화 경로 스위치를 만든다(기본 off). off이면 신호 판정·조회·응답 모두 현행과 완전 동일.
- on이면 셋이 함께 발효된다("확정 사항"의 flag-on 정의):
  - **grounded 신호 재정의**: 결정적 출처(현시점: 브랜드 사전·가격 정규식·제목 휴리스틱) 값이 하나 이상 있어야 full/lexical_only, LLM-only 값만 남은 쿼리는 신호 없음.
  - **하드 조건 정책**: LLM 출처 값은 하드 조건 불가. 강등 후 처리는 **축별 소프트 소비자 유무로 확정**한다:
    - 소프트 소비자(랭킹 가점) 있음 → **소프트 강등 + 응답 intent 유지**: 색·패턴·소재·핏·키워드·착용감.
    - 소프트 소비자 없음 → **미적용 + 응답 intent에서 제거**(칩 미표시): LLM 출처의 성별·사이즈·배제·가격(비명시).
    - 정렬 → 예외적으로 그대로 적용(후보 집합 무관, 결정화는 3b).
  - **resolved 응답 계약(설계 v2.1 ④)**: 외부 평면 intent에는 **실제 적용됐거나 소프트로 반영된 값만** 담는다 — 미적용 LLM 값이 intent·칩에 노출되지 않는다("적용된 조건 = 표시된 칩" 불변식). flag-off 응답은 기존 intent와 완전 동일.
- **완료 기준: flag off로 전체 테스트가 기존과 동일하게 통과하고, on으로 테스트를 돌리면 ①LLM-only 쿼리는 신호 없음·브랜드/가격/제목 쿼리는 신호 있음 ②LLM 색 값이 하드 조건에 없음 ③미적용 LLM 값이 응답 intent에 없음이 각각 보인다.**

### 4. 결정성 게이트 (해시 대상 = 후보 하드 계획만)

- 같은 쿼리에 대해 서로 다른 LLM 의도 fixture들(§1 요동 실측의 4가지 패턴을 본뜬 것)을 주입하는 유닛 게이트를 만든다:
  - **flag-off 기준선**: fixture별 **후보 하드 계획** 해시의 차이를 기록한다(현행은 LLM 값이 하드필터가 되므로 다른 것이 정상 — 이 차이가 cutover 후 사라져야 할 대상임을 테스트 안에 문서화).
  - **flag-on 단언**: fixture가 무엇이든 **후보 하드 계획 해시가 동일**함을 단언한다 — LLM 출처 값이 하드 조건에서 배제되므로 P3-F 시점에 이미 성립한다(전체 실행 계획은 소프트 주석·LLM 정렬이 fixture마다 다를 수 있어 해시 동일성 대상이 아님 — 기준선 기록만).
  - 이 단언은 3a·3b에서 결정적 추출기가 늘어나도 그대로 유지된다(결정적 추출은 쿼리 원문의 함수라 fixture와 무관).
- **완료 기준: 게이트 테스트를 돌리면 flag-on에서 어떤 fixture를 주입해도 후보 하드 계획 해시가 동일함이 단언되어 통과가 보인다.**

### 5. 동작 동일성 검증 (기능 변화 없음 증명)

- 전체 테스트(클라이언트·백엔드)가 통과한다.
- 라우트 단위: 동일한 의도 fixture에 대해 리팩터 전후의 응답이 같음을 비교하는 테스트 — 비교 대상은 결과 목록·mode·칩 재료에 더해 **제목 tier 관련 응답 필드(tier·구제·폐기 표시), DB 호출 횟수·순서, 오류 경로(DB 오류 시 failed 계약)**까지 대표 fixture로 고정한다.
- 실측 관측(참고): dev 서버에서 대표 쿼리 몇 개의 응답을 리팩터 전 커밋과 비교해 다르지 않음을 눈으로 확인(LLM 분산이 있으므로 결과 개수·mode 수준의 확인 — 판정은 fixture 테스트가 담당).
- **완료 기준: 전체 테스트 통과 + 응답·호출 순서·오류 경로 동일성 비교 테스트 통과가 보인다.**

### 6. 문서·PR

- 설계 문서 §4의 P3-F 항목에 완료 표시와 산출물 링크를 단다. T0a 판정 문서의 임계값 확정 표기(이 브랜치에 포함)도 함께 나간다.
- `develop` 대상 PR — 본문에 "기능 변화 없음 + flag 기본 off + 결정성 게이트 기준선"을 명시.
- **완료 기준: PR을 열면 CI 초록불과, 설계 문서 diff에 P3-F 완료 표시가 보인다.**

## 미정 플래그 (임의로 가정하지 않은 것)

- **내부 표현의 파일 배치·이름**: 구현 시 결정(계획에서 못박지 않는다 — 여러 구현이 가능).
- **규칙 버전 문자열의 체계**(추출기별/전체 단위, 갱신 규칙): 구현 시 결정하고 PR에 근거를 적는다 — 단 "비어 있지 않은 안정적 문자열" 불변식은 확정 사항(테스트로 고정).
- **flag 환경변수의 이름·노출 범위**: 서버 전용이라는 제약만 확정, 이름은 구현 시.
