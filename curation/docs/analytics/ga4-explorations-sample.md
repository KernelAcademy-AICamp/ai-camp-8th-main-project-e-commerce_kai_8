# GA4 탐색(Exploration) 분석 샘플 — search-by-llm

> 속성: `search-by-llm` (`properties/547257934`) · 시간대 Asia/Seoul · 통화 KRW
> 이 문서는 GA4 **탐색** 메뉴에서 그대로 따라 세팅할 수 있는 설계도다.
> 탐색은 API로 생성이 안 되므로 GA4 UI(왼쪽 메뉴 **탐색 → 새 탐색 만들기**)에서 손으로 구성한다.

## 0. 현황과 사전작업 (먼저 읽기)

### 실제로 수집 중인 이벤트 (2026-07-25~29 기준)
| 이벤트 | 의미(추정) | 퍼널 단계 |
|---|---|---|
| `search_performed` | 검색 실행 | ① 검색 |
| `result_clicked` | 검색 결과 클릭 | ② 결과 클릭 |
| `detail_viewed` | 상품 상세 조회 | ③ 상세 |
| `outbound_click` | 외부(구매처)로 이동 | ④ 전환 |
| `constraint_removed` | 검색 제약/필터 제거 | 이탈·재검색 신호 |
| `mismatch_reported` | 결과가 검색의도와 불일치 신고 | 품질 신호 |
| 표준 | `page_view`·`session_start`·`first_visit`·`scroll`·`user_engagement`·`form_start`·`click` | — |

### ⚠️ 사전작업: 검색어 분석을 하려면 커스텀 측정기준 등록 필요
현재 이 속성에 **등록된 커스텀 측정기준이 0개**다. `search_performed` 이벤트에 검색어가 매개변수로 실려 있어도, 탐색에서 "검색어별"로 나누려면 매개변수를 **커스텀 측정기준(이벤트 범위)** 으로 먼저 등록해야 한다.

1. GA4 → **관리(⚙️) → 데이터 표시 → 맞춤 정의 → 맞춤 측정기준 만들기**
2. 아래를 등록(이벤트 코드에서 실제로 보내는 매개변수 이름에 맞춰라):

| 측정기준 이름(표시) | 범위 | 이벤트 매개변수 | 용도 |
|---|---|---|---|
| 검색어 | 이벤트 | `search_term` (또는 코드상 실제 키) | 검색어/의도 분석 |
| 결과 수 | 이벤트 | `result_count` | 0건 검색 탐지 |
| 결과 순위 | 이벤트 | `result_rank` / `position` | 클릭 위치 분석 |
| 제거한 제약 | 이벤트 | `constraint` | 어떤 필터가 과하게 걸리는지 |

> 매개변수 실제 키가 확실치 않으면 **관리 → BigQuery/DebugView**나 코드(`gtag('event', 'search_performed', {...})`)에서 확인.
> 등록 후 **집계까지 24~48시간** 걸릴 수 있고, 등록 이전 데이터엔 소급 적용 안 된다.

## 탐색 1 — 검색 퍼널 (기법: 유입경로 탐색 / Funnel exploration)

**보고 싶은 것:** 검색 → 결과 클릭 → 상세 → 외부 전환까지 단계별 진행률과 어디서 가장 많이 빠지는지.

### 만들기
1. 탐색 → **새 탐색** → 기법에서 **유입경로 탐색** 선택.
2. **단계(Steps)** 설정 — 오른쪽 "단계" 연필 아이콘 → 각 단계에 이벤트 조건:

| 단계 | 이름 | 조건(이벤트 이름 =) |
|---|---|---|
| 1 | 검색 실행 | `search_performed` |
| 2 | 결과 클릭 | `result_clicked` |
| 3 | 상세 조회 | `detail_viewed` |
| 4 | 외부 전환 | `outbound_click` |

3. 상단 **"경과 시간 표시"** 켜기(각 단계 사이 소요시간 확인).
4. **"확대된 유입경로(Make open funnel)"** 옵션:
   - **닫힌 유입경로**(기본): 1→2→3→4 순서를 지킨 세션만.
   - **열린 유입경로**: 중간 단계부터 들어온 것도 포함. 처음엔 닫힌 것으로 이탈 지점을 본다.
5. **분류(Breakdown)** 에 `기기 카테고리(deviceCategory)` 또는 `세션 기본 채널 그룹(sessionDefaultChannelGroup)` 드롭 → 어떤 유입/기기가 잘 전환되는지.

### 읽는 법
- 단계별 막대 아래 **완료율/이탈률**을 본다. 예: 2→3에서 급락이면 "결과는 클릭하는데 상세를 안 본다" = 결과 카드가 기대와 다르다는 신호.
- 이탈이 큰 단계에서 우클릭 → **"선택 항목에서 세그먼트 만들기"** 로 이탈 유저를 세그먼트화해 탐색 2·3에서 재사용.

## 탐색 2 — 검색어/의도 분석 (기법: 자유 형식 / Free form)

**보고 싶은 것:** 어떤 자연어 검색어가 결과 0건이거나 클릭이 안 나는지(검색 품질 구멍).

> 전제: 0단계의 **검색어 커스텀 측정기준** 등록 완료. (미등록이면 이 탐색은 이벤트 수만 나오고 검색어별로 안 쪼개진다.)

### 만들기
1. 새 탐색 → **자유 형식** → 시각화 **표(Table)**.
2. **변수(Variables)** 패널에서:
   - 측정기준: `검색어`(커스텀), `결과 수`(커스텀, 있으면), `기기 카테고리`
   - 측정항목: `이벤트 수(eventCount)`, `총 사용자(totalUsers)`
3. **탭 설정(Tab Settings)**:
   - 행(Rows) = `검색어`
   - 값(Values) = `이벤트 수`, `총 사용자`
   - 필터(Filters) = `이벤트 이름` 정확히 일치 `search_performed`
4. **정렬**: 이벤트 수 내림차순 → 많이 쓰는 검색어 상위 확인.

### 파생 표 2개(탭 추가 +)
- **결과 0건 검색어:** 탭 필터에 `결과 수` = `0` 추가(측정기준 등록 시). → LLM 검색이 못 잡는 의도 목록 = 다음 개선 백로그.
- **클릭 안 난 검색어:** 이 표에서 나온 검색어를, `result_clicked`로 필터한 표와 비교. 검색은 됐는데 `result_clicked`가 0인 검색어 = "결과는 떴지만 안 눌린" 케이스.

### 읽는 법
- 상위 검색어 = 핵심 수요. 0건/저클릭 검색어 = 즉시 개선 대상.
- `mismatch_reported`를 이벤트 필터로 건 별도 표를 만들면 "유저가 대놓고 틀렸다고 신고한" 검색 의도까지 잡힌다.

## 탐색 3 — 사용자 경로 (기법: 경로 탐색 / Path exploration)

**보고 싶은 것:** 검색 직후 유저가 실제로 어떤 순서로 움직이는지(재검색·필터제거 루프 등 설계 의도 밖 행동).

### 만들기
1. 새 탐색 → **경로 탐색** → (기존 그래프 있으면 우상단 **"다시 시작"**).
2. **시작점(Starting point)** 설정 → **이벤트 이름** → `search_performed` 선택.
3. 각 단계 노드는 **이벤트 이름** 기준으로 표시(페이지 대신 이벤트가 이 제품엔 더 유용).
4. 노드를 클릭하며 다음 단계로 펼친다. 특히 볼 것:
   - `search_performed` 다음에 또 `search_performed`/`constraint_removed`가 많으면 **한 번에 원하는 결과를 못 찾아 재검색·필터해제 루프**.
   - `result_clicked` → `detail_viewed`로 잘 가는지, 아니면 바로 이탈하는지.
5. 반대 방향도: 시작점 대신 **종료점(Ending point)** 을 `outbound_click`으로 놓고 → 전환 직전 경로 역추적(어떤 흐름이 구매로 이어지나).

### 읽는 법
- 굵은 엣지(=많이 일어난 전이)가 설계 의도와 다르면 UX 수정 포인트.
- `constraint_removed` 비중이 높으면 초기 필터/제약이 과하게 좁게 잡힌다는 뜻 → 검색 기본 파라미터 완화 실험 후보.

## 공통 팁
- **날짜 범위**는 왼쪽 상단에서 조정. 데이터가 적으니 처음엔 "이번 달" 또는 생성일(2026-07-27)~오늘.
- **세그먼트 재사용:** 탐색 1에서 만든 "이탈 유저" 세그먼트를 탐색 2·3 변수 패널로 끌어와 비교(정상 vs 이탈).
- **공유:** 우상단 공유 아이콘 → 같은 속성 권한자에게 보임(탐색은 만든 사람 기준 개인 소유, 공유 필요).
- **표본수 주의:** 현재 이벤트가 수십 건 수준이라 비율 해석은 위험. 화면 구조부터 잡아두고 데이터가 쌓이면 수치 판단.
