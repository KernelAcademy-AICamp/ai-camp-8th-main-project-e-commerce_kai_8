# 온보딩 구현 계획 교차 리뷰 결과

## 판정

**수정 후 재검토가 필요하다.** 질문 1은 실제 결함이다. 현재 신원 전환 순서에 온보딩 선택 전용 승계 절차를 추가하지 않으면, 일반적인 `atee-*` 로컬 키에 둔 선택은 계정에 붙기 전에 삭제된다. 그 밖에도 새 PWA 재진입, 계정 저장·완료 상태, 로그인 전 이탈 계측과 삭제 계약이 1단계에서 빠져 있다.

## ① 지금 해를 끼치는 문제

### 1. [Blocker] 질문 1 — 현재 방식 그대로면 온보딩 선택이 로그인 직후 삭제된다

- 계획은 선택을 로그인 왕복 동안 기기에 유지한다고만 적었다(`docs/plans/2026-08-24-onboarding-implementation.md:60-62, 87-89`).
- 실제 로그인 성공 뒤 `useIdentityReconcile`은 익명→사용자 전환을 감지하고, 삭제 전에 **찜과 성별만** 별도 보관한 뒤 `clearIdentityScopedData()`를 호출하고 페이지를 다시 불러온다(`frontend/features/auth/presentation/view-model/use-identity-reconcile.ts:59-75, 83-94`).
- 정리기는 `localStorage`와 `sessionStorage`를 모두 훑는다(`frontend/shared/identity/identity-reset.ts:23-27`). 삭제 목록은 새 키를 기본 삭제하는 allowlist 방식이라 `atee-` 또는 `atee.`로 시작하는 키는 명시적으로 보존하지 않으면 지워진다(`frontend/shared/identity/identity-scoped-keys.ts:1-5, 10-15, 40-46`; 이 동작을 고정한 테스트는 `frontend/shared/identity/identity-marker.test.ts:84-95`).
- 따라서 온보딩 선택을 보통의 `atee-onboarding-*` 키에 저장하면 삭제된다. 접두사를 피하거나 원본 선택 키 자체를 영구 보존하면 로그아웃·A→B 전환에도 남아 O-35를 깨므로 올바른 해결이 아니다.

**계획에 필요한 변경**: 기존 찜·성별과 같은 전환 전용 절차를 1단계의 선행 계약으로 넣어야 한다.

1. 평소 선택 원본은 신원 종속 키로 두어 로그아웃·계정 전환 때 지워지게 한다.
2. **익명→사용자 전환에서만**, 정리 전에 검증된 선택을 1회용 승계 보관함으로 옮기고 그 보관함만 정리 allowlist에 둔다. 기존 패턴과 순서는 `frontend/shared/identity/wish-carry.ts:28-50` 및 `frontend/shared/identity/gender-carry.ts:21-41`에 있다.
3. 보관함은 대상 사용자 ID에 묶어야 한다. 계정 A에 올리기가 실패한 뒤 로그아웃하여 B가 로그인했을 때 B로 넘어가면 안 된다. A→B·사용자→익명에서는 폐기하거나 대상 불일치로 멈춘다.
4. 다시 뜬 뒤 인증된 호출자의 계정에 `선택 저장 + 온보딩 완료`를 원자적·멱등으로 반영하고, 성공 확인 뒤에만 보관함을 지운다. 실패하면 홈을 개인화 완료 상태로 열지 않고 재시도한다.
5. 로그인 복귀 위치도 전환 정리와 한 계약으로 정해야 한다. 현재 복귀 키 `atee.after-login`도 삭제 대상이다(`frontend/shared/history/after-login.ts:13-34`, `frontend/shared/identity/identity-marker.test.ts:89-95`). effect 실행 순서에 기대지 말고, 로그인 콜백→승계 확정→첫 홈 순서를 결정적으로 보장해야 한다.

### 2. [Blocker] 계정에 무엇을 어떻게 붙이고 첫 추천에 쓰는지가 1단계에서 빠졌다

계획은 “계정에 붙인다”와 “실제 추천 상품이 보인다”만 적는다(`docs/plans/2026-08-24-onboarding-implementation.md:60, 78-89`). 그러나 정본은 온보딩 선택을 계산된 장기 취향과 같은 데이터로 취급하지 말라고 한다(`docs/atee/living/prd.md:146-148`, `docs/atee/living/data-collection-policy.md:24`). 현재 계정 취향 API는 계산된 앵커 프로필만 읽고 쓴다(`frontend/shared/profile/account-profile-api.ts:10-14, 41-56`). 별도 초기 선택·온보딩 완료 상태 계약은 현재 코드에 없다.

1단계 안에 최소한 다음 순서와 완료 기준이 필요하다.

- 인증 사용자만 접근하는 초기 선택 저장 계약과 서버 검증(최소 3개, 허용 후보, 선택 성별 일치, 임의 사용자 ID 입력 금지)
- 중복 콜백·새로고침·응답 유실에도 중복 또는 유실이 없는 원자적 완료 처리
- 저장이 확인되기 전에는 첫 홈을 열지 않는 게이트
- 저장된 선택이 실제 첫 추천 입력에 들어갔음을 확인하는 관찰 지점
- 완료 계정에서는 계정 상태가 기기 임시 상태보다 우선하는 규칙

현재 완료 기준의 “실제 추천 상품”은 무작위·공통 다양성 피드도 통과한다(`docs/plans/2026-08-24-onboarding-implementation.md:89`). 상위 계약은 선택 결과가 추천 입력에 들어갔음을 관찰 가능하게 확인하라고 명시한다(`docs/plans/2026-08-24-taste-discovery-onboarding.md:181-185`). 따라서 “저장된 N개가 추천 요청 입력에 사용됨”과 “성공한 경우에만 개인화 준비 문구가 보임”을 별도 완료 기준으로 두어야 한다.

### 3. [Blocker] 질문 2 — 계정 데이터는 안전하지만 새 PWA의 사용자 여정은 안전하지 않다

iOS 설치 PWA가 빈 저장소로 시작하면 localStorage뿐 아니라 그 컨테이너의 로그인 상태도 없다고 보아야 한다. 현재 Supabase 세션은 쿠키에 둔다(`frontend/shared/supabase/browser-client.ts:1-18`). 브라우저에서 이미 계정에 붙인 선택은 서버에 있으므로 **데이터 자체는 안전**하다. 다만 설치 앱은 로그인하기 전에는 그 계정을 식별할 수 없어 현재 계획대로면 성별·옷 선택을 다시 요구한다.

계획은 완료 계정 재방문을 반복하지 않는다고만 하고(`docs/plans/2026-08-24-onboarding-implementation.md:91-97`), 설치 PWA처럼 “로컬 상태와 세션은 없지만 기존 계정은 있음”인 진입을 다루지 않는다. 성별에는 이미 로그인 상태를 먼저 기다리고 계정 값을 내려받는 선례가 있다(`frontend/shared/gender/use-gender-setting.ts:47-61`, `frontend/shared/gender/gender-account-guard.tsx:35-43`). 온보딩 완료·초기 선택도 같은 계정 우선 복구가 필요하다.

- 첫 화면에 기존 사용자가 먼저 로그인할 경로를 제공하고, 로그인 뒤 계정 완료 상태를 읽어 완료 계정이면 선택 단계를 건너뛰어야 한다.
- `Safari에서 완료 → 홈 화면 설치 → PWA 실행 → 기존 계정 로그인 → 같은 초기 선택을 사용한 홈`을 독립 완료 시나리오로 추가해야 한다.
- 계정이 불완전한 경우의 복구 규칙은 이 경로를 결정하므로 2단계까지 미룰 수 없다.

### 4. [Blocker] 새 계정 데이터의 삭제·초기화 범위가 없다

초기 선택을 별도 계정 데이터로 저장한다면 삭제 계약도 같은 조각에서 닫아야 한다. 현재 계정 삭제는 `auth.users` 삭제와 FK cascade에 의존한다(`backend/supabase/migrations/20260818900000_account_delete.sql:23-39`). 개인화 초기화는 계산된 `c_taste_profiles`와 찜 등을 별도 경로로 지운다(`frontend/shared/signals/signals.ts:337-386`). 새 초기 선택이 별도 테이블이면 FK cascade, 개인화 초기화 포함 여부, 실패 재시도까지 정하지 않으면 서버에 남거나 다음 로그인에 되살아날 수 있다.

계획은 마지막 단계에서 기존 삭제가 “그대로 동작”하는지만 본다(`docs/plans/2026-08-24-onboarding-implementation.md:105-111`). 데이터 생성과 삭제는 원자적으로 함께 설계하고 1단계 완료 기준에서 실제 삭제 후 재로그인까지 확인해야 한다. 공개 처리방침도 취향·찜이 초기화/탈퇴로 지워진다고 약속한다(`frontend/app/privacy/page.tsx:139-155`).

## ② 나중에 비싸지는 문제

### 5. 로그인 전 무기록과 단계별 이탈 계측은 동시에 달성할 수 없다

계획은 온보딩 세 화면에서 서버로 나가는 것이 없어야 한다고 못 박고(`docs/plans/2026-08-24-onboarding-implementation.md:56-62`), 4단계에서는 단계별 이탈과 첫 홈 도달을 보겠다고 한다(`docs/plans/2026-08-24-onboarding-implementation.md:105-111`). O-41은 이 단계별 계측을 P0로 요구한다(`docs/atee/living/decision-log.md:64`).

로그인 전에 이탈한 사람은 이후 로컬 이벤트를 업로드하지 않으므로, 무기록 약속을 유지하면 성별 화면 분모와 단계별 이탈률을 계산할 수 없다. 구현 전에 다음 중 하나를 제품 결정으로 남겨야 한다.

- 최소 익명 온보딩 계측을 허용하고 O-37·수집 방침·공개 처리방침을 함께 변경한다.
- 무기록을 유지하고 로그인 전 이탈률 측정을 포기하며, 로그인 완료자 내부의 회고적 단계 데이터만 측정한다고 한계를 명시한다.

어느 쪽이든 계측을 4단계로 미루면 첫 배포의 기준 데이터를 되살릴 수 없다. P0 최소 계측은 핵심 세로 경로와 함께 배포되어야 한다.

### 6. 1단계가 한 번에 확인 가능한 크기가 아니며, 일부 미정은 시점이 잘못됐다

1단계 하나에 화면 3개, OAuth 왕복, 신원 전환, 계정 저장, 추천 준비, 홈 게이트가 모두 들어가 있다(`docs/plans/2026-08-24-onboarding-implementation.md:78-89`). 이 계획만으로는 실패 지점을 분리해 확인할 순서가 없다. “로컬 선택 유지 → 익명→계정 승계 → 계정 완료 판정 → 추천 입력 반영 → 첫 홈”처럼 각각 바로 관찰 가능한 하위 단계로 나눠야 한다.

미정 5개(`docs/plans/2026-08-24-onboarding-implementation.md:113-123`) 중:

- ② 불완전 계정 복구와 ③ 로그아웃 재시작은 계정/PWA 게이트를 결정하므로 **1단계 전에** 정해야 한다.
- ④ 코치마크는 상위 문서가 P0에서 제외하고 사용성 관찰 뒤 별도 검증한다고 이미 답했다(`docs/plans/2026-08-24-taste-discovery-onboarding.md:134-150`). 미정이 아니다.
- ⑤ 추가 보존 필드는 후보 버전·위치 편향과 계측 해석에 영향을 준다(`docs/plans/2026-08-24-taste-discovery-onboarding.md:179-185`). 첫 배포 뒤에는 유실 데이터를 복원할 수 없으므로 4단계가 아니라 저장 계약 전에 확정해야 한다.
- ① 초기 추천 실패 경험만은 2단계 착수 전 결정으로 두어도 된다. 다만 저장 실패와 추천 실패를 서로 다른 상태로 정의해야 한다.

### 7. 성별·후보·선택 상한 결정은 조건부로 타당하지만 회귀 기준이 부족하다

- “알고리즘으로 좁히고 사람이 최종 선택, 상시 자동 교체 안 함”은 현재 네 자동안의 관찰된 실패를 근거로 한 P0 결정으로 타당하다(`docs/plans/2026-08-24-onboarding-implementation.md:20-44`). 다만 상품 삭제·이미지 실패 시 3개 선택조차 막힐 수 있다. 고정 후보 버전, 유효성 사전 검사, 교체 책임자·트리거, 최소 유효 카드 수를 추가해야 한다. Living PRD도 유효하지 않은 이미지·상품을 제외하라고 한다(`docs/atee/living/prd.md:179-184`).
- “최대 선택 개수 없음”도 후보가 12개라 실질 상한이 12이므로 P0에서 합리적이다(`docs/plans/2026-08-24-onboarding-implementation.md:46-54, 82-89`). 다만 완료 기준은 3개만 시험한다. 4~12개, 전부 선택, 뒤로가기·성별 변경 시 선택 폐기, 요청 크기와 추천 입력의 의미를 확인해야 한다.
- O-39는 온보딩 후보뿐 아니라 무한 피드·검색·상세 하단·큐레이션 전체에 적용된다(`docs/atee/living/prd.md:140-144`). 1단계 완료 기준은 옷 선택 화면만 성별을 검사한다(`docs/plans/2026-08-24-onboarding-implementation.md:89`). 첫 홈 추천과 실패 폴백에도 반대 성별·공용 상품이 없음을 확인해야 한다.
- 기존 찜·성별 승계 순서를 건드리는 변경이므로 익명→사용자, 사용자→익명, A→B 각각에서 찜(O-36)과 계산 취향(O-35)이 새 온보딩 승계와 섞이지 않는 회귀 시나리오가 필요하다.

## 정본 정합성

0단계의 “PRD·결정 기록·데이터 방침·공개 처리방침을 함께 갱신” 완료 주장은 아직 사실이 아니다(`docs/plans/2026-08-24-onboarding-implementation.md:9-16`). 예를 들면:

- 수집 방침 표에는 여전히 `구글 계정 (선택)`이라고 적혀 있다(`docs/atee/living/data-collection-policy.md:9-16`), 같은 문서 본문은 필수라고 한다(`docs/atee/living/data-collection-policy.md:20-24`).
- PRD는 비회원 탐색 경로가 사라졌다고 선언하면서(`docs/atee/living/prd.md:127-136`), 찜 절에는 여전히 비회원이 피드·검색·상세를 쓸 수 있다고 적는다(`docs/atee/living/prd.md:152-156`).
- PRD P0 목록에도 비회원 피드·점진적 가입·가입 전 탐색 이력 승계가 남아 있다(`docs/atee/living/prd.md:236-250`).

이 충돌을 정리한 뒤에 0단계를 완료로 표시해야 한다. 또한 로그인 필수 게이트가 홈만이 아니라 검색·상세·큐레이션 직접 URL에도 적용되는지 접근 매트릭스를 명시해야 한다.

## 리뷰 범위와 검증
