# 온보딩 1단계 Blocker 수정 재검증 결과

## 판정

**수정 후 다시 재검증해야 한다.** 서버가 완료 계정의 값을 덮어쓰는 원래 결함 자체는
막혔고, 깨진 승계 보관함·문서 모순·씨앗 감쇠도 고쳐졌다. 그러나 계정 조회 실패가
자동 재시도 루프를 만들고, 최초 완료 경쟁의 패자가 서버의 실제 성별·판 번호를 받지
못하며, 기존 삭제 큐와 새 온보딩 삭제 큐 사이의 승계가 없다. 개인화 초기화의 밀린
삭제와 계정 온보딩 조회도 서로 경쟁한다.

검토 범위는 요청서대로 `9c172cb..HEAD`다. 요청서에는 “수정 커밋 하나”라고 적혀 있지만
실제 범위에는 `db49f27`과 뒤의 정리 커밋 `533952f`가 함께 들어 있어 둘 다 확인했다.

## ① 지금 해를 끼침

### 1. 실패 상태가 「다시 시도」 화면에 머물지 않고 즉시 무한 재시도된다

- path: `frontend/shared/onboarding/onboarding-account-guard.tsx`
- lines: 48-50, 78
- category: bug
- severity: high

`fetchAccountOnboarding()`이 실패하면 동기화 상태는 `failed`가 된다. 그런데 가드의
effect는 `syncStatus`를 구독하면서 `running`과 `settled`만 멈추고 `failed`에서는 다시
`fetchLocalUserId()`와 동기화를 시작한다. 따라서 상태가
`failed → running → failed → …`로 반복된다. 「다시 시도」 화면은 잠깐 나타났다가
사라지고, 네트워크가 계속 실패하면 RPC를 제한 없이 반복한다. 사람이 버튼을 눌러
`failed → idle`로 바꿀 때만 재시도한다는 주석·UI 계약과 반대다.

원래 결함처럼 완료 계정을 온보딩으로 보내지는 않지만, 수정이 새로운 무한 루프와
영구적인 화면 깜빡임을 만들었다. effect의 시작 조건을 최초 상태와 명시적 재시도
상태로 한정하고, 이 전이를 컴포넌트 수준 테스트로 확인해야 한다.

### 2. “먼저 마친 쪽”의 권위 있는 결과를 돌려주지 않아 패자 클라이언트가 거짓 상태를 설치한다

- path: `backend/supabase/migrations/20260824300000_onboarding_put_first_write.sql`
- lines: 90-98, 171-183
- path: `frontend/shared/onboarding/onboarding-account-sync.ts`
- lines: 147-159
- category: bug
- severity: high

이미 완료한 계정의 서버 행을 덮지 않는 보호는 생겼다. 불완전 계정은 완료 행이 없으므로
정상적으로 처음부터 저장할 수 있고, 개인화 초기화 뒤에는 완료 행을 남겨 온보딩 재진입을
막는 기존 제품 계약도 유지된다.

하지만 조기 반환은 기존 `picks`만 주고 **실제 성별과 `candidates_version`을 주지 않는다.**
승계 클라이언트는 응답을 받은 뒤 자신이 보낸 성별·판 번호가 이겼다고 가정해
`setGenderSetting(gender)`와 `install(... candidatesVersion: version ...)`을 실행하고
보관함까지 지운다. 다른 탭·기기가 먼저 완료했거나 그 뒤 설정에서 성별을 바꾼 경우,
서버는 안전하지만 현재 기기는 패자의 성별·판 번호와 승자의 선택을 섞어 홈을 연다.
조용한 무시가 실제로 클라이언트를 속이는 경로다.

또한 두 요청이 완료 행이 없을 때 정말 동시에 들어오면 둘 다 93행의 존재 검사를 통과할
수 있고, 패자는 171행의 기본 키 삽입에서 오류가 난다. 즉 “먼저 마친 쪽 결과를 조용히
돌려준다”는 계약은 순차 재호출에는 맞지만 동시 최초 완료에는 원자적으로 성립하지 않는다.
최초 완료를 원자적으로 선점한 뒤, 승패와 관계없이 서버의 권위 있는 성별·판 번호·선택을
한 응답으로 돌려줘야 한다.

개인화 초기화로 선택이 비어 있는 완료 계정은 조기 반환이 빈 배열이 되고 프론트가 이를
오류로 처리한다. 정상 게이트에서는 재진입하지 않으므로 데이터 덮어쓰기는 없지만, 이미
열려 있던 오래된 탭에는 “다시 시도”가 영원히 성공하지 않는 화면이 남는다.

### 3. 옛 단일 삭제 큐가 새 온보딩 큐로 승계되지 않아 기존 삭제 약속을 잃는다

- path: `frontend/shared/profile/pending-taste-forget.ts`
- lines: 26-32, 67-77
- path: `frontend/shared/onboarding/pending-onboarding-forget.ts`
- lines: 23-31, 65-77
- category: bug
- severity: high

새 초기화 요청부터는 두 큐가 독립적으로 기록되므로 원래의 부분 성공 결함이 사라졌다.
새 키도 `identity-scoped-keys.ts:19-23`의 신원 전환 유지 목록에 정확히 들어갔다.

그러나 `9c172cb` 형식의 기존 `atee-pending-taste-forget` 항목은 “취향과 온보딩 선택을
둘 다 아직 지워야 함”을 뜻한다. 새 코드는 같은 키를 취향 전용으로 재해석하고 온보딩
큐를 새 빈 키에서 시작한다. 옛 큐가 생기는 두 경우 모두 온보딩 삭제는 남아 있다.

- 취향 삭제가 먼저 실패해 온보딩 삭제를 아직 호출하지 못한 경우
- 취향 삭제는 성공하고 온보딩 삭제만 실패한 경우

업데이트 뒤에는 취향만 재시도한 다음 옛 키를 제거하므로, 계정의 온보딩 선택은 영구히
남는다. 기존 형식이 한 기기라도 존재할 수 있다면 옛 항목을 온보딩 큐에도 한 번 승계해야
한다. `9c172cb` 코드가 어느 기기에도 실행되지 않았다는 배포 증거가 있을 때만 이 지적을
제외할 수 있다.

### 4. 밀린 온보딩 삭제와 계정 온보딩 조회가 경쟁해 지운 선택을 기기에 되살릴 수 있다

- path: `frontend/shared/profile/account-profile-guard.tsx`
- lines: 62-75
- path: `frontend/shared/onboarding/onboarding-account-guard.tsx`
- lines: 48-68
- category: bug
- severity: high

`AccountProfileGuard`는 온보딩 삭제 큐를 재시도하지만, 별도의
`OnboardingAccountGuard`는 동시에 `c_onboarding_get`을 호출한다. 두 가드는 같은 레이아웃의
형제이고 서로의 완료를 기다리지 않는다. 조회가 삭제보다 먼저 응답하면 온보딩 가드는
옛 선택을 기기에 설치하고, 그 뒤 삭제는 서버 행만 지운다. 재시도 성공 경로는 로컬
온보딩 선택을 다시 비우지 않으므로 초기화한 씨앗이 현재 세션에 되살아난다.

각 큐 내부의 순서는 맞지만, **삭제 재시도 → 해당 데이터 조회·설치**라는 전역 순서가
보장되지 않았다. 이 경로는 두 가드를 함께 마운트해 삭제와 조회 응답 순서를 뒤집는
테스트가 필요하다.

### 5. 죽은 카드가 3장 미만이면 안내는 나오지만 같은 성별로 재시도할 수 없다

- path: `frontend/features/onboarding/presentation/components/onboarding-pick-screen.tsx`

- path: `frontend/features/onboarding/presentation/view-model/use-onboarding-flow.ts`
- lines: 96-105, 107-130, 199-203
- category: bug

죽은 카드를 부모 목록에서 제거하고 선택에서도 빼므로 보이는 개수·위치 계산은 이제 같은
목록을 쓴다. 그러나 `tooFew` 화면은 “다시 시도”하라고 쓰면서 재시도 버튼을 렌더하지
않는다. 가능한 조작은 「뒤로」뿐이다. 뒤로 가서 같은 성별을 다시 고르면 `gender` 값이
변하지 않아 후보 조회 effect가 다시 실행되지 않는데 `chooseGender()`는 `loading`을
`true`로 바꾼다. 결과는 끝나지 않는 스켈레톤이다. 다른 성별을 고르거나 페이지 전체를
새로고침하는 것은 해당 사용자의 정상 복구 경로가 아니다.

죽은 카드로 최소 수가 무너졌을 때도 `retryCandidates()`를 직접 실행할 수 있어야 하며,
같은 성별 재선택도 새 요청을 만들도록 해야 한다.

### 6. 서버의 `card_pos` 상한이 실제 반환 목록이 아니라 원본 후보 행 수다

- path: `backend/supabase/migrations/20260824300000_onboarding_put_first_write.sql`
- lines: 58-69, 144-155
- category: data integrity
- severity: high

클라이언트는 죽은 카드를 제거한 현재 목록에서 위치를 다시 계산하고, 서버는 위치 중복과
`pick_seq` 순열을 거부한다. 이 부분은 맞다. 하지만 후보 조회는 상품 조인·썸네일 자격·
성별 재분류·의심 플래그로 행을 제외하는 반면, 저장 검증의 `v_max`는
`c_onboarding_candidates` 원본 행만 센다. 예를 들어 원본은 12장이지만 서버가 3장만
반환한 판에서도 `card_pos=11`이 통과한다. “표시 가능한 범위 밖 위치를 서버가 거부한다”는
원래 결함이 완전히 사라지지 않았다.

CDN 오류로 클라이언트에서만 빠진 카드는 서버가 재구성할 수 없더라도, 적어도 서버가
반환할 수 있었던 목록의 상한은 후보 조회와 동일한 자격 조건으로 계산해야 한다.
