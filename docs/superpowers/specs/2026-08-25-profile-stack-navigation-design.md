# 프로필 화면 push 스택 전환 — 설계

- 작성: 2026-08-25
- 상태: 구현 완료 (2026-08-25) — `docs/superpowers/plans/2026-08-25-profile-stack-navigation.md` 3태스크 전부 완료
- 관련: [마이페이지 분리 설계](2026-08-19-my-page-design.md)

## 배경

지금 `/my`는 `app/@overlay/(.)my/` 인터셉팅 라우트로 열리는데, 전환이 "사이드시트"다 — 오른쪽에서 화면이 밀고 들어오면서 뒤에 깔린 홈이 `scale(0.92)`로 줄어들고 모서리가 둥글어진다(`app/globals.css` `sidebar-in`/`profile-open`). 오른쪽 가장자리를 드래그해 닫는 제스처도 있다(`useSwipeToClose`).

이걸 네이티브 앱처럼 "새 화면이 이전 화면을 완전히 덮으며 쌓이고, 뒤로가기로 한 겹씩 닫히는" push 스택 구조로 바꾼다.

## 범위

**이번 조각** — `/my → /settings` 2단을 push 스택으로. `/my`의 설정 메뉴(`settings-menu-button.tsx`)에서 "회원 탈퇴"가 `/settings`로 연결된다.

**이번 조각이 아닌 것**:
- **`/privacy`(약관·처리방침)는 스택에서 제외한다.** `app/privacy/page.tsx`에는 "뒤로가 아니라 닫기다"(2026-08-24 제품 책임자 결정)라는 명시적 주석이 있다 — 이 화면은 프로필 설정 메뉴(`settings-menu-button.tsx`의 "약관 및 정책")와 `/settings`(`PrivacySettings`), 그리고 **온보딩 3단계 동의 문구**까지 여러 곳에서 열리는 공용 화면이라, "닫기 = 특정 부모로 한 단계"가 성립하지 않는다(예전에 `/my`로 고정했다가 온보딩에서 열었을 때 엉뚱한 곳으로 튀어나가는 버그가 있었다). 그대로 둔다.
  **정정(최종 리뷰에서 발견, 2026-08-25)**: 이 문서는 원래 "닫기는 항상 홈으로"라고 적었는데, 코드를 다시 추적해보니 틀렸다. `/privacy`의 닫기 버튼도 다른 화면과 똑같은 `useBackTo("/")` 메커니즘을 쓰는데, 이 메커니즘은 히스토리에 앱 안 이전 화면이 있으면(`nav-mark`가 `inner`) **그 화면으로 한 단계 뒤로가고**, 없을 때만(직접 진입 등) `/`로 대체한다. 즉 실제로는 "특정 부모로 한 단계"가 아니라 "**한 단계 뒤로, 기록이 없으면 홈**"이다 — 이건 이 앱의 다른 모든 화면과 같은 범용 규칙이라, `/privacy`만 예외적으로 다르게 동작하는 게 아니다. 결론(이번 스택에서 제외해도 된다)은 그대로 맞다 — "부모가 고정되지 않는 공용 화면"이라는 스택 제외 근거는 안 바뀐다.
- `/login` 오버레이(`app/@overlay/(.)login/`) — `/my`와 별개 진입 경로(비로그인 시 뜨는 화면)라 손대지 않는다.
- `RecentStrip`이 여는 상품상세 레이어(`DetailLayers`/`detail-stack.ts`) — 이미 별도의 검증된 스택이고 이번 변경과 무관하다.
- `ProfileStats`에서 찜 폴더로 가는 링크 신설 등 새 내비게이션 추가 — 없던 길을 만들지 않는다.

## 결정 사항

| 질문 | 결정 | 이유 |
|---|---|---|
| 편입 범위 | `/my`·`/settings`만 (`/privacy` 제외) | `/privacy`는 온보딩과도 공유하는 화면이라 "닫기 = 부모로 한 단계"가 성립하지 않는 기존 결정과 충돌한다 |
| URL 주소지성 | 유지 | `/my`처럼 직접 접속·새로고침에도 그 화면이 뜨는 지금 동작을 settings도 그대로 가져야 함(마이페이지는 진입 성능까지 신경 쓴 라우트였다 — 관련: `docs/plans/2026-08-20-my-page-navigation-latency.md`) |
| 아키텍처 | 라우트 확장 (상태 스택 방식 아님) | `/my`가 쓰는 인터셉팅 라우트 + 병렬 슬롯 패턴을 한 단계 더 반복. URL 동기화용 새 코드가 필요 없다. **구현 중 형태가 바뀌었다** — `/my` 안에 중첩하는 첫 시도는 실패했고, 루트에 형제 슬롯으로 두는 구조로 대체됐다(아래 "아키텍처" 절 참고) |
| 전환 스타일 | 완전 덮기(Android식) | 새 화면이 이전 화면을 그대로 덮는다. 뒤 화면은 움직이거나 축소되지 않는다 |
| 스와이프 닫기 | 제거 | 새 push 스택에선 헤더의 뒤로가기 버튼으로만 닫는다 |

## 아키텍처

**첫 시도(2026-08-25, 실패)**: `/my` 자신의 렌더 트리 안(`app/@overlay/(.)my/`)에 `/settings`용 병렬 슬롯을 중첩하는 방식으로 만들었으나, 실제로 구현해 확인한 결과 **동작하지 않았다** — "회원 탈퇴"를 누르면 URL은 `/settings`로 바뀌지만 화면은 그대로였다. DOM을 보면 루트 레이아웃의 `children` 슬롯이 (보이지 않는) 단독 설정 페이지로 바뀌고, `/my`가 들어 있는 `overlay` 슬롯은 갱신되지 않은 채 얼어붙어 그 위를 계속 덮고 있었다. 하드 리로드로도 재현됨. Next.js 공식 문서("The `(..)` convention is based on route segments... it does not consider `@slot` folders in Parallel Routes.")와 관련 커뮤니티 논의(vercel/next.js #94505 — "parallel route slots are preserved only while their owning layout is preserved")를 대조해보면, 원인은 `@settingsOverlay` 슬롯을 **안정적인 공통 조상 레이아웃이 아니라 `(.)my`라는, 그 자체가 조건부로만 존재하는 리프 페이지 안에** 심었기 때문으로 보인다.

**채택한 구조**: `@settingsOverlay` 슬롯을 `/my` 안이 아니라 **루트 레이아웃에 `@overlay`와 형제로** 둔다. `/my`가 이미 성공적으로 쓰는 것과 똑같은 층위의 패턴(안정적인 공통 조상 = 루트 레이아웃)을 하나 더 반복하는 것뿐이라, 이미 검증된 패턴을 복제하는 셈이다.

```
app/
  layout.tsx            ← children · overlay · settingsOverlay 세 자리를 함께 그린다
  @overlay/
    default.tsx
    (.)my/page.tsx        ← 그대로(Task 1에서 만든 버전, layout.tsx 불필요)
  @settingsOverlay/       ← 신설, @overlay와 형제
    default.tsx
    (.)settings/page.tsx  ← 프로필 위에 겹치는 설정 화면
  my/page.tsx / settings/page.tsx   ← 그대로, 독립 라우트
```

- 세 자리(`children`=홈, `overlay`=`/my`, `settingsOverlay`=`/settings`) 다 여전히 실제 라우트로 이어진다. 직접 URL 접속·새로고침은 지금처럼 해당 단계의 독립 페이지가 그대로 뜬다.
- 이 앱에서 `/settings`로 가는 링크는 프로필 화면(설정 메뉴) 안 하나뿐이라, `@settingsOverlay`가 "항상 존재하는" 루트 슬롯이어도 실제로는 프로필을 거칠 때만 채워진다.
- **검증 완료(2026-08-25)**: 형제 슬롯 구조로 구현해 브라우저 DOM 레벨로 확인 — 설정을 열면 홈·프로필·설정 `<main>` 셋이 동시에 마운트되고(`document.querySelectorAll('main').length === 3`), 닫으면 한 단계씩(설정→프로필→홈) 정확히 돌아간다. 첫 시도의 실패(URL만 바뀌고 화면이 안 뜨는 것)는 재현되지 않았다.

## 컴포넌트 변경

- **전환 애니메이션**: `app/globals.css`의 `sidebar-in`(오른쪽 슬라이드 + 뒤 화면 축소)을 걷어내고, 새 화면이 오른쪽에서 100% 슬라이드해 전체를 덮는 애니메이션으로 교체. 뒤 화면에 적용되던 `profile-open` 클래스의 축소·라운딩 효과(`html.profile-open > body > main`)도 제거한다.
- **스와이프 제스처 제거**: `my-page-shell.tsx`에서 `useSwipeToClose` 사용을 걷어낸다.
- **셸 공유화(계획했으나 실제로는 안 함)**: 지금 `my-page-shell.tsx`는 프로필 전용으로 짜여 있어, 설계 당시엔 `/settings` 오버레이와 셸을 공유하는 컴포넌트로 일반화할 생각이었다. 실제 구현에서는 두 화면의 안쪽 레이아웃이 서로 많이 달라(프로필은 세로 레일·인사말이 있는 사이드바형, 설정은 `max-w-md` 단순 목록형) 억지로 공유 컴포넌트를 만들기보다 `push-in` **CSS 클래스만 공유**하고 각자 자기 래퍼(`fixed inset-0 z-N` + `<main className="push-in ...">`)를 그대로 썼다 — `/settings` 단독 페이지·오버레이 페이지 사이의 마크업 중복도 `/my` 단독·오버레이 사이에 이미 있던 것과 같은 패턴(라우트가 조립만 한다는 `frontend/AGENTS.md` 규칙과 일치)이라 새로운 문제가 아니다. 둘의 스타일을 실제로 같이 바꿔야 하는 일이 반복되면 그때 공유 컴포넌트로 뽑는다.

## 내비게이션 / 뒤로가기

닫기(헤더 뒤로가기 버튼, 브라우저 뒤로가기)는 항상 바로 위 부모 화면으로 한 단계만 이동한다:

```
/settings 닫기 → /my
/my 닫기 → /
```

`/privacy`는 스택 밖이라 이 규칙과 무관하다 — 어디서 열렸든 지금처럼 `useBackTo("/")`(한 단계 뒤로, 기록 없으면 홈)로 그대로 둔다.

지금 `useBackTo`/`shared/history/nav-mark.ts`가 `/my`에 대해 하는 일(히스토리 상태에 `root`/`inner` 마킹)을 `/settings` 단계로 확장해 적용한다. `/settings`의 기존 `SettingsHeader`(`BackLink href="/my"`, 고정 라우트 교체)는 이 스택 안에서 열렸을 때는 `/my`로의 소프트 닫기로 동작해야 한다 — 단, 직접 URL 접속으로 진입했을 때는 스택이 없으므로 기존처럼 하드 이동으로 남는다.

## 엣지 케이스

- `/settings`를 북마크 등으로 바로 열거나 새로고침 → 스택 없이 독립 페이지가 그대로 뜬다(오늘과 동일).
- `/my` 안의 `GuestLoginPopup`, `/login` 오버레이 → 이번 변경 범위 밖, 그대로 둔다.
- `/privacy`는 `/my`의 메뉴에서든 `/settings`의 `PrivacySettings`에서든 여전히 일반 라우트 이동으로 열리고, 닫기는 `useBackTo("/")` 그대로(한 단계 뒤로, 기록 없으면 홈) — 이번 변경으로 손대지 않았다.

## 완료 기준 (돌려서 눈으로 확인)

1. 홈 → 프로필: 프로필 화면이 오른쪽에서 슬라이드해 홈을 완전히 덮는다. 홈은 축소되거나 움직이지 않는다.
2. 프로필 → 설정(톱니 메뉴의 "회원 탈퇴"): 설정 화면이 프로필 위로 슬라이드해 덮는다.
3. 설정에서 뒤로가기 → 프로필로, 프로필에서 뒤로가기 → 홈으로. 매번 한 단계씩만 닫힌다.
4. 오른쪽 가장자리를 드래그해도 더 이상 닫히지 않는다(버튼으로만 닫힘).
5. `/settings`를 주소창에 직접 입력하거나 새로고침해도 화면이 정상적으로 뜬다.
6. `/privacy`는 프로필 메뉴·설정 어느 쪽에서 열어도 여전히 닫기 버튼이 `useBackTo("/")`로 동작한다(보통은 한 단계 뒤로, 직접 진입처럼 기록이 없을 때만 홈 — 이번 변경으로 건드리지 않았음을 확인).
7. `npm run check` 통과.

## 미정

없음. 유일한 미정 항목("`/my` 안에 병렬 슬롯을 중첩하는 게 실제로 동작하는가")은 구현 중 검증됐다 — 처음 시도(중첩)는 실패했고, 슬롯을 루트 레이아웃에 `@overlay`와 형제로 옮기는 구조로 해결했다. 자세한 경위는 위 "아키텍처" 절 참고.
