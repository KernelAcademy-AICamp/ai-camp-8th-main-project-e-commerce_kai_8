# admin 이벤트 대시보드 — 설계

- 작성: 2026-08-20
- 상태: 합의됨 / 구현 전
- 관련: [세션 단위 지표 정의](../../atee/living/session-metrics.md) · [데이터 수집·보존 방침](../../atee/living/data-collection-policy.md) · [개인화 알고리즘 설계](2026-08-14-personalization-algorithm-design.md) §4 (이벤트 로그)

## 배경

행동 신호 수집은 이미 돌고 있다. `frontend/shared/signals/`가 8종의 이벤트를 배치로 모아 RPC `c_log_events`로 보내고, Supabase의 `c_events` 테이블에 쌓인다. 지표 SQL도 `backend/db/personalization_metrics.sql`에 5개가 이미 있다.

**없는 것은 그 숫자를 보는 방법이다.** 지금은 `psql`로 접속해 파일을 실행해야만 볼 수 있어서 사실상 한 사람만 본다. 팀이 실험 결과를 함께 보려면 브라우저로 열 수 있는 화면이 필요하다.

앰플리튜드 같은 외부 도구를 붙이는 안도 있었으나(측정 계획이 그 전제로 쓰였다), 이번에는 **직접 만든다**는 것이 제품 책임자의 결정이다. 이벤트를 외부로 내보내지 않아도 되고 데이터 수집 방침을 고칠 일이 없다는 점이 부수적 이득이다.

## 범위

**이번 조각** — `c_events`를 읽어 표로 보여주는 읽기 전용 대시보드. 출입 통제 포함.

**이번 조각이 아닌 것**

- **관리 기능** (상품 숨김·삭제 등 데이터를 고치는 것) — 읽기만 하는 화면과 고치는 화면은 권한 설계도 확인 절차도 다르다. 같은 `admin` 앱에 나중에 메뉴로 붙인다.
- **브라우저 SQL 콘솔** — 편하지만 데이터베이스 전체를 여는 문이다. 필요해지면 별도 조각으로 다룬다.
- **차트** — 1단계는 표만. 표가 먼저 보여야 그 지표가 쓸모 있는지 판단이 된다.
- **실시간 자동 갱신·알림·데이터 내보내기** — 지금 필요가 없다.
- **습관 단계 표** (사람 × 주차 교차표) — [세션 단위 지표 정의 §7 습관 지표](../../atee/living/session-metrics.md)의 성공 지표 그 자체지만 모양이 특이해 일반 카드 틀로는 나오지 않는다. 카드 틀이 선 뒤 전용 화면으로 따로 만든다.

## 1. 전체 구조와 배포

`admin/`을 `frontend/`·`backend/`와 같은 레벨에 새로 만든다. Vercel에는 **별도 프로젝트**로 등록한다 (Root Directory=`admin`).

**같은 repo, 다른 배포**로 두는 이유:

- admin 코드가 실사용자에게 내려가는 번들에 섞이지 않는다.
- admin이 빌드에 실패해도 서비스 배포가 막히지 않는다. 반대도 마찬가지다.
- 도메인이 분리되어 admin 주소가 서비스 주소에서 유추되지 않는다.

리전은 `frontend`와 같은 `icn1`(서울)로 둔다. 이유는 [AGENTS.md](../../../AGENTS.md)에 적힌 것과 같다 — Supabase가 서울에 있고, 기본값으로 두면 요청이 태평양을 두 번 건넌다.

내부 폴더 구조는 [frontend/AGENTS.md](../../../frontend/AGENTS.md)의 clean architecture + MVVM 규칙을 따른다. 단 같은 문서의 "레이어가 아직 필요 없으면 만들지 않는다"도 함께 따른다 — 읽기 전용 대시보드에 쓰이지 않는 레이어는 만들지 않는다.

## 2. 데이터를 읽는 경로

### 2-1. 왜 데이터베이스에 직접 접속하는가

`c_events`는 `anon`·`authenticated` 모두에게서 권한이 회수돼 있다(`c_events.sql`). 그리고 이 설계가 택한 "SQL 파일 하나 = 카드 하나" 방식은 **어떤 SQL이 올지 미리 알 수 없다**는 것이 핵심이다. Supabase의 REST 통로(PostgREST)는 미리 정의된 테이블·뷰·함수만 부를 수 있으므로 이 방식을 담을 수 없다.

따라서 admin 서버는 Postgres에 **직접 접속**한다. 접속 정보는 서버 측 환경변수로만 두며, 브라우저로 가는 것은 표에 들어갈 값뿐이다 — 접속 정보도 SQL 원문도 내려보내지 않는다.

| 대안 | 기각 사유 |
| --- | --- |
| REST 통로 + 지표마다 DB 함수 생성 | 지표 하나 추가에 마이그레이션이 필요하다. 무엇을 볼지 정해지지 않은 지금 단계에서 실험 비용이 너무 크다. |
| 지표마다 화면을 직접 코딩 | 지표 추가 = 코드 작성. 같은 이유로 반복 비용이 크다. 살아남은 지표를 다듬을 때 이 방식으로 옮긴다. |
| 정적 사이트 생성기(Evidence 등)로 미리 구워 배포 | §10 참고. 출입 통제가 성립하지 않는다. |

### 2-2. 접속 계정 — 읽기 전용 + 명시적 읽기 허가

**admin 전용 데이터베이스 계정을 하나 새로 만든다.** 데이터베이스를 새로 만드는 것이 아니라, 같은 데이터베이스에 들어갈 **신분증을 한 장 더 발급**하는 것이다. 이 프로젝트는 이미 `anon`·`authenticated`·`postgres`를 용도별로 나눠 쓰고 있고, 여기에 네 번째를 더한다.

이 계정은 **읽기 권한만** 갖는다. repo의 SQL 파일에 `delete`·`update`가 실수로 섞여도 데이터베이스가 거부한다. `c_events`는 계측 데이터라 지워지면 복구할 수단이 없다 — 규율이 아니라 기계가 막아야 한다.

**기존 `postgres` 접속 정보를 재사용하지 않는 이유**는 세 가지다. ① `postgres`는 삭제·스키마 변경까지 되는 마스터 권한이라 SQL 파일의 실수가 실제 데이터 소실이 된다. ② 그 자격증명 사본이 Vercel이라는 외부 서비스에 하나 더 놓이게 된다. ③ 문제가 생겼을 때 admin 계정만 무효화하면 되지만, `postgres`를 무효화하면 backend·마이그레이션·`psql`이 함께 멈춘다.

**읽기 권한만 줘서는 데이터가 보이지 않는다.** `c_events`는 RLS가 켜져 있고 정책이 하나도 없다. Postgres에서 이는 "테이블 주인 외에는 아무도 못 본다"를 뜻하는데, **거부가 아니라 0건**으로 나타난다. 지금까지 문제가 없었던 것은 주인 계정(`postgres`)으로만 접근했기 때문이다. 이를 놓치면 §7이 막으려는 바로 그 실패(데이터가 없는 것인지 못 읽은 것인지 구분 불가)를 설계가 스스로 만든다.

따라서 **`c_events`에 "이 admin 계정은 읽어도 된다"는 RLS 정책을 마이그레이션으로 추가한다.**

**이 정책은 이 repo의 첫 RLS 정책이다.** 확인 결과 테이블 24개 전부 RLS가 켜져 있고 `create policy`는 한 건도 없다 — 접근을 전부 검증 붙은 RPC로만 열어온 일관된 방침이다. admin은 "어떤 SQL이 올지 미리 알 수 없다"는 성질 때문에 RPC로 담을 수 없으므로 **의도된 예외**이며, 그래서 그 예외가 마이그레이션 파일로 남아 리뷰되는 편이 낫다.

| 대안 | 기각 사유 |
| --- | --- |
| 계정에 RLS 통과 속성(BYPASSRLS)을 부여 | 정책을 안 써도 되지만 ① Supabase에서 만들 수 있는지 **미검증**이고([Discussion #9314](https://github.com/orgs/supabase/discussions/9314)) ② 콘솔에서 손으로 만들어 **설정이 코드에 남지 않으며** ③ 모든 테이블을 무조건 통과해 권한이 필요 이상으로 넓다. |
| `c_events`의 RLS를 끈다 | 방어가 두 겹(권한 + RLS)에서 한 겹으로 준다. 나중에 누가 공개 권한을 한 줄 잘못 주면 그 즉시 열린다. 테이블 24개 전부 RLS를 켜온 방침도 깨진다. |
| 기존 `postgres` 접속 정보 재사용 | 위 세 가지 이유. |

**대가**: 대시보드가 읽을 테이블이 늘면 정책을 한 줄씩 더 써야 한다. 지금 읽을 테이블은 `c_events` 하나뿐이라 당장은 한 줄이면 끝이고, 그 한 줄이 **"admin이 어느 테이블을 읽는지 코드에 적혀 있다"**는 이점이 된다.

**비밀번호는 커밋하지 않는다.** 계정 생성은 사람이 Supabase 콘솔에서 한 번 실행하고 **절차만** 문서로 남긴다. 비밀번호는 Vercel 환경변수에만 존재한다.

**순서 의존이 있다.** 정책은 존재하는 계정을 가리키므로 **계정 생성이 마이그레이션보다 먼저**다. 순서가 바뀌면 마이그레이션이 실패한다. 새 테이블을 대시보드에 넣을 때 권한과 정책을 함께 줘야 한다는 것도 절차 문서에 적는다.

### 2-3. 접속 주소 — 트랜잭션 풀러

Vercel은 요청마다 함수 인스턴스가 새로 뜨는 구조라, 일반 접속을 쓰면 데이터베이스 접속 수가 빠르게 소진된다. 소진되면 **admin뿐 아니라 실서비스도 데이터베이스에 붙지 못한다.**

Supabase가 이 상황을 위해 제공하는 **트랜잭션 모드 풀러** 주소로 접속한다. 세션 모드와 포트 번호가 다르다.

> ⚠️ `backend/.env.example`의 `SUPABASE_DB_URL`은 **세션 풀러**를 안내한다. 마이그레이션 용도로는 맞지만 **admin은 그 값을 그대로 쓰면 안 된다.** 헷갈리면 평소엔 멀쩡하다가 사람이 몰릴 때 서비스가 함께 죽는다.

**트랜잭션 모드에도 두 종류가 있고, 하나는 Vercel에서 아예 동작하지 않는다** (2026-08-20 확인).

| | dedicated pooler | **shared pooler (택함)** |
| --- | --- | --- |
| 호스트 | `db.<ref>.supabase.co:6543` | `aws-N-<지역>.pooler.supabase.com:6543` |
| 네트워크 | **IPv6 전용** (IPv4는 유료 애드온) | IPv4 |
| Vercel | ❌ **Vercel은 IPv6를 지원하지 않는다** | ✅ |

이 프로젝트는 Pro 플랜(O-28)이라 콘솔이 **기본으로 dedicated pooler를 보여준다.** 그것을 그대로 쓰면 **로컬에서는 되는데 배포하면 접속이 끊기는** 형태가 된다 — 개발 중에는 드러나지 않는 종류의 실패다. 콘솔의 `Use IPv4 connection` 토글을 켜서 shared pooler 주소를 쓴다. 판별 기준은 호스트에 `pooler.supabase.com`이 있는지다.

로컬 개발도 같은 주소를 쓴다. 환경마다 다른 경로로 붙으면 이 차이가 배포 때까지 숨는다.

admin의 환경변수는 `backend`의 것과 **이름을 달리해** 혼동을 막는다.

## 3. 출입 통제

1. 로그인하지 않은 요청은 어떤 경로로 들어와도 로그인 화면으로 보낸다.
2. 구글 로그인 후, 이메일이 **허용 목록**(Vercel 환경변수)에 있는지 확인한다. 없으면 데이터를 한 건도 보내지 않고 거절한다.
3. **판정은 서버에서 한다.** 브라우저에서 관리자 여부를 확인하는 방식은 개발자도구로 우회된다.

기존 구글 로그인을 재사용한다 — 계정을 새로 만들 필요가 없고 누가 들어왔는지 남는다.

**운영상 필요한 사전 작업**: admin은 `frontend`와 도메인이 다르므로, Supabase 인증 설정의 리다이렉트 허용 목록에 admin 주소를 추가해야 로그인이 돌아온다. 빠뜨리면 로그인 후 엉뚱한 곳으로 튕긴다.

| 대안 | 기각 사유 |
| --- | --- |
| 공용 비밀번호 하나 | 가장 빠르지만 누가 봤는지 알 수 없고 유출 시 전원에게 다시 알려야 한다. 이 화면에는 사용자 행동 기록 전체가 보인다. |
| Vercel 기본 보호 기능 | 무료(Hobby) 플랜에서는 프로덕션 도메인이 보호되지 않는다. 비밀번호 보호는 월 $150 애드온이 필요하다. |

## 4. 지표 카드 구조

`admin` 안에 지표 폴더를 하나 두고 **지표 하나당 파일 하나**를 놓는다. 파일에 담기는 것:

| 항목 | 예 |
| --- | --- |
| 제목 | 추천 유형별 클릭률 |
| 왜 보는지 한 줄 | 어떤 종류의 추천이 실제로 눌리는가 |
| SQL | `personalization_metrics.sql`에서 옮김 |
| 정렬 순서 | 대시보드에서 몇 번째로 보일지 |

앱은 이 폴더를 훑어 카드 목록을 만들고, 각 카드의 SQL 결과를 **컬럼 이름 그대로 표 머리글로 삼아** 표로 뿌린다. 결과 모양을 미리 알 필요가 없으므로 **새 지표를 넣을 때 화면 코드를 건드리지 않는다.**

**SQL은 repo의 파일에서만 온다.** 브라우저 입력에서 오는 SQL은 실행하지 않는다.

## 5. 시간 기준

모든 집계는 **한국 시간(Asia/Seoul)** 기준으로 날짜를 센다.

`c_events.occurred_at`은 UTC로 저장된다. 그대로 날짜를 세면 한국의 자정~오전 9시 접속이 전날로 집계되어, [세션 단위 지표 정의 §7 습관 지표](../../atee/living/session-metrics.md)의 "서로 다른 2일"과 "7일 구간 경계" 판정이 하루씩 밀린다.

**기준을 한 군데서 정하고 모든 카드가 그것을 쓴다.** SQL 파일마다 각자 처리하게 두면 반드시 빠뜨리는 파일이 생기고, 그 카드만 조용히 하루 밀린 숫자를 보여준다.

---

## 6. 첫 화면 구성

지표 항목은 아직 정해지지 않았다. 다만 화면이 비어 있으면 만든 것이 도는지 확인할 수 없으므로 **이미 검증된 SQL부터** 채운다.

- `backend/db/personalization_metrics.sql`의 5개 — 유형별 노출→행동 전환, 정책 분포, 반복 노출률, 신선도 노출 비율, 세션당 탐색.
- 여기에 "오늘 / 최근 7일 이벤트 수" 수준의 단순한 카드 하나를 더 놓아 **데이터가 실제로 들어오고 있는지**를 한눈에 보게 한다.

기존 SQL을 옮길 때 §5의 시간 기준을 적용한다.

---

## 7. 실패 처리

- **카드 하나의 SQL이 실패하면 그 카드만** 실패로 표시하고 나머지는 정상 표시한다. 하나 때문에 화면 전체가 죽지 않는다.
- **데이터베이스 접속 자체가 실패하면 화면 전체에 크게 알린다.** 조용히 "0건"으로 보이면 데이터가 없는 것인지 못 읽은 것인지 구분할 수 없다. 계측 도구에서 이것이 가장 위험한 거짓말이다.
- 카드가 **정상적으로 0건**인 경우와 **실패한** 경우를 화면에서 다르게 보여준다.

## 8. 테스트와 검증

- **자동 테스트**(vitest): 한국 시간 변환, 허용 목록 판정, 지표 파일 수집 — 모두 순수 로직이라 테스트가 쉽다. [frontend/AGENTS.md](../../../frontend/AGENTS.md)의 "domain부터 테스트를 작성한다"를 따른다.
- **SQL 정확성은 자동 테스트로 확인하지 않는다.** 화면에 나온 숫자를 `psql`로 같은 쿼리를 돌린 결과와 **대조**하고, 대조 결과(양쪽 원본 출력)를 함께 낸다. 판정만 적지 않는다.
- **출입 통제는 실제로 뚫어본다.** 로그인하지 않은 상태, 허용 목록에 없는 계정으로 각 경로에 접근해 데이터가 나오지 않는 것을 확인한다. 확인하지 않았으면 미검증으로 남긴다.
- **읽기 전용이라는 주장도 돌려서 확인한다.** admin 계정으로 `c_events`에 쓰기를 한 번 시도해 데이터베이스가 거부하는 것을 눈으로 본다. §2-2의 안전장치는 실행해보기 전까지는 주장일 뿐이다.

## 9. 미검증·열린 항목

| 항목 | 상태 |
| --- | --- |
| admin 계정 + 정책으로 `c_events`의 행이 실제로 보이는가 | **확인됨 (2026-08-20).** `set role atee_admin_ro` 후 `count(*) = 10,656`. 쓰기는 권한 단계에서 막힌다 — `has_table_privilege`로 delete·update 모두 `false` 확인. |
| 비밀번호 + 트랜잭션 풀러로 실제 외부 접속이 되는가 | **확인됨 (2026-08-20).** 앱이 `atee_admin_ro`로 shared pooler를 통해 붙어 대시보드 숫자가 `select count(*)` 결과와 일치했다(둘 다 10,354). |
| 트랜잭션 풀러로 접속했을 때 지표 SQL의 응답 속도 | 미측정. 데이터가 적어 문제없을 것으로 보나 확인 전이다. |
| Vercel에서의 접속 | **미검증.** 로컬에서만 붙어 봤다. 4단계에서 닫힌다. |
| 보여줄 지표 항목 | 미정 — 의도된 상태. §6으로 시작해 실제로 보게 되는 것을 추린다. |

### 2026-08-20에 실제로 부딪힌 것

`postgres`로 `set role atee_admin_ro`가 `42501: permission denied to set role`로 거부됐다. 원인은 **PostgreSQL 16부터 역할 멤버십이 `admin` / `set` / `inherit` 세 갈래로 쪼개진 것**이다. 역할을 만들면 `admin`만 자동으로 붙고 `set`은 붙지 않는다(실측: `admin=true set=false inherit=false`). `grant atee_admin_ro to postgres with set true` 한 줄로 닫았고, 마이그레이션에 넣어 다음 사람이 같은 벽을 만나지 않게 했다.

**이 과정에서 검증 방법 하나가 무효였다.** `set role`이 실패한 세션에서 `delete`를 시도해 "성공"이 나왔는데, 그것은 `atee_admin_ro`가 아니라 `postgres`로 실행된 결과였다. 권한 확인은 역할을 갈아타는 방식보다 **`has_table_privilege`로 데이터베이스에 직접 묻는 편이 확실하다** — 갈아타기가 실패해도 조용히 다른 답을 주지 않는다.

## 10. 채택하지 않은 전체 대안

**Evidence(정적 사이트 BI)** — 팀에서 제안된 안이다. SQL + Markdown으로 대시보드를 쓰면 정적 사이트가 나오고 이미 있는 SQL을 거의 그대로 쓸 수 있다는 점이 매력적이었다.

기각 사유는 **출입 통제**다. Evidence는 빌드 시점에 데이터를 parquet 파일로 구워 사이트에 포함시키고 브라우저가 그것을 받아 쿼리한다. 즉 **주소를 아는 사람은 `c_events` 전체를 파일로 내려받을 수 있다.** Vercel 무료 플랜은 프로덕션 도메인을 보호하지 않고 비밀번호 보호는 월 $150 애드온이다. [데이터 수집·보존 방침](../../atee/living/data-collection-policy.md)이 약속한 "anon 직접 접근 불가"를 배포 방식으로 우회해 깨뜨리게 된다.

부차적으로 데이터가 실시간이 아니다(갱신 = 재빌드). 이것만이면 감수할 수 있었다.

**외부 제품 분석 도구**(앰플리튜드·PostHog 등) — 무료 구간이 충분하고 퍼널·리텐션이 기본 제공된다. 직접 만들기로 한 결정에 따라 채택하지 않는다. 채택했다면 이벤트가 외부로 나가므로 데이터 수집 방침과 공개 처리방침 문구를 고쳐야 했다.

**Metabase 등 상시 서버형 BI** — Vercel에 올릴 수 없고 상시 서버가 필요해 무료 조건에 맞지 않는다.
