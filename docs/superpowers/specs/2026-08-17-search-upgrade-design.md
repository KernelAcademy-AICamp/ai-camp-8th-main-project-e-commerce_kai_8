# 검색 업그레이드 — 설계안

> 상태: 합의 완료 (2026-08-17 제품 책임자 승인) · 구현 전
> 대체 관계: [플로팅 검색 설계](2026-08-16-floating-search-design.md)가 만든 MVP 검색(`c_search_page`)을 대체·확장한다. 플로팅 검색창의 UI 동작(축소/확장·피드 교체·스크롤 전이)은 그대로 유지한다.

## 1. 배경 — 지금 검색이 왜 부족한가

2026-08-16 PR #15로 들어간 MVP 검색은 **`lower(브랜드명 + ' ' + 제목)` 한 컬럼에 대한 부분 일치**가 전부다. 구조상 다음이 전부 불가능하다.

- 태그(`tags`, 보유율 75.4%)·색상코드(99.7%)·성별(99.2%)·시즌(84.5%)·착용감(28.1%)·`ai_summary` 등 **다른 필드를 하나도 쓰지 않는다.**
- `c_img_vecs`에 96.7만 장 SigLIP2 벡터가 이미 있지만 **검색은 벡터를 전혀 쓰지 않는다.**
- 오타·동의어·한영 별칭·띄어쓰기 변형·의미 검색 미지원 (MVP 한계로 명시돼 있었음).
- 정렬이 `goods_no` 오름차순이라 **관련도 개념이 없다.**

### 결정 기록과의 관계

결정 기록 O-25는 "LLM 자연어 검색을 보조 진입점으로 추가하고 상세는 별도 스펙에서 설계한다"고 남겼고, 개인화 설계 §1도 "검색은 별도 스펙"으로 미뤘다. **이 문서가 그 별도 스펙이다.** Non-goal "검색을 주 경험으로 제공하지 않는다"는 유지된다 — 검색 결과는 여전히 피드 형태로 이어지고, 사용자는 탐색으로 복귀한다.

## 2. 사용자 결정 사항 (2026-08-17)

| # | 결정 | 함의 |
|---|---|---|
| S-01 | **목표는 자연어 문장 검색까지.** "흰 무지 오버핏 반팔", "여름에 시원한 헐렁한 티"가 통해야 한다. | 벡터 검색 + 질의 이해가 모두 필요하고, 런타임 텍스트 인코더 구축이 필수 경로가 된다. |
| S-02 | **오프라인 배치는 허용, 실시간 LLM은 제한적.** 문장형 질의에만 호출하고 결과를 캐시한다. 문장 질의에 한해 1~2초 지연 허용. | LLM은 어느 경로에서도 필수 경로가 아니다. 키워드 질의는 LLM을 타지 않는다. |
| S-03 | **평가는 Codex가 정답셋을 만들고 채점**, 정답률 70% 이상이면 사람 눈 검증으로 넘어간다. | 각 단계의 완료 기준을 "Codex 채점 정답률"로 쓴다. |
| S-04 | **PGroonga 확장 설치 가능.** | 한국어 형태소/n-gram 색인을 정식으로 쓴다. 단, 공유 DB이므로 `c_*` 대상에만 적용한다. |
| S-05 | **검색 경험 전체 재설계.** 입력창·결과 그리드 외에 자동완성·제안·필터 칩 등을 포함한다. | 범위가 커서 UI는 별도 스펙으로 분리한다(§7 E단계). |
| S-06 | **개인화는 순위에만 약하게 반영**하고, 검색 중 행동도 취향 프로필에 반영한다. | 무엇이 걸리는지는 질의가 정하고 개인화는 순서만 조정한다. 지금 꺼둔 검색 노출 계측을 켠다. |

## 3. 조사 결과 — DeepSeek으로 할 수 있는 것과 없는 것 (2026-08-17 확인)

**DeepSeek에는 임베딩 모델이 없다.** 공식 API 문서와 가격 페이지에 올라 있는 모델은 `deepseek-v4-flash`와 `deepseek-v4-pro` 둘뿐이고 **둘 다 텍스트 전용**이다. "deepseek-embedding-v2" 같은 이름은 SEO 문서에만 등장하며 공식 근거가 없고, 공식 저장소에는 임베딩 API를 만들어달라는 이슈가 열려 있다. **따라서 SigLIP2를 DeepSeek으로 대체할 수 없으며, 벡터 생성은 계속 SigLIP2가 담당한다.**

- 비전도 API에는 없다. DeepSeek-VL2·Janus-Pro는 오픈웨이트 자체 호스팅 전용이다. 이미지 기반 속성 추출을 DeepSeek으로 하려면 로컬에서 직접 돌려야 하는데, 우리는 이미 SigLIP2 zero-shot으로 같은 목적을 훨씬 싸게 달성할 수 있으므로 채택하지 않는다.
- 쓸 수 있는 것: function calling, JSON 출력, **context caching**(캐시 히트 시 입력가가 1/50 수준), thinking/non-thinking 모드, 1M 컨텍스트.
- **가격 체계가 2026-08-16 16:00 UTC부터 peak/off-peak로 바뀌었다.** flash 기준 off-peak가 peak의 절반이다. **배치 작업은 off-peak에 돌린다.**

**결론: DeepSeek의 자리는 세 곳이다** — ⓐ 오프라인 카탈로그 속성 보강(C단계), ⓑ 온라인 질의 이해(D단계), ⓒ 상위 결과 재정렬(옵션 F, 기본은 끈다).

### 참고한 외부 사례

- **하이브리드 + RRF가 정석**: Supabase 공식 하이브리드 검색 레시피가 tsvector와 pgvector를 `1/(k+rank)`(k=50 기본) + 가중치로 합친다. 공개 실측에서 순수 벡터 대비 정밀도가 크게 올라간 사례가 보고돼 있다.
- **한국어는 Postgres 기본 전문검색이 불가**. PGroonga가 Supabase에서 확장으로 제공되며 CJK 토크나이저를 갖는다(대안: pg_bigm).
- **LLM을 핫패스에 두지 않는 것이 프로덕션 패턴**: 인기 질의의 재작성을 미리 계산해 캐시하고, 단순 키워드 질의는 분류 단계에서 LLM을 건너뛴다(비용 60~80% 절감 보고).
- **오프라인 속성 보강이 가장 확실한 승리**: 대형 커머스가 LLM으로 카테고리 분류·속성 추출을 대량 수행하는 사례가 다수.
- **한국어 특유 문제(한영 자판 오타·초성·자모 오타)는 LLM 없이 결정론적 규칙으로** 처리하는 것이 정확하고 저렴하다. 공개 구현이 많다.
- 레퍼런스 모음: `frutik/awesome-search`(질의 이해·동의어·오타·하이브리드), `alopatenko/LLMSearchRecommender`(질의 속성 모델링·LLM 재정렬).

### 확인된 기술적 사실 두 가지

1. **우리가 쓰는 체크포인트의 ONNX 변환본이 공개돼 있다** — `onnx-community/siglip2-base-patch16-256-ONNX`. 텍스트 타워만 쓰면 작아서 브라우저·서버 어디든 올릴 수 있다. (리비전 일치는 §7의 게이트에서 검증한다.)
2. **새 zero-shot 속성 축은 이미지 재처리 없이 추가할 수 있다.** `c_img_vecs`에 벡터가 이미 있으므로, 축마다 텍스트 프롬프트를 임베딩해 내적하면 끝이다. 비용은 사실상 0이고 몇 분이면 된다.

## 4. 범위 분해와 순서

한 번에 만들 수 있는 크기가 아니므로 **독립적으로 만들고 검증할 수 있는 6덩어리**로 나눈다. 각 덩어리는 자기 구현 계획(`docs/plans/`)을 갖는다.

| # | 덩어리 | 무엇이 좋아지나 | DeepSeek |
|---|---|---|---|
| **0** | 평가 하네스 | 지금 점수를 알게 된다 (기준선) | — |
| **C** | 속성 보강 | 태그 없는 25% 상품이 검색되고, 필터 재료가 생긴다 | 배치 ✅ |
| **A** | 한국어 색인 + 관련도 정렬 | 오타·자판·띄어쓰기가 걸리고 관련도순이 된다 | — |
| **B** | 의미 검색 (텍스트→이미지) | 문장·느낌 질의가 걸린다 | — |
| **D** | 질의 이해 | 복합 조건이 구조화 필터로 바뀐다 | 온라인 ✅ |
| **E** | 검색 UX 재설계 | 검색이 제품 기능이 된다 | 선택 |

**확정 순서: 0 → C → A → B → D → E.**

- **0이 먼저인 이유**: 기준선 점수가 없으면 이후 어떤 단계도 "좋아졌다"를 말할 수 없다.
- **C가 A보다 먼저인 이유**: 색인 재료를 먼저 갖춰 색인을 두 번 만들지 않는다.
- **A가 B보다 먼저인 이유**: 벡터만 켜면 브랜드·모델명 같은 정확 질의가 오히려 흐려진다. 텍스트 정확도를 먼저 올린 뒤 벡터를 얹는 것이 하이브리드의 정석이다.
- **E가 마지막인 이유**: 화면은 백엔드가 무엇을 줄 수 있는지 확정된 뒤에 설계해야 헛돌지 않는다.

## 5. 런타임 검색 파이프라인

```
검색어 입력
  │
  ├─[1] 정규화 (결정론 · 프론트/서버 동일 규칙)
  │     길이·단어수 상한(문장 허용치로 상향) · 한영 자판 복원 · 자모 정규화(NFC 통일)
  │     초성 질의 감지 · 어휘 사전 기반 편집거리 오타 후보 산출
  │
  ├─[2] 질의 분류 — 키워드형 / 문장형
  │       └ 키워드형이면 [3]을 건너뛴다 (LLM 비용·지연 절감 지점)
  │
  ├─[3] 질의 이해 (문장형만 · DeepSeek · JSON 출력)
  │     → { 구조화 필터, 핵심 키워드, 벡터용 묘사문 }
  │     정규화 질의를 키로 캐시 · 타임아웃/실패 시 규칙 폴백 (검색은 계속된다)
  │
  ├─[4] 후보 생성 — 세 갈래 병렬
  │     ├ 텍스트 : PGroonga 전문검색 (브랜드·제목·태그·보강 속성 텍스트)
  │     ├ 필터   : 구조화 조건으로 좁힌 뒤 인기·신선도순
  │     └ 벡터   : SigLIP2 텍스트 타워 → c_img_vecs ANN (착용샷·단품컷만)
  │
  ├─[5] RRF 융합   Σ wᵢ/(k+rankᵢ) · k=50 시작 · 가중치는 정답셋으로 튜닝
  ├─[6] 가산점     개인화 약하게(프로필 앵커 유사도) + 신선도(기존 로직 재사용)
  └─[7] 페이징     (점수, goods_no) 복합 커서
```

### 설계상 못박아 두는 것

- **노출 자격은 기본 피드와 동일하게 유지한다** — `card_ok`·썸네일·제목·가격 조건. 검색으로 피드에서 제외된 상품이 재노출되면 안 된다(기존 계약).
- **관련도 정렬로 바뀌면 지금의 단순 keyset이 깨진다.** 갈래별 상위 N만 융합 풀로 잡고, 풀을 소진하면 텍스트 갈래만 순수 keyset으로 이어 붙이는 **꼬리 모드**로 전환한다. 무한 스크롤이 끊기지 않으면서 중복·누락도 생기지 않는다.
- **LLM은 어느 경로에서도 필수가 아니다.** [3]이 실패하면 [4]는 원문 키워드로 그대로 돈다. 기존의 "자동 재시도 없이 수동 재시도" 계약은 유지한다.
- **입력 방어는 유지·확장한다.** anon이 직접 호출하는 RPC이므로 길이·단어 수 상한, 와일드카드 escape, 크기 클램프, `security definer` + `search_path` 고정 방침을 그대로 따른다. 문장 질의를 받으려면 상한은 올라가지만 상한 자체를 없애지는 않는다.

## 6. C단계 — 속성 보강

### C1. SigLIP2 zero-shot 축 추가 (이미지 재처리 없음)

기존 `c_img_vecs` 벡터에 프롬프트 임베딩을 내적한다. 비용 0, 소요 수 분. 기존 `img_type`·`graphic` 분류와 같은 패턴(분류 버전 컬럼 포함)을 확장한다.

- 추가 축: 소매길이 · 넥라인 · 핏(오버/레귤러/슬림) · 패턴(스트라이프·체크·타이다이·그라데이션 등) · 무드.
- 신뢰도 미달은 `미상`으로 두고 검색 조건에서 제외한다. 표본 사람 검수로 임계값을 정한다(기존 분류와 동일 절차).

### C2. DeepSeek 배치 속성 추출 (텍스트 근거)

- 입력: 브랜드·제목·태그·색상코드·시즌·성별 (+ `ai_summary` 키워드 — **커버리지 미측정, §11 미정 항목**).
- 출력: 고정 JSON 스키마 — 정규 카테고리 · 색상명(한/영) · 소재 · 프린트 유형 · 스타일 무드 · **검색용 확장어(동의어·한영 별칭·줄임말)**.
- **환각 차단이 핵심이다.** "입력에 근거가 없으면 추측하지 말고 null"을 강제하고, 표본 200건을 사람이 검수해 통과한 뒤에 전량을 돌린다.
- 결과는 새 테이블에 넣고 **원본 `c_goods`는 변경하지 않는다** — 재실행·롤백이 쉬워진다.
- 비용 추정 **$30~70** (226,320행 · off-peak · 시스템 프롬프트 캐싱 기준), 소요 하룻밤. 중단 후 재개 가능하게 만든다.

### C1과 C2가 충돌할 때

| 축 | 우선 | 이유 |
|---|---|---|
| 소매길이 · 넥라인 · 핏 · 패턴 | **C1 (이미지)** | 눈으로 보이는 것은 이미지가 정본이다. 제목은 자주 생략·과장된다. |
| 카테고리 · 브랜드 계열 · 별칭 · 소재 | **C2 (텍스트)** | 이미지로 판별 불가하거나 지식이 필요한 축이다. |

### C3. 검색 텍스트 재생성

`c_search_text`를 확장해 브랜드 + 제목 + 태그 + 보강 확장어 + 색상명 + 속성명을 결합한다. **A단계가 쓸 PGroonga 색인 구조를 이때 미리 반영**해 색인을 두 번 만들지 않는다. 갱신 계약(재수집·재분류 후 재생성)은 기존 문서 방침을 그대로 따르고 `backend/README.md`에 반영한다.

## 7. A·B·D·E 단계

### A — 한국어 색인·관련도 정렬

PGroonga 확장을 켜고 검색 텍스트 테이블에 색인을 건다. 지금의 "좁은 테이블 전체 스캔 + LIKE"를 대체하므로 pg_trgm에서 8초 한도를 넘겼던 문제와 띄어쓰기 변형이 함께 풀린다. 정규화는 **프론트와 서버가 같은 규칙을 쓴다는 기존 계약**을 유지한 채 확장한다 — 한영 자판 복원, 자모 정규화, 초성 질의, 어휘 사전(브랜드명·태그·카테고리에서 추출) 기반 편집거리 오타 후보.

### B — 의미 검색 (텍스트 → 이미지)

SigLIP2 텍스트 타워를 런타임에 올려 질의를 벡터로 만들고 기존 ANN에 태운다. **배치 위치는 이 설계에서 하나로 못박지 않는다** — 브라우저(transformers.js)·서버 함수·외부 추론 엔드포인트 모두 가능하며, 첫 로드 비용과 지연을 실측해 고른다.

> **벡터 공간 일치 게이트(필수).** 런타임 인코더가 로컬 배치와 같은 체크포인트·같은 리비전이 아니면 결과가 **오류 없이 조용히 잘못된다.** 같은 문장을 양쪽에서 임베딩해 수치가 일치하는지 확인한 뒤에만 다음 단계로 간다.

### D — 질의 이해 (문장형만)

분류기가 문장형으로 판정한 질의만 DeepSeek을 태운다. 정규화 질의를 키로 결과를 캐시하고, 타임아웃이면 규칙 폴백으로 넘어간다. 반환 스키마는 §5 [3]과 같다.

### E — 검색 UX 재설계 (별도 스펙으로 분리)

자동완성(어휘 사전 기반 — LLM 불필요) · 최근 검색어 · 오타 제안("혹시 이거?") · **이해 결과를 필터 칩으로 노출하고 개별 해제 가능** · 0건일 때 조건 완화 제안 · 필터 칩. 화면 설계가 필요하므로 별도 스펙으로 분리하고, **이 설계에서는 백엔드가 E에 제공해야 하는 것**(제안어, 적용된 필터 목록, 완화 후보)만 확정한다. 플로팅 검색창의 기존 동작(축소/확장, 피드 교체, 스크롤 전이, 상세 위에서 숨김)은 유지한다.

### 옵션 F — LLM 재정렬 (기본 비활성)

상위 후보를 DeepSeek이 재정렬하는 경로. 지연·비용이 커서 기본은 끈다. **D단계까지 마친 뒤에도 정답률이 목표에 못 미칠 때만 켜는 카드**로 남긴다.

## 8. 평가 하네스 (0단계)

### 검색어 세트

Codex가 만들고 고정한다. 6계열을 고르게 섞는다.

| 계열 | 예 | 현재 |
|---|---|---|
| 브랜드·정확 | `나이키`, `MLB` | 됨 |
| 카테고리·속성 | `반팔`, `흰색 무지티` | 부분 |
| 오타·자판 | `나이크`, `sksdlzl` | 안 됨 |
| 띄어쓰기 변형 | `반팔티` / `반팔 티` | 안 됨 |
| 문장 | `3만원 이하 여름에 시원한 흰 반팔` | 안 됨 |
| 느낌 | `레트로한 프린트`, `조용한 미니멀` | 안 됨 |

### 채점 방법

- 검색어별 상위 20개를 Codex가 적합/부적합으로 채점하고, 정답률 = P@20 평균.
- **계열별 점수를 따로 낸다.** 전체 70%를 넘겨도 특정 계열이 무너져 있으면 통과가 아니다.
- 각 단계 전후로 같은 세트를 돌려 **회귀(이전보다 나빠짐)를 잡는다.**

### 알려진 한계 (합의됨)

Codex는 텍스트(제목·브랜드·속성)로 채점한다. **"느낌" 계열은 이미지를 봐야 판단되므로 Codex 점수를 신뢰하기 어렵다.** 이 계열은 채점에 포함하되 점수는 참고로만 쓰고, 70% 게이트 통과 후 **사람 눈 검증의 필수 대상**으로 표시한다.

## 9. 단계별 완료 기준

각 단계는 "무엇을 하면 무엇이 보인다"로 끝나야 한다.

| 단계 | 완료 기준 |
|---|---|
| **0** | 고정된 검색어 세트로 현재 검색을 돌린 **기준선 정답률이 계열별로 기록**돼 있다. |
| **C** | 보강 결과 표본 200건이 사람 검수를 통과하고, 태그가 없던 상품이 속성으로 검색 후보에 잡히는 것이 보인다. |
| **A** | 오타·자판·띄어쓰기 계열 정답률이 기준선 대비 오르고, **브랜드·정확 계열이 떨어지지 않는다.** |
| **B** | 벡터 일치 게이트를 통과하고, 문장·느낌 계열 정답률이 오르며, **브랜드·정확 계열에 회귀가 없다.** |
| **D** | 문장 계열 정답률이 오르고 문장 질의 p95 지연이 상한 안이며, **키워드 질의 지연은 변하지 않는다**(LLM을 타지 않음이 확인된다). |
| **E** | 별도 스펙에서 정의한다. |
| **전체** | 종합 정답률 70% 이상 → 사람 눈 검증 진행. |

## 10. 공통 안전장치

- **갈래별 스위치** — 텍스트·필터·벡터·LLM을 각각 끌 수 있게 한다. 평가에서 기여도를 분리하는 수단이자, 사고 시 즉시 되돌리는 수단이다.
- **폴백 사슬** — 갈래 하나가 죽으면 나머지로 결과를 낸다. LLM이 죽으면 규칙으로 간다. 전부 실패할 때만 기존의 "수동 재시도" 화면을 보여준다. 개인화 설계의 원칙대로 **폴백 상태에서 개인화인 척하지 않는다.**
- **롤백** — 보강 결과는 별도 테이블이라 드롭·재생성으로 되돌린다. 색인·물질화 테이블의 갱신 계약은 문서에 못박는다.
- **공유 DB 배려** — 이 DB는 ecommerce 앱과 공유다. 확장 추가는 `c_*` 대상에만 쓰고, **전역 확장을 삭제하는 구문은 절대 넣지 않는다**(선례: pg_trgm 전역 삭제 구문 제거).
- **계측** — 검색 이벤트에 질의 유형·LLM 사용 여부·갈래별 기여·지연을 남긴다. 결정 S-06에 따라 **검색 노출 계측을 켜고 검색 중 행동을 취향 프로필에 반영**한다.
- **비밀정보** — DeepSeek API 키는 환경변수로만 다루고 저장소에 넣지 않는다. 클라이언트에서 직접 호출하지 않는다.

## 11. 미정 (지어내지 않고 남겨둠)

1. **런타임 텍스트 인코더 배치 위치** — 브라우저/서버 함수/외부 엔드포인트. B단계에서 첫 로드 비용·지연 실측 후 결정.
2. **RRF 가중치와 k 값** — 정답셋으로 튜닝. k=50은 시작값일 뿐이다.
3. **융합 풀 크기와 꼬리 모드 전환 지점** — 실측으로 정한다.
4. **문장 질의 p95 지연 상한** — 합의된 감각은 1~2초. 정확한 상한은 D단계 실측 후 확정.
5. **계열별 정답률 목표** — 종합 70%는 정해졌으나 계열별 목표는 기준선 측정 후 정한다.
6. **질의 분류 규칙의 임계값** — 무엇을 문장형으로 볼지. 0단계 검색어 세트로 조정한다.
7. **`ai_summary` 커버리지 미측정** — 카탈로그 감사 표에 없다. C2 입력 확정 전에 측정한다.
8. **PGroonga 토크나이저 선택** — 형태소 기반과 n-gram 중 무엇이 이 카탈로그에 맞는지 A단계에서 실측 비교.
9. **정답셋 크기** — 40~60개를 상정하나 Codex가 만들며 확정한다.
