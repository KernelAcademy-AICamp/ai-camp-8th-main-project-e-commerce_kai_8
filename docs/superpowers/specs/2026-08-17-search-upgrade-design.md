## 1. 배경 — 지금 검색이 왜 부족한가

2026-08-16 PR #15로 들어간 MVP 검색은 **`lower(브랜드명 + ' ' + 제목)` 한 컬럼에 대한 부분 일치**가 전부다. 구조상 다음이 전부 불가능하다.

- 태그(`tags`, 보유율 75.4%)·색상코드(99.7%)·성별(99.2%)·시즌(84.5%)·착용감(28.1%)·`ai_summary` 등 **다른 필드를 하나도 쓰지 않는다.**
- `c_img_vecs`에 96.7만 장 SigLIP2 벡터가 이미 있지만 **검색은 벡터를 전혀 쓰지 않는다.**
- 오타·동의어·한영 별칭·띄어쓰기 변형·의미 검색 미지원 (MVP 한계로 명시돼 있었음).
- 정렬이 `goods_no` 오름차순이라 **관련도 개념이 없다.**

### 결정 기록과의 관계

결정 기록 O-25는 "LLM 자연어 검색을 보조 진입점으로 추가하고 상세는 별도 스펙에서 설계한다"고 남겼고, 개인화 설계 §1도 "검색은 별도 스펙"으로 미뤘다. **이 문서가 그 별도 스펙이다.** Non-goal "검색을 주 경험으로 제공하지 않는다"는 유지된다 — 검색 결과는 여전히 피드 형태로 이어지고, 사용자는 탐색으로 복귀한다.

## 3. 조사 결과 — DeepSeek으로 할 수 있는 것과 없는 것 (2026-08-17 확인)

**DeepSeek에는 임베딩 모델이 없다.** 공식 API 문서와 가격 페이지에 올라 있는 모델은 `deepseek-v4-flash`와 `deepseek-v4-pro` 둘뿐이고 **둘 다 텍스트 전용**이다. "deepseek-embedding-v2" 같은 이름은 SEO 문서에만 등장하며 공식 근거가 없고, 공식 저장소에는 임베딩 API를 만들어달라는 이슈가 열려 있다. **따라서 SigLIP2를 DeepSeek으로 대체할 수 없으며, 벡터 생성은 계속 SigLIP2가 담당한다.**

- 비전도 API에는 없다. DeepSeek-VL2·Janus-Pro는 오픈웨이트 자체 호스팅 전용이다. 이미지 기반 속성 추출은 SigLIP2 zero-shot으로 훨씬 싸게 달성하므로 채택하지 않는다.
- 쓸 수 있는 것: function calling, JSON 출력, **context caching**, thinking/non-thinking 모드, 1M 컨텍스트.
- **가격은 peak/off-peak 시간대 요금제다** (2026-08-17 공식 가격표 확인). **peak = 01:00–04:00 및 06:00–10:00 UTC**(한국시간 10–13시·15–19시), 나머지가 off-peak이며 off-peak가 peak의 절반이다. v4-flash off-peak 기준 캐시 히트 $0.007 / 캐시 미스 $0.22 / 출력 $0.66 (1M 토큰당). 캐시 히트는 미스의 약 **1/31**이다. **배치는 off-peak 시간대에 돌린다.**

**결론: DeepSeek의 자리는 세 곳이다** — ⓐ 오프라인 카탈로그 속성 보강(C단계), ⓑ 온라인 질의 이해(D단계), ⓒ 상위 결과 재정렬(옵션 F, 기본은 끈다).

### 참고한 외부 사례

- **하이브리드 + RRF가 정석**: Supabase 공식 레시피가 tsvector와 pgvector를 `1/(k+rank)`(k=50 기본) + 가중치로 합친다. [원논문(Cormack et al., SIGIR '09)](https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking)은 RRF가 Condorcet·개별 rank learning을 능가하며 **k 값에 민감하지 않다**고 보고한다 — 우리 k=50 시작값의 근거다.
- **한국어는 Postgres 기본 전문검색이 불가**. PGroonga가 Supabase 확장으로 제공된다(대안: pg_bigm). **단 형태소 분석기(TokenMecab)는 별도 패키지·한국어 사전이 필요해 관리형 환경에서 쓸 수 있는지 미확인이다** — A단계에서 확인하고, 불가하면 n-gram만 실측 대상으로 한다(§11).
- **LLM을 핫패스에 두지 않는 것이 프로덕션 패턴**: 인기 질의 재작성을 미리 계산해 캐시하고, 단순 키워드 질의는 분류 단계에서 LLM을 건너뛴다.
- **오프라인 속성 보강**이 대형 커머스의 표준 수단이다.
- **한국어 특유 문제(한영 자판 오타·초성·자모 오타)는 LLM 없이 결정론적 규칙으로** 처리하는 것이 정확하고 저렴하다.
- 레퍼런스 모음: `frutik/awesome-search`, `alopatenko/LLMSearchRecommender`.

### 확인된 기술적 사실

1. **우리가 쓰는 체크포인트의 ONNX 변환본이 공개돼 있다** — `onnx-community/siglip2-base-patch16-256-ONNX`. **다만 저장소 전체가 11.4GB이고 단일 INT8 산출물도 378MB다.** 텍스트 타워만 분리했을 때의 실제 다운로드 크기·메모리·모바일 첫 질의 시간은 **미측정**이며, 이를 재기 전에는 배치 위치를 단정하지 않는다(§7 B).
2. **새 zero-shot 속성 축은 이미지 재처리 없이 추가할 수 있다.** `c_img_vecs`에 벡터가 이미 있으므로 축마다 텍스트 프롬프트를 임베딩해 내적하면 된다. 비용은 사실상 0이다.

## 4. 범위 분해와 순서

| # | 덩어리 | 무엇이 좋아지나 | DeepSeek |
|---|---|---|---|
| **0** | 평가 하네스 | 지금 점수를 알게 된다 (기준선) | — |
| **A** | 한국어 색인 + 관련도 정렬 | 오타·자판·띄어쓰기가 걸리고 관련도순이 된다 | — |
| **B** | 의미 검색 (텍스트→이미지) | 문장·느낌 질의가 걸린다 | — |
| **C** | 속성 보강 | 남은 실패 계열을 메운다 (조건부·부분 실행) | 배치 ✅ |
| **D** | 질의 이해 | 복합 하드 조건이 구조화 필터로 바뀐다 (조건부) | 온라인 ✅ |
| **E** | 검색 UX 재설계 | 검색이 제품 기능이 된다 | 선택 |

**확정 순서: 0 → A → B → C → D → E** (S-07).

- **0이 먼저인 이유**: 기준선 점수가 없으면 이후 어떤 단계도 "좋아졌다"를 말할 수 없다.
- **A가 B보다 먼저인 이유**: 벡터만 켜면 브랜드·모델명 같은 정확 질의가 흐려진다. 텍스트 정확도를 먼저 올린 뒤 벡터를 얹는 것이 하이브리드의 정석이다.
- **C·D가 A·B 뒤인 이유(리뷰 M12 반영)**: 태그 75.4%·색 99.7%·성별 99.2%가 이미 있고 SigLIP2 한국어 질의도 검증됐다. **A·B의 홀드아웃 결과에서 실제로 실패한 계열을 확인한 뒤, 그 계열에 필요한 필드만 C로 보강한다.** 22.6만 행 LLM 보강을 무조건 선행하는 것은 70% 목표 대비 과하다. D도 B가 가격 등 하드 조건에서 부족할 때 조건부로 연다.
- **C 실행 조건**: A·B 완료 후 계열별 점수에서 미달 계열이 남고, 그 원인이 **텍스트 재료 부족으로 진단될 때만** 실행한다. 진단 없이 전량 보강하지 않는다.
- **D의 예외 — 부정 조건 계열(G5)에는 조건부가 아니라 필수다.** 씨앗 46건 중 7건이 부정 조건이다(`프린트가 없는`·`목이 안늘어나는`·`그림이 너무 크진 않은`·`너무 스포츠스러운거 말고`·`노란색이 없으면` 등). **벡터 검색은 부정을 구조적으로 다루지 못한다.** 초안에서는 직관으로 적었으나 근거가 확인됐다 — [NevIR](https://arxiv.org/pdf/2305.07614)(EACL 2024)은 대부분의 IR 모델이 부정 질의에서 **무작위 순위 이하**로 떨어지며 **bi-encoder는 그중에서도 가장 나쁘다**고 보고한다(MPNet 8.10%·Jina 14.61%). 우리 SigLIP2가 bi-encoder다. 기준선 G5가 0.0%인 것이 우연이 아니다. 부정은 질의에서 추출해 hard 필터로 빼내야 하고(§5.3), 그 추출이 D단계다. 따라서 **G5 계열의 목표 달성은 D 없이는 불가능**하며, A·B 결과와 무관하게 D를 연다.
- **E가 마지막인 이유**: 화면은 백엔드가 무엇을 줄 수 있는지 확정된 뒤에 설계해야 헛돌지 않는다.

## 5. 런타임 검색 파이프라인

### 5.1 오케스트레이션 경계 (리뷰 B3 — 이 설계에서 확정)

**세 갈래를 단일 SQL 문으로 합치지 않는다.** 한 갈래의 오류나 statement timeout이 문장 전체를 취소해 §10의 "갈래별 독립 폴백"이 성립하지 않기 때문이다.

**서버 오케스트레이터를 둔다** (Next.js Route Handler 등 서버 실행 계층). 근거:

- DeepSeek 키는 서버에만 둘 수 있다(§10 보안). D단계가 오면 서버 계층은 어차피 필요하다.
- 갈래별 독립 타임아웃·부분 실패 처리는 호출을 나눠야만 가능하다.
- 커서 스냅샷·질의 이해 캐시·개인화 동결값을 **한 곳이 소유**해야 계약이 단순해진다.

각 갈래의 DB 접근은 기존 방식대로 RPC를 쓴다. 오케스트레이터는 갈래 호출 → 융합 → 커서 발급을 책임진다. **A단계 첫 RPC를 쓰기 전에 요청/응답 계약을 문서로 고정한다.**

```

  │       └ 키워드형이면 [3]을 건너뛴다
  │

  │     → { hard 필터, soft 힌트, 핵심 키워드, 벡터용 묘사문 }

  ├─[6] RRF 융합  Σ wᵢ/(k+rankᵢ) · k=50 시작 · 가중치는 개발셋으로 튜닝
  ├─[7] 가산점    동결된 개인화 스냅샷 + 시즌 가산 (soft only)
  └─[8] 페이징    고정 융합 집합 + 명시적 커서 계약 (5.4)
```

### 5.3 hard 필터와 soft 힌트 (리뷰 M1)

질의에서 추출한 조건을 두 종류로 나눈다.

- **hard 필터** — 위반하면 결과에 있으면 안 되는 것. 가격 상한/하한, 성별, 명시된 색. **후보 생성 전에 모집단을 좁힌다.** 어떤 갈래도 이를 우회할 수 없다.
- **soft 힌트** — 순위에만 영향을 주는 것. 무드, 스타일, 계절감, 핏 선호.

hard/soft 판정 규칙은 **필터 종류별 표로 고정**하고, LLM이 그 분류를 바꿀 수 없게 한다. LLM은 값만 채우고 종류는 우리 표가 정한다.

**노출 자격은 hard 필터와 동일 위상으로 항상 적용한다.** `c_feed_products` 뷰에는 `card_ok`가 없으므로(리뷰 M5 — 뷰는 크기·썸네일·제목·가격만 검사한다) **세 갈래 모두 상위 N을 자르기 전에 `c_thumb_dims.card_ok`를 적용**한다. 갈래별 자격 누출 0건을 완료 기준에 명시한다.

### 5.4 커서 계약 (리뷰 B1)

"융합 풀 + 꼬리 모드"는 커서에 다음이 모두 들어가야 성립한다. 하나라도 빠지면 중복·누락이 생긴다.

- **모드** — `fused`(융합 집합 소비 중) / `tail`(텍스트 전용 이어붙이기)
- **융합 집합 식별자와 버전** — 첫 페이지에서 확정된 후보 집합을 고정한다. 이후 페이지는 이 집합을 재계산하지 않는다.
- **모드별 커서** — `fused`는 융합 집합 내 위치, `tail`은 텍스트 갈래 전용 커서
- **제외 조건** — `tail`에서 **이미 융합 집합에 포함됐던 상품은 건너뛴다**

전환 시 점수 의미가 바뀌는 것(RRF → 텍스트 관련도)은 **의도된 강등**으로 문서화한다. 융합 집합을 다 본 뒤의 꼬리는 "관련도가 낮은 나머지"이므로 전역 정렬을 주장하지 않는다. 이 주장을 검증하는 테스트(연속 페이지에서 중복 0·누락 0)를 완료 기준에 넣는다.

### 5.5 개인화 동결 (리뷰 B2)

취향 프로필은 탭·찜 즉시 변한다. 1페이지 상품을 열고 2페이지를 요청하면 이미 본 상품이 재채점돼 커서 앞뒤로 이동한다.

→ **검색 제출 시점에 개인화 입력을 동결한다.** 앵커·가중치 스냅샷과 프로필 해시를 커서에 함께 싣고, 같은 검색 세션 동안 그 값만 쓴다. 검색어를 새로 제출하면 그때 다시 동결한다. 기존 개인화 설계의 **최근 노출 제외 목록**도 검색에 동일하게 적용한다.

### 5.6 그 밖에 못박아 두는 것

- **LLM은 어느 경로에서도 필수가 아니다.** [3]이 실패하면 [5]는 원문 키워드로 그대로 돈다.
- **입력 방어는 확장한다.** anon이 닿는 경로이므로 길이·단어 수 상한, 크기 클램프, `security definer` + `search_path` 고정을 유지한다. **단 LIKE용 `%`·`_`·`\` escape는 PGroonga에 통하지 않는다**(리뷰 M7). PGroonga `&@~`는 `OR`·`-` 등 자체 질의 문법을 해석하므로, **사용자 입력에 질의 문법을 허용하지 않고** 전용 escape(`pgroonga_query_escape`)를 통과시킨다. 연산자 수·오타 후보 수 상한도 함께 정의한다.

## 6. C단계 — 속성 보강 (조건부·부분 실행)

**A·B 결과에서 미달 계열의 원인이 텍스트 재료 부족으로 진단됐을 때만, 진단된 필드에 한해 실행한다.**

### C1. SigLIP2 zero-shot 축 추가 (이미지 재처리 없음)

기존 `c_img_vecs` 벡터에 프롬프트 임베딩을 내적한다. 비용 0, 소요 수 분.

- 추가 축: 소매길이 · 넥라인 · 핏 · 패턴 · 무드.
- 신뢰도 미달은 `미상`으로 두고 검색 조건에서 제외한다. 표본 사람 검수로 임계값을 정한다.
- **상품 단위 집계 규칙이 필요하다** (리뷰 M4). `c_img_vecs`는 **이미지별**(상품당 썸네일 + 갤러리 다수) 테이블인데 검색 텍스트는 **상품당 한 행**이다. 슬롯마다 다른 판정이 나올 수 있으므로 다음을 정한다: 어떤 `img_type`·슬롯을 집계 대상으로 삼을지, 다중 이미지 합의·충돌을 어떻게 해소할지, 대표값과 신뢰도를 어떻게 산출할지.
- **버전 관리**: 기존 `classify_ver`는 **이미지 유형 분류 전용**이며 `graphic`에는 버전 컬럼이 없다(리뷰 M4). 새 축은 **자체 버전 컬럼**을 갖는다.

### C2. DeepSeek 배치 속성 추출 (텍스트 근거)

- 입력: 브랜드·제목·태그·색상코드·시즌·성별 (+ `ai_summary` 키워드 — **커버리지 미측정, §11**).
- 출력: 고정 JSON 스키마 — 정규 카테고리 · 소재 · 프린트 유형 · 스타일 무드 · **검색용 확장어(동의어·한영 별칭·줄임말)**.
- **기존 정본으로 결정론적으로 만들 수 있는 값은 LLM 대상에서 제외한다**(리뷰 M12). 색상명은 `c_color_groups`(무신사 공식 54색 정본)에서, 카테고리는 `base_cat`에서 규칙으로 만든다. LLM은 정본이 없는 축만 담당한다.
- **환각 차단**: "입력에 근거가 없으면 추측하지 말고 null"을 강제하고, 표본 200건 사람 검수를 통과한 뒤 전량을 돌린다. 확장어는 **개수 상한**을 두고 **출처(LLM)와 버전을 보존**한다.
- 결과는 별도 테이블에 넣고 **원본 `c_goods`는 변경하지 않는다.**
- 비용 추정 **$30~70**(226,320행 · off-peak · 프롬프트 캐싱 기준). 중단 후 재개 가능하게 만든다.

### C1·C2 충돌 해소

| 축 | 정본 | 이유 |
|---|---|---|
| 소매길이 · 넥라인 · 핏 | **C1 (이미지)** | 눈으로 보이는 것은 이미지가 정본. 제목은 자주 생략·과장된다 |
| 카테고리 · 소재 · 별칭 · 확장어 | **C2 (텍스트)** | 이미지로 판별 불가하거나 지식이 필요 |
| 색상명 | **정본 테이블** | `c_color_groups` — 둘 다 쓰지 않는다 |
| **무드** | **병합** (리뷰 m4) | C1·C2가 모두 생성한다. 상호배타적이지 않으므로 **다중 라벨 + 대표값** 구조로 합치고, 출처를 각각 보존한다 |
| **패턴 / 프린트 유형** | **병합** | 위와 같은 이유. 단일 정본을 강제하지 않는다 |

### C3. 검색 텍스트 갱신

**필드를 하나의 문자열로 합치지 않는다**(리뷰 M9). 브랜드·정확 제목·원본 태그·SigLIP 판정·LLM 확장어를 한 컬럼에 섞으면 브랜드 정확 매칭을 우대하거나 환각성 확장어를 낮게 가중할 수 없어, A단계의 "브랜드 회귀 없음" 기준과 충돌한다. **필드별 컬럼/배열로 나누고 가중치를 부여하며, 각 값의 출처와 버전을 보존한다.**

**갱신은 shadow table 원자 교체로 바꾼다** (리뷰 M6). 현행 계약은 `c_search_text`를 drop 후 재생성하는데, 그대로 두면 카탈로그 갱신 때 **PGroonga 색인이 함께 사라진다.** 새 테이블을 만들어 동일 색인·RLS·grant를 구성한 뒤 원자적으로 교체하고, 이 절차를 `backend/README.md` 갱신 계약에 반영한다.

> **테이블 이름 교체만으로는 부족하다** (2차 리뷰 Major 1·6). PostgreSQL의 의존 객체가 새 테이블을 참조한다고 보장할 수 없으므로 **검색 RPC도 같은 트랜잭션에서 재작성·검증**해야 한다. 그리고 **A단계에서 만든 색인을 C3가 새 필드 구조로 다시 전량 빌드**하게 되는데, 공유 Micro DB에서 두 번째 빌드는 디스크·WAL·I/O 위험을 재발시킨다 — C 착수 시 **재빌드 창(저부하 시간대)과 롤백 절차를 다시 확보**한다. (A→C 순서를 택한 대가이며, 이 재빌드를 피하려면 C의 필드 구조를 A 시점에 미리 확정해야 한다.)

## 7. A·B·D·E 단계

### A — 한국어 색인·관련도 정렬

PGroonga 확장을 켜고 검색 텍스트에 색인을 건다. 정규화는 **프론트와 서버가 같은 규칙**이라는 기존 계약을 유지한 채 확장한다 — 한영 자판 복원, 자모 정규화, 초성 질의, 어휘 사전 기반 편집거리 오타 후보.

- **토크나이저는 실측으로 고른다.** 형태소(TokenMecab) 가용성을 먼저 확인하고, 불가하면 n-gram만 대상으로 한다(§11).
- 질의 escape·문법 정책은 §5.6을 따른다.

### B — 의미 검색 (텍스트 → 이미지)

SigLIP2 텍스트 타워를 런타임에 올려 질의를 벡터로 만들고 기존 ANN에 태운다. **배치 위치(브라우저·서버 함수·외부 엔드포인트)는 실측 후 고른다** — 텍스트 전용 산출물의 다운로드 크기·메모리·모바일 첫 질의 시간을 먼저 잰다(§3 유의점).

> **기대치를 낮춰 잡는다 (논문 근거).** [임베딩의 이론적 한계](https://arxiv.org/html/2508.21038v1)(2025)는 임베딩 차원 d에 대해 **어떤 질의로도 반환할 수 없는 top-k 조합이 존재**함을 증명했고, `누가 사과를 좋아하나?` 수준의 LIMIT 데이터셋에서 최상위 모델이 **recall@100 20% 미만**이었다. 우리 SigLIP2는 768차원 단일 벡터다.
> → **B단계에서 벡터만으로 G4(문장·복합 조건)를 풀려 하지 않는다.** 논문이 권하는 우회로는 cross-encoder·multi-vector·**sparse 모델**이고, A단계의 PGroonga가 그 sparse에 해당한다. **텍스트 갈래를 유지한 채 융합하는 설계가 이론적으로도 옳다** — A를 B보다 먼저 둔 순서가 여기서 근거를 얻었다.
> B단계의 목표는 **G7(느낌)과 G4의 일부**이지 G4 전체가 아니다.

> **벡터 공간 일치 게이트(필수, 리뷰 m2 반영).** 런타임 인코더가 로컬 배치와 다른 체크포인트·리비전이면 결과가 **오류 없이 조용히 잘못된다.** 다만 **양자화 ONNX는 PyTorch 출력과 정확히 일치하지 않을 수 있으므로 단순 수치 동일성으로 판정하지 않는다.** 판정 기준을 둘로 둔다: ⓐ 동일 문장 임베딩의 코사인 유사도가 허용 오차 이내, ⓑ **대표 질의 세트에서 로컬 정밀 검색 대비 Recall@K 게이트 통과**(기존 이진 양자화 게이트와 같은 방식).

### D — 질의 이해 (부정 조건 계열에는 필수, 그 외는 조건부)

**부정 조건 계열(G5)에는 A·B 결과와 무관하게 필요하다(§4). 그 외 하드 조건 처리는 B단계 결과를 보고 연다.**

> **백지에서 시작하지 않는다.** ecommerce에 같은 종류의 파서가 실제로 돌고 있고, 운영 함정(DeepSeek V4의 thinking 모드가 `max_tokens`를 소진해 **오류 없이 빈 응답**을 만드는 문제)과 250건 실측으로 얻은 프롬프트 설계 교훈이 [DeepSeek 사용 정보](../../atee/foundation/deepseek-usage.md)에 이식돼 있다. 구현 전에 이 문서를 먼저 읽는다. C2 배치도 같은 함정을 공유한다. 분류기가 문장형으로 판정한 질의만 DeepSeek을 태우고, 정규화 질의 + 모델/프롬프트 버전을 키로 캐시하며, 타임아웃이면 규칙 폴백으로 넘어간다.

**LLM 출력을 신뢰하지 않는다**(리뷰 M8). 반환 JSON은 **필터 enum allowlist·가격 범위·배열 길이**를 검증해 통과한 값만 쓴다. hard/soft 분류는 우리 표가 정하고 LLM이 바꿀 수 없다(§5.3).

### E — 검색 UX 재설계 (별도 스펙)

자동완성(어휘 사전 기반 — LLM 불필요) · 최근 검색어 · 오타 제안 · **적용된 필터를 칩으로 노출하고 개별 해제** · 0건일 때 조건 완화 제안. **이 설계에서는 백엔드가 E에 제공해야 하는 것**(제안어, 적용된 필터 목록, 완화 후보)만 확정한다. 플로팅 검색창의 기존 동작은 유지한다.

### 옵션 F — LLM 재정렬 (G5 전용 후보로 승격)

초안은 "정답률이 목표에 못 미칠 때만 켜는 카드"였으나, [NevIR 재현 연구](https://dl.acm.org/doi/10.1145/3726302.3730294)(SIGIR 2025)가 **부정 처리에서 listwise LLM 재정렬이 다른 어떤 구조보다 낫다**(다만 사람에는 못 미침)고 보고했다.

→ **G5(부정 조건)에 한해 D단계와 함께 검토한다.** 전면 활성화는 여전히 하지 않는다 — 지연·비용이 크고 나머지 계열은 D단계의 hard 필터로 충분하다.

## 8. 평가 하네스 (0단계)

### 8.1 왜 세트를 나누는가

이 설계에는 손으로 맞추는 값이 최소 6개다(RRF 가중치 3, k, 융합 풀 크기, 분류 임계값, zero-shot 신뢰도 임계값). **같은 세트로 튜닝하고 같은 세트로 70%를 선언하면 그 숫자는 무의미하다**(리뷰 M3).

**세 갈래로 나눈다** (2차 리뷰 B1 — 2분할로는 "단계당 한 번"이 A·B·C·D에서 같은 세트를 네 번 여는 것이라 최종 홀드아웃이 아니고, 채점자 보정 표본에 잠근 세트가 섞이면 그 피드백으로 평가 규칙을 튜닝하게 된다).

- **개발셋** — 자유롭게 본다. 파라미터 튜닝, 판정 기준서 보정, **채점자 검증을 여기서만** 한다.
- **진행셋** — 각 단계(A·B·C·D) 끝에서 한 번씩 열어 진행을 확인한다. 튜닝에 쓰지 않는다.
- **최종 홀드아웃** — **0단계 기준선 측정과 최종 판정, 딱 두 번만** 연다.

**분할 단위는 질의 개별이 아니라 "질의 가족"이다**(리뷰 M9). G3 파생 질의는 원본과, 근접 중복 실사용 질의는 서로 같은 파티션에 묶는다. 흩어지면 개발셋에서 익힌 변환·해석을 홀드아웃에서 다시 시험하는 누출이 된다.

### 8.2 판정은 풀링(pooling)으로 만든다

22.6만 개 전수 판정은 불가능하다.

1. 한 질의에 대해 **비교 대상 모든 시스템**(기준선, A 적용, A+B 적용 …)의 상위 20~30개를 모은다.
2. 중복 제거해 **판정 풀**(질의당 50~80개)을 만든다.
3. **풀만 채점**하고 판정은 이후 단계에서 재사용한다.
4. 새 시스템 결과 중 **미판정 비율**을 함께 잰다. 상위 20개 중 일정 비율 이상이 미판정이면 풀을 다시 돌린다.

**미판정 처리 규칙과 재풀링 임계값은 기준선을 재기 전에 못박는다**(리뷰 M8). 0단계의 첫 풀은 현재 검색 결과만으로 만들어지므로, 이후 A·B가 찾아온 새 상품은 판정이 없다. 미판정을 0으로 볼지 지표에서 제외할지를 나중에 정하면 **신규 시스템에 유리하거나 불리하게 고르게 된다.** 시스템이 추가될 때 블라인드로 판정을 확장하는 절차도 함께 정한다.

### 8.3 질의 출처와 편향 차단

| 출처 | 신뢰도 | 지금 |
|---|---|---|
| 실사용 로그 | 가장 높음 | **ecommerce GA4 18건 확보**(2026-01-01~08-01). aTee 자체 로그는 없다 — 0단계에서 켠다 |
| 사람이 직접 씀 | 높음 | **ecommerce 수기 28건 확보**(AI 유/무 관찰 기록 포함). 빈 계열은 신규 작성 |
| 카탈로그·규칙에서 기계 생성 | 높음(정답 결정론적) | 브랜드·표기 변형은 편향 없이 생성 가능 |
| 카탈로그 어휘에서 LLM 역생성 | 낮음 | 표현 다양성 보강에만 제한적으로 |

**Codex가 카탈로그를 보고 질의를 만들면 "색인한 걸 찾을 수 있나"를 시험하게 된다** — 자기실현적 정답셋이다. 그래서:

- **질의 분포(계열별 비율·개수)는 사람이 카탈로그를 보지 않고 먼저 못박는다.**
- 그 틀 안의 표현 다양성·오타 변형 생성은 Codex가 채운다.
- **최소 20~30%는 사람이 직접 쓴다.** **정답이 없는(0건이 정답인) 질의를 반드시 포함한다.**
- **0단계에서 검색어 로깅을 켠다.** B·D단계에 이르면 실사용 질의가 쌓여 개발셋을 교체할 수 있다.

### 계열 구성

**목표 계열 — 70% 게이트와 회귀 판정의 대상**

| | 계열 | 씨앗 보유 |
|---|---|---|
| G1 | 브랜드·정확 매칭 | 0 — 기계 생성 |
| G2 | 짧은 키워드·카테고리 속성 | 8 (+ 사람 보강 필요) |
| G3 | 표기 변형 (오타·한영 자판·초성·띄어쓰기) | 0 — 기계 생성 |
| G4 | 문장·복합 조건 (가격·색·성별·핏 등 하드 조건) | 11 |
| G5 | **부정 조건** (~없는 / ~말고 / 너무 ~하지 않은) | 7 |
| G6 | 0건이 정답 (카탈로그 밖·무의미) | 7 |
| G7 | 느낌·주관 — **사람 판정이 정본**, Codex 점수는 진단 참고 | 0 — 사람 작성 |

> **G7의 게이트 정의**(2차 리뷰 M7 — 초안은 "Codex 점수 참고"라면서 70% 목표 계열에 넣어 정의가 상충했다). G7은 목표 계열이지만 **종합 점수에는 사람 판정만 반영**하고 Codex 점수는 진단용으로만 남긴다. 그리고 **G7 기준선은 B단계 착수 전에 반드시 확보**한다 — 0단계에서 비워두면 B의 "느낌 계열 상승"과 전체 비회귀를 계산할 기준이 없다. G7이 나중에 추가되면 잠근 파티션의 분포도 바뀌므로, **추가 시점에 전 파티션을 다시 층화**하고 그 사실을 기록한다.

**참고 계열 — 점수만 기록하고 게이트에서 제외 (S-08)**

| | 계열 | 씨앗 보유 |
|---|---|---|
| R1 | 외부지식·추천·TPO·체형·코디 | 13 |

G1·G3는 **정답이 결정론적이라 기계 생성해도 편향이 없다** — 브랜드명은 `c_goods.brand_name`에서, 자판 오타·초성·공백 변형은 규칙 변환으로 만든다. 사람이 새로 써야 하는 것은 **G2 짧은 키워드 보강과 G7뿐**이다.

씨앗과 계열 배정은 [`docs/atee/eval/query-seed.json`](../../atee/eval/query-seed.json)에 있다.

### 8.4 채점 규약

- **역할 분리** — 질의를 만든 세션과 채점 세션을 분리한다. 채점자에게 질의 의도 설명을 주지 않는다.
- **시스템 블라인드 + 순서 무작위** — 어느 시스템이 냈는지, 몇 등이었는지 알리지 않는다. 개별 판정만 받고 지표는 나중에 실제 순위와 대조해 계산한다.
- **판정 기준서(rubric)를 먼저 쓴다** — `2=명시 조건 전부 만족 / 1=일부 만족·근접 / 0=무관`. 브랜드 질의처럼 엄격한 조건은 규칙으로 못박는다.
- **채점 증거 범위를 명시한다** — 채점자에게 상품 제목·브랜드·메타만 주는지 썸네일까지 주는지 정한다(리뷰 M11). 정하지 않으면 사람과 Codex가 서로 다른 증거를 보고 채점해 일치도 수치의 의미가 사라진다.
- **인간 앵커로 채점자를 검증한다** — 사람이 표본을 채점하고 Codex와의 일치도를 잰다. 일치도가 낮으면 하네스 전체를 신뢰할 수 없다. 다음을 지킨다(리뷰 M10).
  - **등급이 순서 있는 3단계이므로 단순 일치도(Cohen's κ)를 쓰지 않는다** — 2와 1의 차이를 2와 0의 차이와 같게 취급한다. 순서를 반영하는 지표(가중 일치도 등)를 쓰고 계열별 신뢰구간을 함께 낸다.
  - **표집은 질의 단위**로 한다(같은 질의의 상품들은 강하게 상관돼 독립 표본이 아니다).
  - **표본은 개발셋에서만** 뽑는다(§8.1).
  - **기준서를 고친 뒤에는 같은 표본이 아니라 별도 확인 표본으로 다시 잰다** — 같은 표본에서 고치고 같은 표본으로 합격 판정하면 과적합이다.
- **텍스트 채점의 한계** — 채점자는 이미지를 보지 못하므로 느낌뿐 아니라 **색·핏·패턴 등 이미지 유래 속성도 검증할 수 없고, C1이 만든 잘못된 라벨을 근거로 채점할 위험이 있다**(리뷰 M3). 이런 계열은 점수를 참고로만 쓰고 **사람 판정을 정답으로 삼는다.**
- **LLM 채점은 "시스템 비교"에는 정당하고 "개별 정답"에는 부족하다.** [LLM-as-judge 연구](https://arxiv.org/html/2601.08919v2)는 LLM 판정자가 사람의 일관성에 못 미치지만 **시스템 수준 평가에는 충분한 경우가 많다**고 보고한다. 우리 용도(A vs B 비교)는 전자다. 다만 "LLM 판정자와 사람이 관련성 기준에서 갈린다"는 지적이 있어 **인간 앵커는 여전히 필요**하다.
- **세션 분리만으로 자기채점 편향이 사라지지 않는다**(리뷰 M11). 같은 모델이 표현을 만들고 관련성을 판정하면 언어적 선호와 지식 편향은 공유된다. 그래서 인간 앵커가 선택이 아니라 필수 게이트다.

### 8.5 규모·지표

- 질의 **120~150개**, 계열당 15건 이상. 계열 비율을 유지한 **층화 분할**을 **개발 / 진행 / 최종 홀드아웃 세 갈래**로 한다(§8.1).
- **정직한 민감도**: 질의를 독립 단위로 본 95% 오차는 120건 규모에서도 **약 ±9~13%p**다(초안에 적었던 "±7~10%p"는 근거 없는 수치였고 2차 리뷰에서 정정됐다). 분할 후 파티션당 계열 표본은 여전히 한 자릿수다. 따라서 **계열별 점수는 자동 합격/불합격 판정이 아니라 "하락이 보이면 사람이 원인을 확인한다"는 트리거로 쓰고, 자동 판정은 종합 점수에만 적용한다.** 진짜 계열별 통계 게이트에는 계열·파티션당 30건 이상(총 700건 규모)이 필요한데 판정 비용이 감당되지 않는다.
- 상품 20개를 독립 표본처럼 세면 같은 질의 안의 강한 상관 때문에 의사 반복이 된다 — **표집과 신뢰구간은 질의 단위로 계산한다.**
- 지표는 **계열 성격에 따라 나눈다.**
  - 상품 단위(G1~G5·G7·R1): **P@20** + **nDCG@20**(3단계 등급) + **미판정 비율**.
  - **G6은 상품 단위로 채점할 수 없다.** 후보가 없어 판정 풀이 만들어지지 않고, 올바른 빈 결과에 P@20을 적용하면 0점이 되어 **억지 결과를 낸 시스템이 오히려 점수를 얻는다**(리뷰 B2). → **질의 단위 zero-result 정확도**로 따로 계산하고, 종합 점수에 합치는 규칙을 판정 기준서에서 먼저 정한다.
  - **등급 1을 P@20에서 적합으로 셀지**를 기준서에서 명시한다. 안 정하면 같은 판정에서 다른 점수가 나온다.
- P@20만으로는 recall·순서 품질·꼬리 전환·중복이 검증되지 않으므로(리뷰 M3) **연속 페이지 중복·누락 0**을 별도 통과 조건으로 둔다.

### 8.6 저장·누출 방지

- 질의·판정을 저장소에 커밋한다(제안: `docs/atee/eval/`). 판정 레코드는 `(질의ID, goods_no, 등급, 채점자, 판정일, 카탈로그 스냅샷 버전)`.
- **골든셋 질의를 C단계 보강 프롬프트나 동의어 사전에 넣지 않는다.** 개발셋은 봐도 된다.

|---|---|
| **0** | 개발/골든 분할과 rubric이 커밋되고, **기준선 정답률이 계열별로 기록**된다. 인간 앵커 200건으로 잰 Codex 일치도(κ)가 기록된다. 검색어 로깅이 켜져 있다. |
| **A** | 오타·자판·띄어쓰기 계열이 기준선 대비 오르고 **브랜드·정확 계열이 떨어지지 않는다.** 자격 누출 0건. 연속 페이지 중복·누락 0. 성능 게이트(§10) 통과. |
| **B** | 벡터 일치 게이트(코사인 허용 오차 + Recall@K) 통과. 문장·느낌 계열 상승, **브랜드·정확 계열 회귀 없음.** 성능 게이트 통과. |
| **C** | 실행 조건(§4)이 성립했음이 기록되고, 보강 표본 200건이 사람 검수를 통과하며, 목표 계열 점수가 오른다. |
| **D** | 하드 조건 질의의 위반 노출 0건. 문장 계열 상승, 문장 질의 p95가 상한 안, **키워드 질의 지연 불변**(LLM 미경유 확인). |
| **E** | 별도 스펙에서 정의한다. |
| **전체** | 골든셋 **목표 계열(G1~G7)** 종합 70% 이상 **그리고 어느 목표 계열도 기준선 대비 하락 없음** → 사람 눈 검증 진행. 참고 계열 R1은 점수를 기록만 하고 게이트에 넣지 않는다(S-08). |

## 10. 공통 안전장치

### 성능 게이트 (리뷰 M2 — A단계부터 적용)

기존 실측에서 **ANN 기반 `c_mix_page`는 동시 4요청에서 각 16~18초로 이미 미통과**였다(Micro 공유 CPU 포화, work_mem 조정으로도 동일). 여기에 PGroonga·필터를 더 얹고 문장 질의에는 LLM 1~2초가 앞에 붙는다. 따라서 D단계 p95만 나중에 정하는 것으로는 부족하다.

**A단계부터 통과 조건으로 둔다**: 갈래별·전체의 cold/warm p50·p95, 동시 2·4요청, DB CPU·버퍼·temp spill, timeout·폴백 발생률. 미달이면 컴퓨트 상향 또는 갈래 축소를 결정하고 **그 결정을 기록**한다.

> **아직 게이트가 아니다** (2차 리뷰 Major 1). 위는 **무엇을 재겠다는 목록일 뿐 합격 상한이 없다.** 갈래를 나눠 호출해도 각 RPC의 anon 8초 제한은 사라지지 않는다. **A 착수 전에 갈래별 응답 상한·전체 응답 상한·허용 폴백률·Micro 유지/상향 결정을 숫자로 확정**해야 이 절이 게이트가 된다(§11).

### 배포 호환·롤백 (리뷰 M11)

현재 PWA는 `p_after bigint`와 `setof c_feed_products`를 전제로 한다. 새 복합 커서·메타데이터를 같은 함수에 넣으면 **캐시된 구버전 클라이언트가 즉시 깨진다.** 갈래 스위치로는 API 계약 실패를 되돌릴 수 없다.

→ **`c_search_page_v2`처럼 병행 배포**하고, 구 RPC와 기존 `c_search_text`를 일정 기간 유지한 뒤 제거한다. 롤아웃·롤백 절차를 계획에 명시한다.

### 공유 DB (리뷰 M13)

**PGroonga 확장 설치와 버전은 DB 전역이다** — `c_*`에만 설치할 수 있는 것이 아니다. 색인 빌드의 디스크·WAL·I/O·잠금이 ecommerce 앱에 영향을 줄 수 있다. 다음을 A단계 착수 전에 수행한다: 설치 가능 버전·권한 확인, 색인 예상 크기 산정, ecommerce 동시 부하 기준 성능 확인, **DDL 실행 창(저부하 시간대) 합의**, 실패한 색인 정리 절차, **"확장은 남기고 c_* 색인만 롤백"** 절차. 전역 확장을 삭제하는 구문은 절대 넣지 않는다.

### 계측 (리뷰 M10)

**"검색 노출 계측을 켠다"만으로는 구현되지 않는다.** `c_events`에는 search surface·policy·source가 없고, 기존 노출 기록 경로는 기록과 동시에 추천 프로필의 최근 노출·감쇠·스타일 부스트를 변경한다. 검색 노출을 random/personalized로 위장해 넣으면 **피드 전환율과 자기강화 보정이 오염된다.**

→ 다음을 **별도로 모델링**한다: `surface=search`, 검색 요청 ID, 질의와 질의 버전, 갈래별 rank·score·fallback 여부, 0건·재질의·이탈. **검색 노출이 취향 프로필에 미치는 규칙을 피드와 분리해 정의**한다(S-06의 "약하게 반영"이 무엇인지 수치로 — **현재 미정, §11**).

2차 리뷰에서 확인된 제약(Major 2·3·4):

- 기존 이벤트 테이블은 **이벤트 타입·컬럼이 고정이고 anon 직접 쓰기·읽기가 막혀 있어** 그대로 추가할 수 없다. 별도 저장소와 검증을 거치는 쓰기 경로가 필요하다.
- 별도 테이블로 만들면 **현재 기기 데이터 삭제 기능이 검색 원문을 지우지 않는다** — 삭제 범위에 반드시 포함시킨다.
- anon이 닿는 쓰기 경로이므로 **요청 크기 상한·기기별 일일 상한·중복/봇 억제**가 필요하다.
- **"결과 수"는 지금 얻을 수 없는 값이다.** 현재 검색 API는 페이지 상품 배열만 돌려주므로 전체 매치 수를 모른다. 첫 페이지 건수인지 전체 매치 수인지 정의를 먼저 정하고, 후자라면 8초 제한 아래 전수 계산 비용을 어떻게 감당할지 정한다.
- **"피드 구성이 안 변한다"로 프로필 미오염을 판정하지 않는다.** 검색 중에도 기본 피드 훅의 상품 목록이 보존되므로 **프로필이 오염돼도 통과하는 거짓 음성**이다. 저장된 장기·세션 프로필을 검색 전후로 직접 비교해야 한다. 또한 **검색 결과를 탭하면 공통 상세 진입점이 실제로 프로필을 갱신**하므로, 그것이 S-06의 의도인지를 확인해 기록한다.

### LLM 비용·남용 방지 (리뷰 M8)

키를 서버에 두는 것만으로 끝나지 않는다. 익명 사용자가 캐시 미스 문장을 계속 만들면 비용과 캐시 저장량이 무한히 는다.

→ 기기/IP별 rate limit · 일·월 예산 상한과 **circuit breaker**(초과 시 규칙 폴백으로 강등) · 동시 실행 상한 · 캐시 TTL과 최대 크기 · **모델/프롬프트 버전을 캐시 키에 포함** · 출력 allowlist 검증(§7 D). **원문 질의를 외부 API·로그로 보낼 때의 보존 기간과 개인정보 방침**을 함께 정한다.

### 폴백·롤백

갈래 하나가 죽으면 나머지로 결과를 낸다. LLM이 죽으면 규칙으로 간다. 전부 실패할 때만 기존 "수동 재시도" 화면을 보여준다. **폴백 상태에서 개인화인 척하지 않는다.** 보강 결과는 별도 테이블이라 드롭·재생성으로 되돌린다.

### 용어 정정 (리뷰 m5)

기존 "신선도"는 **실제 신상품 신호가 아니라 `season_year` 프록시**다(입고·출시 시각이 아님). 검색 결과 설명과 계측에서 `fresh`가 아니라 **`season_year_boost`**처럼 한계가 드러나는 이름을 쓴다.

## 11. 미정 (지어내지 않고 남겨둠)

1. **런타임 텍스트 인코더 배치 위치** — 텍스트 전용 ONNX 산출물의 실제 크기·메모리·모바일 첫 질의 시간 실측 후 결정(B단계).
2. **RRF 가중치와 k** — 개발셋으로 튜닝. k=50은 시작값.
3. **융합 집합 크기와 꼬리 전환 지점** — 실측으로 결정.
4. **문장 질의 p95 상한** — 합의된 감각은 1~2초. 정확한 값은 D단계 실측 후.
5. **계열별 정답률 목표** — 종합 70%는 정해졌으나 계열별은 기준선 측정 후.
6. **질의 분류 임계값** — 0단계 세트로 조정.
7. **`ai_summary` 커버리지 미측정** — C2 입력 확정 전에 측정.
8. **PGroonga 토크나이저** — 형태소(TokenMecab)가 관리형 Supabase에서 가용한지 미확인. 불가하면 n-gram만.
9. **정답셋 크기와 계열별 개수** — 씨앗 46건 확보. 계열별 목표 개수는 사람이 먼저 고정한다.
9-1. **G2 짧은 키워드 보강과 G7 느낌 질의를 누가 쓰는가** — 본인 단독인지 팀원 분담인지 미정. 한 사람에게 편향이 쏠리지 않는 편이 낫다.
10. **C1 상품 단위 집계 규칙** — 슬롯 선택·합의·대표값 산출 방식.
11. **개인화 "약하게"의 수치** — 가산점 크기와 프로필 반영 규칙.
12. **미판정 비율 재풀링 임계값**.
