# 보관함 성별 필터 — 설계 (2026-08-22)

> 앞선 결정: [설정 성별 토글](2026-08-21-gender-setting-toggle-design.md) ·
> [결정 기록 O-39](../../atee/living/decision-log.md)
> 상태: 사람이 네 갈림길(개수 계약·안내 문구·공용/미상·미확정 처리)과 경계 후보를 승인함. 교차 리뷰 전.

## 목적

O-39(고른 성별 라벨과 정확히 같은 상품만 본다)는 피드·검색·상세 하단 탐색·큐레이션에 적용됐고
**보관함만 예외로 남았다.** 예전에 찜한 반대 성별 상품이 계속 보인다. 이 조각이 그 구멍을 닫는다.

검증 가설: **원본 목록과 화면용 목록을 분리하면, 보관함에 성별 필터를 걸어도 폴더 개수·찜 여부
판정·로그인 승계가 깨지지 않는다.**

## 왜 그냥 거르면 안 되나 — 지금 코드가 그런 이유

`useWishlist()`가 내는 **하나의 `entries` 배열**이 네 곳에 쓰인다.

| 쓰는 곳 | 무엇에 | 어느 목록을 읽나 |
|---|---|---|
| 상세 화면(`product-detail`) | 하트 채움 판정(`wished`) | **훅이 반환한 배열** |
| 담기·빼기 | `addWish`/`removeWish`에 넘길 현재 목록 | **공유 저장소 스냅숏을 직접** |
| 폴더 그리드·폴더 상세 | 개수·썸네일·목록 | 훅이 반환한 배열 |
| 담기 시트 | 폴더별 개수·썸네일 | **`product-detail`이 넘겨주는** 훅 반환 배열 |

두 자리가 서로 다른 목록을 읽는다는 점이 중요하다(교차 리뷰에서 정정).

- **훅이 반환한 배열을 자르면** 하트 판정이 곧바로 깨진다 — 숨긴 상품의 상세에서 하트가 빈 채로
  뜨고, 누르면 해제가 아니라 담기 시트가 열린다.
- **담기·빼기는 저장소 스냅숏을 직접 읽으므로** 반환 배열을 잘라도 당장은 멀쩡하다. 대신
  **data 레이어(저장소)에서 자르면** 그때 깨진다 — 담기 한 번이 숨긴 상품을 목록에서 지운다.
- 즉 잘라서는 안 되는 자리가 **두 층에 걸쳐 있다.** 그래서 경계를 그 위(뷰모델)에 둔다.

**로그인 승계는 이미 원본 기준이다.** `uploadCarriedWishes`는 `entries`가 아니라 localStorage에서
읽는다. 다만 키가 둘이고 순서가 있다(교차 리뷰에서 정정).

1. 기기 찜의 원본 키는 `atee-wishlist`다.
2. **익명 → 로그인 전환일 때만** `carryWishes`가 그 값을 `atee-wishlist-migrate`로 옮긴다.
   조건은 "직전 탭 표식이 익명"이다 — 표식이 없는 새 탭은 기준점만 남기고 옮기지 않는다.
3. 업로더가 실제로 읽는 것은 **`atee-wishlist-migrate`**이고, 항목 모양은 상품번호 배열이 아니라
   `{ product: { goodsNo } }` 목록이다.

이 조각의 제약은 "이 경로에 화면용 목록이 닿지 않게 유지하는 것"이지 이 경로를 고치는 것이 아니다.

> 지금 **비회원은 찜을 담을 수 없다**(O-37). 따라서 승계가 실제로 도는 것은 그 결정 이전 버전이
> 남긴 키가 기기에 있을 때뿐이다. 경로가 죽은 것은 아니므로 검증은 키를 직접 심어 확인한다
> (완료 기준 5 — 위 1~3 때문에 "무엇을 어느 키에 심는지"가 관찰의 성패를 가른다).

## 결정 사항

| 갈림길 | 결정 | 근거 |
|---|---|---|
| 원본/화면용 경계 | **`useWishlist`는 원본만. 그 위에 보관함 전용 파생 훅 하나를 얹는다** | 아래 "경계" 절 |
| 판정 규칙의 자리 | **`wishlist/domain/`의 순수 함수** | 프레임워크 의존 없이 테스트된다(frontend/AGENTS.md) |
| 폴더별 개수 | **보이는 개수** — 그리드 타일·담기 시트·폴더 상세 헤더·보관함 총 개수 | 화면의 숫자와 그 화면에 실제 보이는 항목 수가 어긋나지 않는다 |
| 폴더 삭제 확인 문구의 개수 | **원본 개수** | 숨은 것도 실제로 함께 기본 폴더로 옮겨진다. 화면용을 쓰면 문구가 사실과 다르다 |
| 개수의 개수 | **한 폴더에 대해 세 값을 따로 계약한다** — 보이는 수 · 원본 수 · 숨은 수 | 지금은 하나의 값이 헤더와 삭제 확인에 함께 쓰이고, 빈 화면 판정도 같은 값을 본다. 하나로 두면 셋 중 둘이 반드시 거짓말을 한다 |
| 숨은 수의 범위 | **그 폴더 기준** | 전체 보관함 기준으로 세면 다른 폴더의 숨은 상품 수가 지금 열어 둔 폴더의 안내에 섞인다 |
| 숨김 안내 | **폴더 상세에만, 숨김이 1개 이상일 때 한 줄** | 찜이 사라진 게 아니라 숨은 것임을 알린다. 그리드는 깨끗하게 둔다 |
| 공용(남녀공용) | **숨긴다** | 앱 전체 정책(등식)과 같게. O-39가 없애려던 경험(여성 설정인데 사실상 남성복인 공용 썸네일)이 보관함에만 남지 않는다 |
| 성별 미상 | **숨긴다** | 위와 같은 등식 규칙. 큐레이션의 "미상은 남긴다" 비대칭을 보관함까지 늘리지 않는다 |
| 성별 미확정(`null`) | **필터를 걸지 않는다 — 원본 전부** | 숨길 기준값이 없다. 보관함은 새로 불러오는 탐색 목록이 아니라 이미 계정에 있는 데이터다 |
| 하트 판정 | **원본 기준** | 숨긴 상품의 상세를 열면 하트는 채워져 있고, 다시 누르면 원본에서 빠진다 |
| 500개 상한 | **원본 기준 유지**(서버가 센다) | 화면 개수와 다를 수 있다 — 의도된 것이다 |
| 반대 성별 새로 담기 | **막지 않는다** | 이미 열린 상세(성별 토글 설계의 "수용한 구멍 2")에서만 닿는 드문 경로다. 담기면 원본에 들어가고 보관함에서는 숨은 수에 잡힌다 |

### 경계 — 세 후보와 기각 사유

| | 어디서 자르나 | 판단 |
|---|---|---|
| A | data 레이어(`fetchAccountWishes` 또는 공유 저장소) | **기각.** 하트 판정·담기 스냅숏·500 상한이 함께 깨진다. 승계 경로와도 인접해진다 |
| B | `useWishlist`가 원본과 화면용을 둘 다 반환 | **기각.** 이 훅은 상세 화면도 쓴다 — 원본만 필요한 자리에 이름이 비슷한 배열이 하나 더 생기고, 실수로 화면용을 쓰면 곧바로 데이터가 사라지는 종류의 버그가 된다 |
| **C** | `useWishlist`는 원본만. **보관함 전용 파생 훅** 하나가 성별을 읽어 화면용을 만든다 | **채택.** 원본 경로를 한 줄도 건드리지 않는다. 보관함 세 화면이 전부 그 훅을 통과하므로 "한 화면만 필터가 안 걸리는" 누락도 막는다 |

C의 부수 효과로, **건드리지 말라고 지정된 파일들을 하나도 열지 않는다** —
`shared/signals/**`·`account-wish-actions.ts`(열린 PR #74) · `use-feed-view-model.ts` ·
`shared/profile/**` · `backend/**`.

**단, 보관함 폴더 하나로는 끝나지 않는다**(교차 리뷰에서 정정). 담기 시트는 보관함 컴포넌트지만
그리는 목록을 **상세 화면(`features/feed/detail/.../product-detail.tsx`)이 넘겨준다.** 그래서 그
파일의 **넘겨주는 목록 한 자리**를 화면용으로 바꾼다. 같은 파일의 하트 판정·담기·빼기는 원본을
그대로 쓴다. 이 파일은 금지 목록에 없고 변경도 배선 한 줄 수준이지만, "보관함 폴더 안에서만
끝난다"는 표현은 사실과 다르므로 여기에 적어 둔다.

## 구조

```
features/feed/wishlist/
  domain/            # ← 판정 규칙 + "보이는 목록·숨은 수"를 내는 순수 함수 (새로 추가)
  presentation/
    view-model/      # ← 보관함 전용 파생 훅 (새로 추가)
                     #   기존 use-wishlist-folders / use-folder-detail 이 이 훅을 통과하게 바꾼다
                     #   폴더 상세는 보이는 수·원본 수·숨은 수를 따로 내보낸다
    components/      # ← 숨김 안내 한 줄, 빈 화면 분기, 삭제 확인 문구의 개수 출처
features/feed/detail/presentation/components/
  product-detail.tsx # ← 담기 시트에 넘기는 목록만 화면용으로 (하트·담기·빼기는 원본 그대로)
```

의존 방향은 frontend/AGENTS.md 그대로다 — presentation → domain, domain은 아무것도 import하지
않는다(성별 값은 인자로 받는다). 성별을 읽는 곳은 **파생 훅 한 곳뿐**이고, 이미 있는
`shared/gender/use-gender-setting.ts`를 쓴다(새로 만들지 않는다).

## 데이터 흐름

1. 계정 찜 전체가 공유 저장소에 있다 — **지금과 같다. 바뀌지 않는다.**
2. 보관함 화면이 파생 훅을 부른다 → 훅이 원본과 현재 성별 설정을 domain 순수 함수에 넣는다.
3. 순수 함수가 **보이는 목록**과 **숨은 수**를 낸다. 성별이 `null`이면 원본을 그대로 낸다.
4. 폴더 요약·폴더 상세는 **보이는 목록**으로 기존 순수 함수(`summarizeFolders`·`entriesInFolder`)를
   그대로 통과한다 — 개수와 썸네일이 함께 화면용이 된다.
5. 상세 화면의 하트·담기·빼기, 그리고 로그인 승계는 **2~4를 거치지 않는다.**

**설정이 바뀌면:** 성별 저장소를 구독하고 있으므로 재요청 없이 다시 계산된다. 다른 탭의 변경도
루트 레이아웃의 `GenderAccountGuard`가 `bindCrossTabGender`를 걸어둬 같은 경로로 들어온다.

## 화면에서 달라지는 것

- **폴더 그리드** — 타일 개수·썸네일이 보이는 것 기준. 안내 문구 없음. 헤더의 보관함 총 개수도 같다.
- **폴더 상세** — 목록·헤더 개수가 보이는 것 기준. 숨김이 1개 이상이면 목록 위에 한 줄.
- **전부 숨은 폴더** — 지금 뜨는 `"이 폴더는 아직 비어 있어요"`는 사실과 다르다. 이 경우엔 그 문구
  대신 **숨김 안내 한 줄만** 보인다. 원본까지 비었을 때만 기존 빈 화면 문구를 쓴다.
- **폴더 삭제 확인** — `"담긴 찜 N개는 기본 폴더로 이동해요"`의 N은 **원본 개수**.
- **담기 시트** — 폴더별 개수·썸네일이 그리드와 같은 기준(보이는 것).
- **상세 화면** — 변화 없음.

## 오류·경계 상황

| 상황 | 동작 |
|---|---|
| 성별 미확정(`null`) | 필터 없음. 원본 전부 |
| 성별 저장소를 못 읽음 | 기존 규칙대로 `null`로 떨어진다 → 필터 없음 |
| 상품의 성별 라벨이 없음(`null`) | 미상으로 보고 숨긴다 |
| 계정 찜 읽기 실패 | 기존 알림(`notice`) 그대로. 이 조각이 바꾸지 않는다 |
| 로그아웃 | 기존대로 저장소를 비운다. 파생 훅은 빈 목록을 받는다 |

## 테스트

- **domain 순수 함수** — 남성/여성 각각에서 반대 성별·공용·미상이 빠지는지, `null`이면 원본이
  그대로 나오는지, 숨은 수가 원본−보이는 수와 같은지, 빈 목록.
- **기존 테스트가 깨지지 않는 것** — `wish-folders.test.ts`·`wishlist.test.ts`는 원본 규칙이라
  그대로 통과해야 한다. 깨지면 경계를 잘못 그은 신호다.
- **브라우저 관찰** — 아래 완료 기준.

## 완료 기준 (관찰 가능한 것)

1. 반대 성별·공용 상품이 담긴 폴더를 열면 그 상품이 **안 보이고**, 헤더 개수도 그만큼 줄어 있고,
   목록 위에 숨김 안내 한 줄이 있다.
2. 설정에서 성별을 반대로 바꾸면 같은 폴더의 목록과 개수가 **즉시 뒤집힌다**(새로고침 없이).
3. 숨긴 상품의 상세를 열면 하트가 **채워져 있다**. 눌러서 빼면 보관함 원본에서도 사라진다.
4. 폴더 그리드의 타일 개수와, 그 폴더를 열었을 때 보이는 장 수가 **같다**.
5. 옛 기기 찜을 심어두고 로그인하면 **반대 성별 것까지 전부** 계정으로 올라간다(승계 후 설정을 그
   반대 성별로 바꿔 보면 올라온 것이 보인다). 이 조각에서 가장 위험한 지점의 확인이다. 심는 방법은
   둘 중 하나이고, **어느 쪽을 썼는지 기록에 적는다**:
   - **업로더만 확인** — `atee-wishlist-migrate`에 `{ product: { goodsNo } }` 목록을 직접 넣는다.
     옮기기 단계를 건너뛰므로 탭 표식과 무관하게 재현된다.
   - **옮기기까지 확인** — `atee-wishlist`에 넣는다. 이때는 **직전 탭 표식이 익명**이어야 옮기기가
     돈다(로그아웃 상태로 앱을 한 번 연 뒤 로그인). `atee-wishlist-migrate`에 남은 값이 있으면
     덮어쓰지 않으므로 미리 비운다.
6. 전부 숨은 폴더에서 `"아직 비어 있어요"`가 뜨지 않는다.
7. `npm run check`(lint·typecheck·format·test) 통과.

## 범위 밖

- 숨긴 것을 화면에서 임시로 펼쳐 보는 토글 — 하드 필터 정책(설정이 항상 이긴다)에 예외를 만든다.
- 보관함에도 성별 게이트를 거는 것 — 게이트 배치를 바꾸는 별개 작업이다.
- 찜을 담을 때 반대 성별을 막는 것.
- `#63` 죽은 코드 정리, DB·서버 함수 변경(이 조각은 **프론트엔드 전용**이다).

## 보장하지 못하는 것
