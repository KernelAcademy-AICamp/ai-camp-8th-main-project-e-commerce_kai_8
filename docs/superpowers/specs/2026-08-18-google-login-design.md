## 0. 배경 — 지금 상태

aTee는 **계정 개념이 아예 없다.**

- 사용자 식별 = `localStorage`의 익명 기기 ID(`atee-device-id`). 개인정보와 연결되지 않는 가명 ID.
- 찜(`atee-wishlist`)·취향 프로필(`atee-profile`)은 **전부 기기 localStorage**. 서버에는 행동 이벤트만 기기 ID로 쌓인다.
- Supabase는 브라우저에서 공개(anon publishable) 키로 REST RPC만 호출한다. 인증 SDK를 쓰지 않고 서버 비밀키도 없다.
- 설정 화면의 개인화 고지와 수집 방침 문서는 **"회원가입 없이"**, **"이름·연락처·계정 같은 개인정보를 묻거나 저장하지 않습니다"** 라고 명시한다.

따라서 "구글 로그인 추가"는 기능 하나를 붙이는 일이 아니라, **계정이라는 개념을 처음 들여오는 일**이다.

## 1. 합의된 전제 (사람이 결정)

| 항목 | 결정 |
|---|---|
| 최종 목표 | 찜과 취향 프로필을 계정에 저장해 기기 간 동기화 |
| 로그인 게이트 | **찜은 로그인 필수(하드 게이트)**. 피드·검색·상세는 비회원 그대로 |
| 기존 익명 데이터 | **승계하지 않고 버린다** (깨끗한 시작) |
| 인증 제공자 | **Supabase Auth + Google provider** |
| Supabase 프로젝트 | 공유 프로젝트를 **aTee 전용 Auth로 사용**. ecommerce는 중단됐고 Auth를 쓰지 않는다 |
| 세션 보관 | **쿠키(SSR)** |
| 계정 삭제 | **본인만 자기 계정을 지우는 DB 함수** (서버 비밀키 도입 없음) |
| 신원 전환 시 서버 기록 | **남긴다.** 기기 ID를 **회전하지 않으므로** 삭제 손잡이도 지금 그대로 하나다 |
| preview 배포 로그인 | **제외.** 허용 목록에 로컬·프로덕션 정확 URL만 등록하고 preview 와일드카드를 열지 않는다 |
| 보안 헤더 | 인증 경로 **캐시 차단 + 기본 보안 헤더**까지. CSP는 별도 조각(§4에 미완료 위험으로 명시) |
| 이번 스펙 범위 | **조각 1(로그인·로그아웃·계정 삭제)만**, 사용자에게 노출 |

### 조각 나누기 (배포 가능한 단위)

| 조각 | 내용 | 완료 기준 |
|---|---|---|
| **1 (이 문서)** | 구글 로그인·로그아웃·계정 삭제·고지 갱신 | 구글로 로그인하면 설정에 내 계정이 보이고, 새로고침해도 유지되고, 로그아웃하면 사라지고, 계정 삭제를 누르면 다시 로그인했을 때 새 사용자로 시작한다 |
| 2 (별도 스펙) | 찜을 계정 데이터로 | 로그아웃 상태에서 찜 누르면 로그인 유도. 로그인 후 찜하면 다른 브라우저에서도 같은 찜이 보인다 |
| 3 (별도 스펙) | 취향 프로필을 계정에 | 다른 기기에서 로그인하면 피드가 같은 취향으로 뜬다 |

조각 1을 사용자에게 그대로 노출한다. **이 조각만으로 사용자가 얻는 기능은 없다** — 이건 알고 받아들이는 선택이다. 근거: 아직 실사용자가 없고(익명 데이터를 버려도 된다는 결정이 이를 전제한다), 로그인 후 보여줄 가치("내가 많이 고른 것" 취향 요약)는 기획이 끝나지 않았다. 그 기획이 서면 별도 조각으로 만든다.

### 인증 제공자를 Supabase Auth로 고른 이유 (근거 정정)

**정정**: 1차 초안은 "Supabase Auth를 쓰면 토큰이 그대로 기존 RLS에 흘러든다"고 적었다. **틀렸다.** RLS의 `auth.uid()`는 요청의 `Authorization: Bearer` 헤더에서 만들어지는 문맥이고, 앱 쿠키가 Supabase REST로 자동 전달되지 않는다. 현재 RPC 호출은 공개 키만 보내므로 로그인 뒤에도 계속 익명 역할로 돈다.

정정된 근거는 이렇다.

- 백엔드가 이미 Supabase다. 계정 데이터 경로에서 **토큰을 요청에 붙이기만 하면** 이미 있는 RLS·역할 체계를 그대로 쓴다 — 별도 권한 계층을 새로 만들 필요가 없다.
- Clerk(Vercel 마켓플레이스 네이티브)는 로그인 UI가 가장 빠르지만, 찜을 Supabase에 저장하는 순간 Clerk↔Supabase 연동이 추가로 필요하고 계정·과금·대시보드가 둘로 늘어난다.
- Auth.js 직접 구성은 세션·토큰 서명·RLS 연결이 전부 우리 몫이 되고 지금 얻는 게 없다.

## 2. 설계 ① — 구조와 로그인 흐름

### 세션 보관: 쿠키 (선택과 그 대가)

세션을 **쿠키**에 둔다. 브라우저 클라이언트가 세션을 직접 들고 요청마다 토큰을 붙이는 방식이 지금 요구만 보면 더 작다(서버가 사용자를 알아야 하는 경로가 아직 없다). 쿠키를 고른 이유는 서버에서 계정을 읽을 경로를 미리 확보해 두기 위함이며, **그 대가로 아래를 이 조각에서 함께 정한다**:

- **토큰 갱신 주체** — 서버 컴포넌트는 쿠키를 쓸 수 없으므로 요청 경로에서 갱신하는 계층이 필요하다. Next.js 16에서 `middleware`가 `proxy`로 이름이 바뀐 점을 반영한다.
- **서버에서의 신뢰 기준** — 저장된 세션 값을 그대로 믿는 조회가 아니라 검증된 사용자/클레임 조회를 권한 판정에 쓴다.
- **쿠키 속성** — 프로덕션 `Secure`·`SameSite` 설정. 이 방식의 쿠키는 JS가 읽으므로 `HttpOnly`가 아니다.
- **캐시 차단 (필수 산출물)** — 세션을 갱신하며 쿠키를 내려주는 응답이 공유 캐시에 들어가면 **다른 사용자에게 세션이 전달된다.** 인증이 관여하는 경로는 동적으로 처리하고 사설·비저장 캐시 정책을 명시한다. 갱신 계층의 적용 범위(어느 경로에 도는지)도 함께 정한다.
- **기본 보안 헤더 (필수 산출물)** — 현재 `next.config.ts`에 헤더 설정이 전혀 없다. 기본 보안 헤더를 추가한다.
- **CSP는 이 조각에 넣지 않는다 (미완료 위험으로 명시)** — 콘텐츠 보안 정책은 Tailwind·프레임워크의 인라인 스타일 때문에 조율 범위가 크다. 별도 조각으로 분리한다. **그때까지는 XSS가 발생하면 세션 토큰까지 읽힐 수 있다** — 쿠키 세션을 택한 대가이며, 알고 남겨두는 위험이다.
- **사용하는 라이브러리가 beta**라는 점을 인지하고 채택한다.

### 로그인 흐름

1. 설정 화면의 "구글로 계속하기" → Supabase가 구글 동의 화면으로 리다이렉트
2. 동의 후 앱의 콜백 경로로 인가 코드와 함께 복귀
3. 콜백이 코드를 세션으로 교환해 쿠키에 심고, 사용자를 출발 지점(설정 화면)으로 되돌린다

Google 클라이언트 ID/시크릿은 **Supabase 대시보드에만** 넣는다 — repo·`.env`에 새 비밀값이 생기지 않는다. 기존 공개 환경변수 두 개를 그대로 쓴다.

### 로그아웃 범위

로그아웃은 **이 기기만** 끊는다. Supabase의 로그아웃 기본값은 모든 기기의 세션을 끊는 전역 범위이므로, 기기 단위 로그아웃을 명시적으로 지정한다. "같은 브라우저의 다른 탭도 로그아웃 상태로 수렴한다"와 "다른 기기는 유지된다"는 별개 계약이며, 둘 다 완료 기준에서 관찰한다.

### 신원 전환 (리뷰 ①-2·2차 ①-1·①-2 대응)

같은 브라우저에서 A가 로그아웃하고 B가 로그인해도 B가 A의 찜과 개인화 피드를 보는 문제를 조각 1에서 닫는다.

**v2의 절차는 폐기한다.** v2는 "미전송 이벤트 큐를 기존 기기 ID로 먼저 전송한 뒤 ID를 회전한다"고 적었으나, 현재 큐는 한 번에 최대 50건만 보내고 전송 실패를 삼키며 잔여 여부를 호출자에게 알리지 않는다(상한 500건). 즉 **선전송이 완료를 보장하지 못하고**, 남은 이벤트는 전송 시점의 기기 ID를 붙이므로 **새 신원에 귀속된다.** 다중 탭에서는 다른 탭의 메모리 큐가 회전 후에 비워지며 같은 일이 벌어진다.

#### 기기 ID를 회전하지 않는다 (핵심 결정)

v2·v3는 신원 전환 때 기기 ID를 새로 발급했다. **조각 1에서는 회전하지 않는다.**

회전이 만드는 문제는 전부 파생 문제였다 — 이미 저장된 큐에 귀속 정보가 없고, 신호 세션 ID·노출 ID·검색 로그가 전송 시점의 ID를 참조하고, 옛 ID를 보관할 목록·상한·재시도 원장이 필요해지고, 기기별로 나뉜 전송의 부분 실패 계약이 필요해진다. 이 모두가 **조각 1의 가설("구글 로그인이 동작한다")과 무관한 신호 시스템 개조**다.

사람이 요구한 것은 **"B가 A의 찜·취향을 보면 안 된다"**이며, 그것은 로컬 상태를 비우면 충족된다. 회전은 거기에 더해 *서버 신호까지* 신원별로 나누려는 것이고, 그것은 프로필이 계정 소유가 되는 **조각 3의 문제**다.

- **대가**: 같은 브라우저에서 A와 B의 서버 행동 이벤트가 한 기기 ID 아래 섞인다. 개인화는 클라이언트가 보내는 프로필 요약으로 계산되고 그 프로필은 지우므로 **개인화는 새지 않는다.** 섞이는 것은 추천 품질 평가용 표본이다.
- **얻는 것**: **기존 삭제 경로를 전혀 변경하지 않는다** — 기기 ID 하나, 삭제 손잡이 하나. 과거 ID 목록·상한·원장·이벤트 스키마 변경·기존 큐 이관이 전부 불필요해진다. (기존 삭제 경로 자체에 이미 있는 결함은 §4-1 참고 — 이번 변경이 만들거나 악화시키지는 않지만, "삭제 약속이 온전하다"는 뜻은 아니다.)
- **이월**: 서버 신호의 신원별 분리는 **조각 3의 선행 과제**로 명시한다. 그때는 프로필이 계정 소유가 되므로 신호 귀속도 함께 설계해야 한다.

#### 전환 시 하는 일

전환 판정은 **`없음→사용자`, `사용자 A→사용자 B`, `사용자→없음` 세 가지뿐**이다. 최초 세션 복원·토큰 갱신·중복 로그인 이벤트는 신원 전환이 아니므로 처리하지 않는다.

전환 시 **로컬 상태만** 비운다: 찜, 장기 취향 프로필, 세션 취향 프로필, 신호 세션, 노출 맵. **저장소 키뿐 아니라 메모리 캐시까지** 비운다 — 현재 찜 저장소는 모듈 메모리 캐시를 따로 들고 있어 키만 지우면 UI에 남는다.

**이미 화면에 올라온 피드도 함께 버린다.** 피드 화면은 받아온 상품 목록·커서·소진 상태·중복 방지 집합을 신원과 무관하게 들고 있다. 이걸 비우지 않으면 A의 개인화 결과가 B에게 계속 보이고, 다음 요청의 결과가 A의 목록 **뒤에 이어 붙는다.**

**이전 신원에서 시작한 응답은 폐기한다.** 전환 전에 보낸 피드·개인화 요청이 전환 후 도착하면 적용하지 않는다. 전환마다 증가하는 표식을 두고, 응답이 도착했을 때 표식이 바뀌었으면 버린다.

기기 ID와 미전송 이벤트 큐는 건드리지 않는다.

#### 다중 탭과 중단 복구

- **지속 저장소(찜·장기 프로필)**: 어느 탭이든 한 번 비우면 모두에게 비워진다. 어느 신원의 데이터인지 나타내는 **표시자를 기기에 함께 남긴다.**
- **탭별 상태(찜 캐시·노출 맵·세션 프로필·피드 목록)**: 각 탭이 마지막으로 처리한 신원을 기억하고, 현재 세션과 다르면 자기 것을 비운다. 탭끼리 공유 상태를 고쳐 쓰지 않으므로 경합이 없고, 여러 번 실행돼도 결과가 같다.
- **탭별 표식은 새로고침을 견뎌야 한다.** 다른 탭이 공유 표시자를 이미 B로 바꾼 뒤 오래된 탭이 새로고침되면, 그 탭의 메모리 표식은 사라진다. 이때 공유 표시자만 보면 "이미 처리됨"으로 판단해 **그 탭 세션 저장소에 남은 A의 세션 프로필을 놓친다.** 그 상태로 피드 요청이 나가면 세션 ID가 달라졌으므로 **A의 세션 프로필이 방금 비운 장기 프로필로 다시 합쳐진다.** 탭별 표식을 새로고침 후에도 구분 가능한 곳(탭 수명 저장소)에 두거나, **표식이 없는 탭은 무조건 자기 상태를 비우는** 보수적 초기화를 한다.
- **순서 계약**: 프로필을 읽거나 쓰기 **전에** 신원을 확인한다 → 탭 상태를 비운다 → 지속 상태를 비운다 → 처리 표식을 확정한다. 이 순서를 어기면 위 fold가 일어난다.
- **일시 중지됐다 깨어난 탭**: 전환 이벤트를 놓쳤어도 위 비교로 깨어날 때 스스로 비운다. Supabase 클라이언트가 탭 사이로 인증 이벤트를 전파하지만, 그 전파에만 의존하지 않는다.
- **콜백 직후 탭이 닫힌 경우**: 앱 시작 시 표시자와 현재 세션 사용자를 비교해, 다르면 **개인화 화면(찜·개인화 피드)을 그리기 전에** 전환을 수행한다.

### 폴더 배치 (`frontend/AGENTS.md` 규칙)

```
features/auth/
  domain/          세션 상태 전이 등 순수 규칙
  data/            브라우저/서버 Supabase 접근, 로그인·로그아웃·계정 삭제 호출
  presentation/
    components/    구글 로그인 버튼, 설정의 "계정" 섹션
    view-model/    세션 구독 훅 (로그인 상태·로딩·에러)
app/auth/callback/ 프레임워크 어댑터 — 요청/응답 변환과 리다이렉트만
```

콜백 경로는 **어댑터로만** 남긴다. 코드 교환·오류 분류·안전한 복귀 위치 판정은 auth의 data/domain 경계가 맡는다 (`app/`은 라우팅·조립 전용이라는 규칙).

표시 이름 도출 같은 규칙은 만들지 않는다. 이번 조각의 관찰값은 "내 계정 이메일이 보인다"뿐이다.

### transport 경계 계약 (리뷰 ②-2 대응 — 조각 2에서 어길 수 없게 여기 못박는다)

현재 RPC 실행 권한이 **균일하지 않고, 문서화된 의도와도 다르다**:

| 함수 | 명시된 grant | 실제 |
|---|---|---|
| `c_feed_page` · `c_mix_page` · `c_search_page` · `c_search_page_v2` · `c_log_search` 등 | `anon, authenticated` (+ `revoke from public`) | 의도대로 |
| `c_similar_page` · `c_log_events` · `c_forget_device` | `anon`만 | **`revoke ... from public`이 없다.** PostgreSQL 함수는 기본적으로 `PUBLIC`에 실행 권한이 있으므로 **`authenticated`도 호출된다** |

**정정**: v2~v4는 "인증 transport로 갈아끼우면 이 셋이 권한 오류가 난다"고 적었으나 **사실이 아니다.** 새 스키마에서 clean bootstrap해도 `PUBLIC` 경로로 실행된다. (anon도 이미 호출 가능하므로 새로 열린 노출은 아니지만, "DB가 잘못된 transport를 거부한다"는 근거로 쓸 수 없다.)

transport 분리는 **토큰이 어디로 나가는지에 대한 책임 경계**로서 여전히 필요하다. 다만 그 강제는 아래 수단으로 하고, 현재 DB 상태를 근거로 삼지 않는다.

계약 — **문서 규약만으로는 강제되지 않으므로 기계가 막는 수단을 함께 둔다**:

- **공개 카탈로그·기기 신호용 익명 transport**(현재 `shared/supabase-rpc.ts`)와 **계정 데이터용 인증 transport**를 분리해 유지한다. 조각 2·3에서 기존 helper의 전역 교체를 금지한다.
- **DB를 최종 경계로 삼는다.** 계정용 함수·테이블은 `PUBLIC`과 `anon`의 권한을 회수하고 `authenticated`와 RLS만 허용한다. 문서가 아니라 DB가 거부한다.
- **인증 클라이언트를 feature 전역에 노출하지 않는다.** 계정 데이터는 명시된 저장소 메서드로만 접근하고, 임의 함수명 문자열을 받는 통로를 두지 않는다.
- **import 경계를 lint로 막는다.** 피드·검색·신호 쪽에서 계정 transport를 import하거나, 계정 data에서 익명 helper를 import하면 검사에 실패하게 한다 (현재 ESLint에 레이어 제한 규칙이 없다).
- 기존 RPC의 권한을 손대려면 입력 방어·회귀 테스트를 포함한 **별도의 원자적 변경**으로 다룬다. 위 표의 `PUBLIC` 미회수는 이번 조각에서 고치지 않는다(§4-1에 기록).

### 이번에 건드리지 않는 것

- 피드·검색·유사·신호 RPC 호출 경로 — 지금처럼 익명 키로 계속 돈다
- 찜의 서버 저장·하드 게이트, 취향 프로필 동기화

## 3. 설계 ② — 화면·경계 조건·검증

### 화면

설정 화면(`/settings`) 최상단에 **"계정" 섹션**을 새로 둔다. 기존 개인화 고지·초기화 섹션은 그 아래 그대로 유지한다.

- 로그아웃 상태: "구글로 계속하기" 버튼. **로그인하면 뭐가 좋아지는지는 아직 적지 않는다** — 이 조각에서는 실제 이점이 없으므로 그렇게 쓰면 오해가 된다. 지금은 "다음 업데이트에서 찜을 계정에 저장할 예정"처럼 사실만 적는다.
- 로그인 상태: 구글 계정 이메일 + "로그아웃" + "계정 삭제"
- 판정 전(세션 확인 중): 자리를 차지하는 로딩 표시. 로그아웃 UI를 먼저 보였다가 로그인 UI로 튀는 깜빡임을 만들지 않는다.

피드·검색·상세 화면은 이번 조각에서 바뀌지 않는다.

### 계정 삭제

**본인만 자기 계정을 지우는 DB 함수**를 마이그레이션으로 추가한다. 서버 비밀키를 도입하지 않는다.

#### 함수의 보안 계약

- 호출자의 인증 주체를 기준으로 **자기 자신만** 삭제한다. 인자로 대상 사용자를 받지 않는다.
- **`authenticated`에만 권한을 준다는 문장만으로는 부족하다.** PostgreSQL 함수는 생성 시 기본적으로 모든 역할(`PUBLIC`)이 실행할 수 있다. 함수를 만드는 **같은 마이그레이션·같은 트랜잭션에서** `PUBLIC`과 `anon`의 실행 권한을 명시적으로 회수하고 `authenticated`에만 부여한다 — 외부에 열린 순간이 없어야 한다. (Supabase에서는 회수 시 역할을 명시해야 한다.)
- 정의자 권한으로 도는 함수이므로 **검색 경로를 빈 값으로 고정**하고 참조하는 모든 객체를 스키마까지 적는다. 함수 소유자는 사용자 삭제 권한을 가진 신뢰된 역할로 고정한다.
- **인증 주체가 없으면 먼저 오류를 낸다.** 그냥 두면 "0건 삭제"가 되어 성공으로 오인된다.
- **재호출 계약**: 0건 삭제는 **멱등 성공**으로 본다 (이미 지워진 것). 아래 대상 확인 절차가 "다른 계정을 지우는" 사고를 막으므로, 0건을 오류로 만들 이유가 없다.

#### 삭제와 세션의 관계

DB 삭제와 브라우저 세션 폐기는 **원자적이지 않다.** 커밋 뒤 응답이 유실되거나 로그아웃이 실패하면 계정은 지워졌는데 화면은 로그인 상태로 남는다. 반대로 서버 권한 판정이 서명·만료만 확인하면 삭제된 사용자의 토큰도 만료 전까지 통과한다.

- 삭제 호출은 **재시도 가능**해야 하고, UI는 **성공 / 이미 삭제됨 / 응답 불명**을 구분한다.
- 서버 결과와 무관하게 로컬 인증 쿠키 제거를 시도하되, **"서버 계정 삭제 완료"는 확인된 경우에만** 표시한다.
- 즉시 삭제 여부를 확인해야 하는 판정에는 인증 서버에 실제로 물어보는 조회를 쓴다.

**응답 불명 뒤의 재시도는 대상을 반드시 확인한다 (중요).** 삭제가 DB에서 성사됐는데 응답만 유실된 경우, 사용자가 같은 구글 계정으로 다시 로그인하면 **새 사용자(다른 UUID)**가 만들어진다. 이때 "재시도"를 그대로 수행하면 인자 없는 자기 삭제 함수는 이전 계정이 아니라 **방금 만든 새 계정을 정상적으로 삭제한다.** 이건 멱등성이 아니라 데이터 파괴다.

- 삭제를 요청하기 **전에** 대상의 **인증 사용자 식별자와 구글 제공자 신원을 함께** "삭제 대기" 표식으로 남긴다. 표식이 **실제로 저장됐는지 다시 읽어 확인한 뒤에만** 삭제를 호출한다 — 저장소 차단·용량 초과로 표식이 남지 않았는데 파괴 호출부터 보내면 보호 장치가 없다.
- 응답 불명 뒤 다시 로그인하면 **제공자 신원부터 비교**한다.
  - **제공자 신원이 다르다** = 다른 구글 계정으로 로그인한 것. 원래 계정이 지워졌는지 알 수 없으므로 **표식을 유지하고**, 원래 계정으로 로그인해야 마무리된다고 안내한다. (사용자 식별자만 비교하면 이 경우를 "삭제 성공"으로 오판해 손잡이를 버린다.)
  - **제공자 신원이 같고 사용자 식별자가 다르다** = 첫 삭제가 성공하고 재가입된 것. **재호출하지 않고** 표식을 지운다.
  - **둘 다 같다** = 삭제가 서버에 닿지 않았다. 사용자 재확인을 거쳐 다시 삭제한다.
- 삭제가 확인되면 표식을 지운다.

#### 오조작 방지

- 삭제 대상 이메일을 보여주는 **명시적 재확인 단계**를 둔다 (기존 "개인화 데이터 모두 지우기"의 확인 단계와 같은 형태).
- 진행 중 **중복 호출을 차단**하고, 실패·응답 유실 뒤 다시 시도하는 흐름을 제공한다.

#### 남는 것 / 조각 2로 넘기는 것

- **이미 발급된 액세스 토큰은 만료까지 유효하다.** 조각 1에는 계정에 붙은 데이터가 없어 노출되지 않는다. 조각 2의 **선행 조건**으로 지금 못박는다: 계정 소유 테이블은 사용자 행을 실제 외래키로 참조하고 **삭제가 연쇄되게** 한다. 조각 2의 게이트 = "삭제 직전에 확보한 토큰으로 계정 행을 읽거나 쓸 수 없다 / 모든 계정 행이 사라진다 / 다시 로그인해 받은 새 사용자에게 이전 행이 승계되지 않는다".
- 탐색 이력(행동·검색 로그)은 여전히 **기기 ID**로 지운다. 설정의 "개인화 데이터 모두 지우기"가 그 수단이다.
- **"계정과 기기 ID를 연결하지 않는다"의 정확한 뜻**: **서버에 정본 매핑을 만들지 않는다**는 뜻이다. 기기에는 안정적인 기기 ID와 "현재 신원이 누구인지 비교할 수 있는 표시자"가 함께 남으므로, **로컬에서는 상관관계가 존재한다.** 고지에 이 한정을 그대로 적는다 — "연결이 전혀 없다"고 쓰면 사실이 아니다. CSP를 미룬 기간에는 XSS가 이 표시자도 읽을 수 있다는 잔여 위험에 포함한다.
- **계정 삭제는 인증 감사 로그까지 지우지 않는다.** 사용자가 "계정 삭제"를 전체 인증 이력 삭제로 오해하지 않도록, 남는 기록의 범위와 보존 기간을 확인해 수집 방침과 공개 처리방침에 적는다. **확인되지 않은 보존 기간은 숫자를 지어내지 말고 미정으로 남긴다.**

### 고지·정책 갱신 (조각 1 필수 범위)

구글 로그인을 붙이는 순간 현재 고지는 **사실이 아니게 된다**. 아래를 모두 갱신한다.

1. **수집 방침 문서** — "계정 정보를 저장하지 않는다", "기기 ID는 계정과 연결되지 않는다" 문장을 실제와 맞춘다
2. **설정 화면 고지 문구**
3. **최초 방문 배너의 저장소 키 버전을 올린다** (`...-seen-v2` → v3). 저장소 주석 자체가 "수집 범위가 늘면 키를 올려 이미 확인한 사용자에게도 다시 보여라"라고 규정한다
4. **공개 privacy policy 페이지** — 구글은 프로덕션 OAuth 앱에 대해 홈페이지와 동의 화면에서 접근 가능한 개인정보 처리방침을 요구한다. 현재 없다

받는 항목은 **구글 로그인의 필수 범위(식별자·이메일·기본 프로필)로 한정**하고, 그 밖의 범위를 추가로 요청하지 않는다. 실제로 저장되는 것은 사용자 행 외에 연결된 제공자 정보와 세션·최종 로그인 시각이며, 인증 감사 로그에 로그인·갱신·로그아웃과 IP·User-Agent가 남는다는 점까지 고지에 반영한다.

### PRD·결정 기록 갱신 (조각 1 필수 범위)

PRD와 결정 기록(O-12·O-24)은 **"가입 시 기기 프로필을 계정으로 승계한다"**고 명시한다. 이번에 "승계하지 않고 버린다"로 정했으므로, 문서를 먼저 갱신하지 않으면 후속 구현자가 반대 계약을 따르게 된다. 결정 기록에 새 항목으로 남긴다.

### 경계 조건

| 상황 | 처리 |
|---|---|
| 동의 화면에서 취소(`access_denied`) | 설정 화면으로 조용히 복귀. 오류 문구 없이 원래 상태 |
| 구성·네트워크 오류 | 취소와 **구분해서** "로그인에 실패했습니다" 표시. 다시 시도 가능 |
| 콜백 새로고침·뒤로가기·이미 쓴 코드 재제출 | 인가 코드는 1회용이라 재사용 자체는 차단된다. **이때 이미 성립한 유효 세션을 실패 UI로 덮지 않는다** |
| 세션 만료 | 갱신 계층이 처리한다. 요구되는 결과는 "만료 시간이 지나 다시 열어도 로그인 상태가 유지된다" |
| 같은 브라우저 여러 탭 | 한 탭에서 로그아웃하면 다른 탭도 로그아웃 상태로 수렴 |
| 다른 기기의 세션 | 로그아웃해도 유지된다 (기기 단위 로그아웃) |
| 프라이빗 모드·쿠키 차단 | 로그인 실패를 알리고, 비회원 탐색은 계속 되게 둔다 |
| PWA standalone 복귀 | **이번 조각의 완료 기준에서 제외.** 이 repo에는 web app manifest·서비스워커가 없어 설치형 standalone이 아직 존재하지 않는다. PWA를 실제로 만들 때 지원 브라우저 매트릭스와 함께 검증한다 — **미검증** |

### 리다이렉트 허용 목록

허용 목록은 **정확한 URL 두 개**뿐이다. 와일드카드를 쓰지 않는다.

- **프로덕션**: 프로덕션 도메인의 정확한 콜백 URL 하나
- **로컬**: `localhost`로 통일한 개발 서버의 정확한 콜백 URL 하나. 현재 `backend/supabase/config.toml`의 Site URL은 `http://127.0.0.1:3000`이고 추가 허용 목록은 `https://127.0.0.1:3000`(콜백 경로 없음, 게다가 https)이라 **그대로는 동작하지 않는다.** `localhost`와 `127.0.0.1`은 서로 다른 호스트로 취급되므로 개발 서버 접속 origin과 콜백 origin을 `localhost`로 맞추고 config를 갱신한다.
- **preview: 등록하지 않는다 (결정).** Vercel preview는 배포마다 주소가 바뀌어 패턴이 필요한데, 패턴을 열면 **그 범위의 모든 배포가 프로덕션 OAuth의 신뢰된 진입점**이 된다. preview에서는 로그인이 동작하지 않으며 피드·검색만 확인한다. 이 제약을 PR 확인 절차에 적는다.

### 검증

완료 기준은 **관찰 대상을 지정한다.** "된다"가 아니라 무엇을 보고 판정하는지를 적는다.

**자동 — 세 층으로 나눈다** (단위 테스트만으로는 부족하다):

- **단위(vitest)**: 신원 전환 판정(세 가지 전환만 처리하고 토큰 갱신·중복 이벤트는 무시), 전환 시 비우는 로컬 상태 목록, 삭제 대기 표식과 현재 사용자 비교 규칙
- **브라우저 통합**: 두 탭 동시 전환, 일시 중지 후 복귀한 탭, 콜백 직후 탭 종료 뒤 재시작에서 **로컬 상태가 남지 않는지**
- **DB 통합(빈 스키마)**: 계정 삭제 함수의 권한 행렬 — `PUBLIC` 거부 / `anon` 거부 / 토큰 없는 호출 거부 / 자기 자신 삭제 성공 / 재호출 계약 / **타 사용자 생존**. 객체가 이미 있는 DB에서 검증하면 거짓 통과가 난다

**수동(완료 기준)** — 아래를 전부 관찰한다:

| # | 조작 | 관찰 대상 |
|---:|---|---|
| 1 | 구글 계정으로 로그인 | 설정에 내 이메일이 보이고, **인증 사용자 ID를 함께 기록**한다 |
| 2 | 새로고침 | 화면만이 아니라 **서버가 확인한 사용자**도 같은 사용자다 |
| 3 | 두 탭을 열고 한 탭에서 로그아웃 | 다른 탭이 **새로고침 없이 정해둔 상한 시간 안에** 로그아웃되고, 그 탭의 **찜 목록과 다음 피드 요청에 실린 프로필 값**이 비어 있다. 별도 브라우저의 세션은 **유지**된다 |
| 3-1 | 한 탭을 백그라운드로 오래 둬 일시 중지시킨 뒤, 다른 탭에서 로그아웃 → 로그인하고 그 탭으로 복귀 | 복귀한 탭도 자기 상태(찜 표시·노출 맵·세션 프로필·피드 목록)를 비운다 — 전파 이벤트를 놓쳤어도 |
| 3-2 | 다른 탭에서 전환을 끝낸 **뒤에** 오래된 탭을 새로고침 | 그 탭의 세션 프로필이 비워지고, **장기 프로필에 합쳐지지 않는다** (새로고침으로 탭 표식이 사라져도) |
| 3-3 | A의 개인화 피드가 떠 있는 탭에서 요청 응답을 지연시키고, 다른 탭에서 B로 전환한 뒤 복귀 | 이미 보이던 A의 카드가 사라지고, **지연 응답이 도착해도 적용되지 않는다** |
| 4 | 동의 화면에서 취소 | 오류 문구 없이 설정으로 복귀. **네트워크·구성 오류일 때와 화면이 다르다** |
| 5 | 콜백 URL을 보존해 뒤로가기·재접속·동시 두 요청 | 각각에서 **이미 성립한 세션이 실패 UI로 덮이지 않는다** |
| 6 | A로 로그인해 찜·장기 프로필·세션 프로필을 만들고 A→로그아웃→B 로그인 | UI·저장소·**새 피드 요청에 실린 값** 어디에도 A의 것이 없다. **기기 ID는 그대로**이고 미전송 큐는 손대지 않았다 |
| 7 | 계정 삭제 → 다시 로그인 | 같은 구글 이메일이라 이메일은 다시 보인다. **사용자 UUID가 달라졌고**, 인증 테이블에 이전 사용자·연결·세션 행이 없고, **브라우저의 인증 쿠키가 제거됐고**, 삭제 직전에 확보한 토큰으로는 계정 경로를 통과하지 못한다 |
| 7-1 | **커밋 후 응답만 유실**을 흉내 내고 **같은** 구글 계정으로 재로그인 | 제공자 신원이 같고 사용자 식별자가 다르므로 **재호출하지 않는다**. 새로 만든 계정이 지워지지 않는다 |
| 7-2 | 같은 상황에서 **다른** 구글 계정으로 재로그인 | 제공자 신원이 다르므로 **표식을 유지하고** 재호출하지 않는다. 원래 계정으로 로그인해야 마무리된다고 안내한다 |
| 7-3 | **요청이 서버에 닿지 않은** 실패를 흉내 내고 같은 계정으로 재로그인 | 둘 다 같으므로 재확인 후 삭제가 정상 수행된다 |
| 8 | **로컬/테스트 환경에서** 토큰 수명을 권고 최저값으로 낮추고 **재로그인** → 탭을 닫아 자동 선갱신을 막고 만료 후 재접속 → 원래 값 복구 | 새 토큰이 발급되고 서버 확인이 성공한다. 원래 값을 기록해 두고 복구까지 확인한다. (수명 변경은 프로젝트 전역 설정이며 **기존 토큰에 소급되지 않으므로 반드시 재로그인**한다. 공유 프로덕션 설정에서 하지 않는다) |
| 9 | **브라우저·버전과 차단 방식을 미리 적어 고정**하고 first-party 쿠키를 차단 | 개발자 도구에서 **인증 쿠키가 저장되지 않았음**을 확인하고, 로그인은 실패하되 피드·검색은 성공한다 |
| 10 | 기존 배너 확인 상태를 만들어 둔 브라우저로 접속 | 갱신된 배너가 **한 번 다시** 나오고, 닫은 뒤 새로고침에는 다시 안 나온다 |
| 11 | 프로덕션 빌드로 콜백·세션 갱신·계정이 보이는 응답을 확인 | 사설·비저장 캐시 정책이 실제 응답 헤더에 붙어 있고, 합의한 보안 헤더가 지정 경로에 붙어 있다 |

- `npm run check` 통과.

### 사람이 해야 하는 준비 (AI가 대신할 수 없음)

1. **Supabase 대시보드에서 현재 Auth 사용자·활성 provider가 없음을 확인**한다 (전제: ecommerce 중단으로 Auth 미사용)
2. Google Cloud Console에서 OAuth 클라이언트 생성 — 승인된 리디렉션 URI(Supabase 콜백), 승인된 JavaScript 원본, 요청 범위, 동의 화면 브랜딩과 개인정보 처리방침 URL, 테스트 사용자 또는 프로덕션 전환
3. Supabase 대시보드에서 Google provider 활성화 + 클라이언트 ID/시크릿 입력
4. redirect allow list에 **프로덕션 정확 URL과 로컬 정확 URL 두 개만** 등록 (preview 없음)
5. **누가 어느 Google Cloud 프로젝트/OAuth 클라이언트를 소유하는지, 현재 설정 스냅샷, 되돌릴 때(provider 비활성화·redirect 제거·테스트 사용자 정리) 순서**를 기록한다 — 대시보드 설정은 repo에 남지 않는 전역 상태 변경이다

**1~5가 모두 끝나기 전에는 로그인 기능을 켜지 않는다.** 5번(소유권·되돌리기 기록)은 전역 상태를 바꾸기 **전에** 남기는 것이므로 게이트에 포함된다.

## 4-1. 리뷰 중 발견한 기존 결함 (이번 조각 범위 밖, 기록만)

교차 리뷰가 **로그인과 무관하게 이미 존재하던** 결함을 찾았다. 이번 변경이 만들지도, 악화시키지도 않으므로 조각 1에서 고치지 않는다. 묻히지 않도록 여기 적어 둔다.

- **"개인화 데이터 모두 지우기" 직후 늦게 도착한 이벤트가 삭제된 기록을 되살린다.** 서버 삭제 함수는 행을 지울 뿐 "이 기기 ID는 다시 쓰지 말라"는 표식을 남기지 않는다. 삭제로 기존 행이 사라졌으므로 이벤트 중복 무시 계약도 재삽입을 막지 못한다. 다른 탭의 메모리 큐나 진행 중이던 요청이 원인이 된다.
- **미완료 삭제 재시도 큐가 상한을 넘으면 오래된 실패 ID를 조용히 버린다.** 그 기기의 서버 기록은 이후 지울 수 없다.
- **`c_similar_page`·`c_log_events`·`c_forget_device`는 `PUBLIC` 실행 권한을 회수하지 않았다.** 다른 함수들과 달리 `revoke ... from public`이 빠져 있어 의도(`anon` 전용)와 실제가 다르다. anon도 이미 호출 가능하므로 새 노출은 아니지만, 의도와 실제가 어긋난 상태다.

앞의 둘은 **현재 방침 문서와 설정 화면이 이미 "모두 삭제"와 "다음 접속 재시도"를 약속하고 있으므로 현행 계약 위반**이다. 여기 적는 것만으로 닫히지 않는다 — **추적 가능한 별도 작업으로 등록하고, 공개 처리방침의 삭제 문구를 확정하기 전에 처리 여부를 결정한다**(고지 확정의 선행 게이트).

### 2차

2차 리뷰가 지적한 코드 사실은 **모두 직접 확인해 사실이었다**: `flush()`는 최대 50건만 보내고 실패를 삼키며 잔여를 알리지 않는다(상한 500건), 미완료 삭제 큐는 **삭제 실패 시에만** 기기 ID를 보관한다, `clearSignals()`는 찜 캐시를 지우지 않는다, 큐·노출 맵은 탭별 모듈 전역이다.

### 3차

3차 지적의 절반은 **기기 ID 회전이라는 결정 하나에서 파생된 것**이었다. 회전을 조각 1에서 빼기로 하면서 그 파생 항목들은 해결이 아니라 **소멸**한다.

| # | 등급·지적 | 처리 |
|---|---|---|
| ①-1 | 기존 영속 큐에 귀속 정보가 없어 스키마 선배포·이관이 필요 | **소멸** — 기기 ID를 회전하지 않으므로 이벤트에 ID를 새길 이유가 없다. 큐·스키마 무변경 |
| ①-2 | `session_id`·`impression_id`가 다른 기기를 참조할 수 있음 | **소멸** — 기기 ID가 바뀌지 않으므로 교차 참조가 생기지 않는다 |
| ①-3 | 검색 로그가 응답 시점 ID로 오염 | **소멸** — 같은 이유 |
| ①-4 | 표시자 하나로 다중 탭 전환을 멱등하게 못 만듦 | **반영(단순화)** — 공유 ID를 고쳐 쓰지 않으므로 경합이 사라진다. 지속 저장소는 표시자로, 탭별 메모리는 **각 탭이 자기 안에서** 비교해 비운다. 일시 중지 후 복귀 탭을 완료 기준 3-1로 추가 |

| ①-6 | 응답 불명 뒤 재로그인해 재시도하면 **새 계정을 지움** | **반영** — 실제 결함이었다. 삭제 전 대상 식별자를 표식으로 남기고, 재로그인 후 식별자가 **다르면 재호출하지 않는다**. 완료 기준 7-1 추가 |
| ②-1 | ID별 여러 전송의 부분 실패 계약 | **소멸** — 기기별 분할 전송 자체가 없다 |

| ③-1 | 완료 기준 3·6·7·8·9가 판정식이 아님 | **반영** — 전부 재작성. 6은 큐 귀속이 사라져 단순해짐, 7은 쿠키 제거·토큰 권한 확인 추가, 8은 로컬/테스트 환경 한정, 9는 브라우저·차단 방식 고정 |

### 4차

4차는 **"서버가 기기 ID로 개인화하는 경로는 없다"는 v4의 핵심 주장을 코드로 확인해 줬다** (`c_mix_page`는 클라이언트가 보낸 프로필과 제외 목록만, `c_feed_page`는 seed·커서만 받는다). 회전 철회로 3차의 ①-1·①-2·①-3·②-1과 목록 상한 문제가 실제로 소멸했음도 확인됐다.
