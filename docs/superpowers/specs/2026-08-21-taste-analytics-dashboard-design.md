## 1. 목적

마이페이지의 핵심 콘텐츠가 된 취향 분석을 다음 질문에 답할 수 있게 측정한다.

1. 몇 명에게 취향 분석 결과가 제공됐는가?
2. 결과가 나온 사람 중 너무 빨리 이탈하지 않고 화면을 본 사람은 몇 명인가?
3. 다시 취향 분석을 보러 오는 사람이 있는가?
4. 최신 결과를 원해 새로고침한 사람은 몇 명이며, 실제 결과가 바뀌었는가?
5. 기능 자체의 문제로 결과를 제공하지 못한 경우는 얼마나 되는가?

단순한 페이지 진입 수나 새로고침 클릭 수 하나로 기능 가치를 판단하지 않는다. 취향 분석이 자동으로 한 화면에 모두 표시되므로, 스크롤 깊이와 항목별 노출은 측정하지 않는다.

## 2. 확정된 원칙

| 항목 | 결정 | 이유 |
|---|---|---|
| 중심 집계 단위 | 계정 | 같은 사람이 여러 기기를 써도 한 명으로 센다 |
| 보조 식별자 | 기기 ID와 세션 ID를 함께 유지 | 다중 기기 사용과 계측 오류를 조사할 수 있다 |
| 표시 완료 | 취향 분석 요청이 최종 상태에 도달한 때 | 페이지 진입과 결과 제공을 구분한다 |
| 유효 조회 | 분석 결과가 표시된 채 활성 화면에서 3초 유지 | 즉시 이탈을 제외하는 운영 기준이다. 읽었다는 증명은 아니다 |
| 새로고침 | 시도와 결과를 분리 | 시도 후 이탈·실패·변경 없음을 구분한다 |
| 취향 내용 | 분석 로그에 저장하지 않음 | 이 대시보드 목적에 필요 없고 개인정보·쿼리 복잡도만 늘린다 |
| 기본 기간 | 최근 30일 | 적은 사용자 규모에서 7일보다 안정적으로 흐름을 본다 |
| 시간대 | 한국시간(Asia/Seoul) | 날짜와 재방문일 판정을 실제 사용자 날짜와 맞춘다 |
| 표본 표시 | 비율 옆에 분자/분모를 함께 표시 | 작은 표본에서 퍼센트만 커 보이는 오해를 막는다 |

## 3. 상태 정의

취향 분석 요청의 최종 상태를 세 가지로 나누고, 요청 자체가 없는 경우를 예외로 하나 더 둔다.

| 상태 | 사용자에게 보이는 것 | 지표에서의 취급 |
|---|---|---|
| `ready` | 취향 축·색·브랜드 등 분석 결과 | 결과 제공 성공 |
| `collecting` | 아직 취향을 모으는 중이라는 정상 안내 | 기술적 표시는 성공했지만 분석 결과 제공은 아님 |
| `failed` | 취향을 불러오지 못했다는 오류 안내 | 기술 실패 |
| (예외) 상태 기록 없음 | 해당 없음 | 마이페이지는 열렸는데 `taste_analysis_result`가 오지 않은 계정. **`failed`로 세지 않는다.** 계측 유실과 실제 실패를 구분하기 위한 자리다 |

`collecting`을 `ready`와 합쳐 “분석 결과 제공 성공”으로 세지 않는다. 그렇게 하면 아직 결과가 없는 계정까지 핵심 기능을 받은 것으로 부풀려진다. 대신 상태 분포에서 따로 보여준다.

## 4. 이벤트 계약

### 4.1 이벤트 목록

| 이벤트 | 발생 시점 | 중복 규칙 | 핵심 속성 |
|---|---|---|---|
| `my_page_view` | 로그인 상태가 확정되고 마이페이지 본문이 표시된 때 | 페이지 마운트당 1회 | 공통 필드만 |
| `taste_analysis_result` | 최초 조회나 새로고침 뒤 취향 분석이 `ready`·`collecting`·`failed` 중 하나가 된 때 | 요청 1회당 1회 | 요청 ID, 요청 출처(최초·새로고침), 상태, 요청 소요 시간 |
| `taste_analysis_engaged` | `ready` 상태가 활성 화면에서 연속 3초 유지된 때 | 페이지 마운트당 1회 | 기준 시간 3,000ms |
| `taste_refresh_attempt` | 중복 실행 방지 검사를 통과한 새로고침 클릭 | 받아들인 클릭마다 1회 | 새로고침 실행 ID, 실행 전 상태 |
| `taste_refresh_result` | 새로고침 작업이 끝난 때 | 시도 1회당 최대 1회 | 실행 ID, 성공·실패, 접기 결과, 화면 변경 여부, 실패 단계, 전체 소요 시간 |

새로고침 뒤에도 `taste_analysis_result`를 남기는 이유는 처음 `failed`였던 화면이 새로고침으로 `ready`가 되는 회복을 “분석 결과 제공”에 포함하기 위해서다. 같은 새로고침에서 생긴 분석 결과와 새로고침 결과는 같은 요청·실행 ID로 연결한다.

### 4.2 공통 필드

모든 이벤트에는 다음 맥락이 필요하다.

- 이벤트 ID
- 서버 인증값으로 확인한 계정 ID
- 기기 ID
- 세션 ID
- 사용자 발생 시각과 서버 수신 시각
- 계측 계약 버전
- 이벤트별로 허용된 속성만 담는 제한된 속성 묶음

이메일·이름·실제 취향 축·색·브랜드는 넣지 않는다. admin 원본 표에는 계정 ID를 가린 안정적인 표시명으로 보여주고, 실제 UUID는 기본 화면에 노출하지 않는다.

### 4.3 유효 조회 판정

3초 타이머는 다음 조건을 모두 만족할 때만 흐른다.

- 취향 분석 상태가 `ready`다.
- 브라우저 탭이 활성 상태다.
- 취향 분석 화면이 현재 화면이다.

탭이 백그라운드로 가거나 다른 화면으로 이동하면 누적하지 않고 끊는다. 3초는 “읽었다”의 증명이 아니라 즉시 이탈을 제외하기 위한 고정 기준이며, 대시보드 문구도 “완독” 대신 “유효 조회”를 쓴다.

### 4.4 새로고침 결과

새로고침은 아래 순서로 동작한다.

```text
현재 세션 취향을 장기 취향에 반영 → 계정 프로필 저장 → 취향 분석 재조회
```

결과는 다음처럼 구분한다.

| 결과 | 뜻 |
|---|---|
| `changed` | 새로고침이 성공했고 사용자가 보는 분석 결과가 바뀜 |
| `unchanged_with_updates` | 반영할 세션 행동은 있었지만 화면 결과는 같음 |
| `no_updates` | 반영할 새 세션 행동이 없었음 |
| `failed` | 반영·계정 저장·재조회 중 하나가 실패함 |
| `unresolved` | 시도는 남았지만 결과 이벤트가 없음. 이탈·앱 종료·장시간 미완료 가능 |

`changed` 판정을 위해 새로고침 전후의 사용자 표시 결과를 비교하되, 로그에는 원본 결과를 복사하지 않고 변경 여부만 저장한다.

현재 즉시 반영 함수는 `false` 하나로 “반영할 것 없음”과 “브라우저 저장 오류”를 함께 표현한다. 실제 계측에서는 이를 `folded`·`no_changes`·`local_error`로 나눠야 한다. 그렇지 않으면 실패를 `no_updates`로 잘못 센다.

## 5. 저장과 기존 계측의 관계

이 기능만을 위한 외부 분석 도구나 새로운 이벤트 시스템은 만들지 않는다. 기존 계측 계약이 선택한 정본 저장소에 위 이벤트를 추가한다.

현재 자체 admin을 기준으로 하면 기존 행동 이벤트 저장소를 확장하는 안이 가장 작다. 계정·기기·세션·재전송·삭제 경로를 재사용할 수 있고, 취향 분석 로그는 자유 텍스트가 없으며 기존 행동 로그와 보존 목적도 같다. 단, 이벤트별 속성은 서버가 종류·값·크기를 검증해야 한다.

보존기간은 이 기능만 따로 길게 잡지 않고 계정 연결 행동 기록에 확정되는 기간을 그대로 따른다. 계정 삭제 시에는 현재 기기 기록만 지우는 것으로 끝내지 않고, 그 계정 ID가 붙은 취향 분석 이용 기록을 모든 기기 범위에서 삭제한다. 기기 초기화는 해당 기기 ID의 기록을 지운다. 이 범위와 계정 연결 사실은 처리방침 문구와 동시에 배포한다.

[계측 계약 1단계](../../plans/2026-08-21-instrumentation-contract-phase1.md)에 남아 있는 “외부 제품 분석 도구와 자체 기록 중 무엇을 정본으로 할지”가 바뀌면 저장 위치만 달라진다. 이 문서의 이벤트 이름·지표 정의·목업 모양은 그대로 유지한다. 두 저장소에 동시에 보내 어느 숫자가 정본인지 모르게 만들지 않는다.

계정 ID 연결, 기기 ID 유지, 백그라운드 5분·무활동 30분·신원 변경 세션 경계는 이번 기능의 선행 의존성이다. 여기서 중복 설계하지 않는다.

## 6. 기간 계약

### 6.1 기간 선택

- 기본값: 최근 30일
- 빠른 선택: 오늘, 최근 7일, 최근 30일, 전체
- 직접 선택: 시작일과 종료일
- 모든 날짜 경계와 표시는 한국시간 기준
- 오늘은 아직 끝나지 않은 날이라는 표시를 붙인다

선택한 기간은 사용자 발생 시각을 기준으로 시작 시각 이상, 종료 다음 날 시작 시각 미만으로 계산한다.

### 6.2 7일 리텐션

같은 날 화면을 다시 연 것은 리텐션으로 세지 않는다.

- 대상: 선택 기간 안에 처음 `taste_analysis_engaged`가 발생한 계정
- 코호트 성숙 조건: 첫 유효 조회 후 7일이 지난 계정만 분모에 포함
- 성공: 첫 유효 조회 다음 한국 날짜부터 7일 안에 다시 `taste_analysis_engaged`가 발생
- 최근 7일이 아직 지나지 않은 계정은 실패가 아니라 계산 대상 밖으로 표시

리텐션 확인에 필요한 후속 7일 데이터는 선택 기간의 종료일을 넘어도 읽을 수 있다. 선택 기간은 코호트가 처음 들어온 날짜를 정한다.

### 6.3 관찰 세션 구분

기존 결정대로 관찰 세션·자발 세션은 앱이 자동 판정하지 않고 admin에서 사람이 표시한다. 화면에는 `전체 · 자발 · 관찰 · 미분류` 필터를 둔다.

**분류를 입력하는 화면이 생기기 전까지 이 필터는 비활성으로 잠그고 `전체`로 고정한다.** 옆에 `분류 기능 준비 전`을 붙인다. 눌리는데 숫자가 안 바뀌면 기능이 있는 것으로 오해되기 때문이다. 세션 표에는 분류가 붙은 뒤의 모습을 보여주려고 자발·관찰·미분류 샘플을 함께 둔다.

## 7. 지표 정의

모든 계정 수는 선택 기간 안의 고유 계정 수다.

| 지표 | 계산 | 해석할 때 주의할 점 |
|---|---|---|
| 마이페이지 방문 계정 | `my_page_view`가 있는 계정 | 취향 분석을 받을 기회가 있던 계정 |
| 분석 결과 제공률 | `ready` 계정 ÷ 마이페이지 방문 계정 | `collecting`을 성공에 넣지 않는다 |
| 정상 상태 도달률 | `ready` 또는 `collecting` 계정 ÷ 방문 계정 | 기능이 최종 화면을 냈는지 보는 안정성 지표. **“오류 없이”라고 쓰지 않는다** — 실패 뒤 회복한 계정도 여기 포함되고, 그 계정은 이미 오류를 겪었다 |
| 유효 조회율 | `taste_analysis_engaged` 계정 ÷ `ready` 계정 | 3초 기준이며 읽었다는 확정이 아니다 |
| 7일 리텐션 | 다른 날짜에 다시 온 계정 ÷ 코호트 성숙이 끝난 유효 조회 계정 | 최근 계정을 실패로 세지 않는다 |
| 새로고침 계정률 | 새로고침을 1회 이상 시도한 계정 ÷ 유효 조회 계정 | 몇 명이 눌렀는지의 비율이 기본값이다. 클릭 수는 새로고침 결과에서 따로 본다 |
| 계정당 새로고침 횟수 | 새로고침한 계정별 시도 횟수의 중앙값과 범위 | 평균은 한 사람의 연타에 흔들린다 |
| 결과 변경률 | `changed` ÷ 처리 결과가 기록된 시도 | 성공률과 변경률을 같은 뜻으로 쓰지 않는다. 분모가 실패율과 다르다 |
| 새로고침 실패율 | `failed` ÷ 전체 시도 | `unresolved`(완료 기록 없음)는 실패와 따로 표시한다 |
| 첫 요청 결과 분포 | 계정별 첫 초기 조회(`source=initial`)의 상태 | 계정마다 하나뿐이라 합이 방문 계정과 정확히 맞는다. **회복을 여기에 더하지 않는다** |

비율은 항상 `31% · 4/13계정`처럼 분자와 분모를 함께 표시한다. 표본이 10계정 미만이면 “표본 적음” 표시를 붙이고 큰 상승·하락 화살표를 쓰지 않는다.

## 8. admin 화면 구성

현재 admin은 “SQL 하나 = 표 하나”만 표현하며 SQL 결과의 컬럼 이름을 그대로 표 머리글로 쓴다. 아래 화면은 표 이외의 표현이 필요하므로 실제 구현에서는 지표 정의에 표시 형식을 명시해야 한다. 화면이 컬럼 이름만 보고 차트 종류를 추측하게 하지 않는다.

필요한 표시 형식은 네 가지로 제한한다.

- 핵심 숫자 타일
- 일별 막대
- 새로고침 결과 누적 막대
- 원본 표

각 지표 정의는 표시 형식과 함께 축·값·분모·색상 역할을 명시한다. SQL을 추가하는 것만으로 차트가 자동 생성된다고 가정하지 않는다.

**화면은 탭 두 개로 나눈다.** 첫 화면의 집중도를 높이고, 계정 상세를 보지 않을 때는 그 조회를 아예 돌리지 않기 위해서다.

| 탭 | 내용 |
|---|---|
| 개요 | 핵심 숫자 · 일별 추이 · 새로고침 결과 · 첫 요청 결과와 회복 |
| 계정 · 세션 | 계정 표와 세션 상세 |

기간·세션 필터는 탭 위에 한 줄로 두어 두 탭 모두에 걸리게 한다.

**같은 숫자를 두 번 보여주지 않는다.** 핵심 숫자 줄이 이미 `방문 → ready → 유효 조회 → 새로고침`의 단계별 비율을 담으므로, 같은 값을 흐름 카드로 한 번 더 그리지 않는다.

### 8.1 상단 필터

- 기간 빠른 선택과 직접 선택
- 한국시간 표시
- 전체·자발·관찰·미분류 세션 필터
- 마지막 데이터 수신 시각

### 8.2 핵심 숫자 줄

한 줄에 다음 다섯 항목을 둔다.

1. 마이페이지 방문 계정
2. 분석 결과 제공률
3. 유효 조회율
4. 7일 리텐션
5. 새로고침 계정률

각 타일은 큰 값, 분자·분모, 짧은 설명을 함께 보여준다. 직전 기간 비교는 같은 정의와 같은 길이의 기간이 확보될 때만 보조 문구로 표시한다. 표본이 작으면 변화율보다 원수를 우선한다.

### 8.3 첫 요청 결과와 회복

**기준을 못박는다.** 이 카드가 세는 것은 **선택 기간 안에서 각 방문 계정의 첫 초기 조회(`source=initial`) 결과**다. 계정 생애 최초가 아니라 이 기간의 첫 요청이다.

```text
첫 요청 결과 (계정마다 하나)
├ ready              12
├ collecting          4
├ failed              2
│   └ 새로고침으로 회복  1
└ 상태 기록 없음        0
합계 12 + 4 + 2 + 0 = 18계정  (마이페이지 방문 계정과 일치)
```

**회복을 상태 합계에 더하지 않는다.** 한 계정이 `failed` 뒤 `ready`가 되면 두 상태에 모두 들어가 합이 방문 계정보다 커지고, 그때부터 차트가 스스로 설명하지 못해 해명하는 문장이 필요해진다. 첫 요청은 계정마다 하나뿐이므로 합이 정확히 맞고, 회복은 `failed` 아래 가지로 따로 단다.

카드 아래에 두 줄을 덧붙인다.

- 기간 중 한 번이라도 `ready`에 도달한 계정 (= 분석 결과 제공률의 분자)
- 정상 상태 도달 계정 (`ready` 또는 `collecting`)

**단계 흐름(깔때기) 카드는 두지 않는다.** 핵심 숫자 줄과 같은 값을 반복하게 된다.

### 8.4 일별 추이

일별 고유 계정 막대 두 종류만 비교한다.

- 취향 분석 유효 조회 계정
- 새로고침 계정

막대에 마우스를 올리거나 키보드 초점을 옮기면 마이페이지 방문 계정과 각 비율의 분자·분모를 보여준다. 데이터가 없는 날은 0으로, **집계 실패는 0과 다른 오류 상태**로 표시한다. 기본 30일은 일 단위, 90일을 넘는 기간은 주 단위로 묶는다.

**막대는 초점을 받을 수 있는 요소로 만든다.** 마우스 이동에만 반응하면 키보드와 터치에서 값을 열 방법이 없다. 각 막대에 그날 값을 담은 대체 텍스트를 붙이고, 표 뷰를 함께 둬 툴팁이 값을 가두지 않게 한다.

### 8.5 새로고침 결과

한 개의 가로 누적 막대로 다음을 나눈다.

- 결과 변경
- 새 행동은 있었지만 화면 동일
- 새 행동 없음
- 실패
- 완료 기록 없음

색만으로 구분하지 않고 범례에 이름과 건수를 적는다. 실패는 실패 단계별 작은 표를 함께 둔다.

**막대와 범례에는 비율을 넣지 않고 건수만 둔다.** 전체 시도(14건)를 분모로 한 비율과 처리 결과가 기록된 시도(13건)를 분모로 한 변경률이 한 화면에 비슷한 크기로 놓이면, 36%와 38% 중 어느 것이 무엇인지 읽는 사람이 매번 따져야 한다. 비율은 막대 아래에 분모를 밝혀 따로 적는다.

- 처리 결과가 기록된 시도 중 변경 (분모 = 전체 시도 − `unresolved`)
- 전체 시도 중 실패
- 완료 기록이 없는 시도
- 계정당 새로고침 횟수 (중앙값과 범위)

### 8.6 계정 표

`계정 · 세션` 탭에 근거를 확인할 수 있는 표를 둔다.

**행은 계정 하나다.** 한 계정이 여러 기기와 세션을 쓸 수 있으므로, 기기·세션을 행에 하나씩만 적으면 집계 단위가 무엇인지 읽는 사람이 알 수 없다.

| 열 | 내용 |
|---|---|
| 계정 | 가린 안정적 계정 표시명 |
| 기기 수 | 그 계정이 쓴 기기 개수 |
| 세션 수 | 선택 기간 안의 세션 개수 |
| 유효 조회 | 예·아니오 (세션 중 하나라도 있으면 예) |
| 새로고침 총횟수 | 세션별 시도의 합 |
| 최근 상태 | ready·collecting·failed. 회복한 계정은 그 사실을 함께 적는다 |
| 최근 시각 | 한국시간 |

행을 펼치면 세션 상세가 나온다.

| 열 | 내용 |
|---|---|
| 기기 | 가린 기기 표시명 |
| 세션 | 가린 세션 표시명 |
| 세션 구분 | 자발·관찰·미분류 |
| 취향 상태 | ready·collecting·failed |
| 유효 조회 | 예·아니오 |
| 새로고침 | 그 세션의 시도 횟수 |
| 결과 | changed·unchanged_with_updates·no_updates·failed·unresolved |

기본 정렬은 최근 시각 내림차순이다. 사용자가 적은 현재 단계에서는 차트보다 이 표가 오판을 바로잡는 근거가 된다. **세션별 새로고침의 합이 계정 행의 총횟수와 맞는지**가 이 표로 확인할 수 있는 첫 번째 대조다.

## 9. Claude Code용 HTML 목업 제작 지시

### 9.1 산출물

- 독립 실행되는 정적 HTML 한 파일
- 실제 admin 코드와 DB를 변경하지 않음
- 현재 admin의 어두운 색상·카드·표 스타일을 시각적으로 계승
- 데스크톱 우선이되 좁은 화면에서도 가로 잘림 없이 확인 가능
- 가짜 데이터임을 화면에 명시

### 9.2 반드시 보여줄 상태

기본 화면에는 최근 30일의 소규모 표본을 사용한다. 숫자는 서로 계산이 맞아야 한다.

- 방문 계정이 존재함
- `ready`·`collecting`·`failed`가 모두 존재함
- 유효 조회하지 않은 `ready` 계정이 존재함
- 새로고침 결과 다섯 종류가 모두 존재함
- 7일 관찰이 아직 끝나지 않아 분모에서 빠진 계정이 존재함
- 관찰·자발·미분류 세션이 모두 존재함

목업에서 필터를 누르면 실제 데이터를 재계산할 필요는 없다. 선택 상태와 기간 라벨이 바뀌는 정도면 충분하다. 목적은 데이터 엔진 검증이 아니라 정보 구조와 용어 검토다.

### 9.3 예시 데이터 계약

목업 숫자는 아래 관계를 지킨다.

- 분석 결과 제공 계정 ≤ 마이페이지 방문 계정
- 유효 조회 계정 ≤ 분석 결과 제공 계정
- 새로고침 계정 ≤ 유효 조회 계정
- 새로고침 결과 건수 ≤ 새로고침 시도 건수
- 재방문 분모는 전체 유효 조회 계정보다 작거나 같음

### 9.4 문구

사용할 표현:

- "분석 결과 제공률"
- "유효 조회. 결과가 표시된 채 3초 이상"
- "7일 리텐션. 첫 유효 조회 후 7일이 지난 계정만"
- "정상 상태 도달 계정"
- "결과 변경"
- "새 행동 없음"
- "완료 기록 없음"
- "처리 결과가 기록된 시도"
- "집계 실패"
- "상태 기록 없음"
- "최종 수집 시각"

피할 표현:

- "완독" 또는 "끝까지 봄"
- "실시간 분석"
- "새로고침 전환율"
- "평균 새로고침"만 단독 표시
- `collecting`을 성공적인 분석 결과로 포함하는 문구
- "오류 없이 화면을 낸 계정" (회복한 계정은 이미 오류를 겪었다)
- "결과 없음" (취향 분석 결과 자체가 비었다는 뜻으로 읽힌다)
- "조회 실패" (실패한 주체는 사용자의 조회가 아니라 서버 집계다)

문장 부호와 말투:

- **줄표(—)를 쓰지 않는다.** 마침표로 끊거나 쉼표·괄호로 바꾼다.
- 굽은 따옴표 대신 곧은 따옴표를 쓴다.
- 숫자 범위는 `1~5`로 적는다.
- "A가 아니라 B" 식의 뒤집기 표현 대신 B를 그대로 쓴다.
- 조각 문장으로 끝내지 않는다.

## 10. 실패·빈 상태

- 전체 DB 연결 실패: 화면 전체에 오류를 표시하고 숫자를 0으로 대체하지 않는다.
- 카드 하나의 집계 실패: 해당 카드만 실패로 표시하고 다른 영역은 유지한다.
- 선택 기간 데이터 0건: "사용자 0명"과 "집계 실패"를 다르게 표시한다.
- 리텐션 집계 대상 계정 0명: 0% 대신 "계산할 계정 없음"으로 표시한다.
- 새로고침 시도 0건: 결과 막대를 빈 비율로 만들지 않고 "시도 없음"으로 표시한다.
- 방문은 있는데 상태 기록이 없음: "상태 기록 없음"으로 표시하고 `failed`로 세지 않는다.

## 11. 이번 설계에서 하지 않는 것

- 취향 축·색·브랜드별 이용 분석
- 마우스 이동·시선 추적·항목별 체류시간
- 취향 분석이 찜·판매처 이동을 일으켰다는 인과 주장
- 알림·푸시·A/B 테스트
- CSV 내보내기
- 실시간 자동 새로고침
- 외부 분석 도구와 자체 로그의 이중 전송

후속 상품 상세·찜·판매처 이동은 기존 이벤트와 시간 순서로 탐색할 수 있지만, 취향 분석 때문에 발생했다고 단정하지 않는다. 필요성이 확인되면 별도 지표 조각으로 다룬다.

## 12. 구현 전 선행 조건과 검증 기준

### 선행 조건

1. 계정 ID를 서버 인증값으로 이벤트에 연결한다.
2. 기기·세션 ID를 함께 유지한다.
3. 백그라운드 5분·무활동 30분·신원 변경 세션 경계를 적용한다.
4. 계정 연결 행동 기록과 삭제 범위를 처리방침에 반영한다.
5. 자체 기록과 외부 분석 도구 중 정본을 하나로 확정한다.
6. 계정 삭제 시 모든 기기의 계정 연결 취향 분석 기록이 함께 삭제되는 경로를 마련한다.

### 구현 후 눈으로 확인할 기준

- 마이페이지를 열면 같은 계정·기기·세션으로 방문과 분석 결과 이벤트가 이어져 보인다.
- `ready` 상태로 3초 유지하면 유효 조회가 1회만 생기고, 3초 전에 나가면 생기지 않는다.
- 탭을 백그라운드에 둔 시간은 유효 조회 3초에 포함되지 않는다.
- 새로고침을 누르면 시도와 결과가 같은 실행 ID로 연결된다.
- 새 행동 없음, 결과 변경, 저장 실패, 재조회 실패가 서로 다른 원본 행으로 확인된다.
- 선택 기간을 바꾸면 계정 수와 분모가 함께 바뀌고 한국시간 날짜와 원본 시각이 맞는다.
- 코호트 성숙이 끝나지 않은 최근 계정이 7일 리텐션 실패로 잘못 포함되지 않는다.
- 대시보드 합계와 원본 행을 계정 몇 건으로 직접 대조할 수 있다.

자동 테스트와 별개로 실제 브라우저 조작과 원본 이벤트를 함께 제시한다. 실행하지 않은 항목은 통과가 아니라 미검증으로 남긴다.
