# 찜을 계정으로 — 설계 (조각 2)

- 작성: 2026-08-18
- 상태: 합의됨 / 구현 전
- 선행: [조각 1 구글 로그인 설계](2026-08-18-google-login-design.md) — 이 문서가 조각 1이 남긴 게이트를 닫는다
- 관련: [Living PRD](../../atee/living/prd.md) · [결정 기록](../../atee/living/decision-log.md) · [데이터 수집·보존 방침](../../atee/living/data-collection-policy.md)

## 배경

찜은 지금 이 기기의 저장소에만 있다. 로그인과 무관하게 동작하고, 찜 목록도 누구나 열 수 있다.

그런데 조각 1에서 **신원이 바뀌면 앞사람 흔적을 지우는** 규칙을 넣으면서 부작용이 생겼다. 비회원으로 티셔츠 열 개를 찜한 뒤 로그인하면 **열 개가 통째로 사라진다.** 아무 경고도 없다. 한 기기를 여럿이 쓸 때 취향이 새는 것을 막으려던 규칙인데, 같은 사람 입장에서는 손해만 보인다.

동시에 로그인은 아직 아무것도 주지 않는다. 설정 화면이 *"지금은 로그인해도 달라지는 것이 없습니다"*라고 적고 있고 사실이다.

이 조각은 둘을 한꺼번에 해결한다 — **찜을 계정 데이터로 옮기고 로그인을 필수로 한다.** 찜이 기기를 넘어 따라오므로 로그인에 실제 이유가 생기고, 로그인하며 찜을 잃는 일도 없어진다.

## 범위

**이번 조각** — 계정 찜 저장·조회, 찜과 찜 목록의 로그인 게이트, 기존 로컬 찜 옮기기.

**이번 조각이 아닌 것** — 취향 프로필의 계정 이전(조각 3), 찜 공유·폴더·메모, 품절·가격 변동 알림, 찜 기반 추천 강화.

## 1. 저장 구조

계정 찜 테이블 하나를 둔다.

**담는 것**: 사용자, 상품 번호, 찜한 시각. 그게 전부다.

- **상품 정보를 복사하지 않는다.** 목록을 열 때 카탈로그와 이어 붙여 현재 제목·가격·이미지를 가져온다. 가격이 바뀌어도 항상 맞고, 사용자당 저장량이 작다.
- **사용자 행을 외래키로 참조하고 삭제가 연쇄된다.** 조각 1이 조각 2의 선행 조건으로 못박은 것이다. 계정을 지우면 찜도 함께 사라진다.
- **상품 번호에는 외래키를 걸지 않는다.** 카탈로그를 다시 수집할 때 행이 지워지는 일이 생기면 사용자의 찜이 조용히 사라진다. 지금 수집은 덮어쓰기 방식이라 행이 지워지지 않지만, 그 사실에 찜의 생존을 걸지 않는다. 이어 붙일 때 못 찾으면 그 항목만 빠진다.
- **본인 행만 읽고 쓸 수 있게 잠근다.** 다른 사용자의 찜은 조회도 수정도 되지 않는다.
- 목록을 최근순으로 내주므로 사용자·찜한 시각 순서로 찾을 수 있게 한다.

**쓰기는 검증이 붙은 함수를 통한다.** 테이블을 직접 열지 않는다. 이 repo가 이미 그렇게 하고 있고(행동 기록·검색 기록), 상한 같은 계약을 한곳에 둘 수 있다.

**상한은 500개.** 지금 로컬 저장소가 쓰는 값을 그대로 가져온다. 넘으면 거부하고 이유를 보여준다 — 조용히 오래된 것을 버리지 않는다. 로그인한 사용자가 무한히 행을 넣는 것을 막는 선이기도 하다.

## 2. 읽기

찜 목록은 **정의자 권한 함수**로 내려준다. 카탈로그 원본 테이블은 비로그인 조회가 막혀 있어 클라이언트가 직접 이어 붙일 수 없다. 피드가 이미 같은 방식을 쓴다.

**피드 노출 조건을 걸지 않는다.** 썸네일 크기·가격 조건에서 빠진 상품이라도 사용자가 직접 담은 것이니 보여야 한다. 피드에 안 나오는 상품이 찜 목록에는 보이는 것이 맞다.

정렬은 최근에 찜한 것부터다. 상한이 500이므로 한 번에 다 내려준다 — 지금 로컬 목록 화면도 그렇게 하고 있어 동작이 달라지지 않는다.

## 3. 화면

**비회원**
- ♡를 누르면 찜되지 않고 **로그인으로 유도**한다.
- 찜 목록에 들어가려 하면 진입 대신 로그인 유도를 보여준다.
- 피드·검색·상세는 지금 그대로다. 로그인 없이 계속 쓸 수 있다.

**회원**
- 지금과 같은 목록 화면. 데이터 출처만 바뀐다.
- ♡는 **즉시 채워지고** 저장은 뒤따른다. 무한 스크롤 중에 한 박씩 멈추면 안 된다.
- 저장이 실패하면 **하트를 되돌리고 짧게 알린다.** 조용히 어긋난 채로 두지 않는다.
- 같은 상품을 빠르게 여러 번 누르면 **마지막 의도가 이긴다.** 요청이 뒤섞여 반대 상태로 굳는 일이 없어야 한다.

**설정 화면 문구**를 고친다. 지금 *"다음 업데이트에서 찜을 계정에 저장할 예정입니다"*라고 적혀 있는데 이 조각이 그 업데이트다.

## 4. 기존 로컬 찜 옮기기 (일회성)

여기에 함정이 있다. **로그인하면 신원 전환 정리가 먼저 돌아 로컬 찜을 지우고 페이지를 다시 불러온다.** 그대로 두면 옮길 것이 이미 사라진 뒤다.

**순서 계약**

1. 신원 전환을 감지한다.
2. **이전 신원이 익명이고 새 신원이 사용자일 때만**, 로컬 찜을 "옮길 것" 보관함으로 빼둔다.
3. 신원 종속 저장소를 정리한다(찜 포함).
4. 처리 표식을 확정한다.
5. 페이지를 다시 불러온다.
6. 다시 뜬 뒤 로그인 상태이면 보관함을 서버로 올리고 보관함을 비운다.

**보관함은 신원 전환에도 살아남는 목록에 넣는다.** 넣지 않으면 3번에서 방금 빼둔 것이 다시 지워진다.

**옮기는 것은 익명 → 사용자 전환뿐이다.** 다른 전환에서 옮기면 안 된다.

- 사용자 → 익명(로그아웃): 로컬에 있던 것은 이미 서버에 있다. 그냥 지운다.
- 사용자 A → 사용자 B: A의 찜을 B의 계정에 넣는 일이다. **절대 옮기지 않는다.**

**실패하면 보관함이 남아 다음 접속에 다시 시도한다.** 삭제 재시도 목록과 같은 방식이다. 성공한 것만 보관함에서 뺀다.

**이미 계정에 있는 상품은 서버가 무시한다.** 같은 사용자·같은 상품은 한 행이므로 여러 번 올려도 결과가 같다.

**이것은 O-35(승계하지 않는다)의 예외다.** 취향 프로필은 계산된 결과지만 찜은 사용자가 손으로 누른 것이라 성격이 다르다. 결정 기록에 예외를 명시한다.

**대가**: 한 기기를 여럿이 쓰면 **앞사람이 비회원으로 찜해둔 것이 뒷사람 계정으로 들어간다.** 알고 받는 대가다. 익명 → 사용자 전환에서만 일어나므로 계정 사이에서 새지는 않는다.

## 5. 부작용과 위험

**① 비회원에게서 찜 신호가 사라진다.** 지금 개인화는 노출·탭·찜을 함께 쓴다. 찜이 로그인 필수가 되면 비회원 피드는 **가장 강한 신호 하나를 잃는다.** 노출·탭은 그대로라 개인화가 멈추지는 않지만 품질이 떨어질 수 있다. 얼마나 떨어지는지는 재봐야 안다.

**② 지금 되는 기능을 막는 변경이다.** 비회원 탐색 경험이 나빠지고 이탈이 늘 수 있다. 로그인 전환이 오르는지와 이탈이 늘어나는지를 **함께** 봐야 한다 — 한쪽만 보면 판단할 수 없다.

**③ 로그인하지 않은 기존 사용자는 자기 찜을 볼 수 없다.** 기기에 남아 있지만 목록 화면이 막힌다. 로그인하면 그대로 올라온다. 유도 문구에서 이 사실을 알려야 한다.

**④ 찜 목록 조회가 카탈로그와 이어 붙는다.** 500개를 이어 붙이는 비용을 재고, 필요하면 인덱스를 확인한다. 카탈로그 속성 조회가 느려 타임아웃이 난 전례가 있다.

## 6. 계정 삭제와의 게이트

조각 1이 남긴 게이트를 여기서 닫는다.

- 계정을 지우면 **그 계정의 찜 행이 모두 사라진다** (외래키 연쇄).
- **삭제 직전에 확보한 토큰으로 찜을 읽거나 쓸 수 없다.** 사용자 행이 없으므로 본인 확인이 통과하지 않는다.
- 같은 구글 계정으로 다시 로그인해 받은 **새 사용자에게 이전 찜이 승계되지 않는다.**

## 7. 손대지 않는 것

- **행동 기록의 찜·찜해제 이벤트**는 그대로 둔다. 개인화 신호이고 찜 목록과 별개다.
- **익명 카탈로그 호출 경로**를 계정 데이터용 경로로 바꾸지 않는다. 조각 1이 "둘을 섞지 말 것"을 못박아뒀다.
- 피드·검색·상세 화면.

## 8. 완료 기준 (돌려서 눈으로 확인)

1. 로그아웃 상태에서 ♡를 누르면 **찜되지 않고** 로그인 유도가 뜬다.
2. 로그아웃 상태에서 찜 목록에 들어가려 하면 **진입하지 못하고** 로그인 유도가 뜬다.
3. 로그인하면 ♡가 동작하고, 새로고침해도 남고, **다른 브라우저에서 같은 계정으로 로그인해도 같은 목록**이 보인다.
4. 비회원으로 N개를 찜해둔 기기에서 로그인하면 **그 N개가 계정 찜에 들어가 있고** 기기에는 남지 않는다.
5. A로 로그인해 찜한 뒤 로그아웃하고 B로 로그인하면 **A의 찜이 보이지 않는다.** A로 다시 로그인하면 그대로 있다.
6. 서버 저장이 실패하게 만들면 **하트가 되돌아가고** 알림이 뜬다.
7. 같은 상품을 빠르게 여러 번 누른 뒤 새로고침하면 **화면에 보이던 상태와 같다.**
8. 계정을 삭제하면 그 계정의 찜 행이 남지 않고, **삭제 직전 토큰으로 찜을 읽거나 쓸 수 없다.**
9. 피드 노출 조건에서 빠진 상품도 **찜 목록에는 보인다.**
10. 상한을 넘겨 찜하려 하면 거부되고 **이유가 보인다.**
11. 설정 화면에 "다음 업데이트에서 찜을 계정에 저장할 예정"이 더는 없다.

## 9. 자동 검증

- **단위**: 옮기기 판정(익명 → 사용자에서만 옮긴다), 상한 규칙, 마지막 의도가 이기는 규칙.
- **DB 통합(빈 스키마)**: 권한 행렬(비로그인 거부 / 남의 찜 접근 거부 / 본인만 허용), 상한, 중복 무시, **계정 삭제 시 연쇄**, 다른 사용자 생존.

## 10. 미정

- **상한 500이 맞는 값인지.** 지금 로컬 상한을 그대로 가져온 것이고 근거를 따로 재지 않았다.
- **비회원 찜 신호 소멸의 영향 크기.** 재볼지, 잰다면 무엇으로 잴지.
- **로그인 유도의 형태** — 그 자리에서 구글 로그인을 시작할지, 설정 화면으로 보낼지. 실제 화면을 보고 정한다.

## 11. 함께 고쳐야 하는 문서

- **결정 기록** — O-35에 "찜은 예외로 승계한다"를 명시.
- **PRD** — 찜이 계정 데이터가 되고 로그인이 필요해진다는 점.
- **데이터 수집·보존 방침 / 공개 처리방침** — 계정에 저장되는 항목에 찜이 추가된다. 계정 삭제 범위에도 포함된다.
