# 데이터 수집·보존 방침

> 근거 계획: [검색 0단계 평가 하네스](../../plans/2026-08-17-search-eval-harness.md) 1단계 — **방침 확정이 수집보다 먼저다.**

## 무엇을 수집하는가

| 구분 | 저장 위치 | 보존 | 비고 |
|---|---|---|---|
| 익명 기기 ID (localStorage UUID) | 기기 + 서버 기록의 키 | 사용자가 지울 때까지 | 계정·연락처와 연결되지 않는 가명 식별자 (O-24) |
| 행동 신호 (노출·탭·찜·세션 경계) | 서버 `c_events` | 무기한 | 개인화 평가·계측 전용. 프로필 계산은 기기가 한다 |
| 취향 프로필 (선호 요약) | **기기에만** | 사용자가 지울 때까지 | 서버로 보내지 않는다 |
| **검색어 원문·정규화 질의** | 서버 `c_search_logs` | **90일** | 아래 별도 항목 |

## 검색어 — 왜 원문을 저장하고, 무엇이 다른가

**목적**: 검색 품질을 재는 평가셋을 **실제 사용자가 치는 말**로 채우기 위해서다. 지금 평가 씨앗은 다른 제품(ecommerce)에서 가져온 것이라 aTee 사용자의 실제 입력 분포를 반영하지 못한다. 정규화 문자열이나 해시만으로는 이 목적을 달성할 수 없다.

**다른 데이터와 다른 점**: 행동 신호(노출·탭·찜)는 우리가 정의한 값만 들어오지만, **검색어는 사용자가 무엇이든 칠 수 있는 자유 텍스트**다. 의도치 않게 개인적인 내용이 들어올 수 있다. 그래서 다음을 적용한다.

- **보존 90일.** 만료된 기록은 자동으로 지운다. 무기한 보관하지 않는다.
- **길이 상한 200자.** 넘는 입력은 잘라서 저장한다.
- **기기 삭제 요청에 포함.** 설정의 초기화를 실행하면 그 기기의 검색어 기록도 함께 지워진다.
- **취향 프로필과 분리.** 검색어는 별도 테이블에 기록되며 추천 프로필 계산 경로에 들어가지 않는다.
- **anon 직접 접근 불가.** 검증·상한이 붙은 RPC로만 기록되고, 읽기는 허용하지 않는다.
- **고지.** 수집 범위가 늘었으므로 앱 고지 문구를 갱신하고, 이미 확인한 사용자에게도 배너를 한 번 다시 보여준다.

**수집하지 않는 것**: 이름·연락처·계정 정보를 직접 묻거나 저장하지 않는다. 검색어 원문에 그런 내용이 포함될 가능성은 있으며, 그것이 위 보존 기간·삭제 경로를 두는 이유다.

## 삭제

설정 화면의 초기화 버튼 한 번으로 다음이 모두 지워진다.

- 기기: 익명 ID, 세션, 미전송 큐, 취향 프로필
- 서버: 그 기기의 행동 신호(`c_events`)와 **검색어 기록(`c_search_logs`)**

서버 삭제가 실패해도 기기 쪽은 지워지고, 다음 접속에서 서버 삭제를 다시 시도한다.

## 만료 정리의 한계 (알려진 제약)

90일 만료 삭제는 **검색 기록 RPC가 호출될 때 유계로 함께 수행**한다. 별도 스케줄러(pg_cron 등)를 두지 않는 이유는 이 데이터베이스를 ecommerce 앱과 공유하고 있어 전역 확장 추가를 최소화하기 위해서다.

따라서 **검색이 전혀 일어나지 않으면 만료 행이 남아 있을 수 있다.** 트래픽이 끊긴 기간이 길어지면 수동으로 정리하거나 스케줄러 도입을 재검토한다. 이 한계를 알고 택한 절충이다.
