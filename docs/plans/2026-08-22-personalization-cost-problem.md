# 개인화 피드 비용 — 문제 진술 (2026-08-22)

> 상태: **문제 진술만.** 계획도 결정도 아니다. 원인 규명이 먼저다.
> 발견 경위: [성별 토글 0단계 실측](2026-08-21-gender-setting-toggle.md) ⑨·⑪ — 성별 작업을 재다가
> 이 기능과 무관한 기존 한계로 드러났다.

## 관측된 사실

프로덕션 psql 직접 호출, 앵커는 세션 5 + 장기 50(장기 상한이 50이므로 **열심히 쓴 사용자**에 해당),
seed 42, size 30. 원시 기록은 측정 산출물 `g0b-concurrent*.txt`.

| 조건 | 결과 |
|---|---|
| 단독 호출 | 0.5~0.8초 |
| **동시 4건** | 왕복 18.2~18.4초(현행) · 20.0~22.0초(성별 등식판) |
| 동시 4건의 **서버 실행 시간** | 43.2~43.5초 — 풀 대기가 아니라 **DB 연산**이다 |
| 앵커 없는 경우 동시 4건 | 각 ~920ms (문제 없음) |

**성별 등식이 원인이 아니다.** 현행도 같은 대역이고 등식은 약 20%를 더할 뿐이다.
**앵커가 없으면 드러나지 않는다** — 앵커를 많이 가진 사용자에게만 나타난다.

관련 크기(같은 인스턴스):

| | 크기 |
|---|---|
| `c_img_vecs` (이미지 벡터) | **1,808 MB** |
| `c_goods` | 347 MB |
| `c_search_docs` | 97 MB |
| `c_thumb_dims` | 40 MB |
| 인스턴스 RAM / `shared_buffers` | **1 GB / 224 MB** |

벡터 테이블 하나가 전체 메모리의 1.8배다.

## 왜 위험한가

실제 API 경로는 8초 제한이다. 위 요청들은 **실패**하고, 클라이언트는 개인화 실패를 무작위 피드로
폴백한다. 즉 **오류로 보이지 않고 개인화가 조용히 꺼진다.** 사용자에게는 "추천이 별로다"로만
느껴지고 로그에도 실패로 남지 않을 수 있다. (실제 경로로 관찰하지는 않았다 — **미확인**.)

## 언제 터지나

**동시 사용자 수가 임계에 닿을 때.** 지금은 전부 테스트 사용자라 동시 4건이 사실상 일어나지 않는다.
그래서 지금 당장의 결함은 아니다. 다만 사용자가 늘면 **가장 열심히 쓴 사용자부터** 개인화가 꺼진다 —
앵커가 많을수록 느리기 때문이다. 역진적이라는 점이 특히 나쁘다.

## 원인 가설 (전부 미확인 — 진단이 첫 단계다)

1. **벡터 힙이 캐시에 안 들어간다.** 1,808MB 대 `shared_buffers` 224MB. 동시 요청이 서로의 캐시를
   밀어내며 디스크를 반복해 읽는 그림.
2. **요청마다 앵커 수만큼 ANN 프로브를 돈다.** 앵커 55개면 프로브도 그만큼이다.
3. **`work_mem` 경쟁.** 믹스는 16MB, 유사는 64MB를 각자 잡는다. 동시 4건이면 그만큼 곱해진다.
4. **`ivfflat.probes = 40`** 이 동시성 하에서 과할 수 있다.
5. 인스턴스 크기(Micro) 자체.

## 검토할 대안

업계에서 이 문제를 푸는 골격은 **후보 생성과 순위를 나누고, 후보 생성을 미리 만들어 두는 것**이다.
아래는 우리 규모에 맞춰 옮길 수 있는 형태로 적은 것이며, **어느 것도 아직 고르지 않았다.**

### 가. 닮은 상품을 미리 계산해 표로 둔다 (효과가 가장 클 후보)

요청 시점에 벡터 검색을 하지 않고, **상품별 이웃 목록을 오프라인 배치로 만들어** 둔다. 사용자가
오면 그 사람의 앵커들에 대한 목록을 꺼내 합치고 정렬한다 — 벡터 연산이 인덱스 조회로 바뀐다.

- 규모 추산: 피드 자격 22.6만 개 × 이웃 50개 = **약 1,130만 행.** 상품번호 둘과 점수만 담는 좁은
  표라 수백 MB 수준.
- 배치는 오프라인이라 느려도 되고 새 상품만 증분으로 돌릴 수 있다.
- **성별과의 상호작용을 함께 정해야 한다** — 이웃 목록을 성별별로 나눠 만들지, 하나로 만들고 조회
  후 거를지. 성별 규칙이 확정된 뒤에 설계해야 하는 이유다.
- 대가: 이웃이 고정되므로 신선도·다양성 보정을 어디서 할지 다시 정해야 한다.

### 나. 요청에 쓰는 앵커 수를 줄인다

지금은 장기 50 + 세션 전부를 싣는다. 가중치 상위 N개(예: 10)만 쓰면 프로브 수가 그만큼 준다.
**가장 싸게 시도할 수 있는 대안**이지만, 추천 품질에 미치는 영향을 함께 봐야 한다.

### 다. 사용자별 후보 집합을 짧게 캐시한다

같은 사용자가 연속 페이지를 넘길 때 후보를 다시 계산하지 않는다. 무효화 규칙(행동 발생·성별 변경)을
정해야 한다.

### 라. 파라미터 튜닝

`ivfflat.probes`, `work_mem`, 후보 배수를 동시성 하에서 다시 잡는다. 성별 작업에서 후보 배수를
17 → 10으로 내리기로 한 것이 이 방향의 첫 조각이다.

### 마. 인스턴스 크기

가장 단순하지만 비용이 든다. 위 대안들을 재본 뒤 마지막에 판단할 문제다.

### 바. 전용 벡터 검색 분리

DB 밖의 ANN 서비스로 옮긴다. 가장 크고 되돌리기 어려운 변경이라, 앞의 것들이 부족할 때만 본다.

## 왜 성별 작업 뒤인가

- **지금 튜닝하면 다시 해야 한다.** 성별 작업이 같은 코드의 필터 의미를 바꾼다. 실제로 성별 0단계에서
  현행 의미로 잰 수치를 등식 의미로 전부 다시 쟀다.
- **성별 작업이 이 문제를 조금 낫게 한다.** 후보 배수를 17 → 10으로 내리므로 요청당 비용이 준다.
- **성별은 준비됐고 이 문제는 진단이 안 됐다.** 원인을 모르는 일을 준비된 일 앞에 끼우면 둘 다 늦는다.
- **대안 가는 성별 규칙이 확정돼야 설계할 수 있다**(이웃 목록을 성별별로 나눌지가 걸린다).

## 다음 단계

성별 작업이 끝난 뒤, **진단부터** 한다. 위 가설 1~5 중 무엇이 지배적인지 실측으로 가르고, 그 결과로
대안을 고른다. 진단 없이 대안부터 고르지 않는다.

성별 작업 구현 중 남기기로 한 지표(웜 p95, 8초 내 성공률, 설정 변경 후 첫 유효 요청까지의 시간)가
이 진단의 출발 데이터가 된다.
