# 계획 — FOR YOU 개인화 (큐레이션 57개 중 6장을 골라 띄운다)

> 상태: 초안 5차 (2026-08-20) · 1·2단계 완료
> 브랜치: `feature/foryou-visible-six` (origin/develop v0.1.14 기준) · 계획 규칙 = [AGENTS.md](../../AGENTS.md) "계획 작성 규칙"
> 쿼리: [`backend/db/tag_survey.sql`](../../backend/db/tag_survey.sql) · 실측 결과는 맨 아래 "조사 기록"

## 배경 (이 repo를 모르는 사람을 위한 설명)

aTee 홈에는 가로로 미는 칸이 두 개 있다.

- **BROWSE** — 티셔츠 22.6만 개를 훑는 무한 스크롤 피드. **이미 개인화되어 있다.** 사용자가 찜하거나 열어본 상품을 기기에 "앵커"(상품 번호 + 가중치)로 기억해두고, 다음 페이지에 그 앵커와 사진이 닮은 상품을 섞어 준다.
- **FOR YOU** — 주제별 큐레이션을 BROWSE와 같은 2열 모자이크로 깐다. 카드를 누르면 상품 9장이 가로 슬라이드로 넘어간다. **누가 열어도 똑같다.**

칸 이름이 바뀌었어도 사정은 같다 — 그 사람을 위한 것이 아니다.

**큐레이션은 손으로 상품을 고른 것이 아니라 규칙으로 뽑은 것이다.** 데이터베이스의 `curations` 테이블에 큐레이션마다 규칙(`rules`)이 들어 있고 — 예를 들어 "고양이" 큐레이션은 *제목에 고양이·캣·냥이 들어간 상품* — 생성 스크립트가 그 규칙을 SQL 조건으로 바꿔 상품을 뽑아 앱에 실을 파일을 만든다. 규칙에는 제목·태그 키워드 외에 색, 리뷰 AI 요약, 실측 치수 조건도 쓸 수 있다.

## 조사에서 드러난 것 (이 계획의 출발점)

1. **큐레이션이 데이터베이스에 57개 있는데 앱에는 28개만 실려 있다.** 29개가 전부 `active` 상태인데도 쓰이지 않고 있다. 생성 스크립트는 활성 큐레이션을 전부 읽게 되어 있으므로, **다시 돌리기만 하면 57개가 실린다.**
2. **상품 태그로는 주제를 나눌 수 없다.** 태그는 상품의 75.4%에 평균 6개씩 붙어 있지만 대부분 "반팔티·티셔츠·오버핏" 같은 동어반복이고, 주제를 가르는 태그를 하나도 못 가진 상품이 **52%**다. 반면 규칙(제목 기반)은 같은 주제를 훨씬 넓게 잡는다 — "고양이"가 태그로는 302건, 규칙으로는 1,151건.
3. **그래서 개인화가 싸진다.** "내가 찜한 상품이 어느 큐레이션 규칙에 걸리나"만 물으면 되고, 이는 찜한 상품 몇 개에 대해서만 규칙을 판정하는 일이라 카탈로그 전체를 훑지 않는다.

## 무엇을 한다

**큐레이션은 많이 만들어 두고, 화면에는 그 사람용 몇 장만 띄운다.**

1. **큐레이션을 전부 앱에 싣는다.** 화면에 다 나오지는 않지만 고를 재료가 된다. — *1단계에서 61개 완료*
2. **FOR YOU 화면에는 6장만 띄운다.** 그 사람이 찜하고 열어본 상품이 걸리는 큐레이션 중 점수 높은 순으로 고른다.
3. **나머지는 맨 아래 "더보기"로 접어 둔다.**

### 확정된 결정 (2026-08-20 제품 책임자)

- **화면에 6장만.** 61장을 다 깔지 않는다. 이유: 다 깔면 아래쪽 수십 장은 아무도 안 본다. 몇 장만 고르는 행위 자체가 개인화이므로, 따로 "내 취향" 구역을 두어 구분할 필요도 없어진다 — **보이는 것이 전부 그 사람용이다.**
- **나머지는 맨 아래 "더보기".** 만들어 둔 것이 묻히지 않게 통로는 남긴다.
- **점수 = 좁은 큐레이션에 가산점.** 맞히기 어려운 큐레이션일수록 걸렸을 때 점수를 많이 준다. 이유: 그러지 않으면 "여름에 입는 얇은 반팔"(8,180건)처럼 넓은 큐레이션이 거의 모든 사람에게 걸려 항상 뽑히고, 개인화가 아니라 인기순이 된다.
- **갱신 = FOR YOU를 열 때마다.** 찜하고 탭을 넘어오면 바로 반영된다.
- **신규 사용자는 기본 순서 상위 6장.** 화면이 비지 않는다.

> **폐기된 결정 (같은 날 오전):** "맨 위에 내 취향 구역 + 구분선, 아래는 전체 목록". 화면에 6장만 띄우기로 하면서 구분선이 의미를 잃었다.

## 무엇을 하지 않는다

- 큐레이션 안에 담기는 상품을 사람마다 다르게 만들기 (규칙으로 뽑힌 목록 그대로 쓴다)
- 취향 기반 큐레이션 자동 생성
- "더보기"를 편 뒤의 목록 순서 변경
- BROWSE 피드 로직 변경
- 새 큐레이션 규칙 추가 (61개로 시작한다. 부족하면 그때 별도 작업)

## 제약

- **기존 동작 회귀 금지.** FOR YOU의 목록 ↔ 큐레이션 상세 전환, 뒤로가기, 스크롤 복원, 상품 상세 열기는 그대로 동작해야 한다.
- **개인화인 척하지 않는다.** 걸린 큐레이션이 없거나 서버가 실패·지연되면 **기본 순서 6장**을 보인다. 그것이 정상 화면이다.
- **처음 오는 사람도 볼 것이 있다.** 찜한 게 없어도 기본 순서 6장이 뜬다. 화면이 비지 않는다.
- **서버 접근 원칙.** 익명 키로 원본 테이블 직접 조회 금지 — 읽기는 뷰 또는 검증·상한이 붙은 RPC로만. 조작된 입력에 오류나 자원 소모가 나지 않아야 한다. `curations` 테이블은 지금 익명에 열려 있지 않다.
- **DB 성능 여건.** 인스턴스가 작아 캐시에 없는 조회가 몇 초씩 걸린 전례가 있다. 규칙 판정은 찜한 상품 몇 개에만 적용되므로 가벼울 것으로 보지만 — **가정이며 3단계에서 실측한다.**
- **첫 화면은 서버가 그린다.** 서버는 그 사람의 취향을 모르므로 첫 그림은 기본 6장이다. 개인화된 6장으로 바뀌는 순간이 화면이 튀는 것으로 보이지 않아야 한다.
- **파일 크기.** 큐레이션 데이터는 화면에 6장만 나와도 앱 파일에는 61개가 다 실린다(더보기 때문). 1단계 결과 241KB.
- **품질 게이트.** `frontend/`에서 `npm run check`와 테스트 통과.

## 단계와 완료 기준

### 1. 큐레이션을 전부 앱에 싣는다 — ✅ 완료 (57개, upstream `#67`이 처리)

생성 스크립트를 다시 돌려 앱에 실리는 큐레이션 데이터를 새로 뽑는다. 스크립트는 활성 큐레이션을 전부 읽게 되어 있으므로 추가 작업 없이 전부 나온다. 새로 들어오는 것(머슬핏·롤업·오프숄더·검정만·니트티·레이어드·Y2K·자수·골지·파스텔·레터링·포켓티·냉감·메쉬·배색·명화·빨강만·곰토끼·아웃도어/스포츠/SPA 브랜드·신상 등)의 상품이 제대로 뽑혔는지 눈으로 확인한다.

- **완료 기준:** FOR YOU를 열면 카드가 **28장에서 61장으로 늘어난 것이 보인다.** 새로 들어온 큐레이션 중 최소 다섯 개를 열어 상품이 제목과 맞는지 확인한다(예: "검정 하나로만 이뤄진 반팔"에 검정이 아닌 것이 섞여 있지 않은지). 앱 파일이 얼마나 커졌는지 숫자로 기록한다. 기존 화면 동작(상세 열기·뒤로가기·스크롤)은 그대로다.

### 2. 화면을 6장으로 줄이고 "더보기"를 단다 — ✅ 완료

먼저 **고르는 방식과 무관하게** 화면 구조부터 바꾼다. 기본 순서 상위 6장만 띄우고 나머지는 "더보기"로 접는다. 이 단계에는 개인화가 없다 — 누가 봐도 같은 6장이다.

먼저 하는 이유: 화면이 61장에서 6장으로 줄어드는 변화 자체가 크고, 여기서 깨지는 것(스크롤 복원·뒤로가기)을 개인화와 섞어 디버깅하지 않기 위해서다.

- **완료 기준:** FOR YOU를 열면 **카드가 6장만** 보이고 맨 아래에 "더보기"가 있다. 더보기를 누르면 나머지가 이어서 나온다. 큐레이션을 열고 뒤로 가면 보던 자리로 돌아온다. 더보기를 편 상태에서 상세를 열었다 뒤로 와도 편 상태가 유지되는지 확인한다.

### 3. 6장을 그 사람 것으로 채운다

내가 찜하고 열어본 상품이 어느 큐레이션 규칙에 걸리는지 판정하는 경로를 만들고, 점수 상위 6장을 띄운다. 점수는 좁은 큐레이션에 가산점을 준다. FOR YOU를 열 때마다 다시 계산한다.

이 단계에서 정할 것(미정 참고): 가산점을 어떻게 계산할지, 찜한 상품을 몇 개까지 볼지, 찜과 단순 열람에 다른 무게를 줄지, 걸린 것이 6장보다 적을 때 나머지를 무엇으로 채울지, 판정을 서버 어디에 둘지.

- **완료 기준:** 저장소를 비운 새 기기에서 FOR YOU를 열면 **기본 순서 상위 6장**이 보인다(2단계와 같은 화면). 고양이 티를 몇 개 찜하고 FOR YOU를 열면 그 6장 안에 **"고양이 그림 하나로 밀고 가는 티"가 들어와 있다.** 검정 무지 티를 찜하면 "검정 하나로만 이뤄진 반팔"이 들어오고, 이때 "여름에 입는 얇은 반팔" 같은 넓은 큐레이션에 밀리지 않는다. 서버 응답을 강제로 실패시키면 기본 6장이 나오고 화면이 깨지지 않는다. 판정에 걸린 시간을 숫자로 기록한다.

### 4. 마무리 — 검증·기록

브라우저(가능하면 iOS 시뮬레이터도)에서 전체 흐름을 확인하고, 실측치와 확인 결과를 이 문서 실행 기록에 남긴다. `npm run check`와 테스트를 통과시킨다.

- **완료 기준:** 확인 결과(스크린샷 또는 수치)가 이 문서에 적히고, 품질 게이트가 통과한다. 개인화된 6장이 뜬 경우와 기본 6장이 뜬 경우를 나중에 구분해 볼 수 있는 흔적이 남는다.

## 3단계 결정 (2026-08-21 · 미정이던 것을 정한 결과)

| 미정이던 것 | 정한 것 | 이유 |
|---|---|---|

| 판정에 쓰는 무게 | **BROWSE 앵커 가중치 그대로** (탭 1 · 스타일탐색 2 · 찜 4 · 판매처 이동 6) | 두 화면이 같은 취향을 봐야 한다. 새 무게 체계를 또 만들 이유가 없다 |
| 앵커 개수 | **장기 50 + 세션 20 전부** (제목 조회는 1회 70건 상한) | 이미 상한이 걸린 목록이라 따로 자를 필요가 없다 |
| 6장이 안 찰 때 | **기본 순서로 잇는다** | 계획 제약 "화면이 비지 않는다" |
| 더보기 뒤 순서 | **점수 순 → 기본 순서**로 이어진 같은 배열 하나 | 목록이 두 벌로 갈리지 않는다 |
| 기본 6장 → 개인화 6장 전환 | **제목을 localStorage에 캐시**해 두 번째 방문부터 마운트 즉시 정렬 | 조회를 기다리는 동안 바뀌는 것이 화면 튐으로 보인다. 제목은 안 바뀌므로 캐시가 안전하다 |
| 계측 | **이번엔 붙이지 않는다** | 개인화가 걸렸는지는 화면에서 바로 보인다. 필요해지면 BROWSE 이벤트 체계에 붙인다 |

**남은 한계 (의도한 것):**
- 색·리뷰수·실측 치수 조건은 기기가 판정하지 못한다(그 정보가 기기에 없다). 그래서 판정이 실제 큐레이션보다 **조금 넓다** — 고르는 데만 쓰고 큐레이션 내용은 그대로라 넓은 쪽이 안전하다.
- DB 61개 중 **제목 키워드가 있는 39개**만 개인화에 걸린다. 랭킹·색 전용·브랜드 전용 22개는 기본 순서 자리에 남는다.
- 비회원은 개인화되지 않는다(앵커를 쌓지 않는 결정 O-37). 기본 6장이 정상 화면이다.

## 실행 기록

### 1단계 — 큐레이션 57개 (upstream이 이미 처리)

`origin/develop`의 `#67 큐레이션을 슬라이드로 바꾸고 축을 57개로 늘린다`가 이 단계를 이미 끝내 두었다. **이 계획을 세울 때 그 커밋들을 pull하지 않아, 낡은 기반에서 같은 일을 다시 했다가 버렸다.** 그때 생성한 61개짜리 데이터는 슬라이드 UI가 쓰는 장 제목(`head`)·아쉬운 점(`con`)·상황 색(`accent`)이 없어 upstream보다 뒤떨어진 버전이었다. 커밋하지 않고 폐기했고, 낡은 워크트리는 손대기 전 상태로 되돌렸다.

**남길 것:** 큐레이션 정의 적재(`--seed`)는 `delete from curations` 후 다시 넣는다. **적재 중에 생성 스크립트를 돌리면 잘린 결과가 조용히 나온다** — 실제로 61개 중 32개만 뽑힌 적이 있다.

### 3단계 완료 — 개인화 6장 (2026-08-21)

내가 반응한 상품의 **제목**으로 큐레이션 키워드 규칙을 판정해, 걸린 큐레이션을 앞으로 세운다. BROWSE 피드와 **같은 앵커·같은 가중치**를 쓴다.

- **규칙 파일을 따로 뽑았다** (`backend/scripts/gen_curation_rules.py` → `curation-rules.json`, 4.8KB). DB 61개 중 제목 키워드가 있는 39개, 전부 앱의 57개 안에 있다.
  - ⚠️ **`gen_curation_page.py`를 다시 돌리지 않았다.** 그 스크립트는 `curations.json`을 통째로 덮어쓰는데 사람이 쓴 슬라이드 제목 488장(`head`)을 만들지 못한다 — 같이 돌리면 지워진다. 그래서 규칙만 별도 파일로 뽑는 스크립트를 새로 뒀다.
- 점수 = Σ(걸린 앵커 가중치) × `log(226,000 / 큐레이션 건수)`.
- 제목은 `c_feed_products` 뷰에서 in-list 1회로 받고 localStorage에 캐시한다(성별 보강이 이미 쓰는 경로). 두 번째 방문부터는 조회 없이 마운트 즉시 정렬된다.
- 제목 캐시는 `clearProfile()`에서 같이 지운다 — 어떤 상품에 반응했는지가 남아 있어, 앵커만 지우면 초기화가 절반만 된다.

**확인한 것:**
- 실제 `curations.json` + `curation-rules.json`으로 돌려본 결과 — 고양이 티 2개를 찜한 앵커로 **"고양이 그림 하나로 밀고 가는 티"가 1번**. 무지 티 앵커로는 28건·444건짜리 좁은 큐레이션이 2,003건짜리보다 앞. IDF가 의도대로 작동한다.

### 2단계 완료 — 6장 + 더보기 (2026-08-20)

FOR YOU 첫 화면을 앞의 6장(2열 × 3줄)으로 줄이고, 나머지는 그 아래 `더보기 51개`로 접었다. 개인화는 아직 없다 — 누가 봐도 같은 6장이다.
