# 개인화 피드 깊이 — 후보풀 커서 구현 계획 (2026-08-22)

설계 근거: [스펙](../superpowers/specs/2026-08-22-feed-depth-cursor-design.md).
이 계획은 코드 없이 순서와 단계별 완료 기준만 적는다.

## 무엇을 만드나 (이 repo 문맥을 모르는 독자용)

aTee의 홈 피드는 무한 스크롤이다. 로그인해서 행동이 쌓인 사용자에게는 **개인화 믹스**
(서버 함수 `c_mix_page`)가 한 페이지 30장을 만들어 준다. 그 30장은 다섯 버킷에서 온다 —
세션·장기(사용자가 본 상품과 이미지가 닮은 것, 벡터 검색), 부분·반대·다양성(후보풀에서
색·그래픽 규칙으로 고른 것).

후보풀은 카탈로그를 시드 해시(`hk`) 순으로 정렬한 **상위 1,200개**다. 클라이언트는 이미 본
상품 번호를 **제외 목록**으로 실어 보내 중복을 막는데, 그 목록에 **최근 600개만** 담는다.

문제: 630개를 본 뒤로는 **새 상품이 하나도 안 나온다.** 가장 먼저 본 30개가 제외 목록에서
빠지는 순간 `hk`가 가장 낮아 목록 맨 앞으로 돌아오기 때문이다. 무작위 경로(`c_feed_page`)는
제외 목록 대신 **키셋 커서**를 써서 같은 문제가 없다(40페이지 1,200장 전부 고유).

이 작업은 그 커서를 개인화 믹스에도 가져온다.

검증 가설은 하나다: **후보풀에 커서를 붙이면 개인화 피드가 카탈로그 깊이만큼 새 상품을
계속 내놓는다.**

## 배포 단위 — 이번엔 DB를 먼저 올려도 된다

성별 작업과 다르다. 새 인자는 **널 기본값**이고, 없으면 "첫 페이지"라는 **올바른 동작**이다
(성별처럼 필터가 꺼지는 것이 아니다). PostgREST는 이름으로 인자를 맞추므로, 커서를 안 보내는
옛 클라이언트도 새 함수에 그대로 매칭된다. 반환 열이 하나 늘지만 옛 클라이언트는 이름으로
매핑하므로 무시한다.

따라서 **마이그레이션을 먼저 적용해도 안전하고**, 클라이언트는 뒤따라 배포하면 된다.
그래도 한 번에 병합·배포하는 편이 되돌리기 쉽다 — 순서에 여유가 있다는 뜻이지 나누라는
뜻은 아니다.

## 1단계 — 서버: 후보풀에 커서를 붙인다

- **무엇을**: `c_mix_page`에 **커서 인자**(널 기본값)를 더한다. 후보풀이 "맨 앞 1,200개" 대신
  **"커서 다음부터 1,200개"** 를 뜨게 한다. 반환에 **다음 커서 열**을 더해, 이번 페이지에서
  **후보풀 계열 버킷(부분·반대·다양성)이 고른 것들의 최대 `hk`** 를 담는다.
  - 후보풀에서 아무것도 안 골랐으면(벡터만으로 페이지가 찼으면) **받은 커서를 그대로 돌려준다** —
    전진하지 않는다.
  - 커서가 널이면 지금과 완전히 같은 동작이다(첫 페이지).
- **반드시 함께**: 반환 열이 바뀌므로 덮어쓰기로는 안 된다 — **지우고 다시 만든다.** 소유자·
  권한(`anon`·`authenticated`)과 함수 설정(`search_path=public, extensions`,
  `work_mem=16MB`)을 다시 부여한다. 성별 작업에서 함수 설정이 조용히 사라지는 것을 겪었으므로
  옮긴 뒤 다시 조회해 확인한다.
- **주의**: 커서는 "창의 끝"이 아니라 **고른 것들의 최대 `hk`** 다. 창 끝으로 잡으면 페이지마다
  1,200개를 통째로 건너뛰어 카탈로그를 77페이지 만에 소진하면서 정작 보여준 것은 페이지당
  15장뿐인 낭비가 된다.
- **완료 기준**: psql 직접 호출로 —
  1. 커서 없이 부르면 지금과 같은 30장이 나온다.
  2. 응답의 커서 열이 후보풀 계열 상품들의 최대 `hk`와 같다.
  3. 그 커서를 다시 넣어 부르면 **1페이지와 겹치는 상품이 0건**이다.
  4. 커서를 이어가며 **100페이지**를 받으면 누적 고유 **3,000장, 중복 0**.
  5. 옛 호출 형태(커서 없음, 7인자)가 그대로 동작한다 — 배포 중간 상태 확인.
  6. `\df`로 옛 시그니처가 남지 않았고 함수 설정이 보존됐음을 본다.

## 2단계 — 서버: 벡터 버킷이 마르는 지점을 관찰한다

- **무엇을**: 1단계 함수로 커서를 이어가며 페이지마다 **버킷별 반환 수**를 기록한다. 세션·장기
  버킷이 몇 페이지에서 줄기 시작하는지, 그때 다양성 버킷이 그만큼 메워 **30장이 유지되는지**
  본다. 지금까지는 제외 절벽에 가려 21페이지까지밖에 못 봤다.
- **판정**: 벡터가 마른 뒤에도 30장이 유지되면 설계대로다. 페이지가 짧아지면 **중단하고
  보고**한다 — 다양성 backfill이 기대대로 동작하지 않는다는 뜻이다.
- **완료 기준**: 벡터 버킷이 줄기 시작한 페이지 번호와, 그 이후 페이지의 장수·버킷 구성이
  이 계획 파일이나 커밋 메시지에 수치로 적혀 있다.

## 3단계 — 클라이언트: 커서를 왕복시킨다

- **무엇을**: 개인화 요청에 커서를 실어 보내고, 응답의 커서를 다음 요청까지 들고 있는다.
  응답 행마다 같은 값이 실려 오므로 **첫 행에서 읽으면 된다**(행이 없으면 들고 있던 값 유지).
- **버리는 시점**: 성별이 바뀌면(피드 훅의 기존 세대 교체) **커서도 초기화한다** — 후보풀
  구성이 통째로 달라지므로 이어가면 안 된다. 시드가 바뀌는 경우도 같다.
- **제외 목록**: 그대로 둔다. 후보풀은 커서가 막지만 **벡터 버킷은 여전히 제외 목록이 필요**하다
  (`hk` 순서가 아니라 유사도 순이라 커서로 못 막는다). 상한 600도 그대로 둔다 — 이 조각의
  가설은 "커서가 깊이를 회복한다"이지 "제외 목록을 손본다"가 아니다.
- **완료 기준**: 단위 테스트로 —
  1. 첫 요청에는 커서를 안 싣고, 응답의 커서를 다음 요청에 싣는다.
  2. 응답에 행이 없으면 들고 있던 커서를 유지한다.
  3. 성별이 바뀌면 다음 요청에 커서를 안 싣는다.
  4. `npm run check`와 기존 테스트 전체가 통과한다.

## 4단계 — 브라우저 확인

- **무엇을**: Aside 브라우저로 개인화가 걸린 계정에서 홈을 오래 스크롤한다.
- **완료 기준**:
  1. 스크롤을 계속해도 **새 상품이 계속 나온다** — 화면에 뜬 상품 번호를 모아 중복이 없음을
     확인한다(이전 측정은 40번 스크롤에 고유 308개였고 증가가 멎었다).
  2. 설정에서 성별을 바꾸면 처음부터 다시 시작한다.
  3. 요청에 커서가 실려 나가는 것을 네트워크에서 확인한다.

## 5단계 — 검증 기록

- **무엇을**: 위 완료 기준의 결과를 수치로 적고, **안 돌려본 것은 "미검증"으로 명시**한다.
- 남길 지표: 100페이지 누적 고유 수·중복 수, 벡터 버킷이 마르는 페이지, 그 이후 페이지의 장수,
  응답 시간(커서 유무 비교, 웜 평균과 최대).
- **완료 기준**: 위 수치가 이 파일에 적혀 있고, 문제 진술 문서
  (`2026-08-22-personalization-cost-problem.md`)의 "두 번째 관측"에 **해결됨 표시와 결과 링크**가
  달려 있다.

## 범위 밖

- **벡터 버킷의 앵커 회전** — 앵커가 고정인 한 ANN 이웃은 유한하다. 별도 가설이다.
- **동시 4건 43초** — 같은 문서의 다른 관측이고 진단부터 필요하다.
- **제외 목록 상한 조정** — 커서가 후보풀을 맡으면 이 상한의 의미가 줄지만, 줄이는 것은 별도
  판단이다.
- 무작위 경로(`c_feed_page`)와 유사(`c_similar_page`)는 건드리지 않는다.

## 미정

- 후보풀 창 크기(1,200)를 그대로 둘지 — 커서가 붙으면 창을 줄여도 되지만, 줄이면 버킷 규칙
  (색 교집합·그래픽 반전)을 만족하는 후보가 창 안에 없어 페이지가 짧아질 수 있다. 2단계 관찰
  결과를 보고 정한다.
