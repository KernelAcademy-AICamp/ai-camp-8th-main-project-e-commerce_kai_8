# 검색 A단계 — 한국어 색인·관련도 정렬 (구현 계획)

> 설계: [검색 업그레이드 설계안](../superpowers/specs/2026-08-17-search-upgrade-design.md) §7 A · 상태: 착수 전
> 선행: [0단계 평가 하네스](2026-08-17-search-eval-harness.md) — 기준선이 있어야 이 단계의 성공을 말할 수 있다.
> 이 계획은 A단계 하나만 다룬다. B·C·D·E는 각자 계획을 갖는다.

## 목표

**오타·한영 자판·초성·띄어쓰기 변형이 걸리고, 결과가 관련도순으로 정렬되는 것.**

0단계 기준선이 보여준 것: 브랜드 정확 질의(G1)는 0건율 0%로 멀쩡하지만, **표기 변형(G3)은 72%, 문장(G4)은 95%, 부정(G5)은 100%가 0건**이다. A단계는 이 중 **G3(P@20 15.6%)와 G2(58.2%)**를 겨냥한다. G4·G5는 B·D의 몫이다.

**비교점은 진행셋 기준선 38.0%**다(전체 127건 기준선 27.8%와 비교하면 서로 다른 표본이 된다 — [기준선 보고서](../atee/eval/baseline-report.md) 참고).

## 사전 점검 결과 (2026-08-17, 읽기 전용 조회로 확인)

| 항목 | 결과 |
|---|---|
| PGroonga | **3.2.5 사용 가능**, 아직 미설치 |
| pg_bigm | **없음** — 대안이 PGroonga뿐이다 |
| PostgreSQL | 17.6 |
| 접속 롤 | `postgres`, superuser 아님 (Supabase 관리형) |
| pg_cron | **이미 설치·사용 중** (`prewarm_c_img_vecs_bq_idx`, `c_search_logs_retention`) |

**형태소 분석기(TokenMecab)의 가용성은 설치 전에는 알 수 없다.** 설치 직후 확인하고, 없으면 n-gram만 실측 대상으로 한다(설계 §11).

## 하지 않는 것

- 벡터 검색(B)·질의 이해(D)·속성 보강(C)을 건드리지 않는다. 이 단계는 **텍스트 갈래 하나**만 만든다.
- 검색 UI를 바꾸지 않는다(E).
- **개인화 가산점을 아직 넣지 않는다.** 설계 §5.5의 프로필 동결이 함께 필요해 B단계 이후로 미룬다.

## 0단계 — 성능 합격 상한 먼저 정하기

> 구현 리뷰 지적: 지연 상한을 색인·정렬이 다 끝난 뒤에 정하면 **공유 DB에 안 맞는다는 사실이 너무 늦게 드러난다.** 숫자를 먼저 못박고 시작한다.

**무엇을**

- 갈래별 응답 상한·전체 응답 상한·허용 폴백률을 **숫자로** 정한다.
- 미달일 때 무엇을 할지(컴퓨트 상향 / 갈래 축소 / 되돌리기)를 미리 정한다.
- 기존 실측을 비교 기준으로 삼는다 — 벡터 경로가 동시 4요청에서 각 16~18초로 이미 한계를 넘었고, anon SQL 제한은 8초다.

**완료 기준**

- 상한 숫자와 미달 시 행동이 문서에 있다. **이 문서 없이 1단계를 시작하지 않는다.**

---

## 1단계 — 확장 설치와 공유 DB 영향 점검

> ⚠️ **이 DB는 ecommerce 앱과 공유한다.** 확장 설치는 DB 전역이고, 색인 빌드의 디스크·WAL·I/O가 그쪽에 영향을 준다(설계 §10). **사람의 승인 없이 실행하지 않는다.**

**무엇을**

- 설치 전에 정한다: 예상 색인 크기, 실행 시간대(저부하 창), 실패 시 정리 절차, **"확장은 남기고 c_* 색인만 롤백"** 절차.
- ecommerce 쪽에 영향이 갈 수 있는 시간대를 피해 실행한다.
- 설치 직후 **TokenMecab(한국어 형태소) 가용성**을 확인하고 결과를 기록한다.
- 전역 확장을 삭제하는 구문은 절대 넣지 않는다.

**완료 기준**

- 확장 버전·설치 시각·실행 창이 기록되고, **ecommerce 쪽 이상 없음이 확인**된다.
- TokenMecab 가용 여부가 기록되어 2단계의 토크나이저 후보가 확정된다.

---

## 2단계 — 검색 텍스트 재설계와 색인

**무엇을**

- 검색 텍스트를 **필드별로 나눈다**(설계 §6 C3, 2차 리뷰 M9). 브랜드·제목·태그를 한 문자열로 합치면 브랜드 정확 매칭을 우대할 수 없어 "브랜드 회귀 없음" 기준과 충돌한다.
- **shadow table 원자 교체**로 만든다(2차 리뷰 M6). 현행 `c_search_text`는 drop 후 재생성 계약이라 그대로 두면 갱신 때 색인이 사라진다. 새 테이블 → 동일 색인·RLS·grant 구성 → 원자 교체, 그리고 **검색 RPC도 같은 트랜잭션에서 재작성·검증**한다(이름 교체만으로는 의존 객체가 새 테이블을 본다고 보장할 수 없다).
- 토크나이저 후보(형태소 vs n-gram)를 **개발셋으로 실측 비교**하고 고른 이유를 기록한다.
- 노출 자격(`card_ok` 등)은 지금과 동일하게 유지한다.

**완료 기준**

- 색인이 걸린 검색 텍스트가 만들어지고, **갱신 절차를 한 번 돌려도 색인이 살아 있다**(실제로 재생성해 확인).
- 토크나이저 선택 근거가 수치와 함께 기록된다.

---

## 3단계 — 질의 정규화 확장

**무엇을**

- 프론트·서버가 **같은 규칙**을 쓴다는 기존 계약을 유지한 채 확장한다: 한영 자판 복원, 자모 정규화(NFC), 초성 질의 감지, 어휘 사전 기반 편집거리 오타 후보.
- 어휘 사전은 브랜드명·태그·카테고리에서 만든다.
- **색인 엔진 전용 escape를 쓴다**(2차 리뷰 M7). 기존 LIKE용 escape는 통하지 않고, 전문검색 연산자는 자체 질의 문법을 해석한다. **사용자 입력에 질의 문법을 허용하지 않고** 전용 escape를 통과시킨다. 연산자 수·오타 후보 수 상한도 정한다.
- 0단계가 만든 G3 항목은 각각 `origin`(원본 질의)을 갖는다 — **원본은 되는데 변형이 안 되는 것**을 바로 짚을 수 있다.

**완료 기준**

- `아디다스`가 되면 `dkelektm`·`ㅇㄷㄷㅅ`·`아디다드`도 된다.
- `반팔 티`와 `반팔티`가 같은 결과를 낸다.
- 질의 문법 문자를 넣어도 검색 의미가 바뀌지 않는다.

---

## 4단계 — 관련도 정렬과 커서 계약

**무엇을**

- 정렬을 `goods_no` 오름차순에서 **관련도순**으로 바꾼다. 브랜드 정확 일치를 우대하는 가중치를 필드별로 준다.
- **커서는 A단계에 필요한 만큼만 만든다.** 설계 §5.4의 융합 커서(모드·고정 집합·제외 조건)는 갈래가 둘 이상일 때 필요한 것이고, A단계는 텍스트 하나뿐이다. 지금 전부 만들면 B의 실제 융합 구조가 확정되기 전에 계약을 굳혀 재작업이 된다(구현 리뷰 YAGNI 지적). **다만 커서를 나중에 확장할 수 있는 형태로 둔다** — 숫자 하나가 아니라 구조를 주고받게 한다.
- **새 RPC를 병행 배포**한다(2차 리뷰 M11). 구 RPC와 기존 검색 텍스트를 일정 기간 유지해 캐시된 구버전 클라이언트가 깨지지 않게 한다.

**완료 기준**

- 브랜드 질의의 상위 결과가 그 브랜드로 채워진다.
- **연속 페이지에서 중복·누락 0**이 테스트로 확인된다.
- 구버전 클라이언트가 그대로 동작한다.

---

## 4-1단계 — 클라이언트 전환

> 구현 리뷰 지적: 새 RPC가 구조화된 커서를 돌려주는데 **현재 프론트는 숫자 커서와 구 RPC만 이해한다.** 이 작업이 계획에 없으면 A단계가 화면에 반영되지 않는다.

**무엇을**

- 검색 데이터 계층이 새 RPC와 새 커서 형태를 다루게 바꾼다.
- 뷰모델의 페이징 상태를 새 커서에 맞춘다. 기존 무한 스크롤·복원 동작은 유지한다.
- 구 RPC로 되돌릴 수 있게 전환을 끄고 켤 수 있게 한다.

**완료 기준**

- 화면에서 검색했을 때 **새 경로의 결과가 보이고**, 무한 스크롤·검색 해제·스크롤 복원이 그대로 동작한다.
- 전환을 끄면 즉시 구 경로로 돌아간다.

---

## 5단계 — 성능 게이트

> 상한은 0단계에서 이미 정했다. 여기서는 재고 판정한다 — 설계 §10이 "아직 게이트가 아니다"라고 남긴 것이 여기서 닫힌다.

**무엇을**

- **0단계에서 정한 상한**에 대고 잰다: cold/warm p50·p95, 동시 2·4요청, DB CPU·버퍼·temp spill, timeout·폴백 발생률.
- 기존 실측(ANN `c_mix_page` 동시 4요청 각 16~18초 — Micro 공유 CPU 포화)을 비교 기준으로 삼는다.

**완료 기준**

- 상한이 문서에 숫자로 있고, 실측이 그 안에 든다. 미달이면 컴퓨트 상향 또는 갈래 축소 **결정과 근거가 기록**된다.

## 6단계 — 평가

**무엇을**

- 개발셋으로 튜닝한다(가중치·토크나이저·오타 후보 수).
- 튜닝이 끝난 뒤 **진행셋을 한 번 연다.** 열람을 `query-set.json`의 `openLog`에 기록한다.
- 홀드아웃은 열지 않는다.

**완료 기준**

- **G3·G2가 기준선 대비 오르고, G1이 떨어지지 않는다.**
- 계열별 점수와 함께 채점자 일치도를 적는다.
- 자격 누출(비노출 상품 재등장) 0건.

---

## 전체 완료 기준

- 표기 변형이 걸린다(자판·초성·띄어쓰기·오타).
- 결과가 관련도순이고 브랜드 정확 질의가 회귀하지 않는다.
- 성능 상한이 숫자로 정해지고 실측이 그 안에 든다.
- 갱신 절차를 돌려도 색인이 살아 있다.
- 구버전 클라이언트가 깨지지 않는다.

## 미정

1. **색인 실행 창과 ecommerce 영향 허용 범위** — 1단계 착수 전 사람이 정한다.
2. **토크나이저**(형태소 vs n-gram) — 1단계 가용성 확인 + 2단계 실측으로.
3. **필드별 가중치와 관련도 점수 식** — 개발셋 튜닝.
4. **성능 합격 상한 숫자** — **0단계에서** 정한다(1단계보다 먼저).
5. **오타 후보 수·편집거리 상한** — 3단계 실측.
6. **구 RPC 유지 기간** — 4단계.

## 실행 기록

### 0단계 완료 (2026-08-17) — 성능 상한 먼저

현행 검색 웜 p50 75ms / p95 385ms를 재고 [`perf-gate.md`](../atee/eval/perf-gate.md)에 합격 상한을 못박았다(텍스트 갈래 웜 p50 ≤300ms · p95 ≤1,000ms · 동시 4요청 각 ≤3,000ms · 색인 ≤500MB). 미달 시 행동 순서(토크나이저 교체 → 필드 축소 → 컴퓨트 상향 → 되돌리기)도 함께 정했다.

### 1단계 완료 — PGroonga 설치와 토크나이저 결정

**PGroonga 3.2.5 설치** (한국시간 새벽 4시대, 저부하 창). DB 크기 2,290MB → 2,592MB.

**TokenMecab이 있었지만 쓰지 않는다.** 사전이 일본어라 한국어를 형태소 분석하지 못하고 공백·문자종 경계로만 자른다. 실측:

```
MeCab  : '반팔티셔츠 무지티' → [반팔티셔츠] [무지티]
Bigram : '반팔티셔츠 무지티' → [반팔][팔티][티셔][셔츠][츠 ][ 무][무지][지티][티]
```

MeCab을 쓰면 `반팔 티`로 `반팔티셔츠`를 찾을 수 없어 **A단계의 목표인 띄어쓰기 변형을 달성하지 못한다.** → **TokenBigram 채택.** 설계 §11의 미정 8이 이로써 닫혔다.

### 2·4단계 완료 — 색인과 관련도 정렬

`c_search_docs`(brand/title/tags/doc 분리) + shadow table 원자 교체 + 의존 RPC 같은 트랜잭션 재작성. `c_search_page_v2`는 (점수, goods_no) 커서를 돌려준다. 구 RPC와 `c_search_text`는 유지한다.

**성능에서 크게 헤맸다.** 첫 구현이 `반팔` 질의에 **37초**가 걸렸다. EXPLAIN으로 보니 색인 스캔 + top-N 정렬 자체는 214ms였고, **매칭 103,221건을 전부 `c_feed_products`와 조인한 뒤 자른 것**이 원인이었다. 조인 전에 자르도록 바꿔 **웜 p95 162ms**가 됐다(상한 1,000ms).

브랜드 우대는 점수 식의 `case` 가산을 뺐다 — 매칭된 10만 행마다 `brand &@~`가 평가돼 느려진다. 빼도 브랜드 질의 상위 5개가 전부 해당 브랜드였고 G1은 오히려 올랐다.

### 3단계 완료 — 초성과 한영 자판

- **초성**: 단어별 초성 배열 컬럼 + GIN 색인. 처음엔 bigram 부분 일치로 했다가 `ㅁㄴㅇㄹ`이 19건을 물어와 **단어 단위 정확 매칭**으로 바꿨다.
- **한영 자판**: 프론트 도메인 모듈(`hangul-keyboard.ts`). 자모 조합이 필요해 SQL로는 읽기 어렵다. **바로 치환하지 않고 원문이 0건일 때만 폴백**한다 — `nike`도 전부 두벌식 자판 글자라 영어 단어와 구분되지 않기 때문이다. 겹받침을 앞서 합치는 버그(`젝시믹스` → `제ㄳㅣ미ㄳㅡ`)를 다음 글자가 모음인지 내다보게 해서 고쳤다.
- 평가 파이프라인(Python)에도 같은 규칙을 미러링했다. **두 곳에 있으므로 한쪽만 고치면 평가와 실제 검색이 어긋난다** — 코드에 경고를 남겼다.

**G2 회귀의 원인 — 두 가지를 확인했고 하나가 남았다.**

1. **태그(해결)**: 태그를 색인 문서에 넣었더니 `루즈핏 반팔티` 결과에 제목에 "루즈"가 없는 상품이 올라왔다. 태그는 상품과 느슨하게 붙어 있다. 문서에서 뺐다(컬럼은 C단계 필터 재료로 남김).
2. **색이 본체 색인지 구분 못 함(미해결)**: `검정 반팔` 상위에 **`검정로고`** 상품이 온다. 기준서 §3-1 ③이 "색은 본체 색"이라 등급 1인데, 색인 점수는 이를 구분할 수 없다. **이건 텍스트 색인으로 풀 문제가 아니라 C단계(색상 정본 `c_color_groups` 보강)의 몫이다.**

즉 G2 회귀는 "재현율이 늘면서 기준서가 엄격히 보는 항목이 상위로 올라온" 결과다. 0건율은 22.7%로 기준선과 같다 — 못 찾는 게 는 것이 아니라 **찾은 것의 정밀도가 떨어졌다.**

**부수 발견**: `ㅁㄴㅇㄹ`을 G6("자판 뭉개기 = 0건이 정답")에 넣었는데, 초성이 `ㅁㄴㅇㄹ`인 단어를 가진 상품이 19개 실재한다. **기능이 생기면서 평가 항목의 의미가 바뀐 사례**라 G3으로 옮기고 `confidence: low`로 분리했다.

### 남은 것

- **4-1단계(클라이언트 전환) 미실시** — 새 RPC는 서버에만 있고 화면은 아직 구 경로를 쓴다. 사용자가 체감하려면 이 작업이 필요하다.
- **G2 회귀** — C단계에서 색상 정본을 붙여야 풀린다. 지금 A단계 안에서 더 튜닝하는 것은 기준서가 요구하는 구분(본체 색 vs 로고 색)을 텍스트만으로 하려는 것이라 한계가 분명하다.
