# 취향 프로필의 소유권을 계정으로 — 구현 계획

- 작성: 2026-08-19
- 설계: [2026-08-19-taste-profile-ownership-design.md](../superpowers/specs/2026-08-19-taste-profile-ownership-design.md)

코드·함수명 없이 **무엇을 / 어떤 순서로 / 무엇이 되면 끝**만 적는다(`AGENTS.md` 계획 작성 규칙).

## 단계 순서를 이렇게 잡은 이유

핵심은 **취향이 계정에 보관되어 기기를 넘어 따라오는 것**이다. 그래서 그것이 1단계다.

비회원 끄기는 그 귀결이고 되돌리기도 쉬우므로 2단계다. 순서를 바꾸면, 서버 보관이 아직 없는 상태에서 비회원 개인화만 꺼져 **아무도 개인화를 못 받는 구간**이 생긴다.

고지 갱신은 별도 단계로 미루지 않는다. 취향이 서버에 저장되기 시작하는 것이 1단계이므로 **그 단계와 함께 나가야 한다.**

---

## 1단계 — 회원의 취향을 계정에 보관한다

로그인한 사람의 취향이 서버에 저장되고, 다른 기기에서 로그인해도 같은 취향으로 시작한다. 비회원은 이 단계에서 지금과 똑같이 동작한다.

**할 일**

1. 계정 취향을 담을 테이블을 마이그레이션으로 추가한다. **지금 기기에 두는 것과 같은 형태**로 담는다 — 스키마 버전, 앵커(상품 번호·가중치·마지막 시각), 갱신 시각. 구조를 바꾸면 계산 로직을 그대로 못 쓴다.
2. **사용자 행을 외래키로 참조하고 삭제가 연쇄되게** 한다.
3. 본인 것만 읽고 쓸 수 있게 잠그고, 테이블을 직접 열지 않고 **검증이 붙은 함수**를 통한다.
4. 권한은 **함수를 만드는 같은 변경 안에서** 정리한다 — 회수부터 하고 로그인 역할에만 부여한다.
5. 앵커 개수와 담기는 값의 크기에 **상한**을 건다. 클라이언트가 보내는 값을 그대로 믿지 않는다.
6. **로그인하면 서버에서 읽어** 그 상태로 시작한다. 읽기에 실패하면 이번 세션은 빈 상태로 두되, 그 상태를 서버에 덮어쓰지 않는다.
7. 프로필이 바뀌면 서버에 올린다. **매 행동마다 올리지 않는다** — 신호 큐가 쓰는 방식(일정량이 모이거나 화면을 떠날 때)을 따른다.
8. **피드 요청은 지금처럼 프로필을 실어 보낸다.** 믹스 RPC 계약을 바꾸지 않는다.
9. 여러 기기에서 동시에 쓰면 **마지막 저장이 이긴다.** 가중치를 합치지 않는다 — 같은 행동이 두 번 반영될 수 있다.
10. 로그아웃하면 기기에서 지운다. 신원 전환 정리가 이미 그렇게 한다 — 새로 만들지 않는다.
11. **방침·처리방침·설정 문구를 함께 고친다.** "취향 프로필은 서버가 아니라 이 기기에만 저장됩니다"가 거짓이 된다. 계정 저장 항목과 계정 삭제 범위에 취향을 넣는다. **이 단계와 함께 나가야 한다.**
12. 최초 방문 배너의 키를 올린다. 수집 범위가 바뀌었다.

**이 단계에서 정할 것**
- 서버 저장 주기의 구체적 값 — 신호 큐 값을 그대로 따를지, 따로 정할지.

**완료 기준 (눈으로 확인)**
- 로그인해서 상품을 여러 개 열면 취향이 쌓이고, 새로고침해도 남는다.
- **다른 브라우저에서 같은 계정으로 로그인하면 같은 취향으로 시작한다.**
- 로그아웃하면 기기에서 취향이 사라지고, 다시 로그인하면 돌아온다.
- 저장을 실패하게 만들어도 화면이 깨지지 않고, 다음 기회에 다시 올라간다.
- 계정을 삭제하면 서버의 취향 프로필이 남지 않는다.
- 설정 화면과 공개 처리방침에 취향이 계정에 저장된다고 적혀 있고, "이 기기에만 저장"이라는 문구가 없다.
- 피드 응답 시간이 눈에 띄게 느려지지 않는다 (수치로 기록).

**자동 검증 (빈 스키마에서)**
- 권한 행렬: 비로그인 거부 / **남의 프로필 접근 거부** / 본인만 허용.
- 상한 초과 거부, **계정 삭제 시 연쇄**, 다른 사용자 생존.
- 마지막 저장이 이기는 규칙을 단위 테스트로 고정한다.

**검증 기록 (2026-08-19, 실제 Supabase + Aside)**

| 확인한 것 | 결과 |
|---|---|
| 취향이 쌓인다 | 상품 3개를 열자 세션 앵커 3 → 세션이 넘어가며 장기 앵커 3 |
| 서버에 올라간다 | 5초 간격 올리기 뒤 `c_taste_profiles`에 앵커 3, 스키마 버전 1 |
| **서버가 정본이다** | **기기의 취향 키를 통째로 지우고 새로고침해도 3개가 돌아온다** |
| 로그아웃 | 기기에서 사라진다 |
| 재로그인 | 서버에서 3개가 돌아온다 |
| 권한 | PUBLIC 0, RLS 켜짐, 외래키 연쇄 삭제 걸림 |

**돌려보다 알게 된 것**: 장기 프로필은 **세션이 끝날 때** 반영되므로(설계 §6), 상품을 눌러도 같은 세션에서는 `atee-profile`이 비어 있다. 처음에 이걸 모르고 "안 쌓인다"고 오판했다. 세션을 넘겨야 확인된다.

**미검증**: 피드 응답 시간을 수치로 재지 않았다. 믹스 RPC 계약을 바꾸지 않았으므로 피드 경로 자체는 그대로지만, 5초마다 도는 프로필 올리기가 자원을 나눠 쓴다.

## 2단계 — 비회원 경로를 끈다

**되돌릴 수 있어야 한다.** 이 단계는 검증 중이던 가설을 멈추는 것이므로, 되돌리는 경로를 먼저 확인한다.

**할 일**

1. 로그인하지 않았으면 **취향을 계산도 저장도 하지 않는다.**
2. 로그인하지 않았으면 **행동 이벤트를 보내지 않는다.**
3. 로그인하지 않았으면 피드는 **무작위 경로만** 쓴다. 개인화 믹스를 부르지 않는다.
4. 상세 화면의 **닮은 상품 탐색은 그대로 둔다.** 이미지 유사도라 프로필과 무관하다.
5. **검색어 기록은 유지한다.** 목적이 다르다(O-32).
6. 기기 ID는 남긴다. 이제 존재 이유가 **검색어 기록의 키 하나**뿐이므로 고지를 그에 맞게 고친다.
7. 비회원 고지를 단순하게 고친다 — 로그인하지 않으면 탐색 행동을 기록하지 않는다.
8. **되돌리는 경로를 확인한다.** 빌드 시 번들에 고정되는 환경변수로는 재빌드 없이 못 되돌린다.
9. **결정 기록에 O-24를 뒤집는다는 사실과 근거를 남긴다.** 함께 포기하는 것(효과 측정 수단)도 적는다.

**완료 기준 (눈으로 확인)**
- 로그인하지 않고 한참 훑은 뒤 기기 저장소에 **취향 프로필이 없다.**
- 로그인하지 않은 상태의 피드 요청이 **개인화 믹스를 부르지 않는다.**
- 로그인하지 않고 카드를 열고 찜해도 **서버에 행동 기록이 늘지 않는다.**
- 로그인하지 않고 검색하면 **검색어 기록은 남는다.**
- 되돌리는 절차를 **한 번 실제로 돌려봤다.**

**검증 기록 (2026-08-19, 실제 Supabase + Aside)**

| 확인한 것 | 결과 |
|---|---|
| 비회원 기기 저장소 | 장기 취향 `null`, 세션 취향 `null`, 미전송 큐 `[]` |
| 비회원이 부르는 RPC | `c_feed_page`(무작위) 3회, `c_similar_page`(닮은 상품). **`c_mix_page` 0회, `c_log_events` 0회** |
| 서버 행동 기록 | 비회원으로 훑고 카드를 연 뒤에도 **최근 5분 0건** |
| 검색어 기록 | 비회원 검색 "오버핏 반팔"이 **그대로 남았다** (결과 30건) |
| 기기 ID | 남아 있다 — 이제 검색어 기록의 키 하나로만 쓰인다 |

**되돌리는 경로**

- **환경변수로는 못 되돌린다.** `NEXT_PUBLIC_*`는 빌드 시 번들에 고정된다.
- 게이트는 `signals.ts` **세 줄**(`isSignedInNow()`)에 모여 있다. 되돌리려면 그 세 줄을 빼고 배포한다 — 확인했다.
- Vercel의 이전 배포 롤백이 더 빠른 길이지만 **이 프로젝트에서 실제로 해보지 않았다.** 급할 때 처음 시도하지 않도록 한 번 눌러 보는 것을 남겨 둔다.

**돌려보다 겪은 것**: 페이지를 다시 부르면 검사용으로 심은 장치(`fetch` 가로채기)가 함께 날아간다. 새로고침 없이 스크롤로 다음 페이지를 부르게 해야 관찰된다. 이걸 모르고 한 번 "아무 RPC도 안 부른다"고 오판했다.

## 3단계 — 내 취향 카드

**할 일**

1. 내 앵커 상품들의 **핏과 색**을 서버에서 세어 단어와 무게를 돌려준다. 프로필이 서버에 있으므로 집계도 서버에서 한다.
2. **`tags`는 쓰지 않는다.** 브랜드 상품코드·검색 낚시가 섞여 있어 그대로 쓰면 상품코드가 큼직하게 뜬다.
3. 색은 코드가 아니라 **사람이 읽는 이름**으로 바꾼다. 검색 작업에서 만든 이름표를 쓴다.
4. 마이페이지에 클라우드로 그린다. 자주 반응한 것이 더 크게 보인다.
5. **회원에게만 보인다.** 프로필이 계정에 있으므로 자연스럽다.
6. **앵커가 없으면 모으는 중이라고 알린다.** 없는 것을 있는 척하지 않는다.

**이 단계에서 정할 것**
- 보여줄 단어 개수와 크기 단계.

**완료 기준 (눈으로 확인)**
- 로그인해서 여러 상품에 반응한 뒤 마이페이지를 열면 **핏·색 단어가 클라우드로 보이고**, 많이 반응한 것이 더 크다.
- 갓 로그인해 앵커가 없으면 모으는 중이라고 보인다.
- 비회원에게는 이 카드가 보이지 않는다.
- 집계가 **내 앵커만** 센다 (다른 사용자 것이 섞이지 않는다).

---

## 완료 판정

- 위 완료 기준을 **실제로 돌려서** 관찰한다. 돌려보지 않은 것은 "미검증"으로 적는다.
- 조각마다 교차 리뷰를 한 번 받고, Blocker를 고친 뒤의 재검증은 별도로 한다.

## 이 계획이 무효로 만드는 것

**계정 찜 계획의 4단계(부작용 관찰)는 이 계획의 2단계로 불가능해진다.** 비회원 행동 기록이 없어져 비교할 데이터가 사라진다. 그 계획 문서에 그렇게 적는다.
