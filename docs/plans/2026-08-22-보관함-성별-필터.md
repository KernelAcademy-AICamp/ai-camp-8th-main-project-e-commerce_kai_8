# 보관함 성별 필터 — 구현 계획 (2026-08-22)

설계: [보관함 성별 필터 설계](../superpowers/specs/2026-08-22-보관함-성별-필터-design.md) ·
앞선 조각: [설정 성별 토글](../superpowers/specs/2026-08-21-gender-setting-toggle-design.md) · 결정 기록 O-39

**한 줄 목표** — 보관함에서 고른 성별과 라벨이 다른 찜(반대 성별·공용·미상)을 **화면에서만** 숨기고,
원본 목록에 기대는 세 가지(상세 하트 판정 · 담기/빼기 · 로그인 승계)는 그대로 둔다.

## 전제와 제약

- **프론트엔드 전용.** DB 마이그레이션·서버 함수 변경 없음. 서버는 계속 계정 찜 전체를 내려준다.
- **열지 않는 파일** (다른 사람·다른 조각이 편집 중): 신호 모듈 전체 · 계정 찜 동작 파일(열린 PR #74) ·
  피드 뷰모델 · 공용 프로필 모듈 · 백엔드 전체. 이 계획은 이 파일들을 필요로 하지 않는다 —
  필요해지면 그것은 경계를 잘못 그었다는 신호다.
- **성별을 읽는 방법은 이미 있다.** 공용 성별 설정 훅을 쓰고 새로 만들지 않는다.
- 작업 범위는 보관함 기능 폴더(도메인·뷰모델·컴포넌트)와, **상세 화면 컴포넌트의 배선 한 자리**다.
  담기 시트는 보관함 컴포넌트지만 그리는 목록을 상세 화면이 넘겨준다(교차 리뷰에서 확인). 그 파일은
  금지 목록에 없다. **넘겨주는 목록만** 바꾸고 하트 판정·담기·빼기는 원본 그대로 둔다.
- 브랜치는 `feature/wishlist-gender-filter`(이미 만들어 둠). **커밋·PR은 사람이 요청할 때만.**
- 각 단계 끝에서 `frontend`의 통합 검사(lint·타입·포맷·테스트)가 통과해야 다음으로 간다.

## 확인 준비 (1단계 전에 한 번)

화면 확인은 AI가 내장 브라우저로 개발 서버를 띄워 직접 한다. 그러려면 **한 계정의 보관함에
남성·여성·공용 라벨이 섞여 있어야** 한다. 없으면 만들 수 없으므로 먼저 만든다.

- 완료 기준: 로그인한 계정의 한 폴더 안에 **남성 라벨과 여성 라벨 상품이 최소 1개씩** 들어 있고,
  가능하면 공용도 1개 있다. 폴더 그리드에서 그 폴더의 개수가 원본 그대로 보인다(아직 필터 없음).
- 섞기 방법: 설정에서 성별을 한쪽으로 두고 몇 개 담고, 반대로 바꿔 몇 개 더 담는다.
- 공용 상품을 담을 경로가 없으면(앱 전체가 공용을 이미 뺀다) **공용은 미검증으로 남기고** 그 사실을
  8단계 기록에 적는다. 지어내지 않는다.

---

## 1단계 — "이 찜이 지금 성별에서 보이는가" 규칙

가장 중요한 판단을 가장 먼저, 화면 없이 못 박는다.

- 보관함 도메인에 순수 규칙을 둔다: 찜 목록과 성별 설정값을 받아 **보이는 목록**과 **숨은 수**를 낸다.
- 규칙: 상품의 성별 라벨이 설정값과 **정확히 같을 때만** 보인다. 공용·미상(라벨 없음)은 숨는다.
  **설정값이 미확정이면 아무것도 숨기지 않고 원본을 그대로 낸다.**
- 도메인은 React·브라우저 API를 import하지 않는다. 성별은 인자로 받는다.
- 테스트를 같은 폴더에 둔다: 남성 설정 / 여성 설정 / 미확정 / 공용 포함 / 미상 포함 / 빈 목록,
  그리고 **숨은 수 = 원본 수 − 보이는 수**.
- 완료 기준: 테스트를 돌리면 위 여섯 경우가 모두 통과한다. **화면은 아직 아무것도 바뀌지 않는다.**

## 2단계 — 폴더 상세에 적용 (목록과 헤더 개수)

실제로 상품이 보이는 화면이라 여기서 숨김이 처음 눈에 보인다.

- 보관함 전용 파생 훅을 하나 만든다. 원본 찜과 현재 성별 설정을 받아 1단계 규칙을 적용해
  **보이는 목록·숨은 수**를 낸다. 성별을 읽는 곳은 이 훅 하나뿐이다.
- 폴더 상세 뷰모델이 원본 대신 **보이는 목록**으로 그 폴더의 찜을 고르게 한다. 헤더 개수도 같은 기준.
- **개수를 하나로 두지 않는다.** 지금은 한 값이 헤더·삭제 확인 문구·빈 화면 판정에 함께 쓰인다.
  폴더 상세 뷰모델이 **보이는 수 · 원본 수 · 숨은 수** 셋을 따로 내보내게 한다. 셋 다 **그 폴더
  기준**이다(전체 보관함 기준으로 세면 다른 폴더의 숨은 수가 섞인다). 3·5단계가 이 셋을 쓴다.
- 원본을 쓰는 경로(상세 하트·담기/빼기)는 이 단계에서 **건드리지 않는다.**
- 완료 기준: 남성·여성이 섞인 폴더를 브라우저로 열면 **한쪽 성별만 보이고**, 헤더 숫자가 그만큼
  줄어 있다. 설정에서 성별을 반대로 바꾸고 그 폴더로 돌아오면 **보이는 상품이 뒤집혀 있다.**

## 3단계 — 숨김 안내 한 줄과 "전부 숨은 폴더"

- 폴더 상세 목록 위에, **그 폴더의 숨은 수가 1개 이상일 때만** 한 줄을 보여준다. 문구는 찜이
  사라진 것이 아니라 성별 설정 때문에 숨었다는 것과 그 개수를 알린다. 그리드에는 넣지 않는다.
- **전부 숨은 폴더**에서는 기존 "아직 비어 있어요"가 뜨지 않게 한다 — 사실과 다르다. 빈 화면 판정을
  **보이는 수**가 아니라 **원본 수**로 바꾸는 것이 요점이다(2단계에서 나눠 둔 세 값을 쓴다).
  원본까지 비었을 때만 기존 빈 화면 문구를 쓰고, 그 외에는 숨김 안내 한 줄만 보인다.
- 완료 기준: 숨은 것이 있는 폴더를 열면 목록 위에 한 줄이 보이고 그 숫자가 실제로 숨긴 개수와 같다.
  숨은 것이 없는 폴더에는 그 줄이 **없다.** 반대 성별만 담긴 폴더를 열면 "비어 있어요" 대신
  안내 한 줄이 보인다.

## 4단계 — 폴더 그리드·보관함 총 개수·담기 시트

세 자리가 같은 요약 규칙을 쓰므로 함께 맞춘다.

- 폴더 그리드의 타일 개수와 겹쳐 보이는 썸네일, 헤더의 보관함 총 개수를 **보이는 목록** 기준으로
  바꾼다.
- **담기 시트는 경로가 다르다**(교차 리뷰에서 확인). 시트는 보관함 컴포넌트지만 목록을 **상세 화면
  컴포넌트가 넘겨준다.** 그 넘겨주는 목록을 화면용으로 바꾼다 — 이 한 자리를 빠뜨리면 시트에만
  숨긴 상품의 개수·썸네일이 계속 나온다. **같은 화면의 하트 판정·담기·빼기는 원본 그대로 둔다.**
- 완료 기준: 그리드 타일에 적힌 개수와, 그 폴더를 열었을 때 실제로 보이는 장 수가 **같다.**
  숨긴 상품의 썸네일이 타일에도 시트에도 **뜨지 않는다.** 하트를 눌러 시트를 열면 시트의 개수도
  그리드와 같다.

## 5단계 — 폴더 삭제 확인 문구만 원본 개수로

- "담긴 찜 N개는 기본 폴더로 이동해요"의 N은 **원본 개수**여야 한다 — 숨은 것도 실제로 함께 옮겨진다.
  보이는 개수를 쓰면 문구가 사실과 다르다.
- 완료 기준: 숨은 것이 있는 폴더의 관리 메뉴에서 삭제를 누르면, 확인 문구의 숫자가 **헤더에 보이는
  숫자보다 크다**(= 원본 개수와 같다). 실제로 지운 뒤 기본 폴더의 원본 개수가 그만큼 늘어난다.

## 6단계 — 원본 경로가 안 깨졌는지 관찰

이 조각에서 **가장 위험한 지점**이다. 코드를 더 쓰는 단계가 아니라 관찰하는 단계다.

- **하트**: 숨긴 상품의 상세를 연다(직전 방문 기록·뒤로가기로 되살아난 상세 등 닿을 수 있는 경로로).
  하트가 채워져 있어야 한다. 다시 눌러 빼면 보관함 원본에서도 사라진다.
- **담기/빼기**: 보이는 상품을 담고 빼도 다른 폴더의 개수가 엉키지 않는다.
- **로그인 승계**: 옛 기기 찜을 심어두고 로그인한다. 올라간 뒤 설정을 반대 성별로 바꿔 보면 그때
  올라온 것이 보인다 = **원본 기준으로 승계됐다.** 심는 자리를 헷갈리면 아무것도 안 올라가고
  "통과"로 오인하게 되므로, 설계의 "완료 기준 5"에 적힌 **두 방법 중 하나를 골라 그대로** 한다:
  업로더가 읽는 중간 키에 직접 넣거나(탭 표식과 무관), 원본 키에 넣고 **직전 표식이 익명**인
  상태에서 로그인한다(중간 키가 비어 있어야 옮겨진다). **어느 쪽을 썼는지 기록에 적는다.**
- 완료 기준: 위 세 가지가 각각 관찰됐다. 하나라도 못 돌려봤으면 **"미검증"으로 적는다.**

## 7단계 — 설정 변경 반영과 미확정 상태

- 보관함을 연 채로 다른 탭(또는 설정 화면)에서 성별을 바꾸면 **새로고침 없이** 목록·개수가 다시
  계산되는지 본다. 크로스탭 반영은 루트 레이아웃에 이미 걸려 있으므로 새로 만들지 않는다.
- 성별이 미확정인 채로 보관함 주소를 직접 열면 **원본 전부**가 보인다(숨김 없음).
- 완료 기준: 설정을 바꾸면 보관함 화면이 스스로 바뀐다. 미확정 상태에서 연 보관함에는 양쪽 성별이
  모두 보이고, 성별을 고르면 그 순간 줄어든다.

## 8단계 — 검사와 검증 기록

- `frontend`에서 통합 검사(lint·타입·포맷·테스트)를 돌려 통과시킨다.
- 2~7단계의 완료 기준을 **실제로 관찰한 결과**로 이 문서 아래에 기록한다. 관찰하지 않은 항목은
  **"미검증"**으로 남긴다(특히 공용 라벨 상품을 못 담았을 경우).
- 완료 기준: 검사 통과 출력이 있고, 완료 기준마다 관찰 결과 또는 "미검증"이 적혀 있다.

---

## 하지 않는 것

- 숨긴 것을 임시로 펼쳐 보는 토글 — 하드 필터 정책에 예외를 만든다.
- 보관함에 성별 게이트를 거는 것 — 게이트 배치를 바꾸는 별개 작업이다.
- 반대 성별을 **담지 못하게** 막는 것 — 담기면 원본에 들어가고 화면에서만 숨는다.
- 서버가 내려주는 목록을 줄이는 것 — 프론트엔드 전용 제약이자, 원본을 잃지 않기 위한 선택이다.

## 검증 기록

2026-08-22, 로컬 개발 서버(포트 3002)에 내장 브라우저로 접속해 관찰했다. 계정은 로그인 상태였고,
관찰용 찜은 설정 성별을 바꿔가며 직접 담아 섞었다.

| 단계 | 완료 기준 | 결과 |
|---|---|---|
| 1 | 규칙 테스트 6경우 | ✅ 8개 통과(대칭·미상·공용·미확정·참조 안정·순서 유지 포함). 보관함 전체 46개, 저장소 전체 520개 통과 |
| 2 | 폴더를 열면 한쪽 성별만 | ✅ 여성 설정: 기본 폴더 헤더 `기본 1`·상품 1장. 남성으로 바꾸자 같은 폴더가 `기본 7`로 뒤집힘 |
| 3 | 숨김 안내 한 줄이 실제 숨긴 수와 같다 | ✅ 여성 설정에서 "성별 설정에 맞지 않는 6개는 숨겼어요", 남성 설정에서 "2개는 숨겼어요" |
| 3 | 전부 숨은 폴더에서 "비어 있어요"가 안 뜬다 | ✅ 바이바이 폴더(원본 1·전부 숨김): 안내 한 줄만 보이고 빈 화면 문구는 없음 |
| 4 | 타일 개수 = 열었을 때 보이는 장 수 | ✅ 그리드 `기본 1개` → 상세 1장, `기본 7개` → 상세 7장 |
| 4 | 담기 시트도 같은 기준 | ✅ 여성 설정에서 시트가 `기본 1 개`(원본 7일 때) |
| 5 | 삭제 확인 문구는 원본 개수 | ✅ 바이바이: 헤더 0, 확인 문구 "담긴 찜 1개는 기본 폴더로 이동해요" |
| 6 | 숨긴 상품의 하트가 채워져 있다 | ✅ 여성 상품 상세를 연 채 **다른 탭에서** 남성으로 바꿨더니, 그 상세의 하트는 ♥(찜 해제) 그대로 |
| 6 | 담기/빼기가 엉키지 않는다 | ✅ 담기 직후 7→8, 해제 직후 8→7 |
| 6 | **승계가 원본 기준** | ✅ 승계 큐(`atee-wishlist-migrate`)에 남성 1·여성 1을 심고 새로고침 → 큐가 비고, 기본 폴더 원본이 7→9. 남성 설정에서 7 보임+2 숨김, 여성 설정에서 2 보임+7 숨김 = **양쪽 성별이 모두 올라왔다** |
| 7 | 다른 탭 변경이 새로고침 없이 반영 | ✅ 위 하트 관찰과 같은 순간, 뒤 화면이 `기본 6`·"1개 숨겼어요"로 스스로 갱신 |
| 7 | 미확정이면 원본 전부 | ⚠️ **브라우저 미검증** — 아래 참고. 단위 테스트로는 덮여 있다 |
| 8 | `npm run check` | ✅ lint·typecheck·format 통과 |

### 미검증으로 남긴 것

- **성별 미확정 상태의 보관함** — 기기 값을 지우고 새로고침해도, 계정에 값이 있는 사용자는 찜 목록이
  도착하기 전에 성별이 이미 확정된다. 그래서 "필터 없이 원본 전부"가 보이는 창이 열리지 않아 화면으로
  관찰하지 못했다. 규칙 자체는 단위 테스트("미확정이면 아무것도 숨기지 않는다")로 확인돼 있다.
- **공용 라벨 상품** — 앱 전체가 공용을 빼므로 화면에서 공용을 담을 경로가 없어, 보관함에 공용을 넣어
  볼 수 없었다(계획 준비 단계에서 예상한 경우). 규칙은 단위 테스트로만 덮여 있다.
- **실제 폰 체감** — 사람이 확인할 몫이다.

### 관찰 중 알게 된 것

- `atee-gender`를 저장소에 직접 써도 **계정 값이 이긴다**(설계된 동작). 브라우저로 성별을 바꿀 때는
  설정 화면을 써야 한다. 저장소만 고치고 관찰하면 반대 결과를 보고 오판하게 된다.
- 보관함을 연 직후의 스냅숏은 계정 찜이 도착하기 전이라 `0개`로 보인다. 관찰 전에 기다려야 한다.

### 이 검증이 계정에 남긴 데이터

관찰용으로 담은 찜이 계정에 남아 있다(기본 폴더 원본 9개 중 3개, 바이바이 폴더 1개). 그중 2개는
승계 큐로 올린 것이다. **실폰 확인에 성별이 섞인 데이터가 필요하므로 지우지 않고 두었다.**
