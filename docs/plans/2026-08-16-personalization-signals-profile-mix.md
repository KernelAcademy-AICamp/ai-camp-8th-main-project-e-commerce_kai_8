## 배경 (이 repo를 모르는 사람을 위한 설명)

aTee는 티셔츠 22.6만 개를 2열 무한 피드로 탐색하는 PWA다. 1차 작업으로 전 상품 이미지 96.7만 장이 SigLIP2 벡터로 Supabase에 적재되었고, 상세 화면 하단에서 "닮은 상품"으로 이어지는 탐색이 동작한다. 그러나 피드 자체는 여전히 세션 시드 무작위 순서다 — 사용자가 무엇을 눌렀는지 아무것도 기록하지 않고, 기록이 없으니 취향도 반영하지 못한다.

이번 계획은 개인화 설계의 나머지 절반을 구현한다: ① 사용자의 행동(노출·탭·찜·`이 스타일로 계속 탐색`·판매처 이동)을 서버에 기록하고, ② 찜과 스타일 탐색 버튼 UI를 만들고, ③ 기기가 자기 행동으로 취향 프로필(가중치 붙은 앵커 이미지 목록 + 축 선호 요약)을 계산·보관하며, ④ 피드 요청 시 프로필 요약을 보내 5유형(장기 취향 40%·세션 관심 20%·부분 일치 15%·반대 제안 10%·다양성 15%)이 섞인 개인화 페이지를 받는다. 완료되면 "사용자의 행동에 따라 피드 구성이 눈에 보이게 변하고, 모든 노출·행동이 유형 태그와 함께 기록된다"(설계 합의 완료 기준).

## 확정된 결정 (2026-08-16 제품 책임자)

- **범위: 설계 4~6단계를 이 한 계획으로 진행** (1차와 같은 방식 — 한 파일에 단계별 완료 기준).
- **세션 종료 기준 = 비활성 30분으로 확정** (설계의 미정 플래그 해소). 계측 결과를 보고 추후 조정 가능. 결정 기록에 추가한다.
- **개인화 고지·동의 문구는 AI가 한국어 초안을 만들어 제품 책임자 승인 후 반영.**
- **1차에서 남은 사람 작업(이미지 유형 분류 표본 200장 판정)을 이 계획 0단계로 포함**해 마무리한다.

## 제약

- **Supabase 인스턴스 제약(1차에서 실측):** maintenance_work_mem 실질 상한 ~256MB(공유 메모리), 대량 HNSW 빌드 불가 → 벡터 인덱스는 IVFFlat(probes=80) 유지. DB 사용량 2.18GB/8GB — 이벤트 로그는 상한을 두고 운영한다(설계 §4 용량 산식, 예: ~100MB 수준).
- **서버 접근 원칙(기존과 동일):** anon 키로 원본 테이블 직접 조회·기록 금지. 읽기는 뷰·RPC, 쓰기는 검증·상한이 붙은 RPC만 허용. 이벤트 테이블은 select 거부.
- **클라이언트 보관 한도:** 프로필은 localStorage(~5MB)에 요약만 저장(bounded summary — 원시 이벤트를 쌓지 않는다).
- **기존 동작 회귀 금지:** 무한 피드·스크롤 복원·뒤로 가기·상세 하단 유사 탐색은 그대로 동작해야 한다. 개인화 RPC 실패 시 기존 무작위 피드로 폴백하고 개인화인 척하지 않는다.
- **프론트 아키텍처:** clean architecture + MVVM (`frontend/AGENTS.md`) — domain은 순수 TypeScript, 서버·저장소 접근은 data 레이어, 상태·이벤트 처리는 view-model 훅.
- **품질 게이트:** 커밋 전 `npm run check`(lint·typecheck·format)와 vitest 통과.

## 단계와 완료 기준

### 0. 잔여 정리 — 표본 판정 + 문서 정비

1차에서 만들어 둔 판정 도구(backend의 judgment 생성 스크립트)로 표본 200장을 제품 책임자가 판정한다(사람 작업). 결과로 카드 노출 부적합 이미지(디테일·원단, 사이즈표·라벨 등)의 오통과율을 계산하고, 필요하면 유사 탐색 RPC의 노출 신뢰도 임계값을 조정한다. 결정 기록에 이번 결정(세션 30분 확정 등)을 추가하고 PRD의 관련 절을 갱신한다.

- **완료 기준:** 오통과율 수치와 임계값 조정 여부가 이 문서 실행 기록에 적히고, 결정 기록·PRD에서 새 결정을 읽을 수 있다. 조정했다면 상세 하단 유사 탐색에서 부적합 이미지가 눈에 띄게 줄었는지 확인한다.

### 1. 행동 신호 수집 (설계 §4)

익명 기기 ID·세션 ID(비활성 30분 기준)를 만들고, 이벤트(노출·탭·찜/찜해제·스타일 탐색·판매처 이동·세션 경계)를 클라이언트에서 모아 서버 이벤트 테이블에 RPC로 기록한다. 이벤트에는 설계 §4의 공통 필드(클라이언트 생성 이벤트 ID, 정책·버전 필드, 실험 배정 예약 필드)와 노출 추가 필드(노출 ID, 포트폴리오 유형, 신선도 플래그, 순위, 카드 크기, 화면 위치, 이미지 슬롯, 시드)를 담고, 행동 이벤트는 발생한 노출 ID를 귀속한다. 전송 실패는 로컬 큐로 재시도하고 이벤트 ID로 중복을 막는다. 서버 RPC는 요청당 개수·크기 상한, 값 범위 검증, 중복 무시, 기기별 일일 상한을 갖는다. 개인화 고지·동의 문구(AI 초안 → 승인)와 설정의 로컬 초기화 수단도 이 단계에서 노출한다.

- **완료 기준:** 앱에서 피드를 훑고 상세를 열면 — 서버 이벤트 테이블에 노출·탭 이벤트가 유형 태그·노출 귀속과 함께 쌓인 것을 SQL로 확인할 수 있다. 같은 이벤트를 재전송해도 한 건만 남는다. anon 키로 이벤트 테이블 select와 직접 insert는 거부된다. 앱에서 고지 문구와 초기화 수단이 보인다.

### 2. 찜 · `이 스타일로 계속 탐색` UI (설계 §8)

상세 화면에 찜 토글(하트)과 `이 스타일로 계속 탐색` 버튼을 추가해 상세 3요소(찜·스타일 탐색·판매처 이동)를 완성한다. 찜 목록은 localStorage에 보관하고 피드에서 진입하는 최소한의 보관함 화면을 만든다. 두 행동 모두 1단계 이벤트로 기록된다(찜 해제 포함). 스타일 탐색 버튼의 피드 반영 효과는 4단계에서 완성되므로, 이 단계에서는 즉시 체감 가능한 동작(예: 해당 상품 기준 탐색 진입)과 이벤트 기록까지를 범위로 한다 — 구체 동작은 구현에서 결정(미정 플래그 참고).

- **완료 기준:** 상세에서 하트를 누르면 보관함 화면에 그 상품이 보이고, 해제하면 사라진다. 하트·스타일 탐색 버튼을 누르면 서버 이벤트 테이블에 해당 이벤트가 노출 귀속과 함께 기록된 것을 SQL로 확인할 수 있다. 새로고침해도 찜 목록이 유지된다.

### 3. 취향 프로필 — 기기에서 계산·보관 (설계 §5·§6)

기기가 자기 행동으로 장기/세션 취향 프로필을 계산해 localStorage에 저장한다. 형태는 가중치 붙은 앵커 이미지 목록(장기 50·세션 20 상한) + 축 선호 요약(색군·가격대·그래픽 성향). 신호 가중 서열(반복 탐색 < 스타일 탐색 < 찜 < 판매처 이동), 세션 종료 시 장기 반영, 세션 단위 감쇠, 노출 대비 행동 보정(자기강화 방지), 멀티탭 병합(앵커 합집합 + 가중 최대), 스키마·모델 버전 기록, 백업 슬롯 복원 규칙을 설계 §6대로 구현한다. 프로필 계산은 순수 로직으로 만들어 단위 테스트를 붙인다.

- **완료 기준:** 앱에서 찜·탭을 몇 번 하면 브라우저 저장소의 프로필에서 앵커와 축 요약이 갱신된 것을 확인할 수 있다. 30분 비활성(테스트에서는 시간 조작) 후 세션 행동이 장기 프로필에 반영된다. 저장된 프로필을 일부러 손상시키면 백업에서 복원되고, 백업까지 지우면 콜드스타트로 동작한다. 프로필 규칙(가중·감쇠·상한·병합)에 대한 단위 테스트가 통과한다.

### 4. 포트폴리오 믹스 RPC + 피드 통합 (설계 §7·§9)

프로필 요약(앵커 목록 + 축 선호)과 최근 노출 목록(상한 600)을 받아 5유형이 섞인 한 페이지(30장)를 반환하는 추천 RPC를 만들고, 피드가 이를 사용하게 연결한다. 설계 §7의 계약을 따른다: 유형 귀속 우선순위(세션 > 장기 > 부분 일치 > 반대 > 다양성), 후보 부족 시 다양성 backfill과 실제 구성 응답, 페이지 불변성, 콜드스타트(신호 없으면 100% 다양성 = 기존 무작위), `이 스타일로 계속 탐색` 직후 노출 60장 동안 세션 슬롯 부스트, 같은 세션 노출 상품 제외. RPC 실패·타임아웃 시 기존 무작위 피드로 폴백하고 폴백 발생도 계측한다. 응답의 유형 구성은 노출 이벤트의 source_bucket으로 그대로 기록되어 1단계 계측과 연결된다.

- **완료 기준:** 저장소를 비운 새 기기 상태에서는 피드가 기존 무작위와 같다(100% 다양성). 검정 후드 몇 개를 찜하고 피드를 이어 받으면 다음 페이지들에서 비슷한 계열 상품이 눈에 띄게 늘고, 응답·노출 이벤트의 유형 구성(source_bucket 분포)이 5유형 비율과 부합한다. `이 스타일로 계속 탐색`을 누르면 직후 피드가 그 스타일로 확 쏠렸다가 노출 60장 이후 복귀한다. 개인화 RPC를 강제로 실패시키면 무작위 피드로 폴백하고 폴백이 계측에 남는다. 스크롤 복원·뒤로 가기·상세 하단 유사 탐색은 그대로 동작한다.

### 5. 전체 검증 · 마무리

Orca 브라우저와 iOS 시뮬레이터에서 전체 흐름(탐색 → 찜·스타일 탐색 → 피드 변화 → 폴백)을 확인하고, 계측 SQL로 설계 §10의 평가 지표(유형별 찜률·판매처 이동률, 반복 노출률, 폴백 비율)가 산출되는지 확인한다. `npm run check`·vitest 통과 후 이 문서에 실행 기록을 남긴다.

- **완료 기준:** 위 확인 결과(스크린샷 또는 수치)가 실행 기록에 적히고, PR이 develop을 대상으로 열린다. 유형별 지표를 뽑는 SQL 예시가 repo 어딘가(문서 또는 backend)에 남아 다음 사람이 그대로 실행할 수 있다.
