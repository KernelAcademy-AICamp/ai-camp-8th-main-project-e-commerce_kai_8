## 구현 전에 확정된 것

### ① 후보는 알고리즘이 좁히고 사람이 고른다

전달서 §11-3의 답이다. 자동 선정을 네 가지로 돌려보고 **전부 다르게 실패**했다.

| 방식 | 서로 간 거리(최소) | 실패 양상 |
|---|---|---|
| 리뷰 인기순 | 0.017 | 흰 무지 6 + 검정 무지 5 — 사실상 두 종류 |
| k-means 12군집 대표 | 0.045 | 무지가 공간을 지배해 군집이 무지 쪽에 몰린다 |
| 임베딩 farthest-point | 0.379 | 다양하지만 **이상치**를 뽑는다(컴프레션 웨어·헬스장 사진) |
| 프린트 3종 층화 + 퍼뜨림 | 0.228 | 무드가 튄다(사막 로프 당기기, 얼굴 가린 사진) |

빠진 축은 "**상품이 깔끔하게 보이는 사진인가**"인데 카탈로그에 근거가 없다. 그래서:

```
1. 자동으로 후보 풀을 좁힌다
   성별 라벨 일치 · card_ok · 반팔티(category 001001) · 착용샷(img_type=0)
   · 앞모습 · 리뷰 100+ · c_gender_label_flags 제외
2. 서로 가장 먼 12개 기준점을 잡고(리뷰 150+ 중에서) 나머지를 가까운 기준점에 붙인다
3. 묶음마다 리뷰 많은 순 3장을 대안으로 보여주고, 사람이 묶음당 하나씩 고른다
4. 교체는 카탈로그를 크게 갱신할 때만. 상시 자동 교체하지 않는다
```

**앞모습 판별**은 성별 판정에 쓴 것과 같은 방식이다 — SigLIP2 텍스트 프롬프트로 점수를 매겨 걸렀다.
남성 풀 891 → 앞모습 718, 여성 697 → 445.

상시 자동 교체를 하지 않는 이유는 셋이다. 온보딩 첫 화면은 제품의 얼굴이고 12장은 사람이 몇 분이면
고른다. 자동 생성은 위 표처럼 이상한 것을 넣는다. 그리고 **후보가 매번 바뀌면 「선택 개수 분포」
같은 지표가 기준을 잃는다.**

**후보 목록은 버전을 붙여 고정한다.** 상품은 사라진다 — 2026-08-24에 죽은 썸네일 271개를 실제로
지웠다. 그래서 후보 유효성 사전 검사와 최소 유효 카드 수를 §1-2에 완료 기준으로 넣었다.

### ② 최대 선택 개수는 두지 않는다

전달서 §11-2의 답이다. 최소 3개만 강제한다. 후보가 12장이라 **실질 상한은 12**다.

- 제약이 하나 늘면 화면에 설명이 하나 더 붙는다. 지금도 "3개 이상"을 설명 중이다.
- 몇 개를 고르는지 데이터가 없다. 「선택 개수 분포」를 보고 정한다.
- 되돌리기 쉽다. 나중에 상한을 넣는 것은 쉽고, 넣었다 뺐다 해도 사용자가 손해 보지 않는다.

많이 고르면 신호가 약해지는 것은 맞지만 **추천 쪽 가중치로 다룰 일이지 화면에서 막을 일이 아니다.**

### ③ 데이터 제약 — 어기면 개인정보 고지가 거짓이 된다

> **선택은 로그인 전까지 기기에만 두고, 계정이 생긴 뒤 계정에 붙인다.**

O-37("로그인하지 않으면 기록하지 않는다")과 공개 처리방침의 "아무것도 남기지 않습니다"가
이것에 걸려 있다. **온보딩 세 화면에서 서버로 나가는 것이 없어야 한다.**

### ④ 계측 — 로그인 전 이탈은 재지 않는다 (제품 책임자 결정, 2026-08-24)

③과 "단계별 이탈 계측"은 **동시에 달성할 수 없다.** 로그인 전에 이탈한 사람은 아무것도 업로드하지
않으므로 §8 1차 지표의 분모(성별 화면을 본 신규 방문자)를 셀 수 없다.

**무기록을 지키고 측정을 포기한다.**

- 로그인 **완료자** 안에서만 회고적으로 단계 데이터를 본다(각 단계를 언제 지났는지는 승계 보관함에
  담아 올릴 수 있다).
- **로그인 전 이탈률은 영원히 알 수 없다.** O-41이 기록한 대가 ⓒ("이탈이 설치 탓인지 가입 탓인지
  가르려면 계측이 필요하다")는 **이 결정으로 포기한다.** 필요해지면 O-37·수집 방침·처리방침을
  함께 바꾸는 별도 결정이 있어야 한다.
- PRD 지표 표의 「비회원→회원 전환율」은 폐기했고, 대체 지표의 분모 한계를 그 자리에 적었다.

## 1단계 — 핵심 세로 경로

초안은 이 단계에 화면 3개·OAuth 왕복·신원 전환·계정 저장·추천 준비·홈 게이트를 다 넣어
**실패 지점을 분리할 수 없었다.** 각각 바로 관찰 가능한 하위 단계로 쪼갠다.

### 1-0. 진입 판정 — 계정이 기기보다 우선한다

기기에 아무것도 없어도 **계정에는 있을 수 있다.** iOS에서 홈 화면에 설치한 PWA는 Safari와
저장소가 분리돼 빈 상태로 시작한다(별도 조사로 확인). 링크로 온보딩을 마친 사람이 나중에 설치하면
이 경로를 탄다.

- 첫 화면에서 **기존 사용자가 먼저 로그인할 경로**를 제공한다.
- 로그인 상태면 계정의 온보딩 완료 여부를 읽고, 완료 계정이면 선택 단계를 건너뛴다.
- 성별에 이미 같은 선례가 있다 — 로그인을 기다렸다가 계정 값을 내려받는다.

**세 가지 진입 상태를 이렇게 가른다** (2026-08-24 제품 책임자 결정).

| 상태 | 무엇을 보여주나 |
|---|---|
| **완료 계정** (성별 O · 초기 선택 O) | 온보딩을 건너뛰고 홈 |
| **불완전 계정** (성별·초기 선택이 **둘 다 갖춰지지 않음**) | **성별 선택부터.** 반쪽 상태를 이어 붙이지 않는다 |
| **이 기기에서 온보딩을 마친 적이 있음** (로그아웃 뒤 재방문) | **로그인 화면부터.** 온보딩을 다시 돌리지 않는다 |

불완전 계정을 성별부터 다시 시작하는 이유는 반쪽 상태를 이어 붙이는 분기가 늘수록 검증할 조합이
곱으로 늘기 때문이다. 대가는 이미 고른 성별을 한 번 더 묻는 것인데, 화면 하나 값이다.

**"둘 다 갖춰지지 않음"은 "한쪽만 있음"보다 넓게 잡은 것이다.** 한쪽만 있는 계정과 **아무것도 없는
갓 만든 계정**을 같은 규칙으로 처리하려는 것이다 — 아래 로그인 우선 경로가 이것에 걸린다.

**"이 기기에서 마친 적 있음" 표식은 신원 종속이 아니다.** 로그아웃해도 남아야 하므로 정리
allowlist의 **남길 것** 쪽에 둔다. 담는 것은 "이 기기에서 온보딩이 완료된 적이 있다"는 사실뿐이고,
**누가 했는지·무엇을 골랐는지는 담지 않는다** — 그것까지 남기면 앞사람의 취향이 새어 O-35가 깨진다.

#### 온보딩 순서는 두 가지다 (2026-08-24 제품 책임자 결정)

A가 로그아웃한 기기를 **계정 없는 B**가 열면 로그인 화면만 보인다. 이때 B를 온보딩 1단계로
되돌리지 않고, **로그인부터 시킨 뒤 온보딩을 잇는다.**

| 경로 | 순서 | 화면 수 |
|---|---|---|
| 새 기기 (기기 표식 없음) | 성별 → 옷 → 로그인 | 3 |
| 쓰던 기기 (로그아웃 뒤 재방문) | 로그인 → 성별 → 옷 | 2 |

이것이 가능한 이유는 **가입이 별도 경로가 아니기 때문이다.** 인증 진입점은 구글 OAuth 하나뿐이고
(`auth-repository.ts`의 단일 호출), 처음 온 구글 계정이면 그 자리에서 계정이 생긴다. 로그인을 마친
B의 계정은 성별도 초기 선택도 없으므로 위 표의 **불완전 계정**에 그대로 걸려 성별 선택부터 간다.
**진입 판정에 B를 위한 분기를 새로 만들지 않는다.**

- ⚠️ **막다른 길은 경로가 아니라 문구에 있다.** 지금 버튼 문구는 `로그인하기` / `Google 계정으로
  로그인`이라 계정이 없는 사람은 자기 자리가 아니라고 읽는다. **계정이 없어도 눌러야 하는
  버튼임이 읽히는 문구**로 바꾼다.
- **진행 표시가 갈린다.** 3화면 경로는 `1 / 3`, 2화면 경로는 `1 / 2`. 없는 단계를 세지 않는다.
- **저장은 §1-3 한 계약으로 통일한다.** 로그인 우선 경로는 이미 인증돼 있어 화면마다 바로 저장할 수
  있지만 그렇게 하지 않는다 — 불완전 계정이 훨씬 자주 생기고 서버 검증 규칙이 두 벌이 된다.
- **§1-1 승계는 새 기기 경로에서만 돈다.** 로그인 우선 경로에는 익명→사용자 전환 자체가 없다.
  승계가 깨져 있어도 이 경로로는 **안 잡힌다.** §1-1의 완료 기준은 반드시 새 기기 경로로 확인한다.

> **구현 순서 제안**: 로그인 우선 경로를 먼저 세로로 뚫는다. 온보딩에서 제일 깨지기 쉬운 조각
> (§1-1 승계)을 우회하므로 §1-0·1-2·1-3·1-4를 승계 없이 전부 관찰할 수 있다. 승계는 그 뒤에
> 새 기기 경로에 붙인다.

**완료 기준**
- `브라우저에서 온보딩 완료 → 홈 화면에 설치 → PWA 실행 → 기존 계정 로그인`을 직접 하면,
  성별·옷을 **다시 묻지 않고** 같은 초기 선택을 쓴 홈이 열린다.
- 계정의 성별만 지우고(또는 초기 선택만 지우고) 다시 들어가면 **성별 선택 화면부터** 시작된다.
- 로그아웃하고 같은 기기에서 다시 열면 **로그인 화면**이 먼저 보이고, **계정을 한 번도 만든 적 없는
  구글 계정으로** 거기서 로그인하면 이어서 **성별 선택 화면**이 뜬다. 그 경로의 진행 표시는 `1 / 2`다.
- 그 사람이 성별 선택 화면에서 나갔다가 다시 열면 **다시 성별 선택 화면**이다(빈 계정 = 불완전 계정).

### 1-1. 승계 계약 — 이것 없이는 선택이 로그인 직후 사라진다

신원 전환 정리는 **남길 것만 열거하는 allowlist**다. 새로 만든 `atee-*` 키는 **기본으로 삭제된다.**
로그인 성공 → 익명→사용자 전환 감지 → 정리 → 페이지 다시 부르기 순서로 도므로, 아무 대책 없이
저장한 선택은 계정에 붙기 전에 없어진다. 복귀 위치 키도 같은 이유로 삭제 대상이다.

기존에 같은 문제를 푼 자리가 있다 — 찜과 성별은 **정리 직전에 1회용 보관함으로 빼둔다.**
같은 순서를 따르되 다음을 지킨다.

- 평소 선택 원본은 **신원 종속 키**로 둔다 — 로그아웃·계정 전환에서 지워져야 O-35가 지켜진다.
- **익명 → 사용자 전환에서만** 보관함으로 옮긴다.
- 보관함은 **대상 사용자 ID에 묶는다.** A에 올리다 실패한 뒤 로그아웃하고 B가 로그인하면
  **B에게 넘어가면 안 된다.** 대상이 다르면 폐기한다.
- 계정 반영을 **성공으로 확인한 뒤에만** 보관함을 비운다.
- 로그인 콜백 → 승계 확정 → 첫 홈의 순서를 **결정적으로** 보장한다. effect 실행 순서에 기대지 않는다.

**완료 기준**: 온보딩에서 3개를 고르고 로그인하면 — 다시 뜬 화면에서 그 3개가 **계정에 남아 있고**,
로그아웃 후 다른 계정으로 로그인하면 그 3개가 **새 계정으로 넘어가지 않는다.**

### 1-2. 옷 선택 화면

- 진행 표시는 **그 경로의 실제 화면 수**를 센다 — 새 기기는 `1 / 3`·`2 / 3`·`3 / 3`,
  로그인 우선 경로는 `1 / 2`·`2 / 2` (§1-0). 없는 단계를 세지 않는다
- 성별과 일치하는 확정 후보 12장을 2열 카드로. 첫 화면에 6장, 세로로 더 보면 12장
- 최소 3개. 3개 미만이면 다음 버튼이 비활성이고 그 사실이 눈에 보인다
- 선택 카드는 **주황 테두리와 체크 아이콘을 함께** 쓴다 (색만으로 전달하지 않는다)
- 후보 중 상품이 사라졌거나 이미지가 죽었으면 **그 카드를 빼고 그린다.** 유효 카드가 최소 개수보다
  적으면 사람이 후보를 갈아야 한다는 신호를 남긴다
- 뒤로 가서 성별을 바꾸면 기존 옷 선택을 재사용하지 않는다

**완료 기준**: 옷 선택 화면에 **반대 성별·공용 상품이 하나도 없고**, 3개 미만에서는 다음으로 못 가며,
**4개·12개(전부)를 골라도** 다음으로 갈 수 있다. 성별을 바꾸면 앞의 선택이 사라진다.

### 1-3. 계정 저장 계약

정본은 온보딩 선택을 **계산된 장기 취향과 같은 데이터로 취급하지 말라**고 한다. 지금 계정 취향 API는
계산된 앵커만 읽고 쓰므로 **초기 선택과 온보딩 완료 상태를 담을 자리가 없다.** 새로 정해야 한다.

- 인증된 사용자만 쓸 수 있고, 서버가 검증한다 — **최소 3개 · 허용된 후보 목록 안 · 고른 성별과 일치 ·
  사용자 ID를 입력으로 받지 않는다**(호출자의 신원을 쓴다)
- 중복 콜백·새로고침·응답 유실에도 **중복되거나 유실되지 않게** 원자적·멱등으로 처리한다
- 저장이 확인되기 전에는 **첫 홈을 열지 않는다**
- 완료 계정에서는 **계정 상태가 기기 임시 상태보다 우선**한다

**완료 기준**: 저장 요청을 두 번 보내도 결과가 같고, 저장에 실패하면 홈이 열리지 않으며 재시도할 수
있다. 성별과 다른 상품·후보 밖 상품·2개 이하를 보내면 서버가 거부한다.

### 1-4. 첫 홈이 그 선택을 실제로 반영한다

초안의 완료 기준("첫 홈에 실제 추천 상품이 보인다")은 **무작위 다양성 피드도 통과한다.** 상위 계약은
선택이 추천 입력에 들어갔음을 **관찰 가능하게** 확인하라고 요구한다.

**완료 기준**: 고른 N개가 **첫 홈 추천 요청의 입력에 실제로 들어간 것**이 보인다. 초기 추천 준비에
성공했을 때만 `개인화된 추천이 준비됐다`는 표현이 나온다. 첫 홈 추천과 실패 폴백 **양쪽 모두에**
반대 성별·공용 상품이 없다(O-39는 피드·검색·상세·큐레이션 전체에 걸린다).

### 1-5. 삭제 계약 — 만드는 것과 같은 조각에서 닫는다

초기 선택을 계정 데이터로 저장하면 지우는 경로도 같이 정해야 한다. 지금 계정 삭제는 FK cascade에
기대고, 개인화 초기화는 계산된 취향·찜을 별도 경로로 지운다. 새 데이터가 어디에 붙느냐에 따라
**서버에 남거나 다음 로그인에 되살아날 수 있다.**

- 계정 삭제에 포함되는가 — 포함되어야 한다
- 「개인화 데이터 모두 지우기」에 포함되는가 — **포함 여부를 정하고 처리방침 문구와 맞춘다**
- 삭제 실패 시 재시도 경로에 포함되는가

**완료 기준**: 계정을 삭제한 뒤 같은 구글 계정으로 다시 로그인하면 **온보딩을 처음부터 다시** 하게
되고, 서버에 이전 선택이 남아 있지 않다.

## 2단계 — 실패와 재방문

- 인증 취소·실패: 가입 화면으로 돌아오고 성별·옷 선택이 살아 있다. 실패 이유와 재시도 방법이 같은
  화면에 있다. 홈은 열리지 않는다.
- 초기 추천 준비 실패: 성별 조건을 지킨 다양성 피드로 복구한다. **준비되지 않은 추천을 개인화
  결과라고 표시하지 않는다.** 저장 실패와 추천 실패는 **서로 다른 상태**다.
- 온보딩을 마친 계정으로 다시 오면 전체 흐름을 반복하지 않는다.

**완료 기준**: 세 상태를 각각 직접 만들면 — 선택이 사라지지 않고, 거짓 개인화 표시가 없고,
온보딩이 무한 반복되지 않는다.

## 3단계 — 첫 홈 안내

피드를 막지 않는 확인 메시지를 한 번 보여준다. 전체 화면 dim이나 다단계 투어를 쓰지 않는다.

**완료 기준**: 첫 홈에서 안내와 상품이 함께 보이고 **안내를 닫지 않아도 즉시 스크롤할 수 있다.**
같은 계정의 다음 방문에는 안내가 다시 나타나지 않는다.

## 4단계 — 회귀 확인과 최소 계측

계측 범위는 §④로 정해졌다 — **로그인 완료자 안에서만** 본다. 이벤트 이름과 스키마는 기존 계측
계약을 조사한 뒤 정한다. 측정 장치를 기능보다 크게 만들지 않는다.

회귀는 승계 순서를 건드리므로 세 전환을 모두 본다.

- **익명 → 사용자**: 온보딩 선택이 넘어가고, 찜 승계(O-36)와 섞이지 않는다
- **사용자 → 익명**(로그아웃): 앞사람의 선택·취향·찜이 남지 않는다
- **사용자 A → B**: A의 선택이 B로 넘어가지 않는다

**완료 기준**: 세 전환을 각각 직접 실행하면 위가 그대로 관찰된다. 기존 개인정보 삭제·로그아웃·
계정 전환 약속이 깨지지 않는다.

### 구현 중에 잡은 결함 둘

둘 다 **테스트가 아니라 실제로 돌려서** 나왔다.

1. **승계가 조용히 비었다.** 보관함이 camelCase로 쓰고 snake_case로 읽었다. 저장 형태를
   한 함수(`toWire`)로 모으고 테스트를 붙였다.
2. **승계가 서버에 거부당해 무한 재시도에 갇혔다.** 고른 옷의 성별이 보관함에 함께 실리지
   않아서다. 신원 전환 정리가 기기 성별을 지우면 **계정에 있던 옛 성별이 먼저 내려와 자리를
   차지하고**, 그 성별로 반대 성별 후보를 올리다 서버가 거부한다. 보관함이 성별을 함께 담고,
   승계 저장은 그 성별을 쓰며, 성공하면 기기 성별도 그것으로 맞춘다.
   → 실제로 관찰한 실패라 **그 시나리오 그대로 테스트로 박아 두었다.**

`§1-1의 완료 기준은 반드시 새 기기 경로로 확인한다`고 적어 둔 것이 이 둘을 잡았다.
로그인 우선 경로만 봤다면 **둘 다 통과했을 것이다.**

### 설계 판단 — 씨앗은 물러난다

온보딩 선택을 계산된 장기 취향에 **써 넣지 않고, 추천 요청을 만들 때만 합친다.** 써 넣으면
감쇠·상한 같은 앵커 규칙이 사람이 명시적으로 고른 값에까지 적용돼 정본이 금지한 "같은 데이터로
취급"이 된다.

무게는 찜과 같고(4), **실제 행동 앵커가 쌓일수록 선형으로 줄어 20개에서 사라진다.** 고정 무게로
영원히 얹으면 온보딩 선택이 평생 피드를 지배하는데, 처리방침은 이것을 "첫 추천의 **시작점**"이라고
약속했지 종착점이라고 하지 않았다. 20은 튜닝 상수다 — 실측이 아니라 판단이고, 상수 하나만 만지면

## 체크

- [x] **핵심 기능이 첫 단계인가?** — 1단계가 전체 세로 경로다. 그 안에서도 승계(1-1)를 앞에 두었다 —
      이것이 깨지면 뒤가 전부 무의미하다.
- [x] **바로 확인 가능한 크기인가?** — 1단계를 여섯 조각으로 쪼갰고 각각 독립적으로 실행해 볼 수 있다.
- [x] **완료 기준이 "X를 하면 Y가 보인다" 형태인가?** — 모든 조각에 직접 실행해 관찰할 결과를 적었다.
