# 죽은 상품(썸네일 404) 정리 — 계획 (2026-08-20)

## 배경과 결정

- 무신사에서 상품이 내려가면 우리 카탈로그의 썸네일이 깨져 화면에 빈 이미지가 나온다.
- 실측: 썸네일 404가 곧 "내려감"은 아니다 — 표본 40건의 유일한 404는 판매 중인데
  무신사가 썸네일 URL을 갈아끼운 상품이었다(상세 API 200 + 새 경로). 진짜 내려간
  상품은 상세 API(goods-detail.musinsa.com)가 HTTP 404를 준다.
- **결정(2026-08-20, 제품 책임자): 썸네일 404 후보는 상세 API 판정 없이 전부 삭제한다.**
  판매 중이어도 이미지가 깨진 상품은 피드 가치가 없고, 카탈로그는 재수집으로
  되살릴 수 있는 데이터라 되돌림이 가능하다.

## 절차

1. **전수 스캔** — `backend/db/scan_dead_thumbs.py`: c_goods 22.6만 건의 thumbnail에
   HEAD(동시 30). 404만 후보로 기록, 타임아웃·5xx는 재시도 후에도 불확실하면 제외.
   완료 기준: 후보 goods_no 목록 파일과 제외 건수가 출력된다.
2. **백업 + 규모 보고** — `backend/db/delete_dead_goods.sql`이 삭제 전에 해당
   c_goods 행 전체를 CSV로 덤프하고, 삭제 대상 수·찜 겹침 수를 출력한다.
   완료 기준: 백업 CSV 존재, 규모가 예상(~2.5%)과 크게 다르면 중단하고 사람에게 확인.
3. **삭제(한 트랜잭션)** — 파생 테이블(c_search_negation_flags·c_search_fit_measures·
   c_search_docs·c_search_text·c_img_vecs·c_thumb_dims) → c_goods 순.
   c_wishes(사용자 데이터)·c_events(행동 기록)는 건드리지 않는다.
   완료 기준: 남은 c_goods 수 = 이전 − 삭제 대상 수.
4. **사전 재생성** — backend/README 갱신 계약대로 20260817600000(오타 사전),
   20260817900000(색 조건) 재실행. 완료 기준: 두 마이그레이션이 오류 없이 끝난다.
5. **검증** — 삭제된 표본 상품이 피드·검색에 안 나오고, 검색·피드가 정상 동작한다
   (Aside 브라우저). 완료 기준: 표본 goods_no 검색/피드 부재 확인, 첫 화면 정상.

## 주의

- 찜에 담긴 상품이 삭제되면 보관함 목록(c_wish_page의 c_goods 조인)에서 조용히
  사라진다 — 겹침이 있으면 삭제 전에 보고한다.
- 이 절차는 재수집 후에도 반복 사용할 수 있다(스캔 스크립트·SQL을 backend/db에 보관).
