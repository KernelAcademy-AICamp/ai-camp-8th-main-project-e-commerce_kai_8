# 마이페이지 이동 지연 줄이기 (2026-08-20)

## 배경 — 무엇이 문제인가

마이페이지 버튼을 누르면 화면이 바뀌기까지 오래 걸린다. 프로덕션(`ai-camp-8th-main-project-e-commerce.vercel.app`)을 서울에서 실측한 결과다. 각 8회 교차 측정, 중앙값.

| 경로 | 첫 바이트까지 | Vercel 캐시 | 처리 위치 |
| --- | --- | --- | --- |
| `/wishlist` | 0.06초 | `PRERENDER` | 서울 엣지(`icn1`)에서 끝 |
| `/my` (로그인 안 함) | 0.36초 | `MISS` | `icn1` → `iad1`(미국 버지니아) |
| `/my` (세션 쿠키 있음) | 0.64초 | `MISS` | `icn1` → `iad1` |

`/settings`도 `/my`와 같다. `/wishlist`는 같은 계정성 화면인데 6배 빠르다 — 차이는 아래 세 가지에서 온다.

### 원인 1 — 앱 서버가 미국에 있고, 데이터베이스는 아시아에 있다

Vercel 응답 헤더의 `x-vercel-id`가 `icn1::iad1`이다. 요청이 서울 엣지로 들어와 **미국 버지니아의 함수까지 가서** 실행된다. 그런데 Supabase는 아시아에 있다(서울에서 데이터베이스까지 닿는 요청이 0.09초). 즉 로그인 확인 한 번이 **태평양을 두 번 건넌다**: 브라우저(서울) → 엣지(서울) → 함수(미국) → Supabase(아시아) → 함수(미국) → 브라우저(서울).

리전 설정 파일이 저장소에 없다. 현재 리전은 Vercel 프로젝트 대시보드의 기본값이다.

### 원인 2 — 매번 로그인을 확인한다 (사용자가 처음 지목한 부분)

`frontend/proxy.ts`가 `/my`·`/settings`·`/auth` 진입마다 인증 서버에 사용자를 물어본다. 세션 쿠키가 없으면 네트워크 없이 즉시 끝나고(0.36초), 있으면 왕복이 생긴다(0.64초). **차이 0.28초가 로그인 확인 비용**이다. 이 계층은 만료 직전 토큰을 갱신하려고 둔 것인데(`docs/plans/2026-08-18-google-login-phase1.md`), 갱신이 필요 없는 대다수 이동에서도 똑같이 왕복한다.

측정의 한계: 0.28초는 세션 형태의 쿠키를 붙여 잰 값이다. 실제 유효 세션은 갱신이 필요 없을 때 이보다 다소 적을 수 있다. 실계정 브라우저 측정으로 확정해야 한다.

### 원인 3 — 기다리는 동안 화면에 아무것도 없다

앱 라우트 어디에도 로딩 경계 파일이 없다. 그래서 서버 응답이 도착할 때까지 이전 화면에 머문다 — 버튼이 죽은 것처럼 느껴지는 직접 원인이다. 미리 받아두기(prefetch)도 듣지 않는다: `/my`를 미리 받아보면 181바이트짜리 빈 응답이 0.37초 걸려 돌아온다(동적 렌더 + 로딩 경계 없음).

덧붙여, 페이지가 뜬 **뒤에도** 브라우저가 같은 로그인 확인을 한 번 더 한다(`use-auth-session`). 프록시가 이미 확인한 것을 세 번째로 확인하는 셈이고, 그동안 스켈레톤이 더 남는다.

### 왜 `/my`는 캐시가 안 되나

세 가지가 겹쳐 있다. ⓐ 페이지가 주소의 질의 값(`?auth=`)을 서버에서 읽어 강제로 동적 렌더가 된다. ⓑ `next.config.ts`의 인증 경로 목록에 걸려 저장 금지 캐시 정책이 붙는다. ⓒ 프록시 적용 범위에 포함된다. ⓑ와 ⓒ는 **일부러 같은 집합으로 맞춰 놓은 것**이다 — 세션 쿠키를 내려주는 응답이 공유 캐시에 들어가면 다른 사용자에게 그 세션이 전달되기 때문이다. 이 계약은 깨면 안 된다.

---

## 하지 않을 것 (경계)

- **인증 경로의 캐시 차단을 그냥 푸는 것.** 쿠키를 내려주는 응답이 공유 캐시에 들어가는 사고와 직결된다. 프록시가 그 경로에서 쿠키를 쓰지 않게 된 것이 **먼저 증명된 뒤에만** 논의한다.
- **로그인 판정을 저장된 세션 값만 보고 내리는 것.** 권한 판정은 인증 서버에 물어 확인한다는 기존 설계를 바꾸지 않는다. 이 계획이 줄이려는 것은 **갱신이 필요 없는데도 도는 왕복**이지 판정 자체가 아니다.
- **성능을 위해 화면 동작을 바꾸는 것.** 로그인 여부에 따라 보이는 내용은 지금과 같아야 한다.

---

## 단계

각 단계는 그것만 배포해도 되는 한 조각이다. 앞 단계가 막히면 뒤 단계는 독립적으로 진행할 수 있다.

### 1단계 — 앱 서버 리전을 데이터베이스 쪽으로 맞춘다

가장 큰 단일 효과이고 코드를 거의 건드리지 않는다. `/my`뿐 아니라 Supabase와 이야기하는 모든 경로(검색 등)가 함께 빨라진다.

**할 일**

1. Supabase 프로젝트가 실제로 어느 리전인지 대시보드에서 확인한다. (지금은 "아시아"까지만 지연 측정으로 추정한 상태다 — 추정으로 진행하지 않는다.)
2. Vercel 함수 리전을 그 리전과 같거나 가장 가까운 곳으로 지정한다. 저장소의 설정 파일로 둘지 대시보드 설정으로 둘지는 열어 둔다 — 다만 **어느 쪽을 골랐는지 기록으로 남긴다**(설정이 코드에 없으면 다음 사람이 원인을 못 찾는다).
3. 현재 요금제에서 리전 지정이 가능한지 먼저 확인한다. 불가하면 여기서 멈추고 그 사실을 적는다.
4. 배포 후 다시 측정한다.

**완료 기준 (눈으로 확인)**

- `/my` 응답 헤더의 처리 위치 표시에서 **미국 리전이 사라지고** 아시아 리전만 남는다.
- 로그인 상태에서 `/my` 첫 바이트까지가 **0.64초에서 눈에 띄게 줄어든다.** 목표 수치를 미리 못 박지 않는다 — 측정 전후 값을 나란히 기록한다.
- 검색 등 기존 기능이 그대로 동작한다(피드가 뜨고, 검색 결과가 나온다).

**되돌리기**: 리전 설정을 원래대로 되돌리고 재배포. 코드 변경이 없거나 한 줄이므로 되돌리기가 값싸다.

**상태 (2026-08-20): 착수 못 함.** 위 1·3번(Supabase 실제 리전, 요금제에서 리전 지정 가능 여부)을 확인하지 못했다. 추정으로 옮기지 않는다.

### 2단계 — 누르는 즉시 화면이 반응하게 한다

지연을 없애지는 못해도 **버튼이 죽은 것처럼 보이는 문제**를 없앤다. 실제 지연이 남아 있어도 체감이 크게 달라지는 구간이다.

**할 일**

1. 마이페이지와 설정 화면에 로딩 경계를 둔다.
2. 로딩 중 화면은 **완성 레이아웃을 그대로 본뜬 스켈레톤**이어야 한다 — 선 몇 개짜리 자리 표시는 안 된다. 이미 마이페이지 안에 로그인 판정 중 스켈레톤이 있으니 그것과 어긋나지 않게 맞춘다(들어올 때 스켈레톤 → 다른 스켈레톤 → 완성으로 두 번 튀면 안 된다).
3. 다른 경로(찜 보관함·로그인)에도 같은 게 필요한지 판단한다. 그 경로들은 이미 빠르므로 **필요 없다고 판단되면 넣지 않고 이유를 적는다.**

**완료 기준 (눈으로 확인)**

- 홈에서 마이페이지 버튼을 누르면 **즉시** 마이페이지 뼈대가 나타나고, 그 뒤 내용이 채워진다. 이전 화면에 머무는 구간이 없다.
- 스켈레톤에서 완성으로 넘어갈 때 요소 위치가 튀지 않는다.
- 설정 화면도 같다.

**상태 (2026-08-20): 완료.** 로컬 프로덕션 빌드에 서버 지연 3초를 임시로 넣어 재현하고, 실제 계정으로 로그인된 브라우저에서 확인했다.

- 누른 지 0.7초 시점에 마이페이지 뼈대가 화면 전체(머리글·아바타·이름 두 줄·버튼·취향 카드 축 4줄·색 칩·브랜드)에 떠 있었고, 도착 후 화면과 요소 위치가 어긋나지 않았다. 설정 화면도 같다(계정 삭제 영역만 도착 후 아래에 붙는다 — 의도한 것).
- **덤으로 알게 된 것**: 로딩 경계는 이동 중 화면만 바꾸는 게 아니라 서버 응답을 **스트리밍**으로 만든다. 지연 3초를 넣은 상태에서 첫 바이트 0.014초 / 전체 3.0초였고, 첫 응답 HTML 안에 이미 뼈대가 들어 있었다. 주소를 직접 열어도 즉시 그려진다는 뜻이다.
- 뼈대가 두 번 튀지 않는 것은 `app/my/loading.test.tsx`가 지킨다(이동 중 화면과 도착 직후 첫 그림의 HTML을 통째로 비교). 이 테스트가 실제로 어긋남을 잡는지 일부러 깨뜨려 확인했다.

### 3단계 — 갱신이 필요 없는 이동에서 왕복을 없앤다

원인 2를 직접 없앤다. 1·2단계와 독립이다.

**할 일**

1. 세션 갱신 계층이 **매번 인증 서버에 묻는 대신, 토큰이 곧 만료되는 경우에만** 묻도록 조건을 붙인다. 만료가 임박했는지 판단하는 방법(쿠키에 담긴 만료 시각을 로컬에서 읽는 등)은 여러 가지가 가능하므로 하나로 못 박지 않는다.
2. **"곧"이 얼마인지 정한다.** 너무 짧으면 만료된 채로 화면에 도달하고, 너무 길면 왕복을 못 줄인다. 정한 값과 근거를 코드 주석에 남긴다.
3. 판단 자체가 실패하면(쿠키를 못 읽음, 형식이 다름) **지금처럼 물어보는 쪽으로 떨어진다.** 판단 실패를 "갱신 불필요"로 해석하면 세션이 만료된 채 통과한다.
4. 브라우저 쪽 중복 확인(원인 3의 후반부)을 줄일 수 있는지 별도로 살핀다. 서버가 이미 판정한 결과를 화면에 넘기는 방법이 있으나 **페이지를 정적으로 만들려는 4단계와 충돌**한다. 둘 중 무엇을 택할지는 4단계 판단 후로 미룬다 — 이 단계에서는 조사만 하고 결론을 적는다.

**완료 기준 (눈으로 확인)**

- 실제 구글 계정으로 로그인한 뒤 마이페이지를 **연속으로 여러 번** 오간다. 두 번째 이후 이동의 첫 바이트까지가 첫 이동보다 짧고, 로그인 안 한 상태의 값에 가까워진다.
- **토큰이 실제로 만료에 가까워진 상황에서 갱신이 여전히 일어난다.** 만료 시각을 짧게 만든 세션이나 오래 방치한 세션으로 확인한다. 이걸 확인하지 않으면 "빨라졌지만 세션이 안 끊긴다"를 검증한 것이 아니다.
- 로그아웃·재로그인·다른 탭 로그아웃이 지금과 똑같이 동작한다.

**상태 (2026-08-20): 코드 완료, 프로덕션 측정은 남음.**

계획의 1~3번은 **필요 없었다.** 조사해 보니 여유 시간 판단은 이미 라이브러리 안에 있었다 — `getUser()`와 `getSession()`은 **둘 다 같은 갱신 경로**를 타고(`GoTrueClient.__loadSession`, 만료 90초 전부터 갱신: `EXPIRY_MARGIN_MS` = 틱 30초 × 3), `getUser()`만 거기에 **인증 서버 확인 왕복을 더한다.** 우리 갱신 계층은 권한을 판정하지 않으므로 그 확인이 필요 없다. 그래서 직접 만들려던 여유 시간 상수(60초)는 라이브러리의 90초 안에 완전히 묻히는 **죽은 코드**였고, 지우고 `getUser()` → `getSession()` 한 줄 교체로 끝냈다.

*실제 계정으로 로그인된 쿠키로 로컬 프로덕션 빌드를 A/B 측정 (각 6회 중앙값)*

| 방식 | `/my` 응답 시간 |
| --- | --- |
| 예전 (`getUser` — 갱신 + 확인) | 0.080초 |
| 지금 (`getSession` — 갱신만) | **0.008초** |

*세션이 끊기지 않는지 (완료 기준의 핵심)*

- **아직 넉넉한 토큰**(만료까지 23분): 갱신 쿠키 0개, 0.015초. 네트워크로 나가지 않았다.
- **만료된 토큰**(세션 쿠키의 만료 시각을 과거로 바꿔 만듦): 갱신 쿠키 **2개 발급**, 0.153초. 갱신이 그대로 돈다.

*아직 안 한 것*

- **프로덕션 측정.** 위 숫자는 로컬 서버 기준이라 왕복이 서울↔Supabase(약 0.07초)다. 프로덕션은 함수가 미국에 있어 같은 왕복이 약 0.28초였으므로 **효과는 더 크게 나와야 한다** — 배포 후 확인한다.
- **로그아웃·재로그인·다른 탭 로그아웃** 재확인.
- 브라우저 쪽 중복 로그인 확인(원인 3 후반부)은 손대지 않았다. 4단계 판단 후로 미룬다.

### 4단계 (조건부) — 마이페이지의 강제 동적 렌더를 없앤다

`?auth=` 질의 값을 서버에서 읽는 것 때문에 페이지가 절대 미리 만들어지지 않는다. 이걸 화면 쪽에서 읽게 바꾸면 뼈대를 미리 만들어 둘 수 있다.

**이 단계는 앞 단계 결과를 보고 착수 여부를 정한다.** 1~3단계 후에도 지연이 남아 있을 때만 한다. 셋 다 끝나면 남는 이득이 작을 수 있고, 캐시 계약(위 "왜 캐시가 안 되나" ⓑⓒ)에 가장 가까이 가는 변경이라 위험이 제일 크다.

**할 일 (착수하기로 정한 경우)**

1. 로그인 실패 안내를 서버가 아닌 화면에서 읽게 바꾼다.
2. **캐시 정책은 건드리지 않는다.** 저장 금지 정책과 프록시 적용 범위는 그대로 둔다. 이 단계의 이득은 "공유 캐시에 올리는 것"이 아니라 "미리 받아둘 뼈대가 생기는 것"이다.
3. 로그인 실패 안내가 여전히 뜨는지 확인한다.

**완료 기준 (눈으로 확인)**

- 로그인에 실패하고 돌아왔을 때 빨간 안내 문구가 **지금과 똑같이** 뜬다.
- 응답 헤더의 캐시 정책이 **변하지 않았다**(저장 금지가 그대로 붙어 있다).
- 마이페이지 이동이 1~3단계 시점보다 더 빨라졌다. 안 빨라졌으면 되돌린다.

---

## 검증 방법 (공통)

- **측정은 배포된 프로덕션에서 한다.** 로컬 개발 서버는 리전도 캐시도 다르므로 이 문제를 재현하지 못한다.
- **각 단계 전후를 같은 방식으로 재고 숫자를 나란히 남긴다.** 8회 이상 반복해 중앙값을 쓴다 — 1회 측정은 편차에 묻힌다.
- **실제 구글 계정으로 브라우저에서 확인한다.** 명령줄 측정만으로는 "버튼을 눌렀을 때 무엇이 보이는가"를 확인할 수 없다. 특히 2단계는 브라우저로만 확인 가능하다.
- **로그인 상태와 비로그인 상태를 둘 다 확인한다.** 두 경로의 비용이 다르다.

## 미정

- Supabase 프로젝트의 정확한 리전 (1단계 첫 항목에서 확인) — **사람이 확인해 줘야 한다.**
- 현재 Vercel 요금제에서 함수 리전 지정이 가능한지 (1단계에서 확인) — **사람이 확인해 줘야 한다.**
- ~~3단계의 "만료 임박" 기준 시간~~ — 라이브러리가 이미 갖고 있어 정할 필요가 없어졌다(위 3단계 상태 참고).
- 4단계 착수 여부 — 1단계까지 끝내고 프로덕션에서 다시 재본 뒤 판단한다.
- 브라우저 쪽 중복 로그인 확인을 없앨지 — 4단계와 충돌하므로 함께 결정한다.
