# 행동 기반 성별 피드 하드 필터 — 구현 계획 (2026-08-20)

설계 근거: [스펙](../superpowers/specs/2026-08-20-gender-feed-personalization-design.md). 이 계획은 코드 없이 순서와 단계별 완료 기준만 적는다.

## 무엇을 만드나 (이 repo 문맥을 모르는 독자용)

aTee는 티셔츠 이미지를 무한 스크롤로 훑는 PWA다. 피드는 세 경로로 나온다: ① 개인화 믹스(서버 RPC `c_mix_page` — 사용자가 행동한 상품 목록 "앵커"를 클라이언트가 실어 보내면 유사·반대·다양성 상품을 섞어 반환), ② 무작위(`c_feed_page` — 콜드스타트·비회원), ③ 믹스 실패 시 무작위 폴백. 카탈로그 상품에는 성별 속성(남성/여성/공용, 커버리지 99.2%)이 있고, 피드 후보는 좁은 물질화 테이블 `c_thumb_dims`(약 22.6만 행, 성별 열 보유)에서 뽑는다.

목표: 사용자가 남성 상품을 자주 행동(탭·찜)하면 세 경로 모두 남성+공용 상품만, 여성이면 여성+공용만 나오게 한다. 판정은 기기(클라이언트)가 앵커의 성별 분포로 하고, 서버 RPC에 널 허용 성별 인자를 추가해 후보 단계에서 거른다. 인자가 널이면 완전히 기존 동작이다(롤백 경로).

검증 가설은 하나다: **행동만으로 판정한 성별 하드 필터가, 성능 회귀 없이, 세 피드 경로를 확실히 구분한다.**

## 시작값 (튜닝 대상 — 업무 규칙 아님)

- 잠금 문턱: 성별(남성/여성) 있는 앵커의 가중치 합에서 우세 성별 비율 60% 이상, 그런 앵커 최소 3개.
- 풀림: 같은 계산이 문턱 아래로 내려가면 즉시 전체 복귀(대칭).
- 공용·성별 미상 앵커(예: 큐레이션 경로 상품은 성별이 안 실림)는 모수에서 제외.

## 단계

### 0단계 — 성능 게이트 (가장 먼저: 이 기능의 전신인 성별 토글이 2026-08-18 성능 사유로 기각됐다)

- 무엇을: 프로덕션과 같은 데이터가 있는 Supabase에서, 피드 후보 쿼리(`c_thumb_dims` 기반)에 "성별 = 대상 성별 또는 공용" 조건을 얹은 실행 계획과 실제 소요 시간을 잰다. 개인화 믹스의 벡터 검색 버킷에 같은 조건을 얹은 경우도 잰다.
- 판정: 조건 없는 현행 대비 유의미한 회귀(체감 기준: 피드 한 페이지 응답이 기존보다 뚜렷이 느려짐)가 있으면 성별 열 인덱스(부분 인덱스 포함)를 만들어 재실측한다. 인덱스로도 안 잡히면 **여기서 중단하고 실측 수치와 함께 보고**한다 — 이후 단계는 진행하지 않는다.
- 완료 기준: 실측 수치(조건 없음 / 조건 있음 / 인덱스 유무별)가 이 계획 파일이나 커밋 메시지에 기록돼 있고, "진행 가능" 판정이 적혀 있다.

### 1단계 — 서버: 두 피드 RPC에 성별 인자 추가

- 무엇을: `c_mix_page`와 `c_feed_page`에 널 기본값의 성별 인자를 추가하는 마이그레이션을 만든다. 널이면 기존과 완전히 같은 동작. '남성'/'여성' 외의 값은 서버가 널로 강제한다(기존 입력 방어 방식을 따른다). 필터는 후보풀 단계에서 "대상 성별 또는 공용"으로 걸어 모든 버킷(유사·부분·반대·다양성)에 한 번에 적용하고, 벡터 검색 버킷은 후보 배수를 필터율만큼 늘린다. 0단계에서 인덱스가 필요하다고 판정됐으면 같은 마이그레이션에 포함한다.
- 완료 기준: SQL 직접 호출로 — 인자 없이 부르면 기존과 같은 구조의 결과가 나오고, '남성'을 넣으면 결과에 여성 전용 상품이 0건이며(공용은 나옴), '여성'도 대칭으로 동작하고, 임의 문자열을 넣으면 널과 같은 결과가 나온다. 페이지를 이어서 받아도(커서 진행) 동일하게 유지된다.

### 2단계 — 기기: 앵커에 성별 기록 + 우세 성별 판정 규칙

- 무엇을: 기기 취향 프로필의 앵커에 행동한 상품의 성별을 함께 저장하고(행동 시점에 화면의 상품 데이터에 이미 성별이 있음 — 피드·검색 모두), 앵커 목록에서 우세 성별(남성/여성/없음)을 계산하는 순수 규칙을 추가한다. 프로필 스키마 버전을 올리되, 성별 없는 기존 저장분도 그대로 읽히게 한다(성별은 선택 필드). 서버 보관 함수는 앵커 내용을 검증하지 않으므로 서버 변경은 없다 — 단, 프로필 크기 상한(16KB) 안에 머무는지 확인한다.
- 완료 기준: 단위 테스트로 — 남성 상품 행동이 쌓이면 판정이 '남성'이 되고, 반대 성별 행동 몇 번으로 문턱 아래로 내려가면 '없음'으로 돌아오며, 공용·성별 미상만 있는 프로필은 항상 '없음'이고, 성별 없는 옛 프로필을 읽어도 오류가 없다. `npm run check`와 기존 테스트 전체가 통과한다.

### 3단계 — 기기: 판정 결과를 세 피드 경로에 연결 + 기존 앵커 1회 보강

- 무엇을: 회원의 피드 요청(개인화·무작위·폴백 모두)에 판정된 성별을 실어 보낸다. 비회원은 앵커 자체가 없으므로 자동으로 널이다. 이미 저장돼 있던 성별 없는 앵커는 상품 번호로 성별을 한 번 조회해 채운다(기본키 목록 조회라 저렴 — 방법은 구현 시 선택).
- 완료 기준: 브라우저(Orca 내장 브라우저)에서 — 남성 상품을 몇 번 탭한 뒤 새 피드 페이지를 받으면 여성 전용 상품이 0건으로 보이고, 검색에서 여성 상품을 찾아 몇 번 행동하면 잠금이 풀려 전체 성별이 다시 보인다. 믹스를 강제로 실패시켜(예: 네트워크 차단) 폴백 경로에서도 필터가 유지되는 것이 보인다.

### 4단계 — 검증 기록

- 무엇을: 배포 전 최종 실측 — 필터 적용 전후의 피드 응답 시간을 같은 조건에서 비교해 회귀가 없음을 수치로 남긴다. 잠금·풀림이 실제 몇 번의 행동에서 일어나는지 관찰해 시작값(60%/3개)이 "매우 민감" 의도에 맞는지 기록하고, 어긋나면 조정한다.
- 완료 기준: 전후 응답 시간 수치와 잠금·풀림 관찰 결과가 기록돼 있고, 미검증 항목이 있으면 "미검증"으로 명시돼 있다.

## 범위 밖 (후속 후보)

- 마이페이지 취향 카드에 성별 상태 표시, 수동 성별 설정 UI.
- 큐레이션 경로 상품에 성별 실어 보내기(현재는 성별 미상으로 모수 제외 — 동작에는 문제 없음).

## 미정

- 인덱스 필요 여부와 종류 — 0단계 실측이 정한다.
- 문턱 시작값의 최종치 — 4단계 관찰이 정한다.
- 기존 앵커 성별 보강의 구체 방법 — 구현 시 선택(여러 방법 가능, 완료 기준만 고정).

## 0단계 실측 기록 (2026-08-20)

프로덕션 Supabase(`backend/.env.local`의 `SUPABASE_DB_URL`)에서 psql로 직접 측정. 데이터 변경 없음(읽기 전용 — 임시 인덱스도 필요 없어 생성하지 않았다). PostgreSQL 17.6. `c_thumb_dims` 총 226,205행, 자격(`width>0 and card_ok and feed_ok`) 226,194행 — 성별 분포 남성 93,324 / 여성 89,874 / 공용 41,085 / 미상 1,911.

### 1) base_pool 쿼리 (마이그레이션 186~196행, `c_thumb_dims` 직접 스캔)

EXPLAIN (ANALYZE, BUFFERS) 각 3회, Execution Time 기준. 1회차는 이 세션에서의 첫 실행이지만 직전 `count(*)` 조회로 페이지가 이미 캐시돼 있어 콜드/웜 차이는 미미했다(모두 `Buffers: shared hit`만, `read` 없음).

| 쿼리 | 1회 | 2회(웜) | 3회(웜) | 웜 평균 | 스캔 방식 |
|---|---|---|---|---|---|
| 기준선(필터 없음) | 167.6ms | 166.0ms | 166.2ms | 166.1ms | Parallel Seq Scan → top-N heapsort, `Buffers: shared hit=3745` |
| 남성 필터(`gender in ('남성','공용')`) | 132.9ms | 132.6ms | 132.7ms | 132.7ms | 동일 구조, Filter에 gender 조건 추가, `Buffers: shared hit=3745` |
| 여성 필터(`gender in ('여성','공용')`) | 130.6ms | 130.7ms | 130.9ms | 130.8ms | 동일 구조, `Buffers: shared hit=3745` |

성별 필터를 얹으면 정렬 대상 행 수가 줄어(133,125 → 79,138 / 77,315 추정) top-N heapsort 비용이 줄어서 **필터가 기준선보다 오히려 20% 가량 빠르다.** 버퍼 사용량은 세 쿼리 모두 동일(전체 테이블을 훑는 Seq Scan이라 필터 여부와 무관). 인덱스 불필요.

### 2) 벡터 버킷 프로브 (`sess_cand` LATERAL 패턴, 마이그레이션 134~148행)

샘플 앵커: `goods_no=6440370` (`c_img_vecs where img_type in (0,1) limit 1`). 원 쿼리와 동일하게 **LATERAL** 구조로 재구성해야 `c_img_vecs_bq_idx`(ivfflat, bit_hamming_ops) 인덱스가 실제로 쓰인다 — 처음에 비-LATERAL(단순 CROSS JOIN)로 재구성했더니 플래너가 인덱스를 버리고 전체 `c_img_vecs`(약 92만 행)를 Seq Scan + Sort 해 **36초**가 걸리는 것을 확인했다(이 결과는 재구성 오류였고 실제 함수 동작과 무관 — 산출물 2번 원문에 남겨둠). `ivfflat.probes=40`(프로덕션 믹스 RPC와 동일) 설정 후 LATERAL로 재측정:

| 쿼리 | 1회(콜드) | 2회(웜) | 3회(웜) | 웜 평균 | 스캔 방식 |
|---|---|---|---|---|---|
| 프로브 기준선(gender 조건 없음) | 883.9ms | 51.5ms | 33.1ms | 42.3ms | `Index Scan using c_img_vecs_bq_idx` (Order By ivfflat) + `c_thumb_dims_pkey` Memoize 조인 |
| 프로브 + 남성 필터(exists 절 안) | 189.7ms | 31.8ms | 32.9ms | 32.4ms | 동일 구조, `c_thumb_dims_pkey` Filter에 gender 조건 추가 |

1회차는 `c_img_vecs`가 디스크에서 읽혀(`read=158` 등) 콜드였고, 이후 캐시로 33~52ms까지 떨어졌다. 성별 필터를 exists 절 안(가장 얇은 `c_thumb_dims_pkey` 인덱스 스캔)에 추가해도 웜 평균이 오히려 약간 더 빠르다(42.3ms → 32.4ms). 인덱스 불필요.

### 3) statement_timeout (참고)

```
rolname       | setconfig
anon          | statement_timeout=8s
authenticated | statement_timeout=8s
authenticator | statement_timeout=8s, lock_timeout=8s (+ session_preload_libraries)
```
psql 세션 기본값은 `2min`이지만 API 경로(PostgREST)는 8초 제한. 위 실측치는 모두 1초 미만이라 이 한도에 여유가 크다.

### 4) 엔드투엔드 참고 (psql 직접 호출, 인자 기본값)

- `c_feed_page(42, null, 30)` → 267.7ms (30행)
- `c_mix_page('[]','[]','{}',42,30,false)` → 271.6ms (30행, 앵커 없이 무작위 계열 위주)

### 5) 임시 인덱스

만들지 않았다. base_pool·벡터 프로브 모두 필터 적용 후 웜 시간이 기준선과 같거나 더 빨라 판정 기준(2배 미만·절대 300ms 미만)을 이미 만족한다.

### 판정: **진행 가능** (인덱스 불필요)

성별 필터를 얹어도 두 후보풀 쿼리 모두 기준선 대비 느려지지 않았다(오히려 20~25% 빨라짐). `c_thumb_dims`가 226K행짜리 좁은 물질화 테이블이라 Seq Scan 자체가 이미 저렴하고, 필터는 정렬 대상 행 수만 줄이기 때문으로 보인다. 벡터 버킷도 ivfflat 인덱스가 정상적으로 쓰이는 LATERAL 형태에서는 성별 조건이 가장 얇은 PK 인덱스 스캔에 얹혀 영향이 없다. 1단계(서버 RPC에 성별 인자 추가)로 진행해도 좋다.
