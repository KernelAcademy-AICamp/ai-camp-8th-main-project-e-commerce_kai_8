# 검색 성별 하드 조건 (2026-08-20)

## 배경 — 왜 하나

'남성전용'을 검색하면 0건이다. 검색 색인 텍스트(브랜드명+상품명)에 그 문구가 든 상품이
카탈로그에 0개이기 때문이다. 상품의 성별은 제목이 아니라 카탈로그의 성별 라벨 열에
있는데, 검색은 그 열을 해석하지 않는다. 0건이면 화면이 취향 피드로 대체하는데, 그
피드에는 행동 기반 성별 하드 필터(#63)가 걸려 있어 여성으로 판정된 계정에서는
"남성전용을 검색했는데 여성 상품만 나오는" 착시가 생겼다 (2026-08-20 실사용 로그로 확인).

색·카테고리에서 겪은 것과 같은 구조다: 사용자가 말하는 속성이 제목 단어가 아니라
카탈로그 정본 값이다. 성별 라벨 커버리지는 226,194건 중 224,283건(99.2%)이다
(남성 93,324 · 여성 89,874 · 공용 41,085 · 없음 1,911).

적용 대상은 **v2 검색만**이다. 검색 로그 실측으로 2026-08-17 저녁 이후 실사용이 전부
v2였고(문제의 검색 포함), v1은 구조화 조건이 아예 없는 레거시 경로라 손대지 않는다.

## 사람이 정한 것 (1단계 질문 답, 2026-08-20)

- **성별어의 범위**: '남성'·'남자' 같은 일반 성별어 = 해당 성별 + 공용 (피드 #63과
  같은 의미). **'전용'이 붙은 형태('남성전용' 등) = 해당 성별만** (공용 제외).
- **적용 경로**: v2만. (프로덕션이 v2임을 로그로 확인했다.)
- **LLM 확장어 '여성'**: 목록에서 제거한다. 확장어는 질의 문자열에 덧붙는 방식이라,
  성별이 하드 조건이 되면 LLM 추론이 조용히 하드 필터로 변하기 때문이다.

## 기존 도구 조사

색(c_search_color_terms)·카테고리(c_search_category_terms)·브랜드에 이미 같은 구조의
"용어 사전 + 파서" 패턴이 repo에 있다. 외부 도구가 필요한 일이 아니고, 이 패턴을
그대로 따른다. 새로 만드는 것은 사전 내용(성별어)과 색인 열 하나뿐이다.

## 단계

### 1. 성별 용어 사전과 파서 (DB 마이그레이션)

- 용어 → 성별 라벨 매핑 표를 만든다. 기존 카테고리 표와 같은 shadow 교체 방식.
  - 남성 계열: 남성, 남자, 맨즈, 멘즈, 남성용, 남자용 (+ 전용 형태: 남성전용, 남자전용)
  - 여성 계열: 여성, 여자, 우먼즈, 위민즈, 여성용, 여자용 (+ 전용 형태: 여성전용, 여자전용)
  - 공용 계열: 공용, 남녀공용, 유니섹스 (공용은 항상 공용 라벨만)
  - '전용' 형태에는 엄격 표시를 둔다: 엄격이면 해당 성별만, 아니면 해당 성별+공용.
- 질의 단어에서 성별을 뽑고 나머지를 돌려주는 파서를 만든다. 카테고리 파서와 같은
  규칙: **서로 다른 성별을 둘 이상 말하면 조건을 걸지 않는다** (모르면 손대지 않는다).
- 사전 용어가 색·카테고리·브랜드 사전과 겹치지 않는지 적재 시점에 확인한다
  (겹치면 파서 순서에 따라 가로채기가 생긴다 — 기존 브랜드 파서의 같은 주의를 따른다).
- **완료 기준**: 파서에 '남성전용 반팔'을 넣으면 (남성·엄격, 나머지 '반팔')이 나오고,
  '남성 여성'을 넣으면 조건 없음이 나오는 것을 psql로 확인.

### 2. 검색 색인에 성별 열 추가 (DB 마이그레이션)

- 검색 색인 표(c_search_docs)에 성별 열을 추가한다. 기존 재구축 마이그레이션의
  shadow 교체(_next 스왑) 방식을 그대로 따르는 **새 마이그레이션**으로 만들어,
  앞으로 색인 재생성은 이 새 파일을 재실행하는 것으로 바뀐다는 것을 주석에 남긴다.
- 인덱스는 두지 않는다 — #63의 0단계 실측에서 성별 필터는 인덱스 없이 기준선보다
  느려지지 않았다. 검색 쪽도 3단계 완료 기준에서 실측으로 확인하고, 넘으면 그때 판단.
- **완료 기준**: 색인 표에 성별 열이 있고 분포가 카탈로그와 일치(남성 9.3만대 등)함을
  psql로 확인. 재실행해도 같은 결과(재실행 가능성)를 한 번 더 실행해 확인.

### 3. v2 검색 함수에 성별 조건 배선 (DB 마이그레이션)

- 구조화 조건 해석 사슬(브랜드 → 카테고리 → 색 → 가격)에 성별을 끼운다. 자판 복원
  대상 판정(구조화 조건을 뺀 나머지 계산)에도 같은 자리를 추가한다.
- 세 갈래 모두에 성별 조건을 건다: AND 선판정, 갈래 ①(텍스트 매칭), 갈래 ②(하드
  조건만 만족하는 나머지). 엄격이면 해당 성별만, 아니면 해당 성별+공용.
- 하드 조건 유무 판정(v_hard)과 원문 문맥 보존(v0_*)에 성별을 포함한다 —
  빠뜨리면 표기 폴백 뒤 성별 조건이 사라지거나 마지막 후보의 값이 남는다.
- RPC 시그니처는 바뀌지 않는다(성별은 내부 해석). 다음 페이지 계약도 그대로다 —
  성별어는 query_used에 원문대로 남고, 해석이 결정론적이라 재해석이 같다.
- **완료 기준** (전부 psql 실측):
  - '남성전용' → 결과 전원이 남성 라벨. '남성' → 남성+공용만. '여성전용' → 여성만.
  - '남성 반팔' → 남성+공용 ∩ 반팔 카테고리. '검정 남성' → 색과 성별이 함께 걸림.
  - '남성 여성' → 성별 조건 없이 기존과 같은 동작.
  - 2페이지: 1페이지 응답의 query_used와 커서로 요청해 중복·누락 없이 이어짐.
  - 성능: 성별 질의 웜 실행이 기존 웜 p95(수십 ms대)와 같은 자릿수. 넘으면 멈추고
    원인을 본다(인덱스 추가는 그때 판단).

### 4. LLM 확장어 목록에서 '여성' 제거 (프론트)

- EXPANDABLE에서 '여성'을 빼고 프롬프트 버전을 올린다(캐시 무효화).
- 관련 테스트를 고친다.
- **완료 기준**: `npm run check`와 vitest 통과. 프롬프트 버전이 올라가 있음.

### 5. 검증과 교차 리뷰

- backend pytest(마이그레이션 순서·폴백 테스트) 통과.
- 프론트에서 실제로 '남성전용' 검색 → 남성 상품이 보이는 것을 브라우저로 확인
  (0건 대체 피드가 아니라 검색 결과로).
- Codex 교차 리뷰 1회 (조각마다 한 번 규칙). Blocker 수정 후 재검증은 별도로.

## 이 계획이 다루지 않는 것

- v1 검색(레거시 LIKE 경로)의 성별 이해 — 프로덕션이 v2라 실사용 영향 없음.
- 0건 대체 피드가 검색어의 성별 단서와 모순되는 문제 — 이 계획이 성별어 검색을
  0건이 아니게 만들어 이번 사례는 사라지지만, 성별어가 아닌 0건 질의의 대체 피드
  동작은 그대로다. 필요해지면 별도 조각.
- 성별 외 속성(시즌 등)의 구조화 — 한 번에 한 가설만.
