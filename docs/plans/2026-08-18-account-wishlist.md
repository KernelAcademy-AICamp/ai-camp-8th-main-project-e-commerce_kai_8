# 찜을 계정으로 — 구현 계획 (조각 2)

- 작성: 2026-08-18
- 설계: [2026-08-18-account-wishlist-design.md](../superpowers/specs/2026-08-18-account-wishlist-design.md)
- 선행 조각: [구글 로그인 조각 1](2026-08-18-google-login-phase1.md) — `develop` 병합 완료

이 문서는 **무엇을 / 어떤 순서로 / 무엇이 되면 끝**만 적는다. 코드·함수명은 넣지 않는다(`AGENTS.md` 계획 작성 규칙).

## 단계 순서를 이렇게 잡은 이유

핵심은 **찜이 계정에 있어서 기기를 넘어 따라오는 것**이다. 그래서 그것이 1단계다.

2단계(옮기기)가 3단계(게이트)보다 앞이다. 순서를 바꾸면, 기존에 찜해둔 사람이 **옮길 수단이 생기기 전에** 자기 찜을 못 보게 된다.

---

## 1단계 — 계정에 찜을 저장하고 읽는다

로그인한 사람의 찜이 서버에 저장되고, 다른 기기에서 로그인해도 같은 목록이 보인다. 비회원은 이 단계에서 지금과 똑같이 동작한다(로컬 찜).

**할 일**

1. 계정 찜을 담을 테이블을 마이그레이션으로 추가한다. 담는 것은 **사용자·상품 번호·찜한 시각**뿐이다. 상품 정보를 복사하지 않는다.
2. **사용자 행을 외래키로 참조하고 삭제가 연쇄되게** 한다. 조각 1이 남긴 게이트를 닫는 부분이다.
3. **상품 번호에는 외래키를 걸지 않는다.** 카탈로그 재수집으로 행이 지워지는 일이 생겨도 사용자의 찜이 조용히 사라지지 않게 한다.
4. 본인 행만 읽고 쓸 수 있게 잠근다. 테이블을 직접 열지 않고 **검증이 붙은 함수를 통해서만** 쓴다.
5. 권한은 **함수를 만드는 같은 변경 안에서** 정리한다 — 모든 역할과 비로그인 역할의 실행 권한을 회수하고 로그인 역할에만 부여한다. 회수를 빠뜨리면 의도와 실제가 어긋난다(조각 1에서 실제로 그런 함수 세 개를 발견해 고쳤다).
6. 찜 추가에 **상한 500**을 건다. 넘으면 거부하고 이유를 돌려준다 — 조용히 오래된 것을 버리지 않는다.
7. 같은 사용자·같은 상품을 여러 번 추가해도 **한 행**이고 오류가 아니다.
8. 목록 조회는 **정의자 권한 함수**로 내려준다. 카탈로그 원본은 비로그인 조회가 막혀 있어 클라이언트가 직접 이어 붙일 수 없다.
9. 목록에 **피드 노출 조건을 걸지 않는다.** 썸네일·가격 조건에서 빠진 상품도 사용자가 담은 것이니 보여야 한다.
10. 로그인한 사용자의 찜 화면·하트를 계정 데이터에 연결한다. 비회원 경로는 이 단계에서 건드리지 않는다.
11. 하트는 **즉시 반응하고 저장은 뒤따른다.** 실패하면 되돌리고 짧게 알린다. 같은 상품을 빠르게 여러 번 누르면 **마지막 의도가 이긴다.**
12. **익명 카탈로그 호출 경로를 계정 데이터용으로 바꾸지 않는다.** 조각 1이 둘을 섞지 말라고 못박았다.
13. **수집 방침과 공개 처리방침에 찜을 추가한다.** 이 단계부터 찜이 계정에 저장되므로, 저장 항목과 계정 삭제 범위에 들어가야 한다. 이 단계와 함께 나가야 한다.

**이 단계에서 정할 것**
- 상한 500이 맞는 값인지 (지금 로컬 상한을 그대로 가져온 것이고 근거를 따로 재지 않았다)

**완료 기준 (눈으로 확인)**
- 로그인하고 상품 몇 개를 찜한 뒤 새로고침하면 그대로 있다.
- **다른 브라우저에서 같은 계정으로 로그인하면 같은 찜 목록이 보인다.**
- 저장을 실패하게 만들면 **하트가 되돌아가고** 알림이 뜬다.
- 같은 상품을 빠르게 여러 번 누른 뒤 새로고침하면 **화면에 보이던 상태와 같다.**
- 501번째를 찜하려 하면 거부되고 이유가 보인다.
- 피드 노출 조건에서 빠진 상품도 찜 목록에 보인다.
- 계정을 삭제하면 그 계정의 찜 행이 남지 않고, **삭제 직전에 확보한 토큰으로 찜을 읽거나 쓸 수 없다.**
- 설정 화면과 공개 처리방침에 찜이 계정에 저장된다는 사실이 적혀 있다.

**자동 검증 (빈 스키마에서)**
- 권한 행렬: 모든 역할·비로그인 역할·토큰 없는 호출 **거부**, 본인만 허용, **남의 찜 접근 거부**.
- 상한, 중복 무시, **계정 삭제 시 연쇄**, 다른 사용자 생존.
- 객체가 이미 있는 실 DB에서 검증하면 거짓 통과가 난다. 반드시 빈 스키마에서 한다.

## 2단계 — 로그인할 때 기존 로컬 찜을 옮긴다

비회원으로 찜해둔 사람이 로그인하면 그 찜이 계정으로 올라온다. 이 단계가 끝나면 **로그인하면서 찜을 잃는 일**이 없어진다.

**할 일**

1. 신원 전환 처리에 **옮기기**를 끼워 넣는다. 순서가 곧 계약이다.
   - 전환을 감지한다 → **이전 신원이 익명이고 새 신원이 사용자일 때만** 로컬 찜을 "옮길 것" 보관함으로 뺀다 → 신원 종속 저장소를 정리한다 → 처리 표식을 확정한다 → 페이지를 다시 불러온다 → 다시 뜬 뒤 로그인 상태이면 보관함을 서버로 올리고 비운다.
2. **보관함을 신원 전환에도 살아남는 목록에 넣는다.** 넣지 않으면 방금 빼둔 것이 같은 정리에서 다시 지워진다.
3. **옮기는 것은 익명 → 사용자 전환뿐이다.**
   - 사용자 → 익명(로그아웃): 로컬에 있던 것은 이미 서버에 있다. 그냥 지운다.
   - 사용자 A → 사용자 B: **절대 옮기지 않는다.** 옮기면 A의 찜이 B 계정으로 들어간다.
4. 올리기가 실패하면 **보관함이 남아 다음 접속에 다시 시도한다.** 성공한 것만 뺀다. 이미 있는 상품은 서버가 무시한다.
5. 상한을 넘는 양을 옮기려 하면 어떻게 되는지 정하고, 사용자에게 결과를 알린다.
6. **결정 기록 O-35에 예외를 명시한다** — 취향 프로필은 승계하지 않지만 찜은 옮긴다. 취향 프로필은 계산된 결과고 찜은 사용자가 손으로 누른 것이라 성격이 다르다.

**완료 기준 (눈으로 확인)**
- 비회원으로 N개를 찜해둔 기기에서 로그인하면 **그 N개가 계정 찜에 들어가 있고** 기기에는 남지 않는다.
- 이미 계정에 있던 상품과 겹쳐도 중복되지 않고 오류도 나지 않는다.
- 올리기를 실패하게 만들면 **보관함이 남고**, 다음 접속에서 다시 시도해 성공한다.
- A로 로그인해 찜한 뒤 로그아웃하고 **B로 로그인하면 A의 찜이 넘어가지 않는다.** A로 다시 로그인하면 A의 찜은 그대로다.
- 로그아웃할 때는 옮기기가 일어나지 않는다.

**자동 검증**
- 옮기기 판정을 단위 테스트로 고정한다 — 익명 → 사용자에서만 참, 나머지 전환에서는 거짓.

## 3단계 — 찜과 찜 목록을 로그인 필수로 한다

**노출 전 필수.** 이 단계가 이번 조각의 목적이다.

**할 일**

1. 비회원이 하트를 누르면 **찜되지 않고 로그인으로 유도**한다.
2. 비회원이 찜 목록에 들어가려 하면 **진입 대신 로그인 유도**를 보여준다.
3. 유도 문구에 **이 기기에 남은 찜이 로그인하면 올라온다**는 사실을 알린다. 그 안내가 없으면 사용자는 자기 찜이 사라졌다고 본다.
4. 피드·검색·상세는 건드리지 않는다. 로그인 없이 계속 쓸 수 있어야 한다.
5. 설정 화면의 *"다음 업데이트에서 찜을 계정에 저장할 예정입니다"*를 지운다. 이 조각이 그 업데이트다.
6. **PRD를 갱신한다** — 찜이 계정 데이터가 되고 로그인이 필요해진다.

**이 단계에서 정할 것**
- 로그인 유도의 형태 — 그 자리에서 구글 로그인을 시작할지, 설정 화면으로 보낼지. **실제 화면을 보고 정한다.**

**완료 기준 (눈으로 확인)**
- 로그아웃 상태에서 하트를 누르면 **찜되지 않고** 로그인 유도가 뜬다.
- 로그아웃 상태에서 찜 목록에 들어가려 하면 **진입하지 못하고** 로그인 유도가 뜬다.
- 그 유도에서 로그인하면 이 기기의 기존 찜이 올라온 상태로 목록이 열린다.
- 로그인하지 않고도 피드·검색·상세는 그대로 쓸 수 있다.
- 설정 화면에 "다음 업데이트에서 찜을 계정에 저장할 예정"이 더는 없다.

**검증 기록 (2026-08-19)** — 통과. 유도는 문구 대신 **로그인 화면으로 바로 보내는** 방식으로 구현했다(별도 [로그인 화면 설계](../superpowers/specs/2026-08-19-login-screen-design.md) §7-1에 결과를 적었다). 비회원의 설정 화면 접근이 막히지 않은 것도 함께 확인했다.

## 4단계 — 부작용을 관찰한다

이 조각은 **지금 되는 기능을 막는 변경**이다. 효과와 대가를 함께 봐야 판단할 수 있다.

**할 일**

1. **비회원에게서 찜 신호가 사라지는 영향**을 볼 방법을 정한다. 개인화는 노출·탭·찜을 함께 쓰는데 가장 강한 신호 하나가 비회원 경로에서 사라진다.
2. 로그인 전환이 오르는지와 **탐색 이탈이 늘어나는지를 함께** 본다. 한쪽만 보면 판단할 수 없다.
3. 되돌릴 수 있는 경로를 확인한다. 게이트를 끄면 모두가 이전 동작으로 돌아가야 한다. **빌드 시 번들에 고정되는 환경변수로는 재빌드 없이 못 돌린다** — "즉시 롤백 가능"을 주장하려면 그 경로를 실제로 확인한다.

**완료 기준**
- 무엇을 어떻게 보는지가 문서에 적혀 있고, 되돌리는 절차를 **한 번 실제로 돌려봤다.**

## 완료 판정

- 위 완료 기준을 **실제로 돌려서** 관찰한다. 돌려보지 않은 것은 "미검증"으로 적는다.
- 조각마다 교차 리뷰를 한 번 받고, Blocker를 고친 뒤의 재검증은 별도로 한다.

## 미정 (설계에서 넘어온 것)

- 상한 500이 맞는 값인지 — 1단계에서 정한다.
- 비회원 찜 신호 소멸의 영향 크기와 측정 방법 — 4단계에서 정한다.
- 로그인 유도의 형태 — 3단계에서 화면을 보고 정한다.
