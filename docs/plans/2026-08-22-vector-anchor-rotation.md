# 벡터 계열 깊이 — 앵커 회전 구현 계획 (2026-08-22)

설계: [앵커 회전 설계 2차 개정](../superpowers/specs/2026-08-22-vector-anchor-rotation-design.md).
코드 없이 순서와 단계별 완료 기준만 적는다(AGENTS.md 계획 작성 규칙).

> **절차 이탈을 밝힌다.** 이 조각은 사람이 자리를 비운 동안 "멈추지 말고 진행하라"는
> 지시로 돌았고, 설계 → Codex 리뷰 → **구현·측정** → 계획 순서가 됐다. 계획을 뒤에

## 무엇을 만드나 (이 repo 문맥을 모르는 독자용)

개인화 피드 한 페이지 30장 중 12장은 **벡터 계열**이다 — 사용자가 본 상품(앵커)과
이미지가 닮은 것을 찾아온다. 그런데 서버는 클라이언트가 보낸 앵커 50개 중
**가중치 상위 5개(세션 2 + 장기 3)만** 쓰고, 그게 매 페이지 같다. 앵커가 같으면
닮은 상품 목록도 같아서 **22페이지부터 벡터는 새 상품을 하나도 못 낸다.**

이 작업은 페이지마다 **다른 앵커 묶음**을 쓰게 한다.

**검증 가설 하나**: 앵커를 돌려 쓰면 벡터 계열도 계속 새 상품을 낸다.

## 1단계 — 서버: 앵커 회전 ✅ 그림자 검증 완료

- **무엇을**: `c_mix_page`에 회전 인자(정수, 기본값 0)를 더한다. 앵커를 결정적 순서로
  줄 세운 뒤 회전 번호만큼 밀어 세션 2개·장기 3개를 고른다.
  **기준 앵커(부분·반대 버킷의 색·그래픽 기준)는 회전하지 않고** 전체 순위 1위로
  고정하며, 제외 집합에도 계속 포함한다.
- **완료 기준**
  1. **회전 0이면 현행과 완전히 같다** — ✅ 상품 집합·버킷까지 동일 확인
  2. 회전 1·2·3이 서로 다른 앵커 묶음을 고른다 — ✅ 장기 벡터 12개가 매번 다름
  3. 후보풀 계열 중복 0이 유지된다(#81 보장)
  4. 함수 설정·권한이 보존되고 옛 호출 형태가 동작한다

## 2단계 결과 — 회전 범위: **전체 50개 채택** ✅

리뷰는 **상위 15개**로 제한하라고 했다(낮은 가중 앵커가 품질을 끌어내린다).
**실측이 그 권고를 반박했다** — 이득이 거의 사라진다.

| 구성 | 100페이지 벡터 누적 고유 | 벡터 절벽 |
|---|---|---|
| 현행(회전 없음) | **252** | 22페이지 |
| 회전, 상위 15개 *(리뷰 권고)* | **297** | 26페이지 |
| **회전, 전체 50개 (채택)** | **493** | **51페이지** |

전체 50개를 채택한다. 근거: 상위 15개는 묶음이 5개뿐이라 5페이지 만에 한 바퀴 돈다.
품질 대가(낮은 가중 앵커가 운전하는 페이지)는 인정하지만, **지금은 22페이지부터
정확도조차 "이미 본 것"으로 되돌아온다** — 이 조각이 사는 쪽은 다양성이다.

**한계도 명확하다.** 493에서 다시 멈춘다. 앵커 50개를 3개씩 돌면 묶음이 유한하다.
근본 해법은 이웃 사전계산(조각 D)이다.

## 4단계 결과 — 응답 시간 교차 A/B ✅ 회귀 없음

| 위치 | 현행 p50 | 회전 p50 | 비율 | 3초 초과 |
|---|---|---|---|---|
| 1페이지 | 993ms | **862ms** | **0.87배** | 0회 |
| 40페이지 | 1,103ms | **936ms** | **0.85배** | 0회 |

> **하마터면 잘못 결론 낼 뻔했다.** 교차 A/B 전에는 회전판이 p50 4,525ms · max
> **40초**로 보였고 "캐시 지역성 때문에 느리다"고 판단할 참이었다. 실제로는
> **100페이지 측정 두 개를 1GB 인스턴스에서 동시에 돌린 내 측정 장치가 만든 부하**였다.
> 이 저장소에서 "20분 질의"가 데이터가 아니라 질의 구성 탓이었던 것과 같은 실수다.
> **공유 인스턴스에서는 같은 시점 교차 비교 말고는 시간을 믿을 수 없다.**

## 5단계 결과 — 배포 ✅

마이그레이션 적용 완료. 시그니처 10인자, 함수 설정(`search_path`, `work_mem=16MB`),
권한(`anon`·`authenticated`) 보존. 그림자 함수 3개 삭제.

REST 확인:

| 확인 | 결과 |
|---|---|
| 옛 body(회전 인자 없음) | HTTP 200, 30행 |
| 회전 0 | HTTP 200, **옛 body와 벡터 동일** |
| 회전 1 | HTTP 200, **회전 0과 벡터 겹침 0/12** |

## (원래 2단계 서술)


리뷰는 **상위 15개**로 제한하라고 했다(낮은 가중 앵커가 품질을 끌어내린다).
그러나 첫 실측에서 **이득이 거의 사라졌다.**

| 구성 | 100페이지 벡터 누적 고유 | 벡터 새것이 0이 되는 페이지 |
|---|---|---|
| 현행(회전 없음) | **252** | 22 |
| 회전, 상위 15개 | **297** | 26 |
| 회전, 전체 50개 | 측정 중 |  |

- **완료 기준**: 세 구성의 100페이지 수치가 나란히 적혀 있고, 어느 범위를 채택할지와
  그 근거(깊이 이득 대 품질 대가)가 적혀 있다.

## 3단계 — 클라이언트: 회전 번호를 왕복시킨다 ✅ 완료

- **무엇을**: 요청에 회전 번호를 싣고, **비어 있지 않은 개인화 페이지를 실제로 적용한
  뒤에만** 1 올린다. 세대(성별·시드·신원)가 바뀌면 0으로 되돌린다.
- **완료 기준** — 단위 테스트로 ✅
  1. 첫 요청은 회전 0
  2. 페이지를 받을 때마다 정확히 1씩 증가 (0, 1, 2, …)
  3. **빈 응답은 회전을 소비하지 않는다**
  4. 성별 변경 뒤 첫 요청이 회전 0 · 커서 없음
  5. `npm run check`와 테스트 전체 통과 (539개)

## 4단계 — 응답 시간 교차 A/B

**측정 두 개를 같은 인스턴스에서 동시에 돌린 탓에 지금까지의 시간 수치는 못 쓴다.**
(회전 상위15 p50 1,003ms 대 현행 523ms로 보였지만, 그때 다른 100페이지 측정이 함께
돌고 있었다.)

- **무엇을**: 다른 측정을 모두 멈춘 뒤, 같은 시점에 현행과 회전판을 **번갈아** 호출한다.
  워밍업 1회 뒤 5회씩. 1·50·100페이지 위치에서 각각.
- **왜 A/B인가**: 이 인스턴스는 다른 작업과 공유돼 같은 함수가 481ms~3,118ms로 흔들린다.
  저장해 둔 절대값과 비교하면 부하를 회귀로 오인한다(#81에서 겪었다).
- **주의**: 회전은 **다른 임베딩 페이지를 읽으므로** 캐시 지역성이 나빠질 수 있다.
  "앵커 수가 같으니 프로브도 같다"는 알고리즘 예산 이야기이고, IO는 별개다(리뷰 지적).
- **완료 기준**: 1페이지 p50이 현행의 **1.3배 이내**, 어떤 페이지도 **3초 이내**.
  p50·p95·max를 함께 남긴다. 넘으면 **중단하고 보고**한다.

## 5단계 — 배포와 브라우저 확인

- 마이그레이션을 트랜잭션 리허설 뒤 적용하고, **REST로** 옛 body·새 body를 확인한다.
- 브라우저에서 개인화 계정으로 오래 스크롤해 **화면에 뜬 고유 상품이 계속 늘어나는지**
  확인한다. 요청에 회전 번호가 실려 나가고 성별을 바꾸면 0으로 돌아가는 것도 본다.

## 6단계 — 검증 기록

- 설계 "확인 방법" 10개 항목의 결과를 수치로 적고, **안 돌려본 것은 미검증으로 명시**한다.
- 특히 **지표를 나눠 적는다** — 장기 벡터 / 세션 벡터 / 교차(벡터↔후보풀) / 후보풀 내부.
- 리뷰가 제안한 목표치(장기 벡터 960)에 도달했는지, 못 했으면 **분모와 함께 실패로**
  적는다. 조용히 목표를 낮추지 않는다.

## 이 계획이 스스로 경계하는 것

- **회전 0 동등성**이 이 조각의 안전망이다. 이것이 깨지면 기존 사용자의 첫 페이지가
  바뀐다 — 다른 어떤 지표보다 먼저 본다.
- **후보풀 중복 0**(#81 보장)을 따로 센다. 합쳐 세면 회전이 깨뜨렸는지 알 수 없다.
- **시간은 같은 시점 교차로만** 잰다. 이 인스턴스는 공유 자원이다.
- 리뷰의 권고(상위 15개)를 **실측이 반박했다.** 권고를 그대로 따르면 이득이 거의
  없었다 — 근거 없이 따르지 않는다.
