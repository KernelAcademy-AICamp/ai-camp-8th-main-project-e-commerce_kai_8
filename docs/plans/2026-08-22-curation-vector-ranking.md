# FOR YOU 큐레이션 순서를 벡터 유사도로 정한다

작성 2026-08-22 · 브랜치 `feature/curation-personalization`

## 무엇을 / 왜

지금 FOR YOU(큐레이션 57개 중 앞 6장)의 개인화는 **제목 키워드 매칭**이다. 내가 반응한
상품(앵커)의 제목을 받아와, 큐레이션마다 정해 둔 낱말 목록(`kw` 걸리면 통과 / `not` 있으면
탈락)에 걸리는지 본다. BROWSE 피드는 같은 앵커를 쓰면서도 **이미지 임베딩 유사도**로 상품을
고른다 — 두 화면이 같은 취향을 서로 다른 방법으로 읽고 있다.

키워드는 제목에 낱말이 있어야만 걸린다. "고양이 프린트"를 좋아해도 제목에 고양이가 안 적힌
상품만 눌렀다면 아무것도 안 걸리고, 걸려도 낱말이 겹치는 정도라 "얼마나 가까운지"는 모른다.
벡터는 이미지로 재기 때문에 낱말이 없어도 닮은 것을 찾는다.

**이 조각의 가설**: 같은 앵커로 벡터 유사도를 재면, 키워드보다 사람마다 다른 6장이 나온다.

## 결정된 것 (2026-08-22 사용자 확답)

- **붙일 자리** — FOR YOU 목록의 **순서**만. 큐레이션 상세 안의 상품 9장은 건드리지 않는다
  (사람이 쓴 소개 문장이 상품마다 붙어 있어 교체하면 그 글이 떨어진다).
- **키워드는 남긴다** — 벡터로 갈아치우지 않고 **병행**한다. 희소도 보너스와 노출 깎기도
  그대로 쓴다. 벡터 조회가 실패하면 지금의 키워드 순서로 돌아가므로 화면이 나빠지지 않는다.
- **shadow 없이 바로 교체** — 읽기 전용 경로이고 실패 시 기존 순서로 되돌아간다.

## 미정이었던 것 → 실측으로 정한 값 (2026-08-22)

- **섞는 비율** → 벡터 0.5 / 키워드 0.5 (4단계 근거 참고).
- **대표 벡터** → 큐레이션이 보여주는 상품 9장의 대표 이미지(slot 최소) 임베딩 평균을 단위
  길이로. 커버리지가 99.8%라 9장으로 충분했다.
- **재사용 정책** → 두지 않는다(마운트마다 조회). 5단계 실측이 왕복 20ms대라 캐시가 벌어 줄
  것이 없다.

## 설계에서 초안과 달라진 것

초안은 브라우저가 큐레이션 상품 번호 묶음을 서버로 보내는 그림이었다. **바꿨다** — 이 저장소는
같은 이유로 이미 한 번 그렇게 하지 않기로 했다(`c_taste_summary`: "클라이언트가 상품 번호
목록을 보내게 하면 남의 목록을 넣어 카탈로그 속성을 캐낼 수 있다"). 큐레이션 정의는 서버 표
`c_curation_vecs`가 갖고 브라우저는 자기 앵커만 보낸다. 호출당 읽는 벡터도 408개 → 57개로 준다.

## 단계

### 1단계 — 재료가 있는지부터 본다 (커버리지 확인)

큐레이션 57개가 소개하는 상품은 약 500개다. 이 상품들의 **이미지 벡터가 실제로 DB에 있는지**
먼저 센다. 없으면 그 큐레이션은 점수를 낼 수 없고, 몇 개나 그런지 모른 채 만들면 "왜 이 큐레이션은
항상 뒤에 있지"를 나중에 디버깅하게 된다.

- 큐레이션 데이터에서 상품 번호를 모으는 방법은 이미 있다(판매처 주소에서 뽑아낸다).
- 벡터가 있는 상품 수를 큐레이션별로 센다.

**완료 기준**: 큐레이션 57개마다 "상품 n개 중 벡터 있는 것 m개" 표가 나오고, **벡터가 3개
미만인 큐레이션이 몇 개인지** 숫자로 적힌다. 그 수가 많으면(예: 10개 이상) 여기서 멈추고
2단계 설계를 다시 고른다.

### 2단계 — 서버에 점수 함수를 하나 만든다

앵커 목록(BROWSE가 이미 보내는 것과 **같은 모양**: 상품 번호 + 가중치)과 큐레이션별 상품
번호 묶음을 받아, **큐레이션마다 점수 하나**를 돌려주는 함수를 새로 만든다.

- 후보 226,000개를 뒤지는 BROWSE의 검색과 다르다. 비교 대상이 이미 정해진 500개뿐이라
  근사 검색 색인을 타지 않는다 — 가벼워야 정상이다.
- 성별 필터는 이 함수의 일이 아니다. 화면이 이미 내 성별 것만 남긴 뒤 순서를 매긴다.
- 되돌리기 파일을 같은 커밋에 넣는다(이 저장소 관례: `backend/supabase/rollback/`).
- 입력이 비었거나 이상해도 오류 대신 빈 결과로 답한다 — 화면은 기존 순서로 살아 있어야 한다.

**완료 기준**: DB 콘솔에서 앵커 몇 개를 넣어 호출하면 큐레이션 점수가 내림차순으로 나온다.
**앵커를 다른 취향으로 바꿔 다시 호출하면 상위 6개가 달라진다**(안 달라지면 벡터가 순서에
기여하지 않는 것이므로 여기서 원인을 찾는다).

### 3단계 — 화면이 그 점수를 쓴다

FOR YOU 목록을 세우는 자리에서 이 함수를 부르고, 받은 점수를 지금의 점수 계산에 함께 넣는다.
지금 지키고 있는 규칙 세 가지는 그대로 둔다.

- 첫 렌더는 반드시 서버가 그린 기본 순서(하이드레이션이 어긋나면 안 된다).
- 비회원·앵커 없음은 개인화하지 않는다.
- 여러 번 보여준 큐레이션은 점수를 깎는다.

**완료 기준**: 로그인한 계정으로 상품 몇 개를 찜하고 FOR YOU를 열면 **앞 6장이 바뀐다**.
서로 다른 취향의 계정 둘을 비교하면 6장이 서로 다르다.

### 4단계 — 섞는 비율을 정한다

벡터만·키워드만·섞은 것 세 가지 순서를 같은 앵커로 뽑아 나란히 본다. 겹치는 장수와,
"이 사람에게 이게 왜 1등인지" 설명이 되는지를 사람이 판단한다.

**완료 기준**: 고른 비율과 그 이유가 이 문서에 한 문단으로 적힌다. 비교에 쓴 앵커 조합도 남긴다.

### 5단계 — 느려지지 않았는지 본다

- 이 조회가 FOR YOU 첫 화면을 **늦추는지**(조회 전에는 기본 순서가 보이므로, 늦으면 순서가
  눈앞에서 한 번 바뀐다).
- 응답 시간과 호출 횟수를 재고, 필요하면 재사용 규칙을 정한다(위 미정 항목).

**완료 기준**: 응답 시간 실측값이 적히고, 목록이 눈앞에서 바뀌는 것이 보이는지 여부가
"보인다 / 안 보인다"로 적힌다. 보이면 재사용·선조회 중 하나를 붙인다.

### 6단계 — 실패했을 때 안 망가지는지 확인

네 가지를 실제로 만들어 본다: 비회원 / 앵커 0개 / 조회 실패(네트워크 끊기) / 응답 지연.

**완료 기준**: 네 경우 모두 **화면이 기본 또는 키워드 순서로 멀쩡히 그려지고**, 오류 화면이나
빈 목록이 나오지 않는다. 각각 확인했다는 표시를 이 문서에 남긴다.

## 실행 기록 (2026-08-22)

### 1단계 — 커버리지 ✅

큐레이션 57개 / 상품 408개(중복 제거) 중 **407개(99.8%)에 이미지 벡터 있음**. 벡터 3개 미만인
큐레이션 **0개**(최소가 `ringer` 9개 중 8개). 멈춤 조건에 걸리지 않아 그대로 진행했다.

### 2단계 — 서버 점수 함수 ✅

`backend/supabase/migrations/20260822500000_curation_vec_rank.sql` (되돌리기 파일 동봉).
표 `c_curation_vecs`(대표 벡터) + 함수 `c_curation_rank(p_session, p_long)`.
프로덕션 DB에 적용 완료.

앵커를 취향별로 바꿔 호출한 결과 — **자기 큐레이션이 1등으로 올라오고 상위 6개가 통째로 바뀐다**:

| 앵커(그 큐레이션 상품 3개) | 상위 6장 |

| 고양이 프린트 | **cat_print(.806)**, new_graphic, bear_bunny, y2k_motif, summer_thin, body_natural |

앵커 없음·이상 입력(`"x"`, `{"g":"drop"}`)은 **0행** — 오류 대신 정화.

아직 안 했다. 이것을 하기 전에는 3단계를 "완료"로 적지 않는다.

### 4단계 — 섞는 비율 = 벡터 0.5 ✅

페르소나 4명(고양이 / 오프숄더+코케트 / 축구 저지 / 블랙 미니멀)의 상품을 찜한 것으로 보고
세 순서를 비교했다.

관찰 두 가지:

1. **벡터가 키워드의 헛걸림을 밀어낸다.** 고양이 페르소나의 키워드 순서에는
   `washed, baseball_raglan, running, blokecore`가 올라왔다 — 앵커 제목의 "오버핏·반팔" 같은
   낱말이 엉뚱한 규칙에 걸려서다. 벡터 순서는 `bear_bunny, art_print, y2k_motif, pastel_tone`
   으로 그래픽 티 계열이 모였다.
2. **벡터는 색을 약하게 본다.** 비중을 0.7로 올리면 블랙 미니멀 페르소나에게 `white_opaque`가
   3등, 오프숄더 페르소나에게 `red_only`가 6등으로 올라왔다. 이미지 임베딩이 "무지 단색 티"를
   서로 비슷하게 보기 때문이다. 색·소재 낱말은 키워드가 더 잘 잡는다.

0.3은 벡터가 밀려 1번 효과가 약해지고, 0.7은 2번이 눈에 띈다. **둘 다 무너지지 않는 0.5**로 정했다.
(고양이·축구 페르소나는 0.3/0.5/0.7에서 상위 6장이 같았다 — 벡터가 확실히 이기는 경우엔
비율이 순위를 바꾸지 않는다.)

### 5단계 — 성능 ✅ (실측) / ⚠️ (눈으로 확인 미검증)

같은 서울 리전에서 잰 값. `explain analyze`는 계측 부담이 붙어 실제보다 크게 나온다.

| 앵커 수 | 서버 실행(explain) | 왕복 중앙값 |
|---|---|---|
| 5개 | 11.4ms | 16.1ms |
| 20개 | 27.2ms | 20.5ms |
| 70개(상한) | 69.6ms | 22.8ms |

캐시를 두지 않기로 했다 — 왕복이 20ms대라 벌어 줄 것이 없고, 캐시는 앵커가 바뀔 때 지우는
규칙을 하나 더 만든다.
**남은 것**: 목록이 눈앞에서 바뀌는 것이 보이는지 — 실제 화면에서 확인해야 한다.

### 6단계 — 폴백 ✅(3/4) / ⚠️(1/4)

훅 테스트로 확인한 것:

- 비회원 → 기본 순서, **조회 자체를 안 한다**
- 앵커 0개 → 기본 순서, 조회 안 함
- 벡터 조회 실패 → 키워드 순서 유지
- 벡터 0행(앵커를 못 품) → 키워드 순서 유지
- 제목 조회 실패 + 벡터 성공 → **벡터만으로 정렬**(초안에 없던 경우인데, 이게 이 조각의 값이다)

**남은 것**: 응답 지연(3초 타임아웃)은 실제 느린 네트워크에서 확인하지 않았다. 코드 경로는
실패와 같지만 돌려보지 않았으므로 미검증으로 남긴다.
