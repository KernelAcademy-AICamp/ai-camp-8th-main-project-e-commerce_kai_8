# 구글 로그인 (조각 1) — 구현 계획

- 작성일: 2026-08-18
- 설계: [2026-08-18-google-login-design.md](../superpowers/specs/2026-08-18-google-login-design.md) (v5, codex 4라운드 반영)
- 범위: 구글 로그인·로그아웃·계정 삭제·고지 갱신까지. 찜 하드 게이트(조각 2)와 취향 프로필 동기화(조각 3)는 하지 않는다.

이 계획은 코드를 담지 않는다. **무엇을 / 어떤 순서로 / 무엇이 되면 끝**만 적는다. 구현 방법이 여럿인 곳은 열어 두고, 골라야 할 값은 "이 단계에서 정할 것"에 적었다.

---

## 전체 순서와 이유

1. **준비** — 사람이 대시보드에서 해야 하는 것. 이게 안 되면 나머지가 동작하지 않는다.
2. **로그인·로그아웃** — 이 조각의 핵심. 가장 먼저 눈으로 확인한다.
3. **신원이 바뀔 때 앞사람 흔적 지우기** — 로그인이 되고 나서야 검증할 수 있다.
4. **계정 삭제** — 계정이 생긴 뒤에 필요해진다.
5. **고지·정책 갱신** — 사용자에게 노출하기 전 반드시 끝나야 한다.
6. **캐시 차단·보안 헤더** — 쿠키 세션을 택한 대가. 노출 전에 끝낸다.

**노출 게이트**: 1~6이 모두 끝나기 전에는 프로덕션에서 로그인 화면을 사용자에게 보이지 않는다. 특히 **5단계가 끝나기 전에 로그인을 열면 현재 고지가 거짓이 된다.**

## 1단계 — 준비 (사람이 수행)

AI가 대신할 수 없다. 되돌리기 기록을 **바꾸기 전에** 남긴다.

**할 일**

1. Supabase 대시보드에서 현재 Auth 사용자 수와 활성 provider를 확인한다 (전제: ecommerce 중단으로 0건).
2. 누가 어느 Google Cloud 프로젝트·OAuth 클라이언트를 소유하는지, 지금 설정 상태가 어떤지, 되돌릴 때 무엇을 어떤 순서로 끄는지 문서에 적는다.
3. Google Cloud Console에서 OAuth 클라이언트를 만든다 — 승인된 리디렉션 주소, 승인된 JavaScript 원본, 요청 범위, 동의 화면 브랜딩과 개인정보 처리방침 주소, 테스트 사용자 또는 프로덕션 전환.
4. Supabase에서 Google provider를 켜고 클라이언트 ID·시크릿을 넣는다.
5. redirect 허용 목록에 **정확한 주소 두 개만** 등록한다 — 로컬용 하나, 프로덕션용 하나. **preview 주소는 등록하지 않는다.**
6. 로컬 Supabase 설정 파일의 기준 주소를 개발 서버 접속 주소와 **같은 호스트**로 맞춘다. 지금은 개발 서버와 다른 호스트이고 프로토콜도 다르며 콜백 경로도 없어서, 그대로 두면 로그인이 실패한다.

**확정값 (2026-08-18)**

| 항목 | 값 |
|---|---|
| Supabase 프로젝트 | `ngmgpuvvbmrfpluajibi` |
| 구글에 넣는 리디렉션 URI | `https://ngmgpuvvbmrfpluajibi.supabase.co/auth/v1/callback` (하나뿐) |
| 구글 JavaScript 원본 | `http://localhost:3000` · `https://ai-camp-8th-main-project-e-commerce.vercel.app` |
| Supabase Redirect URLs | `http://localhost:3000/auth/callback` · `https://ai-camp-8th-main-project-e-commerce.vercel.app/auth/callback` — **정확히 두 줄, 와일드카드·preview 없음** |
| Supabase Site URL | 개발 중에는 `http://localhost:3000`. **노출 게이트 통과 시 프로덕션 주소로 변경** |
| 로컬 기준 호스트 | `localhost`로 통일 (`127.0.0.1` 사용 금지 — 서로 다른 호스트로 취급돼 로그인이 깨진다) |
| 구글 앱 게시 상태 | **테스트** 유지. 테스트 사용자에 확인용 계정을 등록한다. 프로덕션 게시는 5단계의 공개 처리방침이 생긴 뒤 |

**확인된 전제 (2026-08-18)**: Supabase Auth 사용자 **0명**, 활성 provider는 Email(기본값)뿐. → 공유 프로젝트를 aTee 전용 Auth로 써도 된다는 설계 전제가 사실로 확인됨.

**노출 전 확인 항목**
- Email provider를 끌지 결정한다 (쓰지 않는 통로이고, 켜져 있으면 공개 키로 이메일 가입 호출이 가능하다)
- Supabase Site URL을 프로덕션 주소로 변경한다

**완료 기준**
- Supabase 대시보드에 Google이 "켜짐"으로 보이고, redirect 허용 목록에 주소 두 개가 보인다.
- 기존 Auth 사용자 수가 0건임을 확인한 화면(또는 기록)이 있다.
- 소유권·되돌리기 문서가 저장돼 있다.

## 2단계 — 구글 로그인·로그아웃이 동작한다 (핵심)

**할 일**

1. 인증 라이브러리를 프로젝트에 추가한다. 세션은 **쿠키**에 둔다.
2. 설정 화면 맨 위에 "계정" 영역을 만든다.
   - 로그아웃 상태: 구글로 계속하기 버튼.
   - 로그인 상태: 내 구글 이메일 + 로그아웃 버튼.
   - 판정 전: 자리를 차지하는 로딩 표시. **로그아웃 화면을 먼저 보였다가 로그인 화면으로 튀지 않게 한다.**
   - **"로그인하면 좋아진다"는 문구를 쓰지 않는다.** 이 조각에서 실제로 좋아지는 게 없어서 오해가 된다. 앞으로의 계획을 사실대로만 적는다.
3. 구글에서 돌아오는 경로를 만든다. 이 경로는 **요청을 받아 넘기고 되돌려보내는 역할만** 한다 — 실제 처리와 오류 분류는 인증 기능 안쪽에 둔다(`app/`은 조립 전용이라는 폴더 규칙).
4. 로그아웃은 **이 기기만** 끊는다. 기본값이 모든 기기를 끊는 쪽이므로 명시적으로 지정한다.
5. 세션 갱신 계층을 둔다. 어느 경로에 적용할지 정한다.
6. 서버에서 "누구인지" 판정할 때는 **저장된 값을 그대로 믿는 조회가 아니라 검증된 조회**를 쓴다.

**이 단계에서 정할 것**
- 세션 갱신 계층의 적용 범위(어느 경로에 도는지)
- 세션 만료 확인에 쓸 환경(로컬/테스트)과 원복 절차
- 쿠키 차단 확인에 쓸 브라우저·버전·차단 방식

**주의 — 통로 분리**
- 기존 피드·검색·유사·신호 호출 경로는 **건드리지 않는다.** 지금처럼 공개 키로 계속 돈다.
- 계정용 접근은 별도 통로로만 하고, 인증된 접근 수단을 앱 전역에 열어 두지 않는다. 임의의 함수 이름을 문자열로 받는 통로를 만들지 않는다.
- **검사 도구로 막는다** — 피드·검색·신호 쪽에서 계정 통로를 가져다 쓰거나, 계정 쪽에서 공개 통로를 가져다 쓰면 검사에 실패하게 한다. 지금 lint 설정에는 이런 제한이 없다. 문서 약속만으로는 조각 2에서 실수를 막지 못한다.
- **주의**: "DB가 알아서 막아준다"고 생각하면 안 된다. 공개 전용으로 의도된 함수 세 개가 실제로는 로그인 사용자도 부를 수 있는 상태다(권한 회수가 빠져 있다). 이번 조각에서 고치지 않는다.

**완료 기준 (눈으로 확인)**
- 설정에서 구글로 로그인하면 **내 이메일이 보인다.** 이때 사용자 식별자도 함께 기록해 둔다.
- 새로고침해도 로그인 상태가 유지되고, **서버가 확인한 사용자도 같은 사람**이다.
- 로그아웃하면 이메일이 사라진다. **다른 브라우저의 로그인은 유지된다.**
- 구글 동의 화면에서 취소하면 오류 문구 없이 설정으로 돌아온다. **네트워크·설정 오류일 때는 화면이 다르다.**
- 돌아오는 주소를 따로 보관해 두고 뒤로가기·재접속·동시 요청을 해봐도, **이미 로그인된 상태가 실패 화면으로 덮이지 않는다.**
- **세션이 만료돼도 로그인이 유지된다.** 확인 방법: **로컬 또는 테스트 환경에서** 토큰 수명을 권고 최저값으로 낮추고 → **반드시 다시 로그인**하고(수명 변경은 이미 발급된 토큰에 적용되지 않는다) → 탭을 닫아 자동 갱신을 막고 → 만료 후 다시 접속한다. 새 토큰이 발급되고 서버 확인이 성공하면 통과. 원래 값을 적어 두고 **복구까지 확인한다.** 여럿이 함께 쓰는 프로덕션 설정에서는 하지 않는다.
- **쿠키를 차단하면** 로그인은 실패하지만 **피드·검색은 계속 된다.** 확인 방법: 브라우저와 버전, 차단 방식을 미리 적어 고정하고, 개발자 도구에서 인증 쿠키가 **실제로 저장되지 않았음**을 확인한 뒤 피드·검색을 써 본다.

## 3단계 — 신원이 바뀌면 앞사람 흔적이 남지 않는다

이 조각에서 **가장 틀리기 쉬운 부분**이다. 설계 검토에서 세 번 연속 결함이 나온 곳이다.

**할 일**

1. 신원이 바뀌는 경우를 **세 가지로만** 판정한다: 로그인 안 함 → 사용자, 사용자 A → 사용자 B, 사용자 → 로그인 안 함. **최초 세션 복원·토큰 갱신·같은 로그인 반복은 신원 변화가 아니다.**
2. 신원이 바뀌면 아래를 **모두** 비운다.
   - 찜 — 저장소뿐 아니라 **메모리에 들고 있는 사본까지.** 저장소만 지우면 화면에 남는다.
   - 장기 취향 프로필, 세션 취향 프로필, 신호 세션, 노출 기록
   - **이미 화면에 떠 있는 피드** — 받아온 상품 목록·커서·소진 상태·중복 방지 집합까지. 비우지 않으면 앞사람의 개인화 결과가 계속 보이고 다음 결과가 그 뒤에 이어 붙는다.
3. **바뀌기 전에 보낸 요청의 응답은 버린다.** 전환마다 올라가는 표식을 두고, 응답이 왔을 때 표식이 달라졌으면 적용하지 않는다.
4. **순서를 지킨다**: 취향 프로필을 읽거나 쓰기 **전에** 신원을 확인한다 → 탭 상태를 비운다 → 저장소를 비운다 → 처리 완료 표식을 남긴다. 이 순서를 어기면, 앞사람의 세션 취향이 **방금 비운 장기 취향으로 도로 합쳐진다**(현재 코드가 세션이 바뀌면 이전 세션 취향을 장기로 합치도록 되어 있다).
5. 여러 탭을 고려한다.
   - 저장소는 어느 탭이 비우든 모두에게 적용된다. 어느 신원의 데이터인지 나타내는 표시자를 함께 남긴다.
   - 탭마다 자기가 마지막으로 처리한 신원을 기억하고, 현재와 다르면 자기 것을 비운다.
   - **그 탭 기억은 새로고침을 견뎌야 한다.** 다른 탭이 이미 처리를 끝낸 뒤 오래된 탭이 새로고침되면 기억이 사라져 "이미 처리됨"으로 오판한다. 탭 수명 저장소에 두거나, **기억이 없는 탭은 무조건 비우는** 쪽으로 한다.
   - 잠들었다 깨어난 탭도 스스로 비운다. 탭 사이 알림에만 의존하지 않는다.
6. 로그인 직후 탭이 닫혀 정리가 중단됐다면, 다음 시작 때 표시자와 현재 사용자를 비교해 **찜·개인화 피드를 그리기 전에** 정리한다.

**건드리지 않는 것**
- 기기 ID (새로 발급하지 않는다)
- 미전송 행동 이벤트 큐

**이 단계에서 정할 것**
- 다른 탭이 로그아웃 상태로 따라오는 데 걸리는 **상한 시간**
- 신원 표시자의 형식 (원문 식별자를 그대로 둘지, 알아볼 수 없는 형태로 바꿀지)

**완료 기준 (눈으로 확인)**
- A로 로그인해 찜·취향을 만든 뒤 로그아웃하고 B로 로그인하면, **화면·저장소·다음 피드 요청에 실린 값** 어디에도 A의 것이 없다. **기기 ID는 그대로**이고 미전송 큐도 그대로다.
- 탭 두 개를 열고 한쪽에서 로그아웃하면, **새로고침 없이 정한 시간 안에** 다른 탭도 로그아웃되고 그 탭의 찜·취향 값도 비어 있다.
- 한 탭을 오래 백그라운드에 둬 잠재운 뒤 다른 탭에서 로그아웃·로그인하고 돌아오면, **그 탭도 자기 상태를 비운다.**
- 다른 탭에서 전환을 끝낸 **뒤에** 오래된 탭을 새로고침해도, **앞사람의 세션 취향이 장기 취향으로 합쳐지지 않는다.**
- A의 개인화 피드가 떠 있는 탭에서 응답을 지연시켜 놓고 다른 탭에서 B로 바꾼 뒤 돌아오면, **이미 보이던 카드가 사라지고 늦게 온 응답도 적용되지 않는다.**

**자동 검증**
- 신원 변화 판정(세 가지만 처리하고 나머지는 무시), 비워야 할 항목 목록, 순서 계약을 단위 테스트로 고정한다.
- 탭 두 개 동시 전환 / 잠들었다 깨어난 탭 / 로그인 직후 종료 후 재시작은 브라우저 통합 검증으로 확인한다.

## 4단계 — 계정 삭제

**할 일**

1. **본인만 자기 계정을 지우는 DB 함수**를 마이그레이션으로 추가한다. 대상 사용자를 인자로 받지 않는다.
2. 권한을 **함수를 만드는 같은 변경 안에서** 정리한다 — 모든 역할과 비로그인 역할의 실행 권한을 회수하고 로그인 역할에만 부여한다. **부여만 하고 회수를 빠뜨리면 의도와 달리 누구나 부를 수 있다** (지금 이 repo에 그런 함수가 실제로 세 개 있다).
3. 정의자 권한으로 도는 함수이므로 참조 경로를 고정하고 참조 대상을 모두 명시한다. 소유자는 사용자 삭제 권한을 가진 역할로 고정한다.
4. 인증 주체가 없으면 **먼저 오류를 낸다.** 그냥 두면 "0건 삭제"가 되어 성공으로 오인된다.
5. 0건 삭제는 **이미 지워진 것으로 보고 성공 처리**한다.
6. 설정 화면에 계정 삭제를 넣는다 — **지울 계정 이메일을 보여주는 재확인 단계**를 거치고, 진행 중 중복 클릭을 막는다.
7. **삭제 전에 대상 표식을 남긴다.** 사용자 식별자와 **구글 쪽 신원**을 함께 적고, **실제로 저장됐는지 다시 읽어 확인한 뒤에만** 삭제를 호출한다.
8. 응답이 불명확한 뒤 다시 로그인하면 **구글 쪽 신원부터 비교**한다.
   - **구글 신원이 다르다** → 다른 계정으로 로그인한 것. **표식을 유지**하고, 원래 계정으로 로그인해야 마무리된다고 알린다.
   - **구글 신원은 같고 사용자 식별자가 다르다** → 첫 삭제가 성공하고 재가입된 것. **다시 지우지 않고** 표식만 정리한다.
   - **둘 다 같다** → 삭제가 서버에 닿지 않은 것. 재확인 후 다시 지운다.
   - 사용자 식별자만 비교하면 **다른 구글 계정으로 로그인한 경우를 삭제 성공으로 오판**해, 지워지지 않은 계정의 손잡이를 버린다.
9. 삭제 결과와 무관하게 로컬 인증 쿠키 제거를 시도하되, **"삭제 완료"는 확인된 경우에만** 표시한다.

**이 단계에서 정할 것**
- 표식만 남고 사용자가 원래 계정으로 영영 돌아오지 않는 경우, 표식을 언제까지 유지할지

**완료 기준 (눈으로 확인)**
- 계정 삭제 후 다시 로그인하면 같은 이메일이라 이메일은 다시 보이지만, **사용자 식별자가 달라졌고** 인증 쪽에 이전 사용자·연결·세션이 남아 있지 않고, **브라우저의 인증 쿠키가 제거됐고**, 삭제 직전에 확보한 토큰으로는 계정 경로를 통과하지 못한다.
- 삭제는 됐는데 응답만 유실된 상황을 만들고 **같은** 구글 계정으로 다시 로그인하면, **다시 지우지 않는다.** 새로 만든 계정이 살아 있다.
- 같은 상황에서 **다른** 구글 계정으로 로그인하면, **표식이 유지되고** 안내가 뜬다.
- 요청이 서버에 닿지 않은 실패를 만들고 같은 계정으로 로그인하면, 재확인 후 정상 삭제된다.

**자동 검증 (빈 스키마에서)**
- 모든 역할·비로그인 역할·토큰 없는 호출이 **거부**되고, 자기 자신 삭제는 성공하고, 재호출 계약이 지켜지고, **다른 사용자는 살아 있다.**
- 객체가 이미 있는 실 DB에서 검증하면 거짓 통과가 난다. 반드시 빈 스키마에서 한다.

## 5단계 — 고지·정책 갱신 (노출 전 필수)

구글 로그인을 붙이는 순간 현재 문구는 **사실이 아니게 된다.** 지금 방침 문서와 설정 화면은 "회원가입 없이", "이름·연락처·계정 같은 개인정보를 묻거나 저장하지 않는다"고 적혀 있다.

**할 일**

1. 수집 방침 문서를 실제와 맞춘다.
2. 설정 화면의 고지 문구를 고친다.
3. **최초 방문 배너의 저장소 키 버전을 올린다.** 코드 주석 자체가 "수집 범위가 늘면 키를 올려 이미 확인한 사용자에게도 다시 보여라"라고 규정한다. 안 올리면 기존 사용자는 새 고지를 못 본다.
4. **공개 개인정보 처리방침 페이지를 만든다.** 구글은 프로덕션 OAuth 앱에 대해 홈페이지와 동의 화면에서 접근 가능한 처리방침을 요구한다. 지금은 없다.
5. 받는 항목을 **구글 로그인의 필수 범위로 한정**하고, 실제로 저장되는 것(사용자 행, 연결된 제공자 정보, 세션, 최종 로그인 시각)과 **인증 감사 기록에 접속 정보가 남는다**는 점을 적는다.
6. **"계정과 기기 ID를 연결하지 않는다"를 정확히 한정한다** — **서버에 정본 매핑을 만들지 않는다**는 뜻이다. 기기에는 기기 ID와 신원 표시자가 함께 남으므로 **로컬에는 상관관계가 있다.** "연결이 전혀 없다"고 쓰면 사실이 아니다.
7. **계정 삭제는 인증 감사 기록까지 지우지 않는다**는 점을 적는다.
8. PRD와 결정 기록을 갱신한다. 지금 문서는 "가입 시 기기 취향을 계정으로 승계한다"고 되어 있는데 이번에 **승계하지 않기로** 정했다. 갱신하지 않으면 다음 사람이 반대로 만든다.

**이 단계에서 정할 것 (사람)**
- **인증 감사 기록의 보존 기간** — 확인 전까지 숫자를 적지 않는다. 확인해서 채우거나 "확인 중"으로 둔다.
- 설계 §4-1에 적힌 **기존 삭제 결함 두 건**(지운 직후 늦게 도착한 기록이 되살아남 / 재시도 목록이 가득 차면 오래된 것을 버림)을 이번에 고칠지, 별도 작업으로 뺄지. **처리방침의 삭제 문구를 확정하기 전에 정해야 한다** — 지금 문구는 "모두 삭제"와 "다음 접속 재시도"를 이미 약속하고 있다.

**완료 기준 (눈으로 확인)**
- 기존에 배너를 확인해 둔 브라우저로 접속하면 **갱신된 배너가 한 번 다시 나오고**, 닫은 뒤 새로고침하면 다시 안 나온다.
- 공개 처리방침 페이지가 열리고, 구글 동의 화면 설정에 그 주소가 들어가 있다.
- 방침 문서·설정 문구·PRD·결정 기록에서 "계정을 저장하지 않는다" 류의 문장이 사라졌다.

## 6단계 — 캐시 차단·기본 보안 헤더

쿠키 세션을 택한 대가다. **세션을 갱신하며 쿠키를 내려주는 응답이 공유 캐시에 들어가면 다른 사용자에게 세션이 전달된다.**

**할 일**

1. 인증이 관여하는 응답에 사설·비저장 캐시 정책을 붙인다. 현재 설정 파일에는 헤더 설정이 하나도 없다.
2. 기본 보안 헤더를 추가한다.
3. **콘텐츠 보안 정책(CSP)은 이번에 하지 않는다.** 별도 작업으로 뺀다 — 그때까지는 화면에 악성 스크립트가 끼어들면 세션 토큰과 신원 표시자까지 읽힐 수 있다. **알고 남겨두는 위험**이며 설계 문서에 그렇게 적혀 있다.

**이 단계에서 정할 것**
- 캐시 정책의 정확한 값과 적용 경로
- 기본 보안 헤더의 집합과 적용 경로

**완료 기준 (눈으로 확인)**
- 프로덕션 빌드에서 로그인 콜백·세션 갱신·계정이 보이는 응답의 헤더를 열어보면, 캐시 정책과 합의한 보안 헤더가 **실제로 붙어 있다.**
