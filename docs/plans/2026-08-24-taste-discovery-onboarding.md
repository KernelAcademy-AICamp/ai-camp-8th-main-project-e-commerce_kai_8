# 취향 발견 온보딩 — 제품·UX 구현 전달서 (2026-08-24)

> 상태: **제품 방향 초안 / 구현 전 정본 결정 갱신 필요**
>
> 대상: 이후 구현을 맡는 Claude 또는 다른 개발자·AI
>
> 범위: 첫 방문의 성별 선택부터 첫 개인화 홈 진입까지
>
> 관련 정본: [Living PRD](../atee/living/prd.md) · [결정 기록](../atee/living/decision-log.md) · [데이터 수집·보존 방침](../atee/living/data-collection-policy.md)

이 문서는 제품 책임자와 2026-08-24에 논의한 온보딩 방향을 전달하기 위한 초안이다. 코드·함수명·구현 방법을 정하지 않고, 사용자가 겪을 순서와 단계별 완료 기준만 적는다.

## 1. 왜 바꾸나

aTee가 검증하려는 가치는 단순히 많은 티셔츠를 보여주는 것이 아니라, **사용자가 취향을 설명하지 않아도 탐색할수록 취향을 찾아 주는 경험**이다. 현재 첫 방문은 성별을 고르면 곧바로 홈으로 이동하고, 로그인 화면은 찜을 계정에 저장하는 가치만 설명한다. 이 흐름만으로는 다음 두 가지가 약하다.

- 첫 개인화 추천을 시작할 명시적인 취향 근거가 없다.
- 가입이 왜 aTee의 핵심 가치와 연결되는지 알기 어렵다.

새 흐름은 실제 옷을 고르는 짧은 행동으로 초기 추천의 시작점을 만들고, 가입 화면에서 그 선택이 앞으로 어떻게 더 선명한 취향으로 이어지는지 설명한다.

## 2. 근거·결정·가설 구분

### 기존 근거와 정본 결정

- 1차 타깃은 검색 목적 없이 상품 이미지를 습관적으로 훑고, 마음에 드는 상품을 나중을 위해 보관하는 사람이다. [기회·타깃·JTBD](../atee/foundation/problem-target-jtbd.md)
- 핵심 제품 가설은 사용할수록 화면 구성이 `남의 베스트`가 아니라 `나의 취향`처럼 느껴지는가이다. [Living PRD §1·§5](../atee/living/prd.md)
- 첫 진입에서는 남성·여성 중 하나를 반드시 고르고, 고른 성별 라벨과 정확히 같은 상품만 새 목록에 보여준다. [O-39](../atee/living/decision-log.md)
- 회원의 취향은 계정에 보관하고, 로그인하지 않은 사용자의 탐색 행동은 취향으로 쌓지 않는다. [O-37](../atee/living/decision-log.md)

### 2026-08-24 대화에서 정한 방향

- 목표 흐름은 `성별 선택 → 옷 선택 → 회원가입 → 홈`이다.
- 옷 선택은 스타일 이름을 먼저 고른 뒤 다시 상품을 고르는 다단계 구조로 만들지 않는다.
- 사용자는 실제 옷 사진을 한 화면에서 복수 선택한다.
- 첫 화면에는 6개가 보이고, 세로로 더 보면 전체 10~12개를 볼 수 있는 구성을 우선안으로 한다.
- 최소 3개를 골라야 다음 단계로 갈 수 있다.
- 회원가입 화면의 주인공은 `가입`이 아니라 `취향 찾기를 계속하는 가치`다.
- 첫 홈 진입에서는 전체 화면을 막는 튜토리얼을 사용하지 않는다. 개인화 결과를 즉시 보여주고, 짧은 비차단형 안내만 제공한다.
- dim 코치마크는 홈 진입 즉시 여러 기능을 순회하는 방식으로 쓰지 않는다. 핵심 취향 신호를 사용자가 처음 실행하는 순간에 단 한 번 제공하는 후속안으로 둔다.

### 아직 검증하지 않은 가설

- 3개 이상의 옷 선택이 첫 추천을 사용자의 취향처럼 느끼게 만들 만큼 충분하다.
- 가입 전에 취향 선택을 요구해도, 가입 이유가 명확하면 이탈 증가보다 개인화 가치 이해가 더 크다.
- 10~12개의 서로 다른 옷이 별도 스타일 용어 없이도 충분한 선택 폭을 제공한다.
- 첫 홈의 비차단형 안내만으로 사용자가 `사용할수록 추천이 변한다`는 구조를 이해한다.

## 3. 구현 전 반드시 해결할 정본 충돌

현재 정본은 **로그인은 선택**이며 비회원도 피드·검색·상세를 사용할 수 있다고 명시한다. 새 방향의 `회원가입 강제 후 홈 진입`과 직접 충돌한다.

- [Living PRD §6 비회원 탐색](../atee/living/prd.md)은 가입 없이 피드에 진입한다고 적는다.
- [데이터 수집·보존 방침](../atee/living/data-collection-policy.md)은 로그인하지 않아도 모든 기능을 쓸 수 있다고 적는다.
- [O-35·O-37](../atee/living/decision-log.md)은 로그인 선택 흐름과 비회원·회원 취향 소유권을 전제로 한다.
- 현재 앱도 성별 선택 후 홈을 열며, 로그인은 찜·보관함 등의 필요 지점에서 별도로 유도한다.

따라서 구현 전에 제품 책임자가 다음 변경을 정본에 기록해야 한다.

1. 첫 홈 진입 전 Google 로그인을 필수로 바꿀지 확정한다.
2. 가입 전에 사용자가 직접 고른 상품을 로그인 뒤 계정의 초기 추천 근거로 넘기는 것을 허용할지 확정한다.
3. 허용한다면 이것을 `이전 신원의 계산된 취향 승계`와 구분되는 **사용자의 명시적 선택 승계**로 정의할지 결정한다.
4. Living PRD, 결정 기록, 데이터 수집·보존 방침, 공개 처리방침과 실제 로그인 고지 문구를 함께 갱신한다.

이 네 항목이 정본에 반영되기 전에는 구현을 시작하지 않는다. 화면만 먼저 만들면 제품 약속과 데이터 소유권 계약이 서로 어긋난다.

## 4. 목표 사용자 여정

### 1단계 — 성별 선택 (`1 / 3`)

- 사용자는 남성 또는 여성 중 하나를 고른다.
- 현재 화면의 뉴모피즘 테마와 `어떤 옷을 볼까요?`라는 질문을 유지한다.
- 고르기 전에는 홈과 추천 요청을 시작하지 않는다.
- 고른 값과 정확히 같은 성별 라벨의 상품만 다음 옷 선택 후보에 사용한다.
- 완료 기준: 새 방문자가 한쪽을 고르면 반대 성별·공용·미상 상품이 없는 옷 선택 화면이 보인다.

### 2단계 — 좋아하는 옷 선택 (`2 / 3`)

- 스타일 용어 체크박스 대신 실제 티셔츠 이미지를 2열 카드로 보여준다.
- 첫 화면에는 6개가 보이고, 전체 후보는 10~12개다.
- 후보는 색·그래픽·핏·무드가 서로 구분되도록 다양하게 구성한다. 대중 인기 순위만으로 후보를 정하지 않는다.
- 선택 카드에는 주황색 테두리와 체크 아이콘을 함께 보여준다. 색만으로 선택 여부를 전달하지 않는다.
- 최소 3개를 고르기 전에는 다음 버튼이 비활성임을 분명히 보여준다.
- 3개 이상 고르면 하단 버튼 문구가 선택 개수와 함께 바뀐다.
- 뒤로가기를 누르면 성별 선택으로 돌아가며, 성별을 바꾸면 기존 옷 선택을 그대로 재사용하지 않는다.

화면 문구 초안:

- 제목: `마음에 드는 옷을 골라주세요`
- 설명: `3개 이상 고르면 취향에 맞춰 추천해드려요.`
- 활성 버튼 예시: `3개 선택했어요 · 계속`

완료 기준: 사용자가 카드 3개를 고르면 세 카드 모두 테두리와 체크로 구분되고, 활성화된 계속 버튼을 누르면 선택이 유지된 채 회원가입 화면이 보인다.

참고 시안: [스타일 선택 샘플](../../design/atee-style-onboarding-sample.jpg)

### 3단계 — 취향 가치 중심 회원가입 (`3 / 3`)

- 화면의 첫 메시지는 계정 기능이 아니라 `취향 찾기를 계속하는 이유`를 설명한다.
- 직전에 고른 옷 3개 이상을 시각적으로 다시 보여줘 앞 단계와 연결한다.
- 선택한 옷이 첫 추천의 시작점이며, 이후 탐색 행동으로 추천이 달라진다는 두 가지 효용만 설명한다.
- Google 로그인 버튼은 하나만 제공한다. 버튼 자체에 과도한 마케팅 문구를 넣지 않고, 가입 이유는 버튼 위에서 설명한다.
- 실제 구현에서는 검증된 Google 브랜드 에셋과 허용 문구를 사용한다. 시안 속 로고는 구현 에셋의 정본이 아니다.
- 어떤 정보를 받고 어디에 저장하는지 버튼 아래에서 짧게 알리고, 공개 처리방침으로 이동할 수 있어야 한다.

화면 문구 초안:

- 제목: `취향 찾기를 계속할까요?`
- 설명: `방금 고른 옷에서 시작해, 볼수록 더 나다운 티셔츠를 찾아드려요.`
- 효용 1: `지금 고른 취향에서 추천 시작`
- 효용 2: `볼수록 더 나에게 맞게 변화`
- Google 버튼: `Google로 계속하기` — 최종 문구는 Google 브랜드 요구사항과 기존 공용 버튼 계약을 확인한 뒤 확정
- 계정 안내: `가입하면 취향과 찜이 계정에 저장돼요.`
- 개인정보 안내: `받는 정보는 이메일 주소뿐이에요.` — 실제 수집 범위와 공개 처리방침을 다시 대조한 뒤 확정

완료 기준: 사용자가 회원가입 화면을 열면 방금 선택한 옷, 취향을 찾는다는 가치, Google 로그인 수단, 수집 정보 안내가 한 화면의 명확한 순서로 보인다.

참고 시안: [취향 중심 회원가입 샘플](../../design/atee-taste-signup-sample.jpg)

### 4단계 — 첫 개인화 홈

- 인증과 초기 추천 준비가 끝나면 홈의 실제 상품을 즉시 보여준다.
- 전체 화면 dim이나 여러 단계의 기능 투어로 피드를 가리지 않는다.
- 피드 위 또는 화면 하단에 스크롤을 막지 않는 작은 확인 메시지를 한 번 보여준다.
- 초기 추천 준비에 성공했을 때만 `개인화된 추천이 준비됐다`고 표현한다.

첫 홈 안내 문구 초안:

- 제목: `첫 추천이 준비됐어요`
- 설명: `방금 고른 옷을 바탕으로 시작했어요. 저장하고 둘러볼수록 더 내 취향에 가까워져요.`

완료 기준: 첫 홈이 열리면 사용자는 안내를 닫지 않아도 상품을 보고 스크롤할 수 있고, 안내는 한 번만 나타난다.

## 5. 홈 dim 코치마크 원칙

P0에서는 첫 홈 전체 dim 온보딩을 만들지 않는다. 가입까지 마친 직후는 설명을 더 듣는 순간이 아니라, 약속한 추천 결과를 확인하는 순간이기 때문이다.

dim 코치마크는 다음 조건이 관찰됐을 때만 별도 조각으로 검토한다.

- 사용자가 어떤 행동이 추천을 바꾸는지 이해하지 못한다.
- 찜이나 상품 상세 진입 같은 핵심 취향 신호를 발견하지 못한다.
- 사용성 테스트에서 동일한 도움 요청이 반복된다.

도입한다면 다음 원칙을 지킨다.

- 홈 진입 즉시 여러 기능을 연속 설명하지 않는다.
- 사용자가 해당 기능을 처음 사용하려는 맥락에서 한 대상만 강조한다.
- 탭 한 번으로 닫히며 다시 나타나지 않는다.
- 강조가 없어도 원래 동작을 계속 수행할 수 있다.
- dim 유무는 별도 검증 가설로 취급한다. 이 온보딩 작업과 한 번에 효과를 주장하지 않는다.

문구 예시:

- 제목: `마음에 들면 저장해 주세요`
- 설명: `다음 추천에 취향을 반영할게요.`

## 6. 상태·실패·복구 요구사항

### 인증을 취소하거나 실패한 경우

- 사용자는 회원가입 화면으로 돌아온다.
- 앞서 고른 성별과 옷 선택은 사라지지 않는다.
- 실패 이유와 다시 시도할 방법을 같은 화면에서 확인한다.
- 홈은 열리지 않는다. 단, 이 동작은 `회원가입 필수`가 정본 결정으로 확정된 경우에만 적용한다.

### 초기 추천 준비가 실패한 경우

- 성별 조건을 지킨 다양성 피드로 복구할 수 있다.
- 준비되지 않은 추천을 개인화 결과라고 표시하지 않는다.
- 재시도 여부와 사용자에게 보여줄 실패 문구는 기술 설계 전에 확정한다.

### 재방문한 경우

- 이미 온보딩을 완료한 동일 계정에는 전체 흐름을 반복하지 않는다.
- 계정에 성별은 있지만 초기 취향 근거가 없거나, 그 반대인 불완전 상태의 복구 순서는 **미정**이다.
- 로그아웃 뒤 같은 기기에서 다시 시작할 때 어느 단계부터 보여줄지도 **미정**이다.
- 이 두 상태는 임의로 추정하지 말고 제품 책임자 결정 후 완료 조건을 추가한다.

## 7. 데이터와 추천의 제품 계약

- 옷 선택 단계에서 고른 항목은 `사용자가 직접 고른 초기 취향 근거`다. 계산된 장기 취향과 동일한 데이터라고 가정하지 않는다.
- 로그인 전 선택을 로그인 뒤 계정에 귀속하는 방식은 정본 결정과 데이터 방침이 확정된 뒤 기술 설계에서 정한다.
- 선택 상품 번호, 선택 시각, 후보 집합과 화면 위치 중 무엇을 보존할지는 추천 평가와 개인정보 최소 수집 원칙을 함께 보고 정한다.
- 카드의 크기·위치 때문에 선택 확률이 달라질 수 있으므로, 선택 결과를 곧바로 사용자의 전체 취향이라고 단정하지 않는다.
- 추천 방법은 이 문서에서 특정하지 않는다. 다만 첫 홈에서 `선택한 옷을 반영했다`고 말하려면 실제 추천 입력에 선택 결과가 들어갔음을 관찰 가능하게 확인해야 한다.

## 8. 측정

이 변경의 기능 지표는 전체 제품의 Primary metric인 회원 D7 자발적 재방문율을 대체하지 않는다. 온보딩이 그 실험의 분모를 심하게 줄이거나 특정 성향의 사용자만 남기지 않는지 확인하는 보조 지표다.

### 1차 결과 지표

**신규 방문자의 첫 추천 홈 도달률**

- 단위: 온보딩 대상 신규 방문자 한 명
- 분모: 성별 선택 화면을 본 신규 방문자
- 분자: 성별·옷 선택·회원가입을 마치고 첫 추천 홈에서 실제 상품을 한 번 이상 본 방문자
- 기준선: 새 흐름 배포 전에는 같은 경로가 없어 TBD
- 목표: 기준선과 폐쇄 베타 표본을 확보하기 전까지 TBD
- 미달 시: 강제 가입 시점, 옷 선택 수, 가치 문구를 분리해 한 번에 하나씩 재검증한다.

### 단계별 진단 지표

- 성별 선택 완료율
- 옷 선택 시작·3개 충족·계속 버튼 완료율
- 옷 선택에 걸린 시간과 선택 개수 분포
- 회원가입 시작·성공·취소·실패율
- 첫 홈 로드 성공률과 첫 상품 노출까지 걸린 시간
- 첫 홈에서 첫 유효 행동까지 걸린 시간
- 첫 안내 메시지 노출·닫기와 안내가 피드 탐색을 막은 비율

이벤트 이름과 스키마는 기존 계측 계약을 조사한 뒤 별도 기술 계획에서 확정한다. 측정 장치를 기능보다 크게 만들지 않는다.

## 9. P0 범위와 비범위

### P0

- 3단계 진행 표시가 있는 성별·옷 선택·회원가입 흐름
- 성별과 일치하는 10~12개 옷 후보의 단일 화면 복수 선택
- 최소 3개 선택과 명확한 선택·비활성·활성 상태
- 선택 유지, 인증 실패 복구, 온보딩 완료 계정의 반복 노출 방지
- 첫 추천 준비 성공 여부에 맞는 홈 진입 안내
- 흐름 이탈을 판단할 최소 계측

### 이번 조각의 비범위

- 스타일 카테고리 선택 뒤 상품을 다시 고르는 추가 depth
- 첫 홈 전체를 가리는 다단계 dim 튜토리얼
- 온보딩에서 사이즈·키·연령대 추가 수집
- 취향 편집·초기화 화면
- 관심 없음·이 스타일 줄이기 같은 명시적 부정 신호
- 추천 알고리즘 자체의 재설계
- 다크 모드 신규 확정

## 10. 구현 계획으로 넘길 때의 순서와 완료 기준

이 문서는 제품·UX 계약이다. 실제 구현 전에는 아래 순서로 별도 계획을 작성한다. 하나의 검증 가설은 **새 사용자가 실제 옷을 골라 가입하면, 그 선택을 반영한 첫 홈까지 끊김 없이 도달한다**이다.

### 0단계 — 정본 정책 확정

- 무엇을: 회원가입 필수 여부, 명시적 선택 승계, 데이터 고지 범위를 정본 문서에 반영한다.
- 완료 기준: Living PRD·결정 기록·데이터 수집 방침에서 로그인 선택/필수와 취향 소유권 설명이 서로 모순되지 않는 것이 보인다.

### 1단계 — 핵심 세로 경로

- 무엇을: 새 방문자가 성별을 고르고, 옷을 3개 이상 고르고, 가입을 마친 뒤 선택이 반영된 첫 홈에 도달하는 한 경로를 만든다.
- 완료 기준: 새 브라우저에서 위 순서를 직접 실행하면 반대 성별 상품이 섞이지 않고, 로그인 왕복 뒤에도 선택이 유지되며, 첫 홈에 실제 추천 상품이 보인다.

### 2단계 — 실패와 재방문

- 무엇을: 인증 취소·실패, 초기 추천 실패, 이미 완료한 계정의 재방문을 처리한다.
- 완료 기준: 각 상태를 직접 만들면 선택 유실·거짓 개인화 표시·온보딩 무한 반복 없이 정해진 복구 화면이 보인다.

### 3단계 — 첫 홈 안내

- 무엇을: 피드를 막지 않는 첫 추천 확인 메시지를 한 번 보여준다.
- 완료 기준: 첫 홈에서는 안내와 상품이 함께 보이고 즉시 스크롤할 수 있으며, 같은 계정의 다음 방문에는 안내가 다시 나타나지 않는다.

### 4단계 — 최소 계측과 회귀 확인

- 무엇을: 단계별 이탈과 첫 홈 도달을 판단할 최소 지표를 남기고 기존 성별·로그인·취향·찜 계약의 회귀를 확인한다.
- 완료 기준: 한 번의 테스트 여정이 단계별 성공·실패로 구분되어 보이고, 기존 개인정보 삭제·로그아웃·계정 전환 약속이 그대로 동작하는 것이 확인된다.

## 11. 구현 전 열린 결정

다음은 이 문서가 임의로 확정하지 않는다.

1. 회원가입 강제를 기존 정본 결정의 공식 변경으로 확정할지
2. 최소 3개 이후 최대 선택 개수를 둘지
3. 10~12개 후보를 고르는 기준과 교체 주기
4. 로그인 전 명시적 옷 선택을 계정에 귀속하는 데이터 계약
5. 초기 추천 준비 실패 시 자동 복구와 재시도 중 어느 경험을 제공할지
6. 불완전 계정과 로그아웃 후 재진입의 시작 단계
7. 첫 핵심 행동 코치마크를 P0에 넣을지, 사용성 관찰 뒤 별도 검증할지
